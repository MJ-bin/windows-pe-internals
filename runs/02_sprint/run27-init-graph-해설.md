비유도 그대로 이어 쓴다.

- 프로세스 = **가게**, 스레드 = **직원**, ntdll = 가게 안 **관리실**
- DLL = **건물**, PEB.Ldr = **건물 명부**, 모듈 항목 = **명부 한 줄**
- DDAG 노드 = 명부 줄마다 붙은 **연결 카드**, 간선 = 카드 사이 **끈**, `State` = 카드의 **진행 도장**
- 짐 들이기 = DLL 올리기, **전원 켜기 = DLL 시작 함수(와 TLS 콜백) 부르기**
- 활성화 컨텍스트 = 건물 **전용 작업 지침서**, CONTEXT = 첫 직원의 **업무 시작 메모**
- 정적분석 = **노선도** 읽기, 동적분석 = **버스 타 보기**
- 이번에 두 담당이 새로 생긴다 (비유 이름일 뿐이다):
  - `LdrpInitializeGraphRecurse` = **순서 담당** (카드를 따라 돌며 "누구부터 켤까" 를 정한다). run19 해설의 "전원 켜기 담당" 이 이 사람이다.
  - `LdrpInitializeNode` = **켜기 담당** (카드 한 장을 받아 그 건물 스위치를 실제로 누른다)

**헷갈리지 않게 한 가지 먼저.** run 문서는 Node 안의 반복문 둘을 "**고리 A·고리 B**" 라고 부른다. 여기서 "고리" 는 **반복문(한 바퀴 도는 코드)** 이다.

- [run24 해설](run24-work-queue-해설.md) 2.9 의 "고리" (서로 기대는 **동그라미** 묶음) 와는 다른 말이다.
- 이 글에서는 섞이지 않게 **"한 바퀴 A·한 바퀴 B"** 라고 쓴다 (run 문서의 고리 A·B 와 같은 것).

한 줄로 먼저 말하면 — **이번 바퀴의 핵심 넷**:

1. **자식 먼저, 자기 나중 (후위 순서)** — 순서 담당은 "내가 기대는 건물" 가지를 끝까지 다 켠 **뒤에** 자기를 켠다. 그래서 dll2 → dll1 → exe 순서가 코드에서 그대로 나온다 `[정적]` + `[관찰]` → 2.4
2. **재귀 한 단계 = 아직 도장 7 인 카드 하나** — 이미 켜졌거나(9) 켜는 중(8) 인 카드는 건너뛴다. 같은 카드를 두 번 안 켜는 장치도 **도장 하나뿐**이다 `[정적]` → 2.5
3. **카드 한 장 켜기 = 도장 8 → [TLS → 진입점] → 도장 9** — 진입점의 넷째 인자는 정적 import 모듈이면 **첫 스레드 CONTEXT 포인터**다 `[정적]` → 2.7 · 2.8
4. **exe 카드는 통째로 건너뛴다** — 그래서 exe TLS 콜백은 따로 돈다. 오래된 "왜 exe 만 따로?" 의 답이다 `[정적]` → 2.10

## 1. 이번 바퀴의 질문

### 큰 그림에서 어디인가

오프셋은 모두 **돌아올 자리(ret)** 다.

```
cmd.exe 창에서 "test.exe" 입력
 └─ cmd.exe (부모): CreateProcessInternalW → NtCreateUserProcess … NtResumeThread   (run9 ~ run14)

 test.exe 메인 스레드 (커널)
  KiStartUserThread → PspUserThreadStartup → PspInitializeThunkContext ═▶ IRETQ    (run15·run16)

 test.exe 메인 스레드 (유저, ntdll)
  LdrInitializeThunk
   └─ _LdrpInitialize +0x16c  LdrpInitializeProcess   (가게 전체 세팅)              (run17 ~ run19)
        ├─ +0x19a2  LdrpInitializeKernel32Functions → … (kernel32 준비)             (run20·run21·run25)
        │     └─ … Prepare +0xea → GR(KERNEL32 카드) → KERNELBASE → KERNEL32 켜기   ← 이번 (같은 코드)
        ├─ +0x1aa9 ~ +0x1ab1  짐 들이기 (dll1·dll2 올리기)                           (run22 ~ run24·run26)
        ├─ +0x1af2  LdrpPrepareModuleForExecution (exe 항목)                         (run21·run24)
        ├─ +0x1bbb  LdrpInitializeGraphRecurse (exe 카드)                           ← 이번
        │     ├─ +0x96 GR 재귀 … +0x6a LdrpInitializeNode [dll2] [dll1]             ← 이번
        │     │      └─ +0x16b TLS,  +0x19c 시작 함수                               (run8 관찰, 본문은 Q16)
        │     └─ +0x6a LdrpInitializeNode [exe 카드]                               ← 이번 (새로 그림)
        └─ +0x1c99  LdrpCallTlsInitializers (exe TLS)                               (run19)
   └─ +0x18 NtContinue ═▶ RtlUserThreadStart → … → main                         (run16·run25, 뒤는 추측)
```

- 짐 들이기는 끝났다. 이제 **전원 켜기**(`+0x1bbb`) 안이다.
- 같은 두 함수가 **kernel32 준비 때**(`Prepare +0xea`)에도 쓰인다. 그래서 이번 결과는 그쪽(KERNELBASE → KERNEL32) 관찰도 같이 설명한다.
- flow.md 로는 **2.7** (import DLL 초기화의 틀) 이 중심이다. **2.8** (dll2 → dll1), **2.9** (exe TLS) 에도 줄이 더해졌다.

### 무엇이 궁금했나

run 문서 "목적" 을 줄이면:

1. 순서 담당(GR)은 **어느 목록을 어떤 순서로** 도나? 정말 자식 먼저인가? 무엇을 건너뛰고, 실패하면 어떻게 되나?
2. 켜기 담당(Node)은 카드 도장을 **어떻게 바꾸나**? TLS·진입점을 부르는 **조건과 인자**는? 벽에 붙여 둔 CONTEXT(`LdrpProcessInitContextRecord`)는 **어디에 쓰나**?
3. **exe 카드**는 어떻게 되나? (exe TLS 는 `LdrpInitializeProcess +0x1c31` 쪽에서 따로 부르는데.)
4. run7·run8 에서 본 것 (재귀 깊이, dll2 → dll1 순서) 이 **코드 모양으로 설명되나**?

### 바퀴 전에 알던 것

- `[관찰]` (run7·run8) dll1·dll2 켜기는 `LdrpInitializeProcess +0x1bbb` 아래였다. 순서는 **dll2 → dll1**, 그다음 exe TLS.
  - GR 재귀 깊이: dll1 쪽 2단계, dll2 쪽 3단계.
  - 모듈마다 `LdrpInitializeNode` 안에서 **TLS 먼저(`+0x16b`), 시작 함수 나중(`+0x19c`)**.
- `[관찰]` (run7) kernel32 길: KERNELBASE = `+0x96` 재귀 안의 `+0x6a`, KERNEL32 = 재귀 없이 `+0x6a`.
- `[정적]` (run19) 맨 바깥 `+0x1bb6` 의 첫 인자 = **exe 항목의 연결 카드** (`DdagNode`). 그래서 flow.md 는 "맨 바깥 = test.exe" 라고 적고 `[test.exe 추정]` 을 달아 두었다.
- `[정적]` (run19) 벽에 붙여 둔 CONTEXT(`LdrpProcessInitContextRecord`)를 읽는 곳은 `LdrpInitializeNode +0x17a` **하나**. 무엇에 쓰는지는 몰랐다.
- `[정적]` (run21) 카드 도장이 8·9 면 `Prepare` 는 바로 돌아간다. 7 이면 켜기 쪽으로 간다.
- `[추측]` (flow.md 2.7) "재귀 한 단계 = 모듈 하나". "남한테 기대는 모듈일수록 나중에 켠다 (기초 → 기둥 → 지붕)".
- `[소스]` 의존 관계는 test.exe → dll1 → dll2. 모듈마다 TLS 콜백이 있다.

## 2. 찾은 것

### 2.1 먼저 — 그래프, 노드, 진행 도장

이번 결과는 이 세 말을 알고 읽어야 한다. 처음 보는 눈높이로 천천히 간다.

#### 새 말 — 그래프

- **그래프** = 동그라미 여러 개를 줄로 이은 그림이다. "**누가 누구에게 기대나**" 를 그릴 때 쓴다 `[추측]` (일반적으로 알려진 설명).
  - 동그라미 하나 = **노드**. 여기선 건물(DLL) 하나의 **연결 카드**다.
  - 줄 하나 = **간선**. 여기선 카드 사이 **끈** 한 가닥이다 ([run23 해설](run23-load-dependent-해설.md) 2.3 에서 그 끈을 긋는 코드를 봤다).
- 비유: 게시판에 **연결 카드**를 붙여 놓고, "이 건물은 저 건물이 있어야 돌아간다" 마다 **끈**을 하나씩 이어 둔 판.
- 끈에는 방향이 있다.
  - **부모** = 기대는 쪽 (끈의 시작). 예: dll1.
  - **자식** = 기대받는 쪽 (끈의 끝). 예: dll2.
- test.exe 의 판은 이렇게 생겼다 `[소스]`:

```
 [test.exe 카드] ──끈──▶ [dll1 카드] ──끈──▶ [dll2 카드]
     부모                 자식이자 부모          자식
```

- 실제 판에는 ntdll·kernel32 같은 카드도 있다. 하지만 그 카드들은 이 시점에 이미 켜져 있어서(2.5) 이번 이야기엔 거의 안 끼어든다.

#### 카드 칸 — 이번에 쓰는 것만 `[정적]` (PDB `_LDR_DDAG_NODE`)

| 칸 | 이름 | 뜻 | 비유 |
|---|---|---|---|
| `+0x00` | `Modules` | 이 카드에 속한 명부 줄들 | 카드 밑에 매단 **명부 줄 묶음** (보통 하나) |
| `+0x28` | `Dependencies` | 내가 기대는 자식으로 가는 끈들 | 카드 **앞면** 열쇠고리 |
| `+0x30` | `IncomingDependencies` | 나에게 기대는 부모에서 오는 끈들 | 카드 **뒷면** 열쇠고리 |
| `+0x38` | `State` | 이 카드가 어느 단계까지 왔나 | **진행 도장** |

- 순서 담당이 따라가는 건 **앞면(`Dependencies`) 하나뿐**이다. 뒷면(`IncomingDependencies`)은 안 건드린다 `[정적]`.

#### 새 말 — 노드 State (진행 도장), 이번에 쓰는 번호

[run21 해설](run21-load-dll-internal-해설.md) 2.6 에서 도장표를 봤다. 이번엔 그중 **넷**이 주인공이다. 이름은 PDB 열거 `_LDR_DDAG_STATE` 에서 읽었다 `[정적]`.

| 번호 | PDB 이름 | 뜻 (이름으로 읽음) | 이번에 누가 찍나 |
|---|---|---|---|
| 7 | `ReadyToInit` | 켤 준비 됨 | 켜기 **전에** 다른 곳이 찍어 둔다 (`LdrpNotifyLoadOfGraph +0x19`) |
| 8 | `Initializing` | **켜는 중** | 켜기 담당이 들어가자마자 (`+0x1f`) |
| 9 | `ReadyToRun` | **다 켜짐** | 켜기 담당이 끝낼 때 (`+0x2ba`) |
| **-4** | **`LdrModulesInitError`** | **켜다가 실패** | 켜기 담당 끝 (`+0x2ba`) 또는 순서 담당 실패 길 (`+0x6e`) |

- **-4 는 이번에 처음 적는다.** 헷갈리기 쉬운 이웃이 있다:
  - -3 `LdrModulesSnapError` = **전선 꽂기**(snap) 단계의 실패 (run24 그래프 정리에서 봤다).
  - -4 `LdrModulesInitError` = **전원 켜기** 단계의 실패.
  - run 문서 "정정" 절: 앞 문서들에서 -4 를 SnapError 로 잘못 읽은 곳은 **없다** (`grep` 확인).
- 비유: 카드에 찍는 도장이 **"준비 됨" → "켜는 중" → "다 켜짐"** 으로 바뀐다. 사고가 나면 **"켜기 실패"** 도장.

### 2.2 한눈에 — 두 함수가 하는 일

run 문서 "호출 관계" 를 줄였다. 숫자는 run 문서 그대로. 모두 `[정적]` 이다. 잡일(로그)과 안 탈 갈림(패치 이미지)은 뺐다.

```
LdrpInitializeProcess +0x1bbb (call +0x1bb6)       RCX = exe 카드, 로더 락 안
└─ 순서 담당 GR(카드)
   ├ 입구: 카드 도장 -4 면 바로 0xc0000142                         (+0x9 / +0x16)
   ├ 앞면 끈 한 바퀴 (Dependencies, 먼저 이은 끈부터)
   │    자식 도장 7 → +0x91 (ret +0x96) 자기 자신을 다시 부름 (재귀)
   │    자식 도장 8 → 재귀 안 함, "켜는 중 만남" 깃발만
   │    자식 도장 -4 → 실패
   │    그 밖 (9 등) → 무시
   └ 한 바퀴가 다 끝난 뒤 → +0x65 (ret +0x6a) 켜기 담당 Node(카드)

켜기 담당 Node(카드)
 ├ +0x1f   도장 = 8
 ├ 한 바퀴 A: 카드 밑 명부 줄을 PEB.Ldr 초기화 순서 목록 꼬리에 끼움 (exe 줄은 빼고)
 ├ 한 바퀴 B: 명부 줄마다 (exe 줄은 통째로 건너뜀)
 │    작업 지침서 펴기 (+0x156)
 │    TlsIndex ≠ 0   → +0x16b LdrpCallTlsInitializers(1, 명부 줄)
 │    EntryPoint ≠ 0 → +0x19c LdrpCallInitRoutine(EntryPoint, DllBase, 1, CONTEXT 포인터 또는 0)
 │    지침서 덮기 (+0x1ae)
 │    성공 → 다음 줄 / FALSE·예외 → 0xc0000142, 남은 줄 안 켬
 └ +0x2ba  도장 = 9 (성공) / -4 (실패)
```

- 순서 담당은 **누구부터 켤지** 만 정한다. 실제로 스위치를 누르는 건 켜기 담당이다.
- 순서 담당은 자기 노드를 직접 켜지 않는다. 늘 켜기 담당에게 넘긴다 (`+0x65`).

### 2.3 한 줄씩 읽는 법

run 문서 "호출 지점" 표에서 둘을 골랐다. "누가 / 어디서 / 누구를 / 무엇을 위해" 로 읽는다.

#### 한 줄 읽기 ① — 순서 담당이 자기 자신을 다시 부르는 줄

| caller | call | ret | callee | 조건 | 표시 |
|---|---|---|---|---|---|
| `ntdll!LdrpInitializeGraphRecurse` | `+0x91` | `+0x96` | `LdrpInitializeGraphRecurse` (재귀) | `Dependencies` 의 자식 노드 `State == 7` 일 때, 자식마다 | [정적] + [관찰] run7 |

- **누가**: 순서 담당 GR. 카드 한 장을 들고 앞면 끈을 하나씩 보는 중이다.
- **어디서**: 자기 시작에서 `+0x91` 에서 부르고, 돌아오면 `+0x96`. 콜스택엔 `LdrpInitializeGraphRecurse+0x96` 으로 찍힌다. run7 콜스택에서 본 바로 그 숫자다.
- **누구를**: **자기 자신**. 인자 1 = 끈 끝의 자식 카드.
- **무엇을 위해**: 자식 카드가 아직 "준비 됨"(7) 이면, **그 자식 가지부터 먼저 다 켜려고** 같은 일을 자식에게 시킨다.
- **새 말 — 재귀**: 함수가 자기 자신을 다시 부르는 것. 부를 때마다 콜스택에 한 층이 더 쌓인다. 그래서 콜스택에 같은 이름(`GR+0x96`)이 여러 번 보이면 "몇 층 내려갔나" 를 셀 수 있다.
  - 비유: 반장이 "네 조 다 됐니?" 를 조장에게 묻고, 조장이 다시 조원에게 묻는 식. 묻는 말은 같고, 내려갈수록 한 층 깊어진다.

#### 한 줄 읽기 ② — 켜기 담당이 시작 함수를 부르는 줄

| caller | call | ret | callee | 조건 | 표시 |
|---|---|---|---|---|---|
| `ntdll!LdrpInitializeNode` | `+0x197` | `+0x19c` | `LdrpCallInitRoutine` | 항목 `EntryPoint ≠ 0` | [정적] + [관찰] run7·run8 |

- **누가**: 켜기 담당 Node. 카드 밑 명부 줄 하나를 켜는 중이다.
- **어디서**: `+0x197` 에서 부르고 `+0x19c` 로 돌아온다. run8 이 본 "시작 함수(`+0x19c`)" 가 이 줄이다.
- **누구를**: `LdrpCallInitRoutine`. 인자 넷 (2.8 에서 자세히):
  - `RCX` = 명부 줄의 `EntryPoint` (`+0x194`) — 부를 함수 (dll 이면 `_DllMainCRTStartup`, run8 `[관찰]`)
  - `RDX` = `DllBase` (`+0x190`)
  - `R8D` = 1 (`+0x18a`) — 이유 "프로세스에 처음 붙음"
  - `R9` = CONTEXT 포인터 또는 0 (`+0x170`·`+0x174`·`+0x17a`)
- **무엇을 위해**: 그 건물의 **전원 스위치를 누른다.** 돌아온 `AL` 한 바이트가 "켜졌나" 깃발이다 (`+0x19c`·`+0x1a0`).
- **조건**: 명부 줄 `EntryPoint` 칸이 0 이면 이 줄을 아예 안 지난다. 스위치가 없는 건물은 누를 것도 없다.

### 2.4 핵심 ① 자식 먼저, 자기 나중 — 후위 순서

#### 새 말 — 후위 순서 (자식 먼저)

- 그래프를 끈 따라 돌 때, **자식들을 다 처리한 뒤에 나를 처리하는** 순서를 **후위 순서**라고 한다 `[추측]` (일반적으로 알려진 설명, 영어 post-order).
  - 반대말은 **전위 순서** — 나를 먼저 처리하고 자식에게 간다.
- 비유: **아침 출근 준비.** 나는 엄마 차를 타야 하고, 엄마는 아빠가 차 열쇠를 줘야 출발할 수 있다. 그럼 깨우는 순서는 **아빠 → 엄마 → 나** 다. 내가 기대는 사람부터 먼저 준비가 끝나 있어야 한다.
  - flow.md 2.7 의 "기초 → 기둥 → 지붕" 과 같은 그림이다.
- 왜 이 순서가 필요한가 — 내 짐작 `[추측]` (일반적으로 알려진 설명): dll1 의 시작 함수가 돌 때 dll2 함수를 부를 수 있다. 그때 dll2 가 아직 안 켜져 있으면 곤란하다. 그래서 **기대받는 쪽을 먼저 켠다.**

#### 코드에서 어떻게 보이나 — 단계별로 `[정적]`

1. 순서 담당은 카드 앞면 끈을 **한 바퀴** 돈다 (`+0x37 ~ +0x59`).
2. 끈 끝 자식이 도장 7 이면 **그 자리에서** 재귀한다 (`+0x91`, ret `+0x96`). 재귀가 돌아와야 다음 끈으로 간다.
3. 한 바퀴가 **다 끝난 뒤에야** (`+0x59` 고리 끝 → `+0x5b` 깃발 검사) 자기 카드를 켜기 담당에게 넘긴다 (**`+0x65`**, ret `+0x6a`).
   - 자식이 하나도 없으면 `+0x32` 에서 바로 `+0x62` 로 가서 켜기로.
4. → **자식 가지를 다 끝낸 뒤 자기를 켠다.** 후위 순서다.
5. 형제(같은 부모의 자식 여럿)끼리는 **앞면 열쇠고리에 꿴 순서**다.
   - 끈은 열쇠고리 **꼬리에** 꿴다 (`LdrpRecordModuleDependency +0x89 ~ +0x92`, run23 `+0xf69`).
   - 도는 건 `Tail->다음` (= 맨 앞) 부터 `Tail` 까지.
   - → **먼저 이은 끈(import 표 앞쪽)부터** 본다.

#### 헷갈리는 곳 — 주소는 거꾸로 생겼다 `[정적]`

이 함수는 `.asm` 을 위에서부터 읽으면 오해하기 쉽다. 그래서 run 문서가 따로 적었다.

- `+0x65` (자기 켜기) 가 `+0x91` (재귀) 보다 **주소가 앞**이다.
- 그런데 재귀 덩어리(`+0x89 ~ +0x9a`)는 함수의 `RET`(`+0x87`) **뒤에** 따로 떨어져 있다.
- 한 바퀴 도는 중에 **점프로** 거기 갔다가, `+0x98 JNS +0x56` 으로 한 바퀴 안으로 돌아온다.
- → **코드 주소 순서(`+0x65` 가 앞) 와 실행 순서(재귀가 앞) 가 반대**다.
- [run9 해설](run9-create-user-process-해설.md) 3.7 의 "오프셋 순서 ≠ 실행 순서" 가 여기서도 나온다.
- 비유: 노선도에서 역 번호가 작다고 먼저 지나는 게 아니다. 노선이 옆길로 빠졌다가 돌아오면, 번호 큰 역을 먼저 지난다.

#### test.exe 에 대 보면 — 한 걸음씩

run 문서 "확인된 것" 의 순서 `GR(exe) → GR(dll1) → GR(dll2) → Node(dll2) → Node(dll1) → Node(exe 카드)` 를 풀어 쓴다.

```
GR(exe 카드)                         콜스택 1층
 │ 앞면 끈: dll1 (도장 7) → 재귀
 └▶ GR(dll1 카드)                    2층
     │ 앞면 끈: dll2 (도장 7) → 재귀
     └▶ GR(dll2 카드)                3층
         │ 앞면 끈: 도장 7 인 자식 없음 (재귀 없음 — 추측)
         └▶ Node(dll2)  ①  ← 제일 먼저 켜짐
     ◀ 돌아옴, 한 바퀴 끝
     └▶ Node(dll1)  ②
 ◀ 돌아옴, 한 바퀴 끝
 └▶ Node(exe 카드)  ③  ← 2.10: 실제로는 아무것도 안 켬
```

1. `LdrpInitializeProcess +0x1bb6` 이 exe 카드를 들고 GR 을 부른다 (1층).
2. exe 카드 앞면 끈 끝 dll1 이 도장 7 → `+0x91` 재귀 (2층).
3. dll1 카드 앞면 끈 끝 dll2 가 도장 7 → `+0x91` 재귀 (3층).
4. dll2 의 의존은 다 9 라 재귀가 없다 → 한 바퀴가 그냥 끝난다. 이 줄은 run 문서도 `추측` 이다.
5. 3층 `+0x65` → **Node(dll2)**. dll2 의 TLS·시작 함수가 돈다.
6. 3층이 돌아오면 2층의 한 바퀴가 끝난다 → 2층 `+0x65` → **Node(dll1)**.
7. 2층이 돌아오면 1층의 한 바퀴가 끝난다 → 1층 `+0x65` → **Node(exe 카드)**.

- 결과: 켜지는 순서 **dll2 → dll1 → (exe 카드)** `[정적]`. run7·run8 `[관찰]` dll2 → dll1 과 **같다.**
- 콜스택 층수도 맞는다: dll2 를 켤 때 GR 3층, dll1 을 켤 때 2층. run7·run8 "dll1 2단계, dll2 3단계" `[관찰]` 과 같은 모양이다.
- 다만 "2층 = dll1, 3층 = dll2" 를 **못 박지는** 못한다. 어느 카드가 어느 층인지는 실행 때 값이다 → 동적 Q24.

#### kernel32 준비 때도 같은 모양 `[정적]` + `[관찰]` run7

- `Prepare +0xea` → GR(KERNEL32 카드) → 앞면 끈 끝 KERNELBASE 가 도장 7 → `+0x96` 재귀 → 그 안 `+0x6a` **Node(KERNELBASE)** → 돌아와서 `+0x6a` **Node(KERNEL32)**.
- run7 관찰 "KERNELBASE = `+0x96` 재귀 안의 `+0x6a`, KERNEL32 = 재귀 없이 `+0x6a`" 와 같은 모양이다.
- 이름 대응(어느 층이 KERNELBASE 인지)은 여전히 동적 Q24.

### 2.5 핵심 ② 재귀 한 단계 = 아직 도장 7 인 카드 하나

#### flow.md 의 `[추측]` 을 다듬었다

- 전에 적은 말: "재귀 한 단계 = 모듈 하나" `[추측]`.
- 이번 결과: **틀리지 않았다.** 다만 더 정확한 말은 "**한 단계 = 아직 켜지지 않은(도장 7) 카드 하나**" 다 `[정적]`.

왜 그런가 — 단계별로:

1. 재귀(`+0x91`)는 자식 도장이 **7 일 때만** 간다 (`+0x47`/`+0x4a` → `+0x89`).
2. 자식이 9(다 켜짐) 나 8(켜는 중) 이면 재귀하지 않는다 → **층을 안 만든다.**
3. kernel32 쪽은 kernel32 준비 때 이미 켜졌다 (run7 `[관찰]`). ntdll 카드는 9 로 짐작한다 (아래, `[추측]`). 그래서 test.exe·dll1·dll2 의 앞면에 그 카드들이 있어도 **층이 안 는다** (run 문서 "확인된 것").
4. 카드 하나는 보통 모듈 하나다 (고리 합침이 없으면, run24).
5. → 층 수 = "아직 안 켜진 카드" 수. test.exe 길이면 exe·dll1·dll2 의 3층.

- run7 kernel32 길에서 **ntdll 카드는 층을 안 만들었다** `[관찰]` → ntdll 카드 도장이 7 이 아니었다는 뜻이다. 9 로 짐작한다 `[추측]` — ntdll 카드를 만드는 `LdrpInitializeNtdllDataTableEntry` 본문은 안 읽었다.

#### 같은 카드를 두 번 안 켜는 장치 = 도장 하나 `[정적]`

**새 말 — 마름모 모양 의존**: A 가 B·C 에 기대고, B·C 가 둘 다 D 에 기대는 모양. 그림이 ◇ 같아서 그렇게 부른다.

```
      A
     ↙ ↘
    B   C
     ↘ ↙
      D        ← B 쪽에서도, C 쪽에서도 만난다
```

- 끈을 따라가면 D 를 **두 번** 만난다. 두 번 켜면 안 된다.
- 순서 담당에는 따로 "방문함" 표시가 **없다.** 대신 도장이 그 일을 한다:
  1. B 쪽에서 먼저 D 를 만난다. D 도장 7 → 재귀 → 켜기 담당이 D 를 **8 → 9** 로 바꾼다.
  2. C 쪽에서 D 를 다시 만난다. 이제 D 도장은 9 → "그 밖" → **무시.**
- 비유: 카드에 "다 켜짐" 도장이 찍혀 있으면, 다른 길로 와도 그냥 지나간다. 출석부에 따로 체크하지 않아도 **도장 자체가 출석 표시**다.

#### 순서 담당은 자기 카드가 7 인지 안 본다 `[정적]`

- 입구에서 보는 건 **-4 하나**다 (`+0x9`). 7 인지는 확인하지 않는다.
- 막는 건 부르는 쪽이다:
  - 부모 GR 의 `== 7` 검사 (재귀 전에 본다).
  - `LdrpPrepareModuleForExecution` 의 도장 갈림 (8·9 면 바로 돌아옴, run21).
- 자식을 7 로 올리는 곳 (줄만 봄) `[정적: 줄 일부만]`:
  - `LdrpNotifyLoadOfGraph +0x19` 가 `State = 7`, 실패면 `+0x29` 에서 6 으로 되돌림, 자식 재귀 `+0x61`.
  - 이 함수는 run21 `LdrpPrepareModuleForExecution +0x7b` 가 부른다.

### 2.6 순서 담당의 나머지 갈래 — 짧게, 하나씩

#### 자식 도장으로 갈림 — 표 `[정적]`

| 자식 도장 | 하는 일 | 근거 |
|---|---|---|
| 7 `ReadyToInit` | **재귀** `+0x91` (ret `+0x96`). 돌아와서 음수가 아니면 한 바퀴 계속 | `+0x47`/`+0x4a` → `+0x89` |
| 8 `Initializing` | 재귀 안 함. 지역 깃발 `[RSP+0x40] = 1` 만 | `+0x51`/`+0x54` → `+0x9c` |
| -4 `InitError` | `0xc0000142`, 자기 도장 = -4 쓰고 return | `+0x4c`/`+0x4f` → `+0xb2` → `+0x6e` |
| 그 밖 (9 등) | 무시 (층을 안 만든다) | 다음 끈 |

#### 건너뛰는 끈 — 표시 비트 `[정적]`

- 끈 칸 `+0x18` (부모 카드 자리) 의 **맨 아래 비트 0** 이 켜진 끈은 건너뛴다 (`+0x3a`/`+0x3e`).
- 이 비트를 켜는 곳: `LdrpRecordModuleDependency +0x11a` (칸을 새로 할당했을 때), run23 `LdrpLoadDependentModuleInternal +0x17d9`. 지우는 곳: run23 `+0xede`.
- 뜻은 모른다. "대비용 칸" 쯤으로 짐작 `[추측]` (run23 해설의 짐작과 같다). 뜻 정하기는 **Q54**.

#### 지연 갈래 — "켜는 중" 인 자식을 만났을 때

**새 말 — 지연 갈래**: run 문서가 붙인 이름이다. 자식 중에 도장 8(켜는 중) 이 있었을 때 타는 길이다 (`+0xb9`).

단계별로 `[정적]`:

1. 한 바퀴 중에 도장 8 자식을 만나면 지역 깃발만 1 로 해 둔다 (위 표).
2. 한 바퀴가 끝나면 깃발을 보고 `+0xb9` 로 간다.
3. `+0xbc`: 셋째 인자가 가리키는 바이트에 1 을 쓴다.
4. 그다음 둘 중 하나라도 맞으면 → **그래도 켠다** (`+0x65`):
   - 첫 명부 줄의 `LoadContext`(`항목+0xb0`) 가 0 이다.
   - 둘째 인자 `RDX` 가 `[LoadContext+0x28]` 과 같다.
5. 둘 다 아니면 → `+0xcf` → **켜지 않고 0 (성공) 을 돌려준다.** 도장은 7 그대로.

- 뜻 `[추측]`: 다른 로드 작업이 지금 이 카드의 의존을 켜는 중이면 (예: DllMain 안에서 `LoadLibrary` 를 부르는 **중첩 로드**), 기다리지 않고 **물러나는** 장치.
- 비유: 아빠를 깨우러 갔더니 **누가 이미 깨우는 중**이다. 그 사람이 "다른 집안 일" 로 깨우는 거면, 나는 엄마·나를 서둘러 준비시키지 않고 일단 물러난다.
- test.exe 시동에서는 안 탈 것이다 `[추측]` (flow.md 2.7). 확인은 동적 Q24 (`ntdll+0x87e2f` 에 안 설 것).

#### 둘째·셋째 인자 — 하나는 읽기만, 하나는 쓰기만 `[정적]`

- **`RDX` = 읽기 전용.** 쓰는 곳은 `+0xc9` 비교 한 곳뿐, 재귀에 그대로 넘긴다 (`+0x8e`).
  - 비교 상대 `[LoadContext+0x28]` 은 run22 에서 "결과 상태를 쓸 곳의 포인터" 였다.
  - 그래서 비교 뜻 = "**같은 로드 작업인가**" `[정적: 비교 줄] + [추측: 뜻]`.
  - 비유: 작업 지시서 번호표. "이 카드를 켜는 게 **내 지시서** 일인가?"
- **`R8` = 쓰기 전용.** `+0xbc` 한 곳에서 1 을 쓴다.
  - 재귀 때는 자기 지역 깃발 주소를 넘긴다 (`+0x89 LEA R8,[RSP+0x40]`).
  - → "켜는 중인 자식을 만났다" 신호가 **한 층씩 위로** 올라간다.
  - 맨 위 호출자(`LdrpInitializeProcess +0x1bb6`, `Prepare +0xea`)는 돌아와서 그 바이트를 **안 읽는다.**
  - 비유: 아래층에서 위층으로 쪽지를 올려 보내는데, 맨 꼭대기 사람은 쪽지를 안 펴 본다.

#### 실패하면 — 위로 번진다 `[정적]`

1. 자식 GR 이 음수를 돌려주거나 (`+0x9a`), 켜기 담당이 음수를 돌려주면 (`+0x6c` 안 탐) → `+0x6e`.
2. `+0x6e`: 자기 도장 = **-4**, 같은 값을 그대로 돌려준다.
3. **남은 형제는 안 본다.** 형제 카드는 도장 7 그대로 남는다.
4. 부모도 그 음수를 받으니 똑같이 -4 가 된다 → **맨 위까지 조상이 모두 -4.**
5. 이미 9 가 된 카드를 되돌리는 줄은 **없다.**

- 맨 위 `LdrpInitializeProcess` 는 `+0x1c0e` 실패 쪽으로 간다 (run19).
- 비유: 줄줄이 깨우다가 한 명이 못 일어나면, 그 위로 줄줄이 "켜기 실패" 도장. 이미 깨어난 사람을 다시 재우지는 않는다.

### 2.7 핵심 ③ 켜기 담당 — 카드 한 장 켜기 순서

#### 큰 줄기 한 줄 `[정적]`

**8 → (초기화 순서 목록에 끼움) → 명부 줄마다 [지침서 펴기 → TLS → 진입점 → 덮기 → `ProcessAttachCalled`] → 9**

이걸 하나씩 연다.

#### 1단계 — 들어가자마자 도장 8 `[정적]`

- `+0x1f` **`State = 8`** (무조건). 카드 주소는 `+0x1a` 에서 따로 챙겨 둔다.
- 이 순간부터 다른 길로 이 카드를 만나면 "켜는 중" 이라 재귀하지 않는다 (2.6 표).

#### 2단계 — 한 바퀴 A: 명부의 "초기화 순서" 줄에 세우기 `[정적]`

- 범위 `+0x44 ~ +0x2ef`. 카드 밑 `Modules` 목록을 **꼬리에서 머리 쪽으로** 돈다.
- 명부 줄마다: exe 줄(`LdrpImageEntry`)만 빼고 (`+0x4b`/`+0x4e`), 그 줄의 `InInitializationOrderLinks`(`+0x20`) 를 **PEB.Ldr 초기화 순서 목록(`PebLdr+0x30`) 꼬리에** 끼운다 (`+0x2d4 ~ +0x2e1`).
- 끼우기 전 목록 검사가 틀리면 `+0x66 INT 0x29` (빠른 실패).
- [run18 해설 2.6](run18-proc-init-setup-해설.md#26-pebldr--건물-명부가-생기는-순간-0x1c1) 에서 명부에 줄 세우는 방법이 셋 있다고 봤다. 그 셋째(③ 초기화 순서) 에 dll 들이 **언제** 들어가나가 이번에 보였다: **켜기 바로 직전.**
  - ntdll 은 run18 `LdrpInitializeProcess +0x1283 ~ +0x12d7` 에서 직접 끼워 둔다.
- 그래서 **초기화 순서 목록 순서 = 켜는 순서** 다 `[정적 추론]`.
  - 예측: `main` 에서 그 목록을 따라가면 ntdll, KERNELBASE, KERNEL32, dll2, dll1 (exe 없음) 일 것 `[정적 추론]`. 확인은 동적 Q24.
- 비유: 스위치를 누르기 직전에, 명부의 "켠 순서" 줄 끝에 이름을 먼저 적어 둔다.

#### 3단계 — 한 바퀴 B: 명부 줄마다 켜기 `[정적]`

범위 `+0x7e ~ +0x262`. 같은 목록을 다시 꼬리 → 머리로. **명부 줄마다**:

| 순서 | 자리 | 하는 일 | 비유 |
|---|---|---|---|
| 0 | `+0x9b`/`+0x9e` → `+0x25e` | 명부 줄 == `LdrpImageEntry` 면 **통째로 건너뜀** | 본 건물 줄은 여기서 손 안 댐 (2.10) |
| 1 | `+0x2fd`/`+0x302` | `LoadReason == 9` (패치 이미지) 일 때만 `LdrpApplyPatchImage`. 음수면 끝 (`+0x348` → `+0x2a5`) | test.exe 와는 거리가 먼 특수 길 |
| 2 | `+0xbd`, `+0xf9`/`+0xfe` | 전역 `LdrpCurrentDllInitializer = 명부 줄` → 로그 | 관리실 칠판에 "지금 켜는 건물: ○○" |
| 3 | `+0x151`/`+0x156` | 활성화 컨텍스트 켜기 (명부 줄 `EntryPointActivationContext` `+0x88`) | 건물 **전용 작업 지침서**를 편다 |
| 4 | `+0x166`/`+0x16b` | **TLS**: `TlsIndex ≠ 0` 이면 `LdrpCallTlsInitializers(ECX = 1, RDX = 명부 줄)`. 반환값은 버림 | 직원 **첫 안내** |
| 5 | `+0x197`/`+0x19c` | **진입점**: `EntryPoint ≠ 0` 이면 `LdrpCallInitRoutine` (인자 넷, 2.8) | **전원 스위치** 누르기 |
| 6 | `+0x1a9`/`+0x1ae` | 활성화 컨텍스트 끄기 | 지침서를 덮는다 |
| 7 | `+0x220`, `+0x231` | `LdrpCurrentDllInitializer` 되돌림 → (예외가 없었으면) `Flags |= ProcessAttachCalled` | 칠판을 지우고, 명부 줄에 "스위치 눌렀음" 표시 |
| 8 | `+0x24b`/`+0x250` 또는 실패 길 | 성공이면 `LdrpLogDllState` → 다음 줄. 실패면 2.9 | |

- **TLS 가 진입점보다 먼저**다. 둘 사이에 뒤로 가는 점프도 없다 `[정적]`. run8 `[관찰]` "TLS(`+0x16b`) → 시작 함수(`+0x19c`)" 와 같다.
- 지침서(활성화 컨텍스트)는 TLS·진입점이 **없어도** 줄마다 펴고 덮는다 (flow.md 2.7).
- TLS 쪽 둘째 인자는 `DllBase` 가 아니라 **명부 줄 포인터**다 `[정적]`. 진입점 쪽과 다르다. 그 안에서 무엇을 하는지는 Q16.
- 비유로 한 번에: 켜기 담당은 건물마다 **지침서를 펴고 → 직원 첫 안내(TLS) → 전원 스위치(진입점) → 지침서를 덮고 → "켰음" 표시.**

#### 4단계 — 끝에서 도장 9 (또는 -4) `[정적]`

- `+0x2ba`: 상태가 0 이면 **`State = 9`**, 실패면 **-4**. 상태 코드를 돌려준다.
- 그래서 도장은 **7 → 8 → 9** 로 간다. 7 은 부르기 전에 다른 곳(`LdrpNotifyLoadOfGraph`)이 찍은 것이다. 실패는 8 → -4.

#### 카드 하나에 명부 줄이 여럿이면 `[정적]`

- 왜 "명부 줄마다" 를 돌까? 카드가 **합쳐진 카드**일 수 있어서다 (run24 `LdrpMergeNodes`, 서로 기대는 동그라미를 한 카드로).
- 그러면 명부 줄 여럿을 차례로 켜고, **하나라도 실패하면 나머지는 안 켠다.**
- test.exe·dll1·dll2 는 카드마다 명부 줄이 하나다 (run24, 합칠 동그라미가 없었다).

#### TLS 를 한 번만 본 kernel32 길 — 조건으로 설명된다 `[정적 조건 + 관찰]`

- run8 kernel32 길에서 `LdrpCallTlsInitializers` 는 **한 번만** 보였다 (3번 줄, 콜백 호출 없음) `[관찰]`.
- 부르는 조건은 `TlsIndex ≠ 0` 하나뿐이다 `[정적]`.
- → 그 한 번의 모듈(KERNELBASE 추정)은 `TlsIndex ≠ 0`, 다른 쪽은 0 이었다는 뜻이다.
- 그런데 왜 콜백은 안 불렸나? 그건 `LdrpCallTlsInitializers` **안**의 일이라 Q16.
- 같은 이유로 dll1·dll2 는 TLS 호출이 실제로 불렸으니 두 DLL 의 `TlsIndex` 는 0 이 아니었다 `[정적 조건 + 관찰]` (flow.md 2.8).

### 2.8 진입점 넷째 인자 — 벽에 붙여 둔 CONTEXT 의 쓰임

run19 에서 남은 질문: "벽에 붙여 둔 CONTEXT(`LdrpProcessInitContextRecord`)를 `LdrpInitializeNode +0x17a` 가 **무엇에** 쓰나?" 이번에 답이 나왔다.

#### 답 `[정적]`

- **`LdrpProcessInitContextRecord` 를 읽는 유일한 곳(`+0x17a`) = `LdrpCallInitRoutine` 의 넷째 인자 `R9`.**
- 조건이 하나 붙는다 (`+0x170`·`+0x174`·`+0x17a`):
  - 명부 줄 `Flags` 의 비트 5 **`ProcessStaticImport`** (0x20) 가 켜져 있으면 → `R9` = 그 전역의 값 (첫 스레드 **CONTEXT 포인터**).
  - 꺼져 있으면 → `R9` = **0**.
- `ProcessStaticImport` = 이름 그대로 "**import 표로 붙은 모듈**" 표시로 읽힌다 `[추측: 이름]`.

#### 새 말 — `lpReserved`

- `DllMain(hinstDLL, fdwReason, lpReserved)` 의 **셋째 인자 이름**이다 `[추측]` (일반적으로 알려진 설명).
- 일반적으로 "프로그램 시작 때 import 로 붙은 DLL 이면 NULL 이 아니고, `LoadLibrary` 로 붙은 DLL 이면 NULL" 이라고 알려져 있다 `[추측]` (일반적으로 알려진 설명).
- 비유: 스위치를 누를 때 같이 건네는 **메모 한 장**. "개업 날 처음부터 같이 연 건물이면 첫 직원의 업무 시작 메모를 같이 줄게, 나중에 따로 들인 건물이면 빈손."

#### 그럼 `R9` 가 `lpReserved` 로 가나? — 단계별로

1. 켜기 담당이 싣는 값: `RCX` = `EntryPoint`, `RDX` = `DllBase`, `R8` = 1, `R9` = CONTEXT 포인터 또는 0 `[정적]`.
2. run8 `[관찰]`: `LdrpCallInitRoutine` 의 `r8 = 1` 이 바로 뒤 `DllMain` 의 `rdx = 1` 과 같았다. → 인자가 **한 칸씩 밀려** 들어가는 모양이다.
3. 그 모양대로라면 `RDX`(`DllBase`) → `DllMain` 첫째, `R8`(1) → 둘째, **`R9` → 셋째 `lpReserved`** 다.
4. → **정적 import DLL 의 `lpReserved` = CONTEXT 포인터, `LoadLibrary` 로 붙은 DLL = NULL** 일 것이다.
5. 하지만 3번은 `LdrpCallInitRoutine` **본문을 안 읽은** 짐작이다 → `[추측]`. 본문은 정적 Q16, 실제 값은 동적 Q27.

- 그리고 dll1·dll2 에 `ProcessStaticImport` 가 정말 켜져 있나? 켜져 있을 것 `[추측]` — 이번 두 함수는 이 비트를 **읽기만** 한다. 켜는 곳은 **Q54**.
- 비유로 정리: run19 해설에서 "전원 켜는 동안만 사물함 메모를 벽에 붙여 둔다" 고 했다. 그 메모를 **보는 사람**은 켜기 담당 하나였고, 하는 일은 **스위치와 함께 건네기**였다 (건네받는 쪽이 정말 `lpReserved` 로 받는지는 아직 짐작).

### 2.9 실패와 예외 — FALSE 와 예외는 조금 다르다

#### 새 말 둘

- **예외 착지점** = [예외 보호 구역](run17-ldr-init-entry-해설.md#28-첫-스레드-길--ldrpinitializeprocess-앞뒤로-하는-일)(try/except) 안에서 사고가 났을 때 **실행이 내려앉는 자리**. 평소에는 점프로 닿지 않는다.
  - 비유: 비상구 계단 끝 **착지 매트**.
- **unwind 범위 표** = PE 파일 안에 "이 코드 구간에서 예외가 나면 이 필터를 보고 이 자리로 가라" 를 적어 둔 표로 알려져 있다 `[추측]` (일반적으로 알려진 설명). 결과서가 `pefile` 로 읽었다.
  - 비유: 건물 벽에 붙은 **비상 대피도**.

#### 켜기 담당의 대피도 `[정적]`

- `try/except` 구간 `[+0x10e, +0x1b0)`, 필터 `$filt$1`, 착지점 `+0x1b0`.
  - 필터는 `RtlReportException` 으로 보고한 뒤 **늘 1** (잡아서 착지점으로) 을 돌려준다 (`$filt$1 +0x33`).
- `try/finally` 구간 `[+0x157, +0x1a4)`, 마무리 `$fin$0`.
  - 예외로 빠져나갈 때 운영체제가 `$fin$0` 을 부르고, 거기서 `+0xd` (ret `+0x12`) `RtlDeactivateActivationContextUnsafeFast` — 지침서를 덮는다.
- 착지점 `+0x1b0`: 예외 표시 = 1, 성공 깃발 = 0 → `+0x1fe` 로그 → `+0x220` 으로 정상 길과 합류.
- → TLS 구간(`+0x166`)도 진입점 구간(`+0x197`)도 다 `[+0x10e, +0x1b0)` 안이다. **TLS 콜백이든 DllMain 이든 예외를 던지면 여기서 잡힌다.**
- [run19 해설 2.11](run19-proc-init-modules-해설.md#211-exe-tls-콜백--전원-다-켠-뒤에) 의 "비상구로 나가더라도 지침서는 덮고 나간다" 가 DLL 쪽에도 똑같이 있다.

#### 결과 비교 — 표 `[정적]`

| 일어난 일 | 상태 코드 | `ProcessAttachCalled` (0x80000) | `ProcessAttachFailed` (0x100000) | 남은 명부 줄 |
|---|---|---|---|---|
| 성공 (`AL ≠ 0`) | 0 | 켬 (`+0x231`) | — | 다음 줄로 |
| DllMain **FALSE** (`AL == 0`) | **`0xc0000142`** (상수, `+0x298`) | 켬 | 켬 (`+0x29e`) | 안 켬 |
| TLS·DllMain **예외** | **`0xc0000142`** | **안 켬** | 켬 | 안 켬 |
| `LdrpApplyPatchImage` 음수 | 그 값 그대로 | — | 안 켬 | 안 켬 |

- 왜 FALSE 일 때 `ProcessAttachCalled` 가 켜지나: 그 표시는 "스위치를 **눌렀다**" 는 뜻이라서다 — 눌렀는데 안 켜진 것. 예외면 스위치 누르기가 **끝까지 못 간** 것이라 안 켠다. (이 해석은 비트 이름으로 읽은 것 `[추측: 이름]`.)
- `LdrpCallTlsInitializers` 의 반환값은 **버린다.** 그래서 TLS 쪽 실패는 **예외로만** 알려진다 `[정적]`.
- 실패 코드가 늘 같은 상수라는 점도 기억해 두자: DllMain 이 FALSE 면 무엇이 잘못됐든 `0xc0000142` 다.
- 그리고 2.6 대로 이 음수가 위로 번져 조상 카드가 모두 -4 가 된다.

#### 도구 이야기 — 착지점은 지도에서 빠졌다

- `_calls.tsv` (호출 지도) 는 켜기 담당의 호출을 **11곳**으로 적었다. 실제는 **12곳**이다.
- 빠진 하나 = 착지점 안 `+0x1fe` (ret `+0x203`) `LdrpLogInternal` `[정적: 원본 바이트]`.
- 이유: Ghidra 가 점프로 안 닿는 착지점(`+0x1b0 ~ +0x21f`)을 **코드로 안 따라갔다.** `.asm` 에 "읽지 않은 틈" 으로 남았다.
- 결과서가 원본 바이트(`objdump`)와 unwind 범위 표(`pefile`)로 찾아냈다. flow.md 첫머리 "정적 근거" 에도 이 방법을 한 줄 더 적었다.
- 비유: 노선도 제작 프로그램이 **비상 통로**는 길로 안 그렸다. 그래서 대피도를 따로 펴 보고 찾았다.

### 2.10 핵심 ④ exe 카드는 통째로 건너뛴다

#### 오래된 질문

- run19 에서 본 것: exe TLS 콜백은 `LdrpInitializeProcess +0x1c31` 조건 → `+0x1c94` (ret `+0x1c99`) 에서 **따로** 부른다.
- 그런데 exe 도 카드가 있고, 순서 담당은 exe 카드에서 출발한다. 그럼 켜기 담당이 exe 를 켜면 되지 않나? **왜 exe 만 따로?**

#### 답 — 단계별로 `[정적]`

1. 켜기 담당은 명부 줄 포인터를 **전역 `LdrpImageEntry`** 와 비교한다 (run19 해설의 **벽 주소록** 속 exe 명부 줄).
2. 같으면 한 바퀴 A 에서도 (`+0x4b`) 한 바퀴 B 에서도 (`+0x9b`) **건너뛴다.**
   - `ImageDll` 비트를 보는 게 아니라 **포인터 비교**다.
3. exe 카드에는 명부 줄이 exe 하나뿐이다 → 할 일이 하나도 없다.
4. → Node(exe 카드) 는 **도장 8 → 9 만 쓰고 0 을 돌려준다.** 로그·지침서·TLS·진입점이 **하나도 없다.**
5. 이 호출은 맨 바깥 GR 프레임의 `+0x65` (ret `+0x6a`) 에서, **dll1·dll2 를 다 켠 뒤** 불린다 (2.4 그림의 ③).
6. → 그래서 exe TLS 는 `LdrpInitializeProcess +0x1c94` 에서 **따로** 돈다. exe 진입점은 로더가 부르지 않고 `NtContinue` 뒤에 간다 (flow.md 2.10).

- 비유: 켜기 담당은 카드에 매달린 명부 줄이 **본 건물**이면 "이건 내 일 아님" 하고 넘긴다. 본 건물 직원 첫 안내(exe TLS)는 세팅 담당(`LdrpInitializeProcess`)이 옆 건물들 다 켠 뒤 **직접** 한다.

#### run8 표에 exe 카드가 없던 것도 맞는다 `[정적]` + `[관찰]`

- run8 의 멈춤점은 `LdrpCallTlsInitializers`·`LdrpCallInitRoutine` 이었다 (부른 곳 Node `+0x16b`·`+0x19c`).
- exe 카드는 거기까지 **안 간다** (3번에서 건너뜀). 그러니 run8 표에 exe 카드가 안 나오는 게 코드와 맞다.
- 이 Node(exe 카드) 호출은 **관찰한 적이 없다.** flow.md 에도 "실행은 미관찰" 로 적었다.
  - 결과서의 예측: Node **입구**에 멈춤점을 걸면 exe 시동 중 **3번** 설 것 (GR 3층 → dll2, 2층 → dll1, 1층 → exe 카드). `+0x16b`·`+0x19c` 는 2번. 다만 DLL 안에서 `LoadLibraryExW` 로 중첩 로드가 생기면 더 설 수 있다.

### 2.11 정리 — 비유로 한 번 더

- 관리실에는 **순서 담당**과 **켜기 담당**이 있다.
- 순서 담당은 **본 건물 카드**를 들고 출발한다. 앞면 끈을 따라가서, 끈 끝 카드가 "준비 됨" 이면 그 카드부터 처리하러 **한 층 내려간다.** "다 켜짐" 이나 "켜는 중" 카드는 건너뛴다.
- 한 카드의 끈을 다 보고 나서야 그 카드를 켜기 담당에게 넘긴다. 그래서 **가장 끝 건물(dll2) 부터** 켜진다.
- 켜기 담당은 카드에 "켜는 중" 도장을 찍고, 명부의 "켠 순서" 줄에 이름을 적고, 건물마다 **지침서 펴기 → 직원 첫 안내 → 전원 스위치(정적 import 면 첫 직원 업무 메모를 같이 건넴) → 지침서 덮기** 를 한다. 끝나면 "다 켜짐" 도장.
- 사고(FALSE·예외)가 나면 "켜기 실패" 도장이 위로 줄줄이 찍힌다.
- **본 건물 줄**은 켜기 담당이 손대지 않는다. 그건 세팅 담당이 나중에 따로 한다.

### 2.12 곁가지 — 결과서·요청서와 다른 곳

run 문서가 이미 적은 것을 옮긴다. 이 글은 run 문서를 따랐다.

- 요청서(sast/22) 의 "Node 호출 11" → 실제 **12곳** (2.9 도구 이야기). 요청서는 고치지 않는다.
- 결과서 2-10 의 "`+0x348 JMP +0x875`" 는 절대 주소 끝자리(`0x18000e875`)를 그대로 적은 것이다. 함수 시작 기준으로는 **`+0x2a5`** (`.asm` 확인). 이 글(2.7 표 1번)도 `+0x2a5` 로 적었다.
- 버전 대조: `_calls.tsv` 의 `LdrpInitializeProcess +0x1bb6/+0x1bbb`, `LdrpInitializeNode +0x166/+0x16b`, `+0x197/+0x19c` 가 run7·run8 콜스택과 같다. 다시 뽑은 `.asm` 도 앞 것과 글자까지 같다.

### 큰 그림에서 어떻게 이어지나

- 지금까지 그림 2 의 `(2) import DLL 초기화` 는 **관찰한 콜스택**이었다. "이렇게 불렸다" 는 알았지만 "왜 이 순서인가" 는 짐작이었다.
- 이번에 그 순서가 **코드의 모양**(후위 순서 + 도장 검사)에서 나온다는 걸 봤다. 관찰과 코드가 맞물렸다.
- 그리고 처음으로 **exe 카드가 이 길을 어떻게 지나는지**가 그림에 들어갔다. exe TLS(`(3)`) 가 왜 따로 있는지도 같이 풀렸다.
- 다음 구간은 **켜기 담당이 부르는 두 함수의 안쪽**이다 (Q16, 정적):
  - `LdrpCallTlsInitializers(1, 명부 줄)` 안 — TLS 콜백을 어떻게 찾아 `ImageTlsCallbackCaller` 로 넘기나. kernel32 길에서 콜백이 안 불린 이유.
  - `LdrpCallInitRoutine(EntryPoint, DllBase, 1, R9)` 안 — 정말 한 칸씩 밀어 `DllMain(DllBase, 1, R9)` 가 되나. `AL` 을 어떻게 돌려주나.
- 그게 끝나면 전원 켜기 구간(`+0x1bbb`)의 **정적 지도는 거의 다 찬다.** 남는 건 실제 값을 보는 버스 타기(Q24·Q25·Q27)다.
