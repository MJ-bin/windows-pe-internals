## 1. 이번 바퀴의 질문

### 큰 그림에서 어디인가

test.exe 를 실행하면 대략 이런 순서로 일이 일어난다 (01_sprint 에서 디버거로 본 흐름).

```
cmd.exe 창에서 "test.exe" 입력
 └─ cmd.exe (유저 쪽): "새 프로그램 띄워 줘"
     └─ 시스템 콜로 커널에 부탁
         └─ nt!NtCreateUserProcess          ← 이번 바퀴 (Q1)
              새 가게(test.exe) 짓기, 첫 직원(첫 스레드) 뽑기, 등록하기
 ─ ─ (2.2 공백: 첫 직원은 언제 일을 시작하나?) ─ ─
 test.exe 첫 스레드 출발 (커널)
  └─ ntdll 로더: dll 올리기, TLS 콜백, DllMain
      └─ main
```

- 이번 구간에서 일하는 건 **test.exe 가 아니라 부모 cmd.exe** 다.
- test.exe 는 아직 "만들어지는 중" 이라 자기 코드를 한 줄도 안 돌렸다 `[관찰]` (run3).

### 무엇이 궁금했나

1. `NtCreateUserProcess` 가 **직접 부르는 함수를 전부**, 코드에 적힌 순서대로 보고 싶다.
2. 01_sprint 에서 디버거로 본 오프셋 4개가 **코드에서도 똑같은 자리**인지 맞춰 보고 싶다.
3. 새로 만든 첫 스레드를 **멈춘 채로 두는지, 풀어 주는지** 코드로 볼 수 있는 데까지 보고 싶다 (flow.md 2.2 `[공백]`).

### 바퀴 전에 알던 것

- `[관찰]` (run3) 부모 cmd.exe 의 **스레드 하나**에서 차례로:
  - `NtCreateUserProcess` 를 `nt!KiSystemServiceCopyEnd+0x28` 이 부름 (시스템 콜 입구)
  - `NtCreateUserProcess +0xc36` → `PspAllocateProcess`
    - 그 안 `+0x2314` → `MmCreatePeb`
  - `NtCreateUserProcess +0xe5c` → `PspAllocateThread`
  - `NtCreateUserProcess +0xfc2` → `PspInsertProcess`
  - `NtCreateUserProcess +0x101a` → `PspInsertThread`
    - 그 안 `+0x807` → `PspCallProcessNotifyRoutines`
- `[관찰]` (run3) 옛날 방식 함수 `nt!PspCreateProcess` 는 **안 불렸다.**
- 그런데 이건 **우리가 멈춤점을 건 함수만** 본 것이다.
  - 그 사이사이에 다른 함수를 몇 개나 더 부르는지는 몰랐다.
- `[공백]` (2.2) `NtCreateUserProcess` 가 끝난 뒤 ~ test.exe 첫 스레드가 출발하기 전.

## 2. 바탕 개념

> 이 절의 "뜻"은 **일반적으로 알려진 설명**이다 `[추측]` (이 프로젝트에서 직접 확인한 게 아니다).
> 이 프로젝트에서 본 사실에는 따로 태그를 붙였다. 비유는 설명일 뿐이라 태그가 없다.

말이 많아서 네 묶음으로 나눴다.

- **무대**: 커널과 유저 / 시스템 콜 / 프로세스 / 스레드
- **주소 읽기**: 함수와 주소 / 오프셋 / 부르는 자리와 돌아올 자리 / 콜스택
- **문서 읽기**: 정적분석과 동적분석 / 표시 태그 / 그림의 점선 정적 상자
- **이번 결과에 나오는 말**: 직접 호출과 간접 호출 / 비트와 플래그 / 스레드를 멈춘 채로 만들기 / 핸들 / 이미지 섹션 / 한 주소에 이름 여럿 ICF 별칭

**무대**

### 커널과 유저

- 뜻: Windows 안의 코드는 크게 두 층에서 돈다.
  - **커널** = 운영체제의 중심. 메모리·프로세스·파일을 전부 관리한다. 권한이 가장 세다.
  - **유저** = 우리 프로그램(test.exe)과 그 도우미(ntdll, kernel32 등)가 도는 층. 커널 쪽 메모리는 직접 못 만진다.
- 비유: 큰 상가 건물.
  - 커널 = **관리사무소**. 건물 전체의 땅·전기·출입을 관리한다.
  - 유저 = **각 가게**. 자기 가게 안에서는 마음대로지만, 새 가게를 내거나 땅을 더 받으려면 관리사무소에 신청해야 한다.
- 이 프로젝트에서:
  - 이름 앞의 `nt!` = 커널(`ntoskrnl.exe`) 함수. `ntdll!` = 유저 쪽 함수.
  - 이번 바퀴에 나오는 함수는 **전부 `nt!`**, 즉 전부 커널 안이다.

### 시스템 콜

- 뜻: 유저 코드가 커널에게 일을 부탁할 때 쓰는 **정해진 문**.
- 비유: 관리사무소의 **신청 창구**. 가게 주인은 사무실 안으로 못 들어가고, 창구에 신청서를 내면 담당자가 처리해 준다.
- 이 프로젝트에서:
  - `[관찰]` (run3) cmd.exe 는 시스템 콜로 커널에 들어오고, 창구 담당 `nt!KiSystemServiceCopyEnd+0x28` 이 `NtCreateUserProcess` 를 불렀다.
  - `[정적]` (run9) 코드상 `NtCreateUserProcess` 를 직접 부르는 함수는 없다 (Ghidra 의 호출자 목록이 빈다). 창구가 "번호표 보고 담당자 찾아가는" 식으로 간접으로 부르는 모양과 맞다.
  - 그러니 `NtCreateUserProcess` 는 "새 가게 내 주세요" 신청서를 처리하는 **담당자**다.

### 프로세스

- 뜻: 실행 중인 프로그램 하나를 담는 그릇. 자기만의 메모리 공간과 자원을 가진다.
- 비유: **가게**.
  - 주소 공간(그 프로세스가 쓸 메모리 범위) = 가게가 받은 **빈 땅**.
  - exe·dll 을 메모리에 올리기(매핑) = 그 땅에 **건물 갖다 놓기**.
  - PEB(프로세스 정보 묶음, 유저 쪽이 읽는 것) = 가게 문 앞 **안내판**.
- 이 프로젝트에서: 이번 구간은 관리사무소가 test.exe 라는 **새 가게를 짓는 중**이다. 신청한 쪽은 cmd.exe 가게다.

### 스레드

- 뜻: 프로세스 안에서 **실제로 코드를 한 줄씩 실행하는 일꾼**. 프로세스엔 적어도 하나가 있어야 일이 돈다.
- 비유: 가게의 **직원**. 가게 건물만 있고 직원이 없으면 아무 일도 안 일어난다.
- 이 프로젝트에서:
  - `[관찰]` (run3) 이번 구간의 호출은 전부 **cmd.exe 의 직원 한 명(스레드 하나)** 이 했다.
  - test.exe 의 **첫 스레드(첫 직원)** 는 이 안에서 "뽑히기만" 한다. 일을 시작하는 건 그림 2 쪽이다.

**주소 읽기**

### 함수와 주소

- 뜻:
  - **함수** = 이름 붙은 코드 덩어리. 다른 함수가 "이거 해 줘" 하고 부를 수 있다.
  - **주소** = 그 코드가 메모리 어디에 있는지 나타내는 숫자.
  - `nt!PspAllocateProcess` = `nt` 모듈 안의 `PspAllocateProcess` 라는 함수. (모듈 = exe·dll 파일 하나)
- 비유: **요리책**.
  - 모듈 = 요리책 한 권 (`nt` 책, `ntdll` 책)
  - 함수 = 책 안의 레시피 한 편
  - 주소 = 그 레시피가 시작하는 **쪽수**
- 이 프로젝트에서:
  - 커널 함수 이름은 Windows 버전마다 다르다. 그래서 이름을 쓰기 전에 목록(`_index.tsv`)으로 먼저 확인한다.
  - `[정적]` 이번 커널(26100.9457)의 함수 목록은 34982개다 (결과서).

### 오프셋

- 뜻: **함수 시작에서 몇 바이트 떨어진 자리**인지 나타내는 숫자.
  - `NtCreateUserProcess+0xc36` = `NtCreateUserProcess` 시작에서 `0xc36` 바이트 뒤.
  - `0x` 는 "16진수다" 라는 표시. `+0x…` 를 보면 "함수 안 몇째 자리" 라고 읽으면 된다.
- 비유: 쪽수(주소)가 아니라 "**레시피 시작부터 몇째 줄**".
  - 책을 새로 찍으면 쪽수는 바뀔 수 있다. Windows 도 부팅할 때마다 커널이 놓이는 주소가 바뀔 수 있다.
  - 그래도 **같은 판(같은 빌드)** 이면 "레시피 안 몇째 줄" 은 그대로다.
- 그래서 이게 왜 중요하냐면:
  - 디버거에서 본 `+0xc36` 과, Ghidra 로 코드를 읽어서 본 `+0xc36` 을 **서로 맞대 볼 수 있다.**
  - 단, 같은 판이어야 한다. 그래서 run9 는 먼저 **커널 PDB GUID** 가 run3 때와 같은지 봤다 `[정적]` (`C29EBFB06B78B3C020DCA66D99713F9E1`, 같음 → 같은 커널).
  - PDB GUID = 그 판의 **고유 번호** 정도로 생각하면 된다.

### 부르는 자리와 돌아올 자리

이게 이번 바퀴에서 제일 헷갈리기 쉬운 부분이라 천천히 간다.

- 뜻:
  - 함수 A 가 함수 B 를 부르려면, A 안 어딘가에 `call` 명령이 있다. 이 자리 = **부르는 자리** (`call`, 결과서에선 `call_off`).
  - B 가 일을 끝내면 A 는 `call` **바로 다음 명령**부터 이어 간다. 이 자리 = **돌아올 자리** (`ret`, 결과서에선 `ret_off`).
- 비유: 레시피 A 의 12째 줄에 "소스는 레시피 B 를 보세요" 라고 쓰여 있다.
  - B 를 보러 가기 전에 **책갈피를 13째 줄에** 꽂는다. 돌아와서 이어 읽을 줄이니까.
  - 부르는 자리 = 12째 줄 ("B 보세요" 가 적힌 줄)
  - 돌아올 자리 = 13째 줄 (책갈피 꽂은 줄)
- 이 프로젝트에서:
  - run 문서 표에는 둘 다 적혀 있다. 예: `PspAllocateProcess` 는 call `+0xc31`, ret `+0xc36`.
  - 이 글에 옮긴 표에서는 늘 **ret 이 call 보다 5 크다** (예: `+0xc31` → `+0xc36`, `+0x295` → `+0x29a`).
    - `[정적]` 결과서: 이 함수의 호출은 전부 `CALL rel32` 라는 한 가지 모양이다.
    - `[추측]` 이 모양의 명령은 5바이트짜리라서 그렇다 (일반적으로 알려진 설명).
  - **디버거 콜스택에 찍히는 건 돌아올 자리(ret)** 다 (run 문서 "오프셋 읽는 법").
  - **flow.md 그림 라벨도 ret** 을 쓴다. 그래야 디버거 화면과 그림을 바로 맞대 볼 수 있다.

### 콜스택

- 뜻: 지금 멈춘 자리까지 "**누가 누구를 불러서 여기까지 왔나**" 를, 돌아올 자리들로 보여 주는 목록. WinDbg 에서는 `k` 명령으로 본다.
- 비유: 꽂혀 있는 **책갈피 더미**.
  - A 를 읽다 B 로, B 를 읽다 C 로 가면 책갈피가 두 개 꽂힌다.
  - 맨 위 = 지금 읽는 곳. 아래로 갈수록 먼저 펼쳤던 레시피.
- 이 프로젝트에서: run3 에서 `PspCallProcessNotifyRoutines` 입구에 멈췄을 때를 생각해 보자.
  - 아래 그림은 로그 원문이 아니라, run3 표의 "부른 곳" 칸을 **콜스택 모양으로 쌓아 본 것**이다.

```
nt!PspCallProcessNotifyRoutines        ← 지금 여기 (함수 입구)
nt!PspInsertThread+0x807               ← 책갈피 1: PspInsertThread 로 돌아올 자리
nt!NtCreateUserProcess+0x101a          ← 책갈피 2
nt!KiSystemServiceCopyEnd+0x28         ← 책갈피 3 (시스템 콜 창구)
```

- 한 줄 읽기: `nt!PspInsertThread+0x807` =
  - "`PspInsertThread` 가 누군가(바로 위 줄 `PspCallProcessNotifyRoutines`)를 불렀고, 끝나면 `+0x807` 로 돌아온다."
  - 그러니 **부르는 명령 자체는 그보다 조금 앞**에 있다. `[정적]` (run9) 실제로 call 은 `+0x802`.

**문서 읽기**

### 정적분석과 동적분석

- 뜻:
  - **정적분석** = 프로그램을 **실행하지 않고** 코드를 읽는 것. 이 프로젝트에서는 서버의 Ghidra 로 한다.
    - 디스어셈블 = 기계어를 사람이 읽을 수 있는 명령 줄로 바꾼 것.
    - 디컴파일 = 그걸 다시 C 언어 비슷하게 써 본 것.
    - PDB = 마이크로소프트가 주는 **함수 이름표** 파일. 이게 있어야 `FUN_1409…` 대신 `PspAllocateProcess` 같은 이름이 보인다.
  - **동적분석** = 프로그램을 **실제로 돌리면서** 멈춤점을 걸고 보는 것. 이 프로젝트에서는 WinDbg 커널 디버거로 한다.
- 비유: 버스 노선 알아보기.
  - 정적 = **노선도**를 읽는 것. "이 정류장들을 지난다" 가 다 보인다. 갈림길이 있으면 두 길 다 보인다.
  - 동적 = **실제로 버스를 타 보는 것**. 오늘 이 버스가 갈림길에서 어느 쪽으로 갔는지 안다.
- 이 프로젝트의 규칙: **노선도 먼저**(정적), 노선도로 못 정하는 것만 **타 본다**(동적).
  - run9 는 노선도만 본 바퀴다.

### 표시 태그

- 뜻: 문서의 사실마다 "**어떻게 알게 됐나**" 를 붙인 꼬리표.

| 태그 | 뜻 | 버스 비유 |
|---|---|---|
| `[관찰]` | 디버거로 실행 중에 **직접 본 것**. "실제로 일어났다" | 버스를 타서 그 정류장을 지나는 걸 봤다 |
| `[정적]` | 코드에 **그렇게 쓰여 있는 것**. 실행 때 그 길로 갔는지는 모른다 | 노선도에 그 정류장이 있다 |
| `[추측]` | 짐작, 또는 일반적으로 알려진 설명. 직접 안 봤다 | "아마 저쪽으로 가겠지" |
| `[공백]` | 아직 아무것도 안 봤다 | 노선도도 안 봤다 |
| `[소스]` | `sample/` 소스에 그렇게 쓰여 있다 | (우리가 직접 그린 노선) |

- run 문서 표에서는 `[관찰]` 대신 `[26100.9457 확인]` 이라고 쓴다. 같은 뜻이다.
- 둘 다로 봤으면 **둘 다** 붙인다. 예: `[관찰]+[정적]` = "노선도에도 있고, 타 보니 진짜 지나갔다".
- 제일 중요한 차이: **`[정적]` 은 "그 길이 있다" 이지 "그 길로 갔다" 가 아니다.**
  - 이번 바퀴에서 이 차이가 크게 나오는 곳이 3절의 "첫 스레드를 멈춰 두나" 다.

### 그림의 점선 정적 상자

- 뜻: flow.md 그림 1 에 run9 부터 생긴 상자 모양이다.
  - **실선 테두리** 상자 = 디버거로 **불리는 걸 본** 함수 `[관찰]`.
  - **점선 테두리 + `(정적)`** 상자 = 코드에 call 이 **있지만**, 실행 때 정말 불렸는지는 아직 안 본 함수 `[정적]`.
  - 화살표 라벨 `+0x…` 는 두 경우 모두 **돌아올 자리(ret)** 다.
  - 라벨 앞의 `(1)`, `(2)` … 는 부른 순서다. 점선 상자가 섞여 있으면 **코드 흐름 순서**로 매긴 번호다.
- 비유: 지도에서 **실선 길 = 내가 걸어 본 길**, **점선 길 = 지도에만 있는 길**.
- 그림 1 의 한 화살표를 읽어 보면 (모양만):

```
nt!NtCreateUserProcess --"(2) +0x6cb"--> [ nt!IopCreateFile (정적: exe 파일 열기) ]   ← 점선 상자
```

  - "`NtCreateUserProcess` 가 **두 번째로**, 돌아올 자리 `+0x6cb` 에서 `IopCreateFile` 을 부르는 **코드가 있다**. 실행 때 탔는지는 아직 안 봤다."

### 직접 호출과 간접 호출

- 뜻:
  - **직접 호출** = call 명령에 부를 곳이 박혀 있다. 코드만 보고도 누구를 부르는지 안다.
  - **간접 호출** = 어딘가에 적힌 주소(함수 포인터)를 꺼내서 그리로 간다. 그 칸에 실행 때 무엇이 들어 있는지 봐야 안다.
- 비유:
  - 직접 = 레시피에 "**35쪽 레시피 B** 보세요" 라고 쓰여 있다.
  - 간접 = "**냉장고에 붙은 메모**에 적힌 레시피를 보세요". 메모는 그날그날 바뀔 수 있다.
- 이 프로젝트에서 `[정적]` (run9):
  - `NtCreateUserProcess` 의 직접 호출 83줄 중 **2곳이 실은 간접 호출**이다: `+0x5b2`, `+0x11bb`.
    - `+0x5b2` 는 전역 포인터 `nt+0xfd83d0`, `+0x11bb` 는 `nt+0xf04d30` 을 읽어서 부른다. 0 이면 안 부른다 (결과서).
  - 목록에는 `_guard_dispatch_icall` 이라는 이름으로 찍혀서 직접 호출처럼 보였다 (결과서 "스크립트 문제 1").
    - `[추측]` 이건 CFG 라는 보안 장치의 문지기 함수다. 간접 호출을 하기 전에 "가도 되는 곳인지" 검사하고 넘겨 준다 (일반적으로 알려진 설명).
  - 진짜 대상은 **실행해 봐야** 안다 → 5절.

### 비트와 플래그

- 뜻:
  - 숫자 하나를 **0/1 스위치 여러 개**로 쪼개 쓰는 방법이 있다. 스위치 하나 = **비트**. 맨 오른쪽 스위치 = **bit0**.
  - 이런 스위치 묶음으로 쓰는 값 = **플래그**.
- 비유: 신청서 아래쪽의 **체크 칸 여러 개**. bit0 = 첫 번째 체크 칸.
- 이 프로젝트에서:
  - `NtCreateUserProcess` 의 8번째 인자 `ThreadFlags` 가 이런 체크 칸 묶음이다.
    - `[추측]` 인자 이름 `ThreadFlags` 는 알려진 함수 모양에서 빌린 것이다. 이 빌드 PDB 로 확인한 건 아니다.
  - `[정적]` (run9) 입구에서 **bit0 말고 다른 칸이 체크돼 있으면** 바로 에러 값 `0xc000000d` 로 돌려보낸다.
    - 검사에 쓰는 틀이 `0xfffffffe` = "bit0 만 빼고 전부" 다 (결과서: `ThreadFlags & 0xfffffffe` 가 0 이 아니면 에러).
    - 즉 **허용되는 체크 칸은 bit0 하나뿐**이다.

### 스레드를 멈춘 채로 만들기

- 뜻: 스레드를 만들되 "**아직 일 시작 금지**" 상태로 두는 것 (영어로 suspend).
  - 누군가 나중에 풀어 줘야(resume) 일을 시작한다.
- 비유: 새 직원을 뽑아 놓고 목에 "**대기**" 팻말을 걸어 둔다. 팻말을 떼 주는 사람이 따로 있어야 일한다.
- 왜 이런 걸 하나:
  - `[추측]` 부모가 새 프로세스 준비를 마저 끝낼 시간을 벌려고, 멈춘 채로 만들고 나중에 풀어 준다고 알려져 있다. 부모 유저 쪽(`KERNELBASE!CreateProcessInternalW` 등, 이름 확인 필요)이 시스템 콜로 따로 풀어 준다는 짐작이다 (flow.md 2.2). 이 빌드에서는 아직 확인 안 했다 → Q5.
- 이 프로젝트에서:
  - 커널 함수 이름으로는 `KeSuspendThread`(팻말 걸기)가 이번에 나온다 `[정적]`.
  - `KeReadyThread` 도 나온다 `[정적]`. `[추측]` "CPU 탈 준비 됨" 줄에 세우는 것. 팻말이 걸려 있으면 줄에 서도 바로 일하진 못한다 (flow.md 2.2).

### 핸들

- 뜻: 프로그램이 커널이 가진 물건(프로세스, 스레드, 파일 등)을 가리킬 때 쓰는 **번호표**.
- 비유: 부모가 자식 가게를 가리킬 때 쥐는 **손잡이**.
- 이 프로젝트에서 `[정적]` (run9):
  - **프로세스 핸들**: `NtCreateUserProcess +0x10a7` (call `+0x10a2`) `PspCreateObjectHandle`.
  - **스레드 핸들**: `PspInsertThread +0x525` (call `+0x520`) 같은 `PspCreateObjectHandle`.

### 이미지 섹션

- 뜻: exe 파일을 "**메모리에 올릴 수 있는 모양**" 으로 준비해 둔 커널 쪽 물건 (flow.md 2.1 의 설명).
- 비유: 설계도(exe 파일)를 보고 미리 짜 둔 **조립식 건물 세트**. 아직 땅(주소 공간)에 갖다 놓지는(매핑) 않았다.
- 이 프로젝트에서 `[정적]` (run9): `NtCreateUserProcess +0x93c` (call `+0x937`) `MmCreateSpecialImageSection` 이 이걸 만든다.

### 한 주소에 이름 여럿 ICF 별칭

- 뜻: 링커가 **내용이 똑같은 함수들을 하나로 합쳐** 공간을 아끼는 일이 있다 (ICF). 그러면 한 주소에 이름이 여러 개 붙는다. 도구는 그중 하나만 보여 줄 수 있어서, **엉뚱한 이름**이 찍히기도 한다.
- 비유: 한 집에 **38가족**이 사는데 문패는 하나만 걸려 있다. 문패만 보면 전혀 상관없는 가족 이름이 보인다.
- 이 프로젝트에서:
  - `NtCreateUserProcess +0x3cb` 의 호출이 그런 경우다. run 문서에는 "잡일" 로 묶여 이름 없이 지나간다.
  - `[정적]` 그 대상은 **0 을 돌려주는 빈 함수**다 (결과서: 3바이트 `xor eax,eax; ret`).
  - 같은 주소에 이름이 38개 붙어 있다 (`pdb_aliases.py --lookup ntoskrnl.exe 0x490960`). 결과서 목록엔 그중 저장장치 쪽 이름(`SC_DEVICE` …)이 찍혔지만 `NtCreateUserProcess` 와는 관련 없다.

### 3.2 한 줄씩 읽는 법

트리 한 줄을 "**누가 / 어디서 / 누구를 / 무엇을 위해**" 로 풀어 읽어 보자.

**(4) `+0xc36` `PspAllocateProcess` `[관찰]+[정적]`**

- 누가: `NtCreateUserProcess`
- 어디서: 돌아올 자리 `+0xc36` (부르는 자리는 `+0xc31`)
- 누구를: `PspAllocateProcess`
- 무엇을 위해: `[추측]` 새 프로세스의 정보 묶음(`_EPROCESS`)과 메모리 공간을 준비한다. 비유하면 **가게 건물 짓기** (flow.md 2.1).
- 태그 뜻: run3 에서 디버거로 **실제로 불리는 걸 봤고**, run9 에서 코드에도 **같은 자리에 call 이 있는 걸** 봤다.

**(2) `+0x6cb` `IopCreateFile` `[정적]`**

- 누가: `NtCreateUserProcess`
- 어디서: 돌아올 자리 `+0x6cb` (부르는 자리 `+0x6c6`)
- 누구를: `IopCreateFile`
- 무엇을 위해: `[정적]` **실행 파일(exe)을 연다.** 접근권 `0x100020` = 실행 + 동기. 비유하면 **설계도(exe 파일) 꺼내 오기**.
- 태그 뜻: 코드엔 있다. test.exe 실행 때 정말 이 줄을 지났는지는 **아직 안 봤다** (그래서 그림에선 점선 상자).

**(10) 안의 (1) `+0x2e5` `KeSuspendThread` `[정적]` 조건부**

- 누가: `PspInsertThread` (← `NtCreateUserProcess` 가 `+0x101a` 에서 부른 함수)
- 어디서: 돌아올 자리 `+0x2e5` (부르는 자리 `+0x2e0`)
- 누구를: `KeSuspendThread`
- 무엇을 위해: 첫 스레드에 "대기" 팻말 걸기. 단, **플래그 bit0 가 켜졌을 때만** 이 줄로 온다 `[정적]`.
- 태그 뜻: 노선도에 **갈림길**이 있고, 그중 한쪽 길에 이 정류장이 있다. 오늘 버스가 어느 쪽으로 갔는지는 모른다.

### 3.3 83줄을 다섯 구간으로

관찰한 4개 함수를 **울타리**로 삼아 83줄을 나누면 이렇다 `[정적]`.

| 구간 | 범위 | 호출 수 | 하는 일 (요약) | 가게 비유 |
|---|---|---|---|---|
| (가) | `PspAllocateProcess` 앞 | 47 | 재료 모으기: 인자 검사, exe 파일 열기, 이미지 섹션 만들기, 토큰·권한·서명 검사 | 신청서 검토, 설계도 꺼내기, 조립식 세트 준비, 자격 검사 |
| (나) | `PspAllocateProcess` ~ `PspAllocateThread` | 10 | 첫 스레드 준비: 시작 문맥, 스레드 플래그 바꾸기 | 첫 직원의 첫 업무 지시서, "대기" 체크 칸 옮겨 적기 |
| (다) | `PspAllocateThread` ~ `PspInsertProcess` | 5 | 보호 프로세스 검사 등 | 특수 가게끼리 안 맞는지 확인 |
| (라) | `PspInsertProcess` ~ `PspInsertThread` | **0** | 호출 없이 인자만 채움 | 바로 다음 서류로 |
| (마) | `PspInsertThread` 뒤 | 17 | 부모 쪽 마무리: 프로세스 핸들, 결과 기록, 정리 | 손잡이 건네기, 결과 적기, 뒷정리 |
| 경계 | 관찰 4개 | 4 | | |

- 합치면 47 + 10 + 5 + 0 + 17 + 4 = **83** (결과서).
- 관찰 4개 사이에 **꽤 많은 일**이 숨어 있었다는 게 핵심이다. 특히 (가) 47개. 가게를 짓기(`PspAllocateProcess`) 전에 서류·설계도·자격 검사를 먼저 한다.

### 3.4 관찰과 코드가 맞았다

| 관찰 (run3, 콜스택) | 코드 call | 코드 ret | callee | 일치 |
|---|---|---|---|---|
| `+0xc36` | `+0xc31` | `+0xc36` | `PspAllocateProcess` | 예 |
| `+0xe5c` | `+0xe57` | `+0xe5c` | `PspAllocateThread` | 예 |
| `+0xfc2` | `+0xfbd` | `+0xfc2` | `PspInsertProcess` | 예 |
| `+0x101a` | `+0x1015` | `+0x101a` | `PspInsertThread` | 예 |

- `[관찰]` run3 + `[정적]` run9: 네 줄 모두 **돌아올 자리까지 같다.** `PspInsertThread +0x807` → `PspCallProcessNotifyRoutines` 도 같다 (call `+0x802`).
- `[정적]` 네 함수는 `NtCreateUserProcess` 안에서 **한 번씩만** 불린다. 코드 순서도 관찰 순서와 같다.

왜 이게 반가운가 (단계별로):

1. 디버거(실행 중)와 Ghidra(파일)는 서로 다른 도구다.
2. 둘이 **같은 판의 커널**을 봤고(GUID 같음), 같은 함수의 **같은 줄**을 가리켰다.
3. 그래서 Ghidra 로 읽은 노선도가 **실제 버스가 다니는 노선도와 같은 것**이라고 믿을 수 있다.
4. 그래도 `[정적]` 줄들은 여전히 "**길이 있다**" 일 뿐이다. "**그 길로 갔다**" 는 디버거로 봐야 한다.

### 3.5 사이에 호출이 0개인 구간 (라)

- `[정적]` `PspInsertProcess` 와 `PspInsertThread` 사이엔 **호출이 하나도 없다.** 인자만 채우고 바로 넘어간다.
- `[정적]` 그래서 생기는 재밌는 점: `PspInsertProcess` 가 실패를 돌려줘도, `PspInsertThread` 를 **먼저 부른다.** 실패 검사는 그 뒤 `+0x1025` 에서 한다.
  - 비유: "가게 등록" 결과를 확인하기 전에 "직원 등록" 서류부터 넣고, 그다음에 둘 다 확인하는 순서.

### 3.6 첫 스레드를 멈춰 두나, 풀어 주나 (2.2)

이번 바퀴에서 제일 중요한 추론이다. 근거를 하나씩 쌓아 보자.

**근거 1 — 입구의 체크 칸 검사** `[정적]`

- `ThreadFlags`(8번째 인자)에서 허용되는 체크 칸은 **bit0 하나뿐**이다 ([비트와 플래그](#비트와-플래그) 참고).
- 다른 칸이 켜져 있으면 바로 `0xc000000d` 로 돌아간다 (`+0x1bf` TEST → `+0x1ce` JZ → `+0x11f9`).

**근거 2 — 체크 칸 옮겨 적기** `[정적]`

- `(6) +0xdd3` `PspMapThreadCreationFlags` 가 그 값을 **커널 안쪽 플래그로 바꾼다.**
- 바뀐 값은 `PspInsertThread` 의 4번째 인자로 넘어간다.
- 단, 이 함수 본문(80바이트)은 이번에 안 열어 봤다. **bit0 가 그대로 bit0 로 가는지는 모른다** `[공백]` (flow.md 2.1).

**근거 3 — 갈림길** `[정적]`

- `PspInsertThread` 안에서, 넘겨받은 플래그의 bit0 가
  - 켜져 있으면 → `+0x2e0` 에서 `KeSuspendThread` 를 부른다 ("대기" 팻말 걸기).
  - 꺼져 있으면 → `+0x2db` 의 `JZ` 로 그 줄을 **건너뛴다.**
    - `JZ` = "0 이면 점프". 여기서는 "체크 안 돼 있으면 팻말 거는 줄을 건너뛰어라" 라는 뜻으로 쓰였다.

**근거 4 — 끝에서 늘 지나는 자리** `[정적]`

- 함수 끝 쪽 `+0x5a1` 에서 `KeReadyThread` 를 부른다. **팻말을 걸었든 안 걸었든** 지나는 자리다.

**근거 5 — 뒤쪽에 "풀어 주기" 가 없다** `[정적]`

- `NtCreateUserProcess` 에서 `PspInsertThread` 뒤의 호출 17개에 Resume·Ready·Start 같은 이름이 **없다.**
- 프로세스 핸들 만들기, 결과 기록, 정리뿐이다.

**그래서:**

- 첫 스레드를 멈춰 둘지는 **실행 때 값(ThreadFlags bit0)** 이 정한다. 코드만으로는 test.exe 때 어느 쪽인지 **못 정한다.**
- 만약 멈춰 뒀다면, 풀어 주는 건 **`NtCreateUserProcess` 밖**의 일이다 `[정적]`.

**아직 확인 아님:**

- test.exe 때 bit0 가 실제로 켜졌는지 `[공백]` → 디버거로 봐야 한다.
- 누가 풀어 주는지 `[공백]`. `[추측]` 부모 유저 쪽(`KERNELBASE!CreateProcessInternalW` 등, 이름 확인 필요)이 따로 풀어 준다 → Q5.

비유로 다시 정리하면 (태그 없음):

- 관리사무소는 신청서의 첫 체크 칸을 보고, 새 직원 목에 "대기" 팻말을 걸지 말지 정한다.
- 팻말을 걸든 안 걸든, 직원을 "출근 대기 줄" 에 세우는 것까지는 한다.
- 팻말을 떼 주는 건 관리사무소 담당자(`NtCreateUserProcess`)의 일이 아니다. 누가 떼 주는지는 다음에 본다.

곁가지 하나 `[정적]`: `KeSuspendThread` 를 부른 직후, 스레드의 어떤 비트(`[스레드+0x5a0]` bit0, 이름 모름)가 켜져 있으면 `KeForceResumeThread` 로 바로 푸는 길도 있다. `[추측]` 에러 때 쓰는 길로 보인다 (결과서).

### 3.7 오프셋이 큰데 먼저 실행되는 줄 — 오프셋 순서 ≠ 실행 순서

트리에서 `PspInsertThread` 안을 보면 이상한 점이 있다.

- `(2) +0x807` 이 `(3) +0x5a6` 보다 **숫자가 큰데 먼저**다.

이유 `[정적]`:

1. `+0x4b8` 의 `JNZ`(조건 점프)가 함수 **뒤쪽 덩어리**(`+0x7bb` ~)로 건너간다.
2. 거기 `+0x802` 에서 알림(`PspCallProcessNotifyRoutines`)을 부른다.
3. `+0x809` 의 `JMP` 로 다시 `+0x4be` 로 돌아온다.
4. 그다음에 `+0x5a1` 에서 `KeReadyThread`.

그래서 실행 흐름은 **팻말(Suspend) → 알림 → 출근 대기 줄(Ready)** 이다.

- 비유: 레시피 중간에 "**부록 3쪽을 보고 다시 여기로 오세요**" 라고 쓰여 있는 것. 부록은 책 뒤쪽(큰 쪽수)에 있지만 먼저 읽는다.
- 교훈 `[정적]` (결과서): **오프셋 순서가 늘 실행 순서인 건 아니다.** 에러 길·공통 정리 길이 코드 뒤쪽에 모여 있고, 서명 검사 재시도는 루프다. 그래서 그림의 `(n)` 번호는 "**성공 길로 보이는 코드 흐름 순서**" 다.
- 참고 `[추측]` (flow.md 2.1): 이 알림 덩어리는 **첫 스레드일 때만** 들어가는 모양이다.

### 3.8 그 밖에 확인된 것

- `[정적]` 옛날 방식 `PspCreateProcess` 를 부르는 코드가 **없다.** run3 관찰("안 불림")과 맞는다.
- `[정적]` points.md 에 `[확인 필요]` 로 적어 둔 `MiCreateImageFileMap`, `MmInitializeProcessAddressSpace`, `PspMapSystemDll`, `MmCreateTeb` 는 이 빌드에 함수로 **있지만**, `NtCreateUserProcess` 가 **직접** 부르지는 않는다.
  - 더 깊은 곳(Q2 이후)에서 찾을 일이다.
- `[정적]` `(5) +0xd22` `PspCreateUserContext` 에는 **반대쪽 길**이 있다: `+0xd3e` (call `+0xd39`) `PspGetContextThreadInternal`. 이미지 섹션 참조가 있으면 앞쪽, 없으면 뒤쪽이다.
  - `[추측]` 일반 exe 실행이면 앞쪽(`PspCreateUserContext`)일 것.
- `[정적]` 성공 길 끝 `(12) +0x1129` (call `+0x1124`) 에서 `PspUpdateCreateInfo` 를 **값 6** 으로 부른다 (`+0x111f` `MOV ECX,0x6`).
  - `[추측]` 6 = "성공" 이라는 건 알려진 값이다. 이 빌드에서 이름으로 확인하진 않았다.
  - `[정적]` 실패 길에서는 같은 함수를 다른 자리(`+0x75f`, call `+0x75a`)에서 값 1 또는 2 로 부른다.
