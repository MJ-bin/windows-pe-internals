### 비유 — 그대로 이어 쓴다

- 커널 = **관리사무소**, 프로세스 = **가게**, 스레드 = **직원**, ntdll = 가게 안 **관리실**, 짐 = **개업 준비물**, 짐 지도 = 준비물 **점검표**.
- 이번 대화에서 오케스트레이터는 **이삿짐** 으로 설명했다. 가게 그림과 같은 이야기다 — 가게가 새 자리로 **이사 들어와 개업 준비를 하는 날** 이라고 보면 된다.
  - 점검표 = **이삿짐 목록**. 상자 (칸) 마다 줄이 하나씩 있다.
  - **Q78** = 목록의 상자마다 "**누가 쌌나**" 를 찾는 일.
  - 목록 밖 짐 = **벽에 박은 못** (IAT — 앞 해설의 벽 콘센트와 같은 것), **옆방 가구** (다른 DLL 의 객체), **옆집에 맡긴 물건** (csrss 쪽 기록).
- run 문서가 이번에 더한 비유: 일 목록 = 이삿날 **작업 지시서 전체**.
  - 짐 지도는 그중 "어느 서랍에 뭘 넣었나" 만 적은 표였다.
  - 이번엔 지시서 전체 (일 86개) 를 쓰고, 서랍 밖에 놓인 짐 (바닥 상자 · 옆집 창고 · 이웃 집 서랍) 이 얼마나 되는지 셌다.

## 1. 이번 바퀴의 질문

### 큰 그림에서 어디인가

이번에도 길 위의 한 점이 아니다. 짐 지도 범위 **전체**를, 이번엔 **일 단위로** 잘랐다. run 문서 1장의 A ~ H 여덟 덩어리가 시간 순서로 이렇게 놓인다.

```
cmd.exe 의 부탁 (CreateProcess)
 │  A  부모 입구 + 커널 NtCreateUserProcess 안   일  1 ~ 35   사진 전 ~ K3~P0 (K1·K2·K3 이 이 안)
 │       (파일 열기 · 섹션 · 프로세스 객체 · 주소 공간 · PEB · 첫 스레드 · 등록 · 알림)
 │  B  부모 마무리 (부모 · csrss)                 일 36 ~ 39   K3~P0
 │  C  test.exe 첫 스레드 커널 쪽 (⓪)             일 40 ~ 43   K3~P0 · P0~P1
 │  D  ntdll 입구 · LdrpInitializeProcess 앞쪽     일 44 ~ 64   주로 P1~P1a
 │  E  kernel32 · kernelbase 준비                  일 65 ~ 67   P1a~P1b
 │  F  병렬 로딩 · exe import                      일 68 ~ 69   P1a~P1b
 │  G  DLL 하나를 올리는 공통 부품                  일 70 ~ 79   P1a~P1b
 │  H  켜기와 은퇴                                 일 80 ~ 86   P1a~P1b · P1b~P2 · P2 이후
 │                                        ← 이번 바퀴: 이 전체를 "일" 로 셈
 └─ RtlUserThreadStart → (CRT) → main    (범위 밖)
```

- 오른쪽 끝은 run44 사진 구간이다 (run 문서 1장 표의 "구간" 열). 정확한 값은 일마다 그 열을 본다.

- 범위는 짐 지도와 같다: 프로세스 생성 → 첫 스레드의 `NtContinue` 은퇴 (요청서).
- 부모 유저 쪽과 csrss 쪽은 **이름·한 줄 설명까지만** 넣었다 (요청서 "배경").

### 무엇이 궁금했나

시작은 사용자의 질문이다 (plan 결정 기록 2026-10-26).

> "지도의 관심은 (1) 구조체가 언제 초기화·결정되나 (2) nt·ntdll 이 초기화에서 무슨 일을 해 주나 — 후자가 더 넓은데, Q78 구조체 추적 외의 일 (PE 로드, DLL 로드 등) 은 다 정리됐나?"

- (1) 은 짐 지도 `baggage.md` 가 맡는다 (Q76 · Q77 끝, Q78 남음).
- (2) 는 더 넓다. 그런데 흐름도는 "단계마다 대표 지점만" 이라서, 일의 **순서·대표 함수**는 있지만 일을 **빠짐없이 센 목록**은 없었다 (요청서 "배경").
- 그리고 오케스트레이터가 이렇게 짐작했다 `[추측]`: Q78 은 **칸에서 거꾸로** 줄기를 따라가니, 체크리스트에 없는 짐을 남기는 일은 Q78 로는 안 보인다.

그래서 요청서는 질문 넷을 냈다.

1. **일 목록**: 범위 안에서 nt·ntdll 이 하는 일을 빠짐없이 표로.
2. **분류**: 일마다 (가) / (나) / (다).
3. **대기 항목과 잇기**: 일마다 걸린 Q 번호. 어디에도 안 걸리면 "새 할 일".
4. **빠짐 점검**: sast/38 callee 표 637줄이 모두 어느 일에 들어가나.

- 일마다 줄기를 **끝까지 파는 건 이번 범위 밖**이다 (그건 Q78 · 뒤 항목). "구현할지" 로 거르지도 않는다.

### 바퀴 전에 알던 것

- `[정적]` (run43, sast/38) 체크리스트 = 구조체 **21종** (커널 14 · 유저 7) 직접 칸 **1,456** + ntdll 전역 `.data`·`.mrdata`·`.00cfg` **493**. **exe 의** 섹션 사슬·파일 객체만 읽었고 다른 이미지 것은 없다.

## 2. 찾은 것

### 2.1 새 말 — "일" 과 그 경계

- **새 말 — 일**: 한 덩어리 작업. 예: "exe 이미지 섹션 만들기", "PEB 만들기", "IAT 연결 (snap)" (결과서 "읽는 법").
  - 비유: 이삿날 **작업 지시서의 한 줄**. "냉장고 들이기" 처럼 한 번에 묶이는 작업.
- 번호는 **시간 순서**다. 다음 바퀴부터 "일 55" 처럼 부른다. 결과서 · run 문서 · 짐 지도 7.6 이 같은 번호를 쓴다.
- 세는 법 둘 (결과서):
  - DLL 하나를 올리는 일은 kernel32 · kernelbase · dll1 · dll2 가 **같은 부품** (일 70 ~ 79) 을 거친다. 그래서 모듈마다 따로 안 세고 **부품별로 한 번만** 셌다.
    - 비유: 이삿짐 트럭 네 대가 와도, "짐 내리기 → 엘리베이터 → 방에 놓기" 지시는 한 번만 쓴다.
  - `PspAllocateProcess` 의 14묶음 (run10) 을 일 8 ~ 23 으로 **다시 잘랐다**.
- **"일" 의 경계는 결과서가 정한 판단이다** (결과서 "한계"). 다른 자름도 가능하다. 그러니 "86" 은 "정답 개수" 가 아니라 "이렇게 자르면 86" 이다.

### 2.2 일 86개를 큰 줄기로 다시 묶으면

사용자가 궁금했던 건 "구조체 초기화 말고 **어떤 일들**이 있나 (PE 로드, DLL 로드 …)" 였다.

run 문서 1장 표는 **시간 순서** (A ~ H) 로 놓여 있어서, "PE 로드는 어디어디인가" 처럼 **종류로** 찾기는 어렵다. 그래서 이 글이 **종류별로 다시 묶었다.**

- 묶음은 이 글이 읽기 편하려고 나눈 것이다. 일 번호와 내용은 run 문서 그대로다. 86개가 각각 한 묶음에만 들어간다.

### 2.5 Q78 은 정확히 무엇을 하나 — 천천히

사용자가 이 바퀴에서 **두 번** 물었던 곳이다. 여기를 이해해야 2.6 ~ 2.8 의 제안과 결정이 읽힌다.

#### Q78 의 한 줄 정의 (plan Q78)

- **짐 지도 C — 쓴 자리·줄기 (정적)**: 체크리스트의 **칸마다** 쓴 자리 (직접 / 주소 넘김 / 붙이기 / syscall / 입력) 와 지도 경로를 찾는다.
- 줄기 위에서는 **끝까지** 판다 (더 부르는 게 없는 함수, 또는 syscall). 줄기 밖 callee 는 이름만, 공용 부품은 한 번만.

#### 핵심은 "출발점이 칸" 이라는 것

- Q78 은 **체크리스트의 한 줄 (칸) 에서 출발**한다.
- 그 칸에 값을 넣은 줄을 찾아 **거꾸로** 함수 사슬을 따라간다.
- 비유: 이삿짐 목록을 펴 놓고, **상자마다** "이 상자 누가 쌌어?" 를 찾는다. 목록의 줄이 곧 할 일 목록이다.

#### 예 — `PEB.ProcessHeap` (오케스트레이터가 대화에서 든 예)

짐 지도 3.1 의 한 줄이다.

| 칸 | 단계 | 놓는 법 | 쓴 주인 | 경로 | 근거 |
|---|---|---|---|---|---|
| `_PEB +0x30 ProcessHeap` | ② | 주소 넘김 | ntdll | `②… → LdrpInitializeProcessHeap` | `[정적]` run18 · 사진 `P1~P1a` |

- 이 줄에는 "프로세스 힙 핸들. **쓰는 줄은 callee 안 (안 봄)**" 이라고 적혀 있다.
- 그러니 Q78 이 이 칸에서 할 일은:
  1. 출발: 체크리스트 줄 `PEB +0x30 ProcessHeap`.
  2. 칸 주소를 넘겨받은 `LdrpInitializeProcessHeap` (일 52 의 대표 함수) 안으로 들어간다.
  3. 실제로 칸에 쓰는 줄을 찾는다.
  4. 그 줄까지 이어진 사슬을 끝까지 적는다 (더 부르는 게 없거나 syscall 까지).
- 비유: "창고 열쇠 (`ProcessHeap`)" 상자를 누가 쌌나 → 관리실의 "창고 짓기 담당" 을 찾아간다 → 그가 열쇠를 상자에 넣는 순간을 확인한다.

#### 그런데 같은 일 52 가 남기는 **다른 짐**은?

- 일 52 "프로세스 힙 만들기" 는 **가·나** 다.
  - 가 = `PEB.ProcessHeap` 같은 체크리스트 칸.
  - 나 = 힙 구조 자체 (`_HEAP`) 와 그 안의 블록들 → **C7** (2.6).
- `_HEAP` (ntdll PDB 에 정의 0x2c8 `[정적]`) 은 체크리스트 21종에 **없다**. 이삿짐 목록에 "창고 선반 구조" 라는 줄이 없는 것과 같다.
- 그래서 Q78 은 `LdrpInitializeProcessHeap` 안을 **지나가긴** 하지만, 적는 건 목록에 있는 칸 (`ProcessHeap`) 뿐이다. `_HEAP` 안을 칸별로 적을 **출발점이 없다.**

#### 일 77 (snap) 도 같은 모양이다

- 일 77 "IAT 연결 (snap)" 도 **가·나** 다.
  - 가 = `_LDR_DDAG_NODE` 칸 (run 문서 2.1 표: `_LDR_DDAG_NODE` 를 쓰는 일에 77 이 있다).
  - 나 = IAT 칸 자체 — 이미지 페이지 안 값 → **C5**.
- Q78 은 노드 칸 때문에 `LdrpSnapModule` 까지는 **간다.** 하지만 IAT 칸 (test.exe 91 · dll1 89 · …) 은 목록에 줄이 없으니 적지 않는다.
- 비유: 벽 콘센트 (IAT) 는 이삿짐 목록에 없다. 상자 주인을 찾다가 "전기 기사" 를 만나긴 하지만, 목록에 없는 콘센트 배선까지 Q78 이 적지는 않는다.

#### 그래서 오케스트레이터의 짐작이 나왔다

- Q78 은 칸에서 출발한다 → **목록 밖 짐에서는 출발할 수 없다** `[추측]` (요청서 "배경", 이번 바퀴로 확인됨).
- 목록 밖 짐: 벽에 박은 못 (IAT), 옆방 가구 (다른 DLL 객체), 옆집에 맡긴 물건 (csrss).
- 이걸 확인하려고 이번 Q81 이 먼저 돌았다. 결과: **48개 일이 목록 밖 짐을 남긴다.**

#### 새 말 — 정의 레코드 vs 정방향 선언 (C1 · C2 를 가른 것)

  - 정의 없음 (정방향 선언만): `_LDRP_LOAD_CONTEXT`, `_EPROCESS_QUOTA_BLOCK` `[정적]`
- 그래서 C1 (칸 표 만들 수 있음) 과 C2 (오프셋으로만 적어야 함) 가 갈렸다.

### 2.7 decompiler 의 제안 — "Q78 을 넓히지 말고 옆 항목을 두자"

사용자가 처음에 이해가 안 됐다고 한 말이다. 한 단어씩 풀면 이렇다.

#### "넓힌다" 와 "옆 항목" 이 각각 무슨 뜻인가

- **Q78 을 넓힌다** = Q78 의 **출발점 목록** (체크리스트 21종 + ntdll 전역) 에 C1 ~ C12 를 더 넣는다. Q78 한 항목이 목록 밖 짐까지 다 맡는다.
  - 비유: 상자 주인 찾는 사람에게 "벽의 못도, 옆방 가구도, 옆집에 맡긴 물건도 **같이** 봐 줘" 라고 일을 얹는 것.
- **옆 항목을 둔다** = Q78 은 지금 범위 그대로 두고, 목록 밖 짐은 **다른 번호의 항목**으로 따로 한다.
  - 비유: 상자 주인 찾기는 그 사람이 그대로 하고, 못은 **설계도로 계산하는 사람**, 옆방 가구는 **사진첩을 뒤지는 사람**에게 따로 맡기는 것.

#### 왜 넓히지 말자고 했나 — 근거 → 그래서

결과서 3.2 의 이유를 단계로 놓으면:

1. **근거**: (나) 는 대부분 Q78 의 방식 (칸 → 쓴 자리) 으로는 안 보인다. 이유는 셋이다.
   - **칸 표가 없다** — C1 (PDB 정의는 있지만 표를 아직 안 만듦), C9 (KERNELBASE·KERNEL32 전역 — 공개 이름 목록은 만들 수 있지만 크기는 짐작 `[추측]`).
   - **다른 프로세스·다른 모듈이다** — C9 (다른 DLL), C12 (부모·csrss). 그리고 Q78 의 "구간 안 함수만" 은 **nt·ntdll 로 한정**이라 KERNELBASE·KERNEL32 시작 함수에는 **닿지 않는다** (결과서 제안 3).
   - **칸이 아니라 구역이다** — C7 (힙 안 블록), C8 (스택·뷰·맡긴 문맥).
2. **그래서**: 같은 항목에 넣으면, Q78 은 "칸에서 거꾸로 쓴 줄 찾기" 와 **성격이 다른 일**을 섞어 하게 된다. 결과서는 체크리스트 확장 (칸 표 만들기) 에 대해서도 "Q78 안에 넣을 수도 있지만 Q78 은 '쓴 자리 찾기' 라 성격이 달라서 따로 두는 쪽을 권한다" 고 썼다.
3. **게다가**: 남는 곳마다 **더 싼 길**이 따로 있다 (아래 A ~ D).
4. **그래서 제안**: Q78 은 "체크리스트 21종 + ntdll 전역" 에 그대로 두고, 제안 1 ~ 4 를 **옆 항목**으로. **정하는 건 사용자.**

#### 남는 곳마다 맞는 길 — A / B / C / D (결과서 3장 "읽는 법")

| 기호 | 뜻 | 비유 | 해당 (결과서 제안) |

- 비유: 현관에서 들어온 사람 명단 (1단계) 만 보면, 2층 방에서 일한 사람·옆집에서 일한 사람은 명단에 없다.

#### "이름만 아는" 일이 많다

- 태그 `[추측: 이름]` 인 일: 7 ~ 14 (`PspAllocateProcess` 안 묶음), 53 ~ 54.
- 이 일들은 (가) 로 나눴어도 **어느 칸인지는 아직 모른다** — Q78 몫 (결과서 5.5).

### 2.10 본문을 읽어 닫은 빈 곳 6건

이번 바퀴에서 Ghidra 로 **본문을 직접 읽은** 함수가 있다 (depth 0, 1차 6개 · 2차 8개). 분류하려고 읽었는데, 덤으로 짐 지도의 빈 곳 6건이 닫혔다 (run 문서 6장, 결과서 6장).

#### (1) `ProcessParameters` 를 힙으로 옮기는 주인 = `RtlpInitParameterBlock`

run44 가 `[관찰]` 로 보고 `[공백]` 으로 남긴 것이다 ([run44 해설](run44-baggage-snap-해설.md) 2.14 (1)).

호출 관계 (run 문서 그대로, 돌아올 자리 기준):

```
LdrpInitializeProcess
 ├─ +0xc32  RtlpInitEnvironmentBlock  옛 블록에서: 환경 힙 복사 → EnvironmentVersion +1 (+0x86)
 │                                    · Environment (+0x8d) · EnvironmentSize (+0x94) → +0xa0 RtlpSetupEnvironmentHashTable
 └─ +0xc3f  RtlpInitParameterBlock    +0x3b RtlAllocateHeap(PEB.ProcessHeap, Length) → +0x57 통째 복사
                                      → 포인터 9개 새 자리 기준 (+0x6b ~ +0x106) → PEB+0x20 = 새 블록 (+0x10d)
                                      → +0x130 NtFreeVirtualMemory(옛 블록, MEM_RELEASE)
```

단계로 읽으면 `[정적]`:

1. `RtlAllocateHeap(PEB.ProcessHeap, 0, 블록.Length)` — 창고 (힙) 에 **같은 크기** 자리를 빌린다 (ret `+0x3b`).
2. 옛 블록을 **통째 복사**한다 (ret `+0x57`).
3. 안쪽 포인터 9개를 **새 블록 기준으로** 고친다. 0 이 아닐 때만 (`+0x6b ~ +0x106`).
   - 칸: `CurrentDirectory` · `DllPath` · `ImagePathName` · `CommandLine` · `WindowTitle` · `DesktopInfo` · `ShellInfo` · `RuntimeData` · `RedirectionDllName` 의 `Buffer`.
4. `PEB+0x20` 에 새 블록 주소를 쓴다 (`+0x10d`).
5. 옛 블록을 `NtFreeVirtualMemory(-1, 옛 블록, 0, MEM_RELEASE)` 로 푼다 (ret `+0x130`).

사진과 맞춰 보면 `[관찰]` run44:

- 옛 private 영역 VAD 가 P1 → P1a 에 **사라진다** ← 5번과 맞음.
- 바뀐 포인터 칸: `CurrentDirectory` · `ImagePathName` · `CommandLine` · `WindowTitle` · `DesktopInfo` · `ShellInfo` ← 3번과 맞음.
- 0 이라 그대로인 칸: `DllPath` · `RuntimeData` · `RedirectionDllName` ← 3번의 "0 이 아닐 때만" 과 맞음.

`Environment` 는 왜 9개 안에 없나:

- 바로 앞 `+0xc32 RtlpInitEnvironmentBlock` 이 **옛 블록**에서 환경을 **별도 힙 블록**으로 복사하고, `Environment` (`+0x8d`) · `EnvironmentSize` (`+0x94`) 를 쓰고, `EnvironmentVersion` 을 +1 한다 (`+0x86`) `[정적]`.
- 그 뒤 통째 복사로 그 값이 새 블록에 넘어간다. 곧 `Environment` 는 **이미 힙을 가리키고 있어서** 고칠 필요가 없다.
- run44 의 `EnvironmentVersion` 0 → 3 중 **+1 만 여기**다. 나머지 +2 는 모른다 (`+0xa0 RtlpSetupEnvironmentHashTable` 쪽일 수 있음 `[추측]`).

비유:

- 관리실 직원이 부모가 써 준 **개업 서류**를 창고의 새 서류철로 옮긴다.
- 먼저 "부록 (환경)" 을 따로 떼어 창고 다른 칸에 옮겨 두고, 부록 위치를 서류 표지에 적는다.
- 그다음 서류 전체를 새 서류철에 베끼고, 안의 "몇 쪽 참조" 9곳을 새 서류철 쪽수로 고친다.
- 안내판 (PEB) 의 "서류는 여기" 칸을 새 서류철로 바꾸고, 옛 서류 뭉치는 치운다.
- run44 해설에서 "누가 옮겨 적었는지는 사진에 안 찍혔다" 고 했던 **그 사람의 이름**이 `RtlpInitParameterBlock` 이다.

그리고 **`PEB.ProcessParameters` 를 쓰는 주인은 둘**이 됐다:

- ① nt `PspCopyAndFixupParameters` (`+0x52b` · `+0x347`, run32) — 커널이 새 프로세스에 블록을 처음 놓을 때 (일 20).
- ② ntdll `RtlpInitParameterBlock` (`LdrpInitializeProcess +0xc3f`, 함수 안 `+0x10d`) — 관리실이 창고로 옮길 때 (일 55).
- 짐 지도 3.1 에 ② 줄이 더해졌다.

#### (2) `LdrInitializeMrdata` (109바이트) — 일부 닫힘

- `_LdrpInitialize +0x14a` 가 부른다 (일 46).
- 하는 일 `[정적]`: `memset` 뒤 `.data` `LdrpMrdataLock` = 0 (`+0x23`) → 시스템 정보 조회 (클래스 0, ret `+0x3e`) → 성공이면 `.mrdata` `LdrpAllocationGranularity` (`+0x46`) · `LdrpMaximumUserModeAddress` (`+0x52`).
- 사진과 맞음 `[관찰]` (dast/04 P1a): `LdrpMaximumUserModeAddress` = `0x7ffffffeffff`, `LdrpAllocationGranularity` = `0x10000`, `LdrpMrdataLock` 은 끝까지 0*.
- **안 쓰는 것**: `LdrpMrdataBase` · `LdrpMrdataSize` · `LdrpMrdataHeap` · `LdrpMrdataHeapUnprotected` · `LdrpMrdataUnprotected` → 이름만 보면 이 함수 몫 같았지만 아니었다. 그대로 모름 (baggage 7.5).
- 비유: "관리실 칠판 담당" 이라는 이름표를 단 직원이 실제로는 칠판 **세 칸**만 썼다.

#### (3) CFG 도우미 두 칸 — 정적과 사진이 다르다

이번 바퀴에서 가장 조심해서 읽어야 할 곳이다. 단계로 놓는다.

1. **정적 근거** `[정적]`: `LdrpInitializeCfgScpHelpers` (일 61, `LdrpInitializeProcess +0x180b`) 는 CFG 강제가 켜져 있고 ntdll 헤더 · LoadConfig 플래그가 맞으면:
   - `LdrProtectMrdata(0)` 으로 `.mrdata` 를 연다.
   - `LdrpGuardCheckIcallNoESFptr` = `LdrpValidateUserCallTarget` (`+0x6b`), `LdrpGuardDispatchIcallNoESFptr` = `LdrpDispatchUserCallTarget` (`+0x79`).
   - `LdrProtectMrdata(1)` 로 닫는다.
2. **사진 근거** `[관찰]` (run44 덤프 로그 17b 를 이번에 다시 읽음):
   - `LdrpGuardCheckIcallNoESFptr` = ntdll + `0xfac60` — 8장 모두 같다. 아무것도 안 하는 3바이트 함수 (같은 주소 이름 26개).
   - `LdrpGuardDispatchIcallNoESFptr` = ntdll + `0x166480` (`_guard_dispatch_icall`, P1a ~ P2).
   - 반면 `LdrpValidateUserCallTarget` 은 rva `0x1244e0`, `LdrpDispatchUserCallTarget` 은 `0x124580` (`_index.tsv`).
3. **그래서**: 사진 값은 코드가 넣을 함수가 **아니다.** 둘 중 하나가 틀렸다기보다, **test.exe 에선 그 갈래의 조건이 안 맞아서 안 탔다** `[추측]`.
4. **그렇다면**: 두 값의 주인은 파일 처음 값이거나 다른 쓰는 곳이다.
   - `LdrpGuardCheckIcallNoESFptr` 는 `.mrdata` 끝 페이지라 K1 부터 읽혔다 (파일 값 `[추측]`).
   - `LdrpGuardDispatchIcallNoESFptr` 는 앞 페이지라 `≤P1a` → Q80 의 "파일 처음 값과 P1a 값 비교" 로 가려진다.
5. **아직 확인 아님**: 조건 (`LdrControlFlowGuardEnforced` 결과, 헤더 · LoadConfig 플래그) 의 실제 값 → Q80.

- 비유: 작업 지시서에 "보안 강화 날이면 경비 담당자 연락처를 A 로 바꿔 적어라" 가 있다. 그런데 사진 속 칠판엔 다른 연락처가 그대로 적혀 있다. → 그날은 "보안 강화 날" 이 아니었던 것 같다.
- 그래도 짐 지도 기준으로는 "쓴 자리" 를 찾았으니, `.mrdata` 두 칸이 **아는 칸**으로 옮겨졌다 (2.11).

#### (4) NLS — 코드 페이지 두 칸

- **새 말 — 코드 페이지**: 글자를 숫자로 바꾸는 **번호표** 의 이름 `[추측]` (일반적으로 알려진 설명). `0xfde9` (65001) 은 run 문서 값 그대로, `0x3b5` (949) 는 사진 값.
  - 비유: 가게에서 쓰는 **문자 번호표 몇 번 판**을 쓰나.
- `LdrpInitializeNlsInfo(PEB)` (일 47, `+0x1cd`) 가 `PEB.ActiveCodePage` (`+0x34c`) · `OemCodePage` (`+0x34e`) 를 쓴다 `[정적]`.
- 값을 고르는 순서 `[정적]`:
  1. 매개변수 `Flags` 비트 27 이 켜져 있으면 곧장 `0xfde9` (`+0x77`, 두 칸 한 번에).
  2. 아니면 매니페스트 (`LdrpFusionManifestCodePages`).
  3. 없으면 레지스트리 (`RtlpQueryNlsSystemCodePages`: `NtOpenKey` · `NtQueryValueKey`).
  4. 그것도 실패면 `0xfde9`.

  - 그래서 → ntdll 은 **같은 값을 다시 쓴 것**이다. K1 전에 처음 쓴 쪽은 모른다 `[공백]` (`MmCreatePeb` 후보 `[추측]`).
  - run44 의 VAD `C_949.NLS` · `l_intl.nls` 가 이 섹션들일 것 `[추측]` (커널 쪽 본문은 안 읽음 → Q89).

#### (5) import 리다이렉션 — test.exe 에선 안 탄다

- **새 말 — import 리다이렉션**: 이름으로 보면 import 를 다른 곳으로 돌리는 장치 `[추측: 이름]`. 이번에 본 건 **언제 타는지** 뿐이다.

- 그래서 flow.md 2.4 · 2.5 의 "올리는지 모름" 이 닫혔다. 일 63 은 (다).
