## 1. 이번 바퀴의 질문

### 큰 그림에서 어디인가

run128 ~ run145 와 같은 자리, **초기화 밖** 이다. `main` 뒤 프로그램이 웹을 쓸 때의 옆길이다.

```
cmd.exe 의 부탁 (CreateProcess)
 │  커널: 프로세스 · 주소 공간 · PEB · 첫 스레드
 │  ntdll: LdrInitializeThunk → LdrpInitializeProcess → DLL 들이기 · 전원 켜기
 └─ NtContinue (은퇴) → exe 진입점 → (CRT 점선 상자) → main
                                                        │
      test.exe 는 여기서 RPC 를 안 쓴다 [소스]          │ 웹을 쓰는 프로그램이라면 (요청 쪽 에뮬레이터 로그):
                                                        └─ WinHttpSendRequest                                       (run128)
                                                             └─ 신청 담당 winnsi → 전화 부서 rpcrt4 → 114 에 전화       (run129 · run141)
                                                                  ├─ 첫인사 · 질문 탑 · 답 검사 (묻는 쪽)               (run133 · run137)
                                                                  ├─ 질문 용지 3 · 7 · 8 중 무엇을 고르나, 칸 꼴은      ← 이번 (묻는 쪽)
      ── 다른 가게: svchost (RPCSS) 안 114 ──────────────────────┼──────────────────────────────
                                                                  └─ 114 가 장부에서 골라 탑을 채우는 법                (run145)
```

- 이번엔 **묻는 쪽 (rpcrt4)** 의 서식 설명서를 읽었다. 114 쪽 (`ept_map`) 은 한 군데만 곁다리로 봤다.

### 왜 이 질문이 지금 왔나

PE_emulator 쪽에서 막혔다 (요청 쪽 에뮬레이터 로그 — 진짜 Windows 관찰 아님).

- r19 에서 **프로시저 7** 요청이 fault `0x6d1` 로 끝난 샘플이 197, 프로시저 3 은 46.
  - 일반적으로 알려진 설명 `[추측]`: `0x6d1` 은 "프로시저 번호가 범위 밖" 이라는 RPC 오류다. 흉내 114 의 창구 표에 7 이 없으니 (`epm.cpp :280` 창구 표 `{{3, …}, {8, …}}`) 맞아떨어진다.
- 그래서 갈래 BG04 **시도 2** 가 7 을 열면서 **3 꼴 (`FC_FP`)** 로 풀었다.
  - 근거로 삼은 건 run145 `:264` "3 · 7 은 요청 NDR 꼴만 다름 (`FC_FP` 포인터 ID)" 였다.
- 그랬더니 진짜 클라이언트 요청이 **풀기 실패 (`0x6f7`)** → 되돌림.
- 그러니 물음은 하나다: **용지 7 은 진짜 어떤 꼴인가? 그리고 run145 의 그 줄은 맞았나?**

### 무엇이 궁금했나

요청서의 두 가지:

1. **프로시저 3 (`0xeff42`) · 7 (`0xefff0`) 의 파라미터 표** — run137 3-1 의 프로시저 8 표와 같은 꼴로. 그리고 탑 octets 66 일 때 요청 길이 (3 / 7 SID NULL / 7 SID 있음). 원문 "확인 거리" 표 (PE_emulator 의 02 가 `pefile` 로 읽은 덤프 — 근거 아님, 대조용) 와 칸마다 맞나.
2. **run145 `:264` 정정** — 어떻게 고쳐 읽나. (되면) NDR64 쪽도 같은 관계인가.

### 바퀴 전에 알던 것

- `[정적]` (run137 3-0) rpcrt4 EPM 의 NDR 2.0 프로시저 문자열 시작 `0xefeb2` 와 오프셋 표 — 3 = `0xeff42`, 8 = `0xf003e`.
- `[정적]` (run137 3-1) 프로시저 8 파라미터 표 — 객체 · 탑은 **참조** (포인터 ID 없음), SID 는 `FC_UP`. 그리고 `:238` "**3 은 객체 · 탑이 `FC_FP`**".

- `[정적]` (run145) 114 쪽에서 3 · 7 · 8 은 **한 몸** (같은 직원). 3 은 `ept_map +0x43` 에서 SID 칸에 0 을 넣어 7 (`ept_map_auth`) 로 넘긴다.

- 몰랐던 것: **7 의 칸 꼴** 자체, 3 의 칸 전부, 손님이 셋 중 무엇을 언제 고르나.

## 2. 찾은 것

### 2.1 한눈에 — 용지 셋 나란히 `[정적]`

run 문서 4절 표 그대로.

| 비교 | 3 (`0xeff42`) | 7 (`0xefff0`) | 8 (`0xf003e`) |
|---|---|---|---|
| 파라미터 수 | **7** | 8 | 8 |
| 비동기 핸들 | 없음 | 없음 | **있음** (스택 0) |
| 객체 UUID | **`FC_FP` (ID 4 B)** `0x000a` | 참조 `0x010a` | 참조 `0x010a` |
| 질문 탑 | **`FC_FP` (ID 4 B)** `0x000b` | 참조 `0x010b` | 참조 `0x010b` |
| SID | **없음** | `FC_UP` (ID 4 B) | `FC_UP` (ID 4 B) |
| 이어받기 핸들 20 B · `max_towers` 0 ~ 500 · 출력 셋 | 같음 | 같음 | 같음 |
| 닿는 타입에 `FC_FP` (`0x14`) | **있음** | 없음 | 없음 |

- 읽는 법: **가운데 칸 (7) 과 오른쪽 칸 (8) 은 "비동기 핸들" 줄만 다르다.** 왼쪽 칸 (3) 은 객체 · 탑 · SID 세 줄이 다르다.
- 그래서 run145 의 "3 · 7 은 `FC_FP`" 에서 **3 은 맞고 7 은 틀렸다.**

### 2.2 한 줄씩 읽는 법

파라미터 칸 한 개는 **6 B** 다: attr 2 · 스택 자리 2 · 타입 오프셋 (또는 기본형) 2 `[정적]`.

- **새 말 — attr** = 칸마다 붙은 **성질 비트** (입력인가 · 출력인가 · 크기를 세나 …). 비트 이름은 공개 `PARAM_ATTRIBUTES` 순서로 맞춘 것 `[추측: 이름]`.
  - 비유: 용지 칸 옆에 찍힌 작은 도장들. "손님이 채움" · "직원이 채움" · "**바로 씀 (스티커 없음)**" 같은 것.
- **새 말 — 스택 자리** = 그 인자가 부르는 쪽 스택에서 **몇 번째 칸** 에 놓이나 (`0x08` · `0x10` …). NDR 엔진은 이 자리에서 인자를 꺼내 차례대로 줄 세운다.
  - 비유: 직원이 서류철에서 몇 번째 장을 꺼내 용지에 옮겨 적나.

#### 줄 ①: 프로시저 7 파라미터 0 — `0xf000e` `0x010a` `0x08` `+0xc` (run 문서 3-2)

- **누가**: rpcrt4 안 NDR 2.0 프로시저 7 설명서의 **첫 칸** (rva `0xf000e`).
- **어디서**: 스택 자리 `0x08` 의 인자 (= 객체 UUID 포인터 — 이 이름은 `[추측: 이름 대응]`).
- **누구를**: 타입 `+0xc` — `15 03 10 00 …` = **16 B 구조체 (GUID)** 를 **바로** 가리킨다.
- **무엇을 위해**: attr `0x010a` 에 **`0x0100` (단순 참조)** 비트가 켜져 있다. 그래서 "포인터 → 대상" 두 단계를 거치지 않고, **대상 16 B 를 선 위에 바로** 싣는다. 포인터 ID 는 없다.
- 비유: 용지 7 의 1번 칸엔 "바로 씀" 도장이 찍혀 있다. 그래서 스티커 없이 16 B 이름표를 곧장 붙인다.

#### 줄 ②: 프로시저 3 파라미터 0 — `0xeff60` `0x000a` `0x08` `+0x2` (run 문서 3-1)

- **누가**: 프로시저 3 설명서의 첫 칸 (rva `0xeff60`).
- **어디서**: 같은 스택 자리 `0x08` (객체 UUID 포인터).
- **누구를**: 타입 `+0x2` — `14 00 08 00` = **`FC_FP` (전체 포인터)** → 다시 `+0xc` (줄 ①과 **같은** 16 B 구조체).
- **무엇을 위해**: attr 이 `0x000a` 라 **`0x0100` 비트가 꺼져 있다.** 그래서 한 번 포인터 타입 (`FC_FP`) 을 거친다 → 선 위에 **포인터 ID 4 B 가 먼저** 오고, 그 뒤에 16 B.
- 비유: 용지 3 의 1번 칸엔 "바로 씀" 도장이 없다. 대신 "**스티커 붙인 상자**" 라고 적혀 있다. 그래서 스티커 4 B 부터 붙이고, 상자 안에 같은 16 B 이름표를 넣는다.

- 둘을 나란히 보면: **가리키는 최종 타입 (`+0xc`) 은 같다.** 다른 건 그 사이에 포인터 한 겹 (`FC_FP`) 이 있느냐 하나다.

### 2.3 어디서 읽었나 — 설명서의 목차 `[정적]`

### 2.4 ★ 포인터 종류 셋 — 스티커 이야기를 천천히 `[정적]` (일반 설명은 `[추측]`)

run 문서 3절 · 4절. run137 해설 2.11 의 말을 이번 비교에 맞춰 다시 짚는다.

#### 셋이 무엇인가

- NDR 은 포인터 인자를 **종류에 따라 다르게** 줄 세운다. 형식 문자열에 종류가 적혀 있다 `[정적]`.
- **참조 포인터 (단순 참조)** — 이번 7 · 8 의 객체 · 탑. attr `0x0100` 이 켜져 대상 타입을 바로 가리킨다.
  - 선 위: **ID 없이 내용만 바로** `[정적]`.
  - 일반적으로 알려진 설명 `[추측]`: "절대 NULL 이 아님" 을 약속한 포인터라, 있다 / 없다를 알릴 필요가 없다.
  - 비유: "**늘 들어 있음**" 이 약속된 상자. 스티커가 없다.
- **고유 포인터 `FC_UP`** (`12 00 …`) — 7 · 8 의 SID, 응답 배열 원소.
  - 선 위: **포인터 ID 4 B 먼저** (NULL 이면 0), 0 이 아니면 그 뒤에 본문 `[정적]` + `[규칙]`.
  - 비유: "**있음 / 없음**" 스티커만 붙는 상자.
- **전체 포인터 `FC_FP`** (`14 00 …`) — **3 의** 객체 · 탑뿐.
  - 선 위: 이것도 **포인터 ID 4 B 먼저**, 0 이 아니면 본문.
  - 고유 포인터와 다른 점 (run 문서 5절 `[규칙]`): **같은 ID 가 두 번 나오면 둘째는 본문이 안 따라온다.** 그래서 객체 · 탑 ID 는 서로 다를 것이다 `[규칙]`.
  - 비유: 스티커에 **상자 번호** 까지 적는다. 같은 번호가 또 나오면 "아까 그 상자예요" 하고 내용물을 다시 안 넣는다.

#### 이번 바퀴에서 이게 왜 갈림길인가 — 단계로

1. 3 · 7 · 8 은 모두 "객체 UUID · 질문 탑" 을 **같은 최종 타입** (`+0xc` · `+0x58`) 으로 싣는다 `[정적]` (2.2).
2. 다른 건 **그 앞에 포인터 한 겹이 있느냐** 다.
   - 3: attr `0x000a` · `0x000b` → 타입 `+0x2` · `+0xa0` = **`FC_FP`** → 그다음 `+0xc` · `+0x58`.
   - 7 · 8: attr `0x010a` · `0x010b` (**`0x0100` 켜짐**) → `+0xc` · `+0x58` **바로**.
3. 그래서 선 위에서는 3 만 객체 앞 4 B · 탑 앞 4 B 가 **더** 있다.
4. 받는 쪽이 이걸 헷갈리면 처음 4 B 부터 어긋나고, **그 뒤 칸이 전부 밀린다** (2.11).

### 2.8 ★ 손님은 언제 어느 용지를 쓰나 — `LookupNextChunk` `[정적]`

run 문서 7절 · "호출 관계". rpcrt4 `LookupNextChunk` (rva `0x5a070`) 가 셋 중 하나를 고른다.

```
rpcrt4!LookupNextChunk
 ├─ +0x31 → +0x219 ~ +0x238   SID 고르기 → [RSP+0xd8]  (또는 +0x26f NormalizeAccountSid)
 ├─ [RDI] ≠ 0 (비동기)
 │   ├─ +0x5b   RpcAsyncInitializeHandle(RDI+0x308, 0x70)
 │   └─ +0x122  Ndr64AsyncClientCall(0xe11e8, 8, …)      프로시저 8
 └─ [RDI] = 0 (동기)  +0x127 ~ +0x132  SID NULL ?
     ├─ 예    +0x170  NdrClientCall3(0xe11e8, 3, …)       프로시저 3
     └─ 아니오 +0x1b3  NdrClientCall3(0xe11e8, 7, …)       프로시저 7
```

- (나무 오프셋은 ret 자리. `+0x31` · `+0x127 ~ +0x132` · `+0x219 ~ +0x238` 은 함수 안 줄. 콜스택으로 본 적 없음.)

#### 한 걸음씩

1. 들어오자마자 `[RSP+0xd8]` 칸을 **0 으로** 둔다 (`+0x1c`). 이 칸이 SID 지역 변수다.
2. `[RDI+0x10] ≠ 0` 이면 (`+0x2a` · `+0x31`) SID 고르기로 간다 (`+0x219`).
   - 비트 `0x10` 켜짐 · `[RDI+0x300] == 0` 이면 `[[RDI+0x10]+0x10]` 을 SID 로 (`+0x22f` · `+0x238`).
   - `[RDI+0x18] ≠ 0` 이면 대신 `+0x26f NormalizeAccountSid` 가 그 칸에 써 준다.
   - 이 칸들이 **무슨 뜻인지는 안 풀었다** `[공백]` (4절).
3. `[RDI] ≠ 0` 이면 **비동기** → 비동기 핸들을 채우고 (`+0x56`) **프로시저 8** (`+0x112 LEA EDX,[R8+8]` · `+0x11d` call).
4. 동기면 (`+0xce` → `+0x127`) `MOV R9,[RSP+0xd8]` · `TEST` · `JNZ` 로 **SID 가 NULL 인가** 본다.
   - NULL → **프로시저 3** (`+0x160 LEA EDX,[R8+3]` · `+0x16b` call).
   - 있음 → **프로시저 7** (`+0x1a3 LEA EDX,[R8+7]` · `+0x1ae` call). SID 는 `+0x18e MOV [RSP+0x30],R9` = 스택 자리 `0x18` — 2.6 표 #2 자리와 같다.

#### 그래서 무엇이 정해지나

- `[정적]` 이 코드는 **7 을 SID ≠ NULL 일 때만** 부른다. "7 + SID NULL" 은 이 코드에서 안 나온다.
  - 그래서 r19 의 7 요청 (197 샘플) 엔 SID 본문이 따라올 것이다 `[추측: 샘플이 rpcrt4 의 이 길로 7 을 낸다고 볼 때 — 스텁을 직접 짓는 경우는 모름]`.
- `[정적]` 3 의 객체 포인터는 `+0xb9 LEA R10,[RDI+0x1c]` 라 **늘 비-NULL**. `LEA` 는 주소를 계산만 하니 0 이 나올 수 없다.
- `[정적]` `max_towers` 는 셋 다 **4** 상수 (8 `+0xe6` · 3 `+0x143` · 7 `+0x181`).
- `[정적]` 인자 자리가 2.6 · 2.7 의 스택 자리와 그대로 맞는다 (3: 객체 `0x08` · 탑 `0x10` · 핸들 `0x18` · `max_towers` `0x20`, 7: SID `0x18` · 핸들 `0x20` · `max_towers` `0x28`).
- 비유: 손님 전화 부서는 "**비동기로 걸 거면 용지 8**, 동기인데 신분 번호가 없으면 **오래된 용지 3**, 신분 번호가 있으면 **용지 7**" 로 고른다.
- 짚을 것: 비동기 길 (8) 은 SID 가 NULL 인지 **안 가른다** — SID 칸 `[RSP+0xd8]` 을 그대로 `[RSP+0x38]` 에 실어 8 을 부른다 (run 문서 7절 `+0x112` · `+0x11d` 줄). run133 · run145 의 "우리 손님은 SID NULL" 은 이 8 길 이야기다.

### 2.9 요청 길이 — 몇 바이트를 받게 되나 `[정적]` + `[규칙]`

run 문서 5절. 칸 · 차례 · 크기는 `[정적]` (2.6 · 2.7 표), 4 정렬 패딩 · "최상위 포인터 인자는 ID 바로 뒤에 본문" · "conformance 는 본문 앞" 은 `[규칙]`.

| 경우 (탑 octets 66) | 길이 |
|---|---|
| **3, 객체 · 탑 둘 다 있음** | **124 B** (`0x7c`) |
| 3, 객체 NULL · 탑 있음 | 108 B |
| 3, 객체 있음 · 탑 NULL | 48 B |
| **7 (= 8), SID NULL** | **120 B** (`0x78`) — run137 해설 2.12 의 8 표와 같다 |
| **7 (= 8), SID 있음 (하위 권한 n)** | **132 + 4n B** |

#### 한 줄 읽기 — 3 의 124 B

run 문서 5절 첫 줄을 앞에서부터 따라간다.

- `+0x00` 객체 **ID** 4 → `+0x04` UUID 16 (여기까지 20 B — 7 이라면 UUID 16 만)
- `+0x14` 탑 **ID** 4 → `+0x18` conformance 4 (66) → `+0x1c` `tower_length` 4 (66) → `+0x20` octets 66
- `+0x62` 패딩 2 (다음 칸을 4 의 배수 자리로)
- `+0x64` 핸들 20 → `+0x78` `max_towers` 4 → 끝 `0x7c` = **124**
- 7 의 120 B 와 견주면: 3 은 **ID 두 개 (+8 B)** 가 더 있고 **SID 칸 (NULL 이어도 4 B) 이 없다.** 그래서 4 B 차이가 난다.
  - run 문서의 길이 식 (아래) 으로 봐도 같다: 3 = `56 + 4정렬(L)`, 7 SID NULL = `48 + 4정렬(L) + 4` — 둘 사이가 4 B.

#### SID 칸 길이 식

- NULL = **4 B** (ID 0 하나).
- 있음 = 4 (ID) + 4 (conformance = n) + 8 (머리) + 4n = **16 + 4n B**.
- 그래서 7 SID 있음은 SID NULL 120 B 에서 SID 칸 4 B 를 16 + 4n B 로 바꾼 것 = **132 + 4n** (run 문서 5절 칸 차례 표: `+0x5c` SID ID · `+0x60` conf · `+0x64` 머리 8 · `+0x6c` 하위 권한 4 × n · `+0x6c + 4n` 핸들 20 · `+0x80 + 4n` `max_towers`).

| SID 예 | n | 7 · 8 요청 길이 |
|---|---|---|
| 없음 | — | 120 |
| `S-1-5-18` · `S-1-5-19` 류 | 1 | **136** |
| `S-1-5-32-544` 류 | 2 | 140 |
| `S-1-5-21-a-b-c-rid` 류 | 5 | 152 |

- 탑 길이가 L 일 때 (run 문서): 3 = `56 + 4정렬(L)` · 7 = `48 + 4정렬(L) + SID 칸`. 예 L = 73 → 3 = 132 · 7 SID NULL = 128 · 7 n=1 = 144.
- `[공백]` 3 의 포인터 ID **값** (선 위에 정확히 얼마가 적히나) 은 안 정했다. 서버는 0 / 0 아님만 가르면 된다.

### 2.10 응답은 셋 다 같다 — 그리고 NDR64 도 같은 관계 `[정적]`

#### 응답

- 핸들 20 → `num_towers` 4 → 배열 (max_count · offset · actual_count · 원소 ID × n · 탑마다 `[len][len][octets]` 4 정렬) → 상태 4 `[정적]` (run 문서 5절).

- 다른 건 배열 크기를 읽는 스택 자리뿐: 3 = `0x20` · 7 = `0x28` · 8 = `0x30` 의 `max_towers`.
- 비유: 질문 용지는 둘 (3 꼴 / 7 = 8 꼴) 이지만, **답장 양식은 하나** 다. run145 의 "같은 직원" 과 맞는다.

#### NDR64

- NDR64 프로시저 포인터 표 `0xe7e40` (9칸): 3 → `0xe7d00` · 7 → `0xe7c60` · 8 → `0xe7870` `[정적]`.

### 2.15 정리 — 비유로 한 번 더
