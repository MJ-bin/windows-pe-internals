### 비유: 그대로 이어 쓴다

- 커널 = **관리사무소**, ntdll = 가게 안 **관리실**, 스레드 = **직원**.
- 시스템 콜 = 관리사무소 **신청 창구**. ntdll 스텁 = 관리실 **전화기**, 시스템 콜 번호 = **단축 번호** (= run29 의 **번호표**, 같은 것).
- `KiServiceTable` = 관리사무소의 **번호부** (= run29 의 **번호표 안내판**, 같은 것).
- 트랩 프레임 = 직원 책상의 **출발 메모** (run15).
- run 문서가 이번에 쓴 그림 (그대로 가져온다):
  - 번호부 **인쇄본** (PE 파일) 엔 담당자 **자리 번지**만 적혀 있다.
  - 관리사무소가 **문 여는 날** (부팅) 따로 있던 **"서류 몇 장 가져와야 하나" 표** (`KiArgumentTable`) 를 보고, 번호부 칸마다 **"자리까지 거리 + 서류 장수"** 를 한 칸에 겹쳐 다시 적는다.
  - 전화를 받으면 그 칸에서 거리로 담당자를 찾고, 장수만큼 서류를 손님 **가방** (유저 스택) 에서 옮겨 담는다.
  - 끝나면 **답** (`RAX`) 과 **돌아갈 문** (`RCX`) 만 쥐여 주고, 쓰던 **메모지 몇 장** (`RDX`·`R10`·`XMM0~5`) 은 지워서 돌려보낸다.

### 한 줄로 먼저: 무엇을 얻었나

| 질문 | 답 (run 문서 그대로) |
|---|---|
| 1. 서비스 표 칸 하나에서 함수·스택 인자 수를 어떻게 뽑나 | **파일 칸 = 그냥 함수 rva.** 부팅 때 `KeCompactServiceTable` 이 `((rva − 표) << 4) \| 스택 인자 수` 로 고쳐 쓴다. 커널은 `SAR 4` → 함수, `AND 0xf` → 스택 인자 수 `[정적]` |
| (1 덤) 스택 인자 수란 | 레지스터 4개 **다음**, 유저 `RSP+0x28` 부터 옮길 **8바이트 칸 수** `[정적]` |
| 2. 번호표 | `_workspace/sast/51_syscall-args_table.tsv` 489줄. 스택 인자 0 인 302칸은 실제 인자 0 ~ 4개 (표로 못 정함) `[정적]` |
| 3. ntdll 스텁과 1:1 인가 | export 스텁 **488개 ↔ 488칸**. 빠진 1칸 = `0x5a` `NtQuerySystemTime`. 같은 번호 내부 스텁 `Np*` 6개 `[정적]` |
| 4. 돌아갈 때 레지스터 (보통 출구 `SYSRET`) | `RAX` 답, `RCX` 돌아갈 자리, `R11` RFLAGS, `R8` 유저 RSP, **`RDX`·`R10`·`XMM0~5` = 0**, `R9` = 0 / 유저 RBP (`KiKvaShadow` 따라) `[정적]` |
| (덤) 로더 끝 `NtContinue` 는 | 이 출구를 **안 탄다** (`IRETQ`, run29). 레지스터 = 맡긴 문맥 값 `[정적]` |
| (덤) 콜스택 `CopyEnd+0x28` | 파일로는 `+0x25`. 3바이트 차이는 못 풀었다 → Q107 (2) |

이 글에서 붙잡아 둘 세 줄:

> **(1) PE 파일의 서비스 표 칸은 "그냥 주소" 다. 거기서 끝자리를 읽으면 늘 0 이다. 인자 수는 옆 표 `KiArgumentTable` 에 있다.**
>
> **(2) 부팅 뒤 메모리 칸은 "거리 + 장수" 를 한 칸에 겹친 꼴이다. PE_emulator 가 알던 모양은 이쪽 기준으로 맞다.**
>
> **(3) 보통 시스템 콜에서 돌아오면 `RDX`·`R10`·`XMM0~5` 는 0 이다. 로더 끝 `NtContinue` 만 예외다.**

## 1. 이번 바퀴의 질문

### 큰 그림에서 어디인가

이번 구간은 흐름도의 **한 지점**이 아니다. 시스템 콜이 지나는 **공용 길**이다. 그림 1·2 에서 세 번 지난다.

```
cmd.exe 의 부탁 (그림 1, 부모 스레드)
 KERNELBASE → ntdll 스텁 NtCreateUserProcess  번호 0xd1
   ══▶ SYSCALL → [시스템 콜 입구 … 칸 풀기 … 인자 복사]  ← 이번
        └─ CALL → nt!NtCreateUserProcess  …  → [출구 SYSRET]  ← 이번
 KERNELBASE → ntdll 스텁 NtResumeThread  번호 0x52
   ══▶ SYSCALL → [같은 길]  ← 이번
test.exe 첫 스레드 (그림 2)
 커널 시동 → LdrInitializeThunk → 로더 …
   └─ ntdll 스텁 NtContinue  번호 0x43
       ══▶ SYSCALL → [같은 입구]  ← 이번
            └─ CALL → nt!NtContinue … IRETQ  (이 출구는 안 탐, run29)
 → (CRT) → main

(부팅 때, 흐름도 범위 앞)
 KiInitializeKernel → KeCompactServiceTable  번호부 고쳐 쓰기  ← 이번
```

- flow.md 로는 **2.2 새 절 "시스템 콜 입구·출구"** 다. 그림 1·2 의 `KiSystemServiceCopyEnd` 상자 셋이 다 여기에 해당한다.
- 맨 아래 "부팅 때" 는 test.exe 를 실행하기 **훨씬 전**이다. 지도 범위 앞이지만, 번호부 칸 모양을 정하는 곳이라 같이 봤다.

### 왜 이 질문이 지금 왔나

- `../PE_emulator` (진짜 nt·ntdll 과 같은 이름·호출관계로 짓는 에뮬레이터) 가 syscall 입구를 만들고 있다.
- 지금은 syscall 로그에 **레지스터 인자 4개** (`R10`·`RDX`·`R8`·`R9`) 만 남긴다.
- 5번째 인자부터는 유저 스택에 있는데, syscall 마다 **몇 개인지 몰라서** 못 남긴다.
- PE_emulator 가 아는 "일반적인 칸 모양" (위 비트 = 함수까지 거리 `>> 4`, 아래 4비트 = 스택 인자 수) 은 우리 쪽에서 확인한 적이 없었다 `[추측]` (요청서 "배경").
- 그런데 run29·run34 는 같은 표를 **그냥 rva 로 읽어서** 489칸 다 맞았다. 두 이야기가 서로 안 맞아 보였다. 이걸 풀어 달라는 요청이다.

### 무엇이 궁금했나

요청서 질문 넷:

1. **칸 모양**: `KiServiceTable` 칸 하나에서 (a) 함수 주소, (b) 스택 인자 수를 어떻게 뽑나? 파일 값을 부팅 때 고쳐 쓰는 코드가 있나?
2. **번호표**: 번호 → (커널 함수 이름, 스택 인자 수, 전체 인자 수) 489줄 기계용 파일.
3. **ntdll 스텁과 1:1 인가**: 스텁 모양 `4c 8b d1 b8 imm32` 인 것의 번호가 489칸과 짝이 맞나?
4. **돌아갈 때 휘발 레지스터**: 보통 출구 (`SYSRET`) 에서 유저가 받는 값은? (run29 는 "처리기 본문 안 읽음" 이었다.)

### 바퀴 전에 알던 것

- `[정적]` (run29) ntdll `NtContinue` 스텁 `MOV EAX,0x43` → `KiServiceTable[0x43]` = `nt!NtContinue` (rva `0x6adde0`). 489칸 **모두** 함수 시작과 맞음.
- `[정적]` (run34) `[0xd1]` = `nt!NtCreateUserProcess`, `[0x52]` = `nt!NtResumeThread`. 스텁 모양 `+0x12 SYSCALL` / `+0x15 INT 0x2e`.
- `[관찰]` (run3·run44) 커널 `Nt*` 함수 바로 위 프레임 = `nt!KiSystemServiceCopyEnd+0x28`.
- `[추측]` (run29 해설 2.3) "보통 시스템 콜은 창구 앞 (`+0x14`) 으로 돌아온다" — 처리기 본문은 안 읽었다.
- `[추측]` (PE_emulator) 칸 = `(오프셋 << 4) | 개수`.

## 2. 찾은 것

### 2.1 한눈에

run 문서 "호출 관계" 를 조금 줄였다.

```
(아무 스레드, 유저 → 커널 → 유저 — 보통 시스템 콜 한 번)
ntdll!Nt* 스텁   +0x0 MOV R10,RCX · +0x3 MOV EAX,번호
 ══▶ +0x12 SYSCALL
nt!KiSystemCall64            (objdump. 여기로 오는 것은 [추측])
 │  +0x0 SWAPGS · +0x15 ~ +0x23 출발 메모 · +0x3e RCX ← R10
 ══▶ nt!KiSystemServiceUser  R8·R9·R10·XMM0~5 저장 → 그대로 내려감
 ══▶ nt!KiSystemServiceStart
 │  +0xf            번호 & 0xfff
 │  +0x4d ~ +0x58   칸 SAR 4 → R10 = 함수
 │  +0xb0           칸 & 0xf → 스택 인자 수
 │  +0x100 ~ +0x16c 유저 RSP+0x28 … 를 커널 스택으로
 └─ +0x195          CALL RAX → nt!Nt*     (관찰은 CopyEnd+0x28)
 │  +0x1a0 … +0x309 R10 = 0 … 조각 RDX=0·XMM0~5=0·RCX·R11
 ├─ ══▶ 조각 +0xaf SYSRET                         KiKvaShadow 꺼짐
 └─ ══▶ KiKernelSysretExit ══▶ +0x71 SYSRET        켜짐

(부팅 때, 흐름도 범위 앞)
KiInitializeKernel   (+0xfa 갈림의 0 쪽만)
 └─ +0x25c  KeCompactServiceTable(KiServiceTable, KiArgumentTable, KiServiceLimit, 0, 이미지 시작)
         │  +0x1b ~ +0x3d  칸 = ((rva − 표) << 4) | (인자표 >> 2)
         └─ +0x47  KiLockServiceTable
```

- 모두 `[정적]` 이다. 단 `KiSystemCall64` 로 **오는 것** 자체는 `[추측]` (2.12 끝).
- 호출 기호 (`├─`, `└─`) 옆 `+0x..` 는 ret 자리, 기호 없이 들여쓴 `+0x..` 는 그 함수 안 줄이다.
- `══▶` 는 호출이 아니라 **실행이 넘어가는 것**이다 (돌아오지 않음, 또는 그냥 아래로 흘러감).
- "조각" = `KiSystemServiceStart` 끝에 붙은 조각 `FUN_1406c20cc` 기준 오프셋이다. 본문 기준으로는 `+0x50c` 를 더한다 (예: `SYSRET` = 본문 `+0x5bb`).

이름표 넷 — `KiSystemServiceRepeat` (`+0x14`), `KiSystemServiceCopyStart` (`+0x100`), `KiSystemServiceCopyEnd` (`+0x170`), `KiSystemServiceExit` (`+0x1a0`) — 은 **따로 된 함수가 아니다.** 전부 `KiSystemServiceStart` (rva `0x6c1bc0`, 1364바이트) **안의 PDB 이름표**다 `[정적]`.

- 그래서 콜스택에 보이는 `KiSystemServiceCopyEnd+0x28` 은 "`KiSystemServiceStart` 안, 이름표 `CopyEnd` 에서 0x28 뒤" 라는 뜻이다.
- run15 의 `KiStartUserThread` 도 함수가 아니라 이름표였다 ([run15 해설 2.3](../02_sprint/run15-user-thread-startup-해설.md)). 같은 종류다.

### 2.2 한 줄씩 읽는 법

#### 한 줄 읽기 ①: `└─ +0x25c  KeCompactServiceTable(KiServiceTable, KiArgumentTable, KiServiceLimit, 0, 이미지 시작)`

- **누가**: `KiInitializeKernel` — 부팅 때 커널을 준비하는 함수. 관리사무소가 **문 여는 날** 하는 일이다.
- **어디서**: `+0x257` 에서 부르고, 돌아올 자리가 `+0x25c` 다. 인자는 바로 앞 `+0x233 ~ +0x250` 에서 싣는다.
- **누구를**: `KeCompactServiceTable` (번호부를 고쳐 쓰는 사람).
- **무엇을 위해**: 번호부 (`KiServiceTable`) 489칸을 하나하나 "거리 + 서류 장수" 꼴로 **다시 적으려고**.
  - 넘기는 것: `RCX` = 번호부, `RDX` = 서류 장수 표 (`KiArgumentTable`), `R8D` = 칸 수 (`KiServiceLimit`), `[RSP+0x20]` = 이미지 시작.
- 태그 `[정적]`. 단 이 CALL 은 `+0xfa` 갈림의 **한쪽에만** 있다 (2.4). 부팅 때 정말 지나갔는지는 정적으로 못 정한다.

#### 한 줄 읽기 ②: `│  +0x4d ~ +0x58   칸 SAR 4 → R10 = 함수`

- **누가**: `KiSystemServiceStart` — 신청 창구 안쪽, 전화를 받은 관리사무소 직원.
- **어디서**: 자기 안 `+0x4d` ~ `+0x58` (명령 네 줄). 부르는 줄이 아니다.
- **누구를**: 번호부의 **그 번호 칸**을 읽는다 (`+0x4d MOVSXD R11,dword [R10+RAX*4]`).
- **무엇을 위해**: 칸에서 **담당자 자리 (함수 주소)** 를 뽑으려고. `+0x54 SAR R11,4` → `+0x58 ADD R10,R11` 하면 `R10` = 함수 주소.
- 태그 `[정적]`. 무슨 셈인지는 2.5 에서 천천히.

#### 한 줄 읽기 ③: `└─ +0x195  CALL RAX → nt!Nt*`

- **누가**: 같은 `KiSystemServiceStart`.
- **어디서**: `+0x190 MOV RAX,R10` / `+0x193 CALL RAX` (2바이트). 돌아올 자리가 `+0x195` 다.
- **누구를**: ② 에서 뽑은 함수 — 그 번호의 커널 `Nt*` (예: `0xd1` 이면 `nt!NtCreateUserProcess`).
- **무엇을 위해**: 담당자에게 일을 맡기려고. 이때 스택 인자는 이미 커널 스택에 옮겨져 있다 (2.6).
- 태그 `[정적]`. 콜스택에선 이 자리가 `CopyEnd+0x28` 로 보였는데, 파일로는 `CopyEnd+0x25` 다. 3바이트 차이는 2.12.

### 2.3 핵심 ① 파일 칸과 메모리 칸은 다르다 — 질문 1

이번 바퀴의 한가운데다. 천천히 간다.

#### 새 말 — 서비스 표 칸 압축 (부팅 때 고쳐 쓰기)

- PE 파일에 저장된 `KiServiceTable` 칸 값과, 부팅 뒤 **메모리에 있는** 같은 칸 값이 **다르다**. 부팅 때 커널이 칸을 한 번 고쳐 쓰기 때문이다 `[정적]`.
- 고쳐 쓴 꼴은 32비트 칸 하나에 **두 정보** (함수까지 거리, 스택 인자 수) 를 **겹쳐 담은** 것이다. 이걸 이 글에선 "칸 압축" 이라고 부른다 (함수 이름 `KeCompactServiceTable` 의 Compact 를 따름).
- 비유: 번호부 **인쇄본**과, 문 연 날 관리사무소 직원이 **연필로 고쳐 쓴** 번호부.

#### 인쇄본 (PE 파일) 엔 무엇이 적혀 있나 `[정적]`

- 칸 하나 = 32비트 = **함수 rva 그대로**. "이미지 시작에서 몇 번지" 다.
- 489칸 **모두** 아래 4비트가 0 이다.
  - 아래 4비트 = 16진수로 쓰면 **맨 끝 한 자리**다. 예: `0x006adde0` (`NtContinue`) 의 끝자리 `0`.
- 그래서 run29·run34 가 "rva 로 읽었더니 489칸 다 함수 시작과 맞았다" 는 **인쇄본 기준으로 맞는 방법**이었다.

#### 문 연 날 고쳐 쓴 번호부 (메모리) 엔 무엇이 적혀 있나 `[정적]`

칸마다 이렇게 바꾼다 (`KeCompactServiceTable +0x1b ~ +0x3d`):

```
새 칸 = ((함수 rva − 0xdadc0) << 4) | (KiArgumentTable[번호] >> 2)
```

- `0xdadc0` = 번호부 자신의 rva. 그러니 `함수 rva − 0xdadc0` = **번호부에서 담당자 자리까지 거리**.
- `<< 4` = 16진수로 **한 자리 왼쪽으로 민다.** 10진수에서 ×10 하면 끝에 0 이 붙듯, 끝에 **빈 자리 하나**가 생긴다.
- `| 개수` = 그 빈 끝자리에 **서류 장수**를 써 넣는다. 한 자리 (4비트) 라 0 ~ 15 까지 들어간다.

#### 비유로 한 번 더 — 전화번호 끝자리

- 인쇄본 번호부: "43번 담당 → **6adde0 번지**". 인쇄본의 번지는 모두 끝자리가 0 이다.
- 문 연 날: 직원이 이 줄을 지우고 "43번 → **번호부에서 ○○ 걸음**" 같은 **거리**로 바꿔 쓴다. 그리고 한 자리 밀어서 끝에 칸을 하나 만들고, 거기에 **"서류 0장"** 의 `0` 을 적는다.
  - 실제로 고쳐 쓴 칸 값은 아래 표 (결과서 계산값) 를 본다.
- 그러니 **인쇄본을 보고 끝자리를 읽으면 늘 "서류 0장"** 이 나온다. 인쇄본엔 아직 장수를 안 적었으니까.

#### 예 넷 — 끝자리를 보자

결과서가 계산한 메모리 값이다. **메모리에서 직접 본 값은 아니다** (→ Q107 (1)).

| 번호 | 함수 | 인쇄본 (파일) | 서류 장수 표 바이트 | 고쳐 쓴 칸 (계산) | 끝자리 = `& 0xf` |
|---|---|---|---|---|---|
| `0x0` | `NtAccessCheck` | `0x0039d590` | `0x10` | `0x02c27d04` | 4 |
| `0x43` | `NtContinue` | `0x006adde0` | `0x00` | `0x05d30200` | 0 |
| `0x52` | `NtResumeThread` | `0x00a2d600` | `0x00` | `0x09528400` | 0 |
| `0xd1` | `NtCreateUserProcess` | `0x00a01340` | `0x1c` | `0x09265807` | 7 |

- 인쇄본 열은 끝자리가 모두 `0` 이다.
- 고쳐 쓴 칸 열은 끝자리가 **그 함수의 스택 인자 수**다. `0xd1` 이면 `7`.

#### 서류 장수 표 — `KiArgumentTable` `[정적]`

- rva `0xdb568`, **1바이트 칸 489개**. PDB 공개 이름이다.
- 값은 "스택 인자 **바이트** 수 (4바이트 단위)" 꼴이다. 489바이트가 모두 4의 배수 (`0, 4, 8, …, 52`) 라 `>> 2` (÷4) 해도 잃는 게 없다.
- `>> 2` 하면 **8바이트 칸 수** = 스택 인자 수가 된다.
  - 예: `NtCreateUserProcess` `0x1c` → 7. `NtAccessCheck` `0x10` → 4.
- 비유: 번호부 옆에 따로 묶여 있던 **"서류 몇 장" 표**. 문 연 날 이걸 보고 번호부 끝자리에 옮겨 적는다.

#### 그래서 PE_emulator 는 어느 쪽을 읽어야 하나 `[정적]`

| 에뮬레이터가 읽는 곳 | 스택 인자 수 | 함수 주소 |
|---|---|---|
| **PE 파일** 의 `KiServiceTable` | 칸 `& 0xf` 하면 **늘 0 (틀림)**. 대신 `KiArgumentTable[번호] >> 2` | 이미지 시작 + 칸 |
| **부팅 뒤 메모리 꼴**을 흉내 낸 칸 | 칸 `& 0xf` | 표 시작 + (칸 `SAR 4`) |

- PE_emulator 가 알던 `(오프셋 << 4) | 개수` 는 **메모리 쪽 기준으로 맞다.** 틀린 게 아니라, 어느 번호부 (인쇄본 / 고쳐 쓴 것) 이야기인지가 빠져 있었던 것이다.
- run29·run34 의 "rva 그대로" 도 **인쇄본 쪽 기준으로 맞다.** 두 이야기가 둘 다 맞았다.

### 2.4 누가 언제 고쳐 쓰나 — `KeCompactServiceTable`

#### 부르는 곳 `[정적]`

- `KiInitializeKernel +0x257` CALL (ret `+0x25c`). 인자는 2.2 한 줄 읽기 ① 그대로.
- 이 CALL 은 `+0xf7 TEST R15D,R15D` / `+0xfa JNZ` 갈림의 **0 쪽에만** 있다.
  - `R15D` 는 `+0x5a` 에서 스택 인자로 받는다. **첫 CPU 번호**로 보인다 `[추측]`.
  - 그렇다면 "CPU 0 이 부팅할 때 한 번만" 고쳐 쓴다는 뜻이 된다 `[추측]`. CPU 마다 고쳐 쓰면 두 번 압축되어 망가질 테니 자연스러운 그림이다 — 이건 내 짐작이다 `[추측]`.
  - 실제로 지나갔는지는 정적으로 못 정한다 → 메모리 칸 값을 보면 같이 풀린다 (Q107 (1)).

#### 하는 일 (루프 `+0x1b ~ +0x3d`, 칸마다 한 번) `[정적]`

| 줄 | 하는 일 |
|---|---|
| `+0x1b MOVZX EAX,byte [RBX]` | 서류 장수 표 한 바이트 |
| `+0x21 ~ +0x2a` | `EDX = 이미지시작 − 표 + 칸값` = 번호부에서 함수까지 **거리** |
| `+0x27 SHR EAX,2` | 장수 바이트 ÷ 4 |
| `+0x2d SHL EDX,4` | 거리를 한 자리 밀기 |
| `+0x30 OR EDX,EAX` | 끝자리에 장수 |
| `+0x32 MOV [R11],EDX` | 그 칸에 **다시 씀** |

- 루프가 끝나면 `+0x42` CALL `KiLockServiceTable` (ret `+0x47`). 표를 잠그는 쪽으로 보인다 `[추측]` (이름만 봄).

#### 다른 곳에서 고쳐 쓰나 `[정적]`

- `KiServiceTable` 을 가리키는 곳은 **둘뿐**이다 (`_refs/KiServiceTable.tsv`):
  - `KiInitializeKernel +0x250` — 위 CALL 의 인자.
  - `KiInitSystem +0xfa` — 서술자에 주소만 넣음.
- 그러니 고쳐 쓰는 곳은 `KeCompactServiceTable` 하나다.

#### 새 말 — 서술자 (`KeServiceDescriptorTable`)

- 번호부 하나에 대한 **안내 카드**다. 칸 `+0x0` = 번호부 주소, `+0x10` = 칸 수 (Limit), `+0x18` = 서류 장수 표 주소 (`KiInitSystem +0x101`·`+0x115`·`+0x122`) `[정적]`.
- 비유: 번호부 표지에 붙은 **색인 카드**. "이 번호부는 여기, 489번까지, 장수 표는 저기."
- 재밌는 점 `[정적]`: 카드에 장수 표 주소 (`+0x18`) 가 **남아 있지만**, 전화 받는 길 (`KiSystemServiceStart`) 은 그걸 **안 읽는다.** 번호부 끝자리만 본다.
  - 왜 이렇게 겹쳐 담나는 근거 문서에 없다. 한 번 읽어서 두 정보를 다 얻으려는 것으로 보인다 `[추측]`.

#### 덤 — win32k 번호부

- 그래픽 (GUI) 쪽 시스템 콜 번호부 (서술자 `[1]`) 는 `PsInitializeWin32kServiceTable +0x8e` → `MmCompactServiceTable` 이 **따로** 누른다 (이름만, 범위 밖) `[정적]`.
- test.exe 의 ntdll 은 이 번호부를 쓸 일이 없다 (2.8).

### 2.5 커널이 고쳐 쓴 칸을 읽는 법 — `SAR 4`, `AND 0xf`

전화를 받은 `KiSystemServiceStart` 가 하는 일이다 `[정적]`.

#### (a) 함수 주소 — 끝자리 떼고 거리만

| 줄 | 하는 일 |
|---|---|
| `+0x49 MOV R10,[R10+RDI]` | 서술자에서 번호부 시작 주소 |
| `+0x4d MOVSXD R11,dword [R10+RAX*4]` | 그 번호 칸을 **부호 있게** 읽음 |
| `+0x51 MOV RAX,R11` | 끝자리용으로 하나 복사 |
| `+0x54 SAR R11,4` | **끝자리 떼기** (한 자리 오른쪽으로) |
| `+0x58 ADD R10,R11` | 번호부 시작 + 거리 → `R10` = **함수 주소** |

**새 말 — 부호 있게 읽기 (`MOVSXD`, `SAR`)**

- 32비트 칸을 64비트로 넓힐 때, 맨 앞 비트를 **음수 표시**로 보고 늘리는 것이다. `SAR` 도 같은 식으로 "음수면 음수 그대로" 오른쪽으로 민다.
- 비유: 거리에 **"앞으로 / 뒤로"** 방향이 붙어 있다. 담당자 자리가 번호부보다 **앞쪽**이면 거리가 음수가 될 수 있다.
- 이 빌드에선 칸이 가리키는 rva 가 `0x20a9f0 ~ 0xb6e8b0` 으로 **모두 번호부 (`0xdadc0`) 뒤**라서, 음수 거리는 하나도 없다 `[정적]` (결과서).
  - 그러니 이번엔 "부호 있게" 가 결과를 바꾸지 않는다. 에뮬레이터가 음수 처리를 안 해도 이 빌드 값은 같게 나온다 — 이건 내 짐작이다 `[추측]`.

#### (b) 스택 인자 수 — 끝자리만

| 줄 | 하는 일 |
|---|---|
| `+0xb0 AND EAX,0xf` | 끝자리 = **스택 인자 수 n** |
| `+0xb3 JZ` | 0 이면 복사 안 하고 `CopyEnd` 로 |
| `+0xb9 SHL EAX,3` | n × 8 (바이트 수) |

- (a) 의 `+0x51` 에서 복사해 둔 `RAX` 를 여기서 쓴다. **한 칸을 한 번 읽어서** 두 정보를 다 뽑는 구조다.

### 2.6 핵심 ② 스택 인자 = 레지스터 4개 **다음**부터 — 질문 1 덤

#### 새 말 — 스택 인자 (레지스터 4개 다음부터)

- x64 Windows 에선 함수 인자 **첫 4개를 레지스터** (`RCX`·`RDX`·`R8`·`R9`) 로, **5번째부터는 스택**에 놓는다 `[추측]` (일반적으로 알려진 호출 규약).
- 그리고 부르는 쪽은 스택에 **그림자 공간 0x20** (레지스터 4개 몫의 빈 칸) 을 비워 둔다 `[추측]` (같은 규약, [run16 해설](../02_sprint/run16-thunk-context-해설.md) 에서 한 번 나옴).
- 비유: 직원이 서류 **4장은 손에** 들고 (레지스터), **나머지는 가방에** (유저 스택) 넣어 창구에 온다. 가방 맨 위엔 "돌아갈 곳 쪽지" 와 **빈 주머니 4개** (그림자 공간) 가 있다.

#### 스텁이 `RCX` 를 `R10` 으로 옮기는 이유

- 스텁 `+0x0 MOV R10,RCX` 로 첫 인자를 `R10` 에 옮긴다 `[정적]` (run29).
- 커널 입구 `KiSystemCall64` 는 들어오자마자 `RCX` 를 **돌아갈 RIP** 로 출발 메모에 적고 (`+0x15 ~ +0x23`), `+0x3e MOV RCX,R10` 으로 첫 인자를 `RCX` 로 **되돌린다** `[정적]`.
- 그러니 `SYSCALL` 이 `RCX` 칸을 "돌아갈 자리" 로 써 버리는 것으로 보인다 `[추측]` (일반적으로 알려진 `SYSCALL` 동작). run29 해설 2.3 에서 짐작했던 것이 이번에 커널 쪽 코드로 앞뒤가 맞았다.
- 그래서 PE_emulator 로그의 레지스터 4개도 `RCX` 가 아니라 **`R10`·`RDX`·`R8`·`R9`** 다.

#### 가방에서 꺼내는 자리 `[정적]`

| 줄 | 하는 일 |
|---|---|
| `+0xbc LEA RSP,[RSP-0x70]` / `+0xc1 LEA RDI,[RSP+0x18]` | 커널 쪽 받는 자리 마련 |
| `+0xc6 MOV RSI,[RBP+0x100]` | 출발 메모의 `Rsp` 칸 = **유저 RSP** |
| `+0xcd LEA RSI,[RSI+0x20]` | 그림자 공간 0x20 **건너뜀** |
| `+0xd1 ~ +0xe1` | 유저에서 왔으면 `MmUserProbeAddress` 로 자름 (유저 주소인지 확인) |
| `+0xf0 ~ +0xfa` | 사다리 끝에서 `n × 8` 바이트 **앞으로 뛰어듦** |
| `+0x100 ~ +0x16c` (`CopyStart`) | 8바이트 복사 **14쌍** |

- 복사 한 쌍 = `MOV RAX,[RSI+k]` / `MOV [RDI+k],RAX`. `k` 는 `0x70` 부터 `0x8` 까지 내려간다.
- 그래서 개수 `n` 이면 **마지막 n 쌍만** 돈다 (`k = 8, 16, …, 8n`). 처음 옮기는 칸 = `RSI + 8` = 유저 `RSP + 0x20 + 8` = **`RSP+0x28`**.
- 그럼 유저 `RSP+0x0 ~ +0x7` 은 뭔가: 스텁은 스택에 아무것도 안 쌓으니, 스텁을 **부른 쪽의 돌아올 주소**로 보인다 `[추측]` (일반 규약 + 스텁 바이트). 그 위 `+0x8 ~ +0x27` 이 그림자 공간이다 `[추측]`. 비유의 "돌아갈 곳 쪽지 + 빈 주머니 4개" 가 이것이다.

#### 새 말 — 복사 사다리

- 같은 "8바이트 옮기기" 를 **14번 써 놓은 줄**이다. 반복문 대신 펼쳐 둔 것.
- 개수에 따라 사다리 **중간으로 뛰어들어** 아래쪽만 밟는다. n = 0 이면 사다리를 아예 안 탄다 (`+0xb3 JZ`).
- 비유: 14칸짜리 사다리. 서류가 3장이면 아래 3칸 자리로 바로 뛰어내려서 3칸만 밟고 내려온다.

#### 그래서 로그에 남길 것 `[정적]`

```
R10, RDX, R8, R9,  [유저 RSP + 0x28 + 8·i]  (i = 0 … n−1)
```

- 예: `0xd1` `NtCreateUserProcess` 는 n = 7. 인자 11개 = 레지스터 4 + 유저 스택 `RSP+0x28 ~ +0x58` 7칸 (flow.md 2.1).
- 사다리가 14쌍이라 **코드상 최대 14**. 이 빌드 표의 최대값은 **13** 이다. (4비트 끝자리는 15 까지 담을 수 있지만 그건 안 쓴다.)
- 손님 가방 → 관리사무소 책상으로 서류를 **옮겨 놓은 뒤에** 담당자를 부른다 (`+0x193 CALL RAX`). 담당자는 자기 책상 (커널 스택) 에서 서류를 읽는다.

### 2.7 번호표 — `_workspace/sast/51_syscall-args_table.tsv` (질문 2)

#### 생김새 `[정적]`

- 머리 1줄 + **489줄** (`0x0` ~ `0x1e8`). 탭 구분. 머리줄엔 `#` 이 없다.
- 열 다섯:

| 열 | 뜻 |
|---|---|
| `number` | 번호 (16진, `0x43` 꼴) |
| `nt_function` | 커널 함수 PDB 이름 |
| `stack_args` | `KiArgumentTable[번호] >> 2` = 고쳐 쓴 칸의 끝자리 |
| `total_args` | `4 + stack_args` |
| `ntdll_stub` | 같은 번호를 쓰는 ntdll `Nt*` export. 없으면 빈칸 |

- 예 (tsv 그대로): `0xd1 NtCreateUserProcess 7 11 NtCreateUserProcess`, `0x43 NtContinue 0 4 NtContinue`.

#### `total_args` 4 는 "4개" 가 아니다 — 읽는 법 주의

- `stack_args > 0` 이면 `total_args` 가 **정확한** 인자 수다 (레지스터 4 + 스택 n).
- `stack_args = 0` 이면 실제 인자는 **0 ~ 4개**다. 표만으로는 몇 개인지 **못 정한다** `[정적]`.
  - 이때 `total_args` 4 는 "**레지스터 4칸**" 이라는 뜻일 뿐이다.
  - 예: `NtClose` 는 1개, `NtContinue` 는 2개인데 **둘 다 4** 로 적혀 있다.
- 왜 못 정하나: 서류 장수 표는 **가방에 든 장수**만 센다. 손에 든 서류 (레지스터) 가 몇 장인지는 원래 안 적는다.
- 로그용으로는 문제없다. 레지스터 4개는 늘 다 남기고, 스택은 0개면 된다.
- 이런 칸이 **302칸**이다.

#### 분포 `[정적]`

`stack_args`: 칸 수 — 0: 302 / 1: 72 / 2: 44 / 3: 13 / 4: 12 / 5: 16 / 6: 11 / 7: 9 / 8: 2 / 9: 1 / 10: 2 / 12: 3 / 13: 2. (11·14 는 없다.)

#### 손 대조 `[정적]`

- 결과서가 디컴파일 `.c` 의 매개변수 수와 맞춰 봤다: `0x43` `NtContinue` 0 (2개), `0x52` `NtResumeThread` 0 (2개), `0xd1` `NtCreateUserProcess` 7 (11개), `0x19` `NtQueryInformationProcess` 1 (5개), `0x1d0` `NtSystemDebugControl` 2 (6개). 이미 있던 `Nt*.c` 12개 **모두 어긋남 없음.**
- 하나 배울 점: `0x4a` `NtCreateSection` 은 `.c` 가 매개변수 **1개**로 잘못 나왔다. `.asm` 에서 `[RSP+0x28/0x30/0x38]` (5·6·7번째) 를 읽는 줄을 보고 **7개**로 맞췄다.
  - 얇은 감싸개 함수는 Ghidra `.c` 매개변수 수가 모자라게 나온다. 인자 수 대조는 `.asm` 의 `[RSP+0x28 이상]` 읽기로 한다. (run55 해설 2.3 의 "짧은 함수는 `.c` 가 정보를 빼먹을 수 있다" 와 같은 이야기다.)

#### 이름 고르기 — ICF 다시 짧게

- **ICF** = 링커가 **내용이 똑같은 함수를 하나로 합치는** 것. 그러면 한 주소에 이름이 여럿 붙는다 ([run9 해설](../02_sprint/run9-create-user-process-해설.md#한-주소에-이름-여럿-icf-별칭), 비유: **문패 하나에 여러 가족**).
- 시스템 콜에선 이게 "**여러 번호가 같은 담당자 한 명을 같이 쓴다**" 로 나타난다 `[정적]`:
  - 한 커널 주소에 PDB 이름이 여럿인 칸이 **21칸**.
  - 예: `0x705290` 한 곳을 **12번호**가 같이 쓴다 (`0x6d`·`0xb0`·`0xe2`·`0xee`·`0x128`·`0x1a2`·`0x1a3`·`0x1b6`·`0x1b7`·`0x1e2`·`0x1e7`·`0x1e8`).
  - 비유: 번호부에서 12개 단축 번호가 **같은 자리**로 연결된다. 그 자리 담당자는 내용이 같은 일 (결과서상 그 이름들 중엔 `NtCreateEventPair`·`NtVdmControl` 등이 있다) 을 하나로 처리한다.
- 결과서는 그런 칸에 **ntdll 스텁 이름**을 골라 적었다. 그래서 `nt_function` 489개가 서로 다 다르다.
- 주의: 이 칸들은 **이름만 보고 함수 본문을 가리면 안 된다.** 본문은 같다.

### 2.8 ntdll 스텁은 488칸과 1:1 — 질문 3

#### 스캔 결과 `[정적]`

- ntdll 실행 섹션 전체에서 `4c 8b d1 b8` (`MOV R10,RCX` / `MOV EAX,번호`) 를 찾았더니 **494곳**.
- 494곳의 뒤 16바이트가 **모두 같다**: `TEST byte [0x7ffe0308],1` / `JNZ +3` / `+0x12 SYSCALL` / `+0x14 RET` / `+0x15 INT 0x2e` / `+0x17 RET`. 앞에 다른 명령이 붙은 스텁은 없다.
  - 즉 run29·run34 가 본 스텁 모양 (공용 게시판 확인 → `SYSCALL` 또는 옛 쪽문) 이 **예외 없이 전부**다.
- 494 = **export 스텁 488** + **내부 스텁 `Np*` 6**.

#### 488 ↔ 489 — 남는 한 칸 `0x5a` `[정적]`

- export 스텁 488개의 번호가 번호부 489칸 중 **488칸**과 짝이 맞는다 (번호 같고, 이름도 그 칸 PDB 이름 안에 있음 — 488/488).
- 남는 1칸 = **`0x5a` `NtQuerySystemTime`**.
  - ntdll 의 `NtQuerySystemTime`·`ZwQuerySystemTime` export 는 스텁이 아니다. `E9` JMP 로 `RtlQuerySystemTime` (ntdll rva `0xed060`) 에 넘긴다.
  - 그래서 test.exe 가 ntdll 로 `0x5a` 를 부를 길은 **없다**.
  - 유저에서 **공용 게시판의 시계**를 읽고 커널에 안 들어가는 길로 보인다 `[추측]`. 비유: 시간 물어보러 관리사무소에 전화할 필요 없이, 로비 게시판 시계를 보면 된다.
- `NtGetTickCount` 도 같은 꼴 (`E9` → `RtlGetTickCount`, rva `0x145570`) 이고 커널 번호부에 같은 이름이 없다.
- `Nt`/`Zw` 로 시작하는 export 983개 중 스텁 아닌 7개는 위 셋과 `NtdllDefWindowProc_A/_W`·`NtdllDialogWndProc_A/_W` (`FF 25` 간접 JMP, 이름만 `Ntdll…`) 다.

#### 같은 번호의 내부 스텁 `Np*` 6개 `[정적]`

| 번호 | 내부 스텁 | 짝 export 스텁 |
|---|---|---|
| `0xf` | `NpClose` | `NtClose` |
| `0x23` | `NpQueryVirtualMemory` | `NtQueryVirtualMemory` |
| `0x28` | `NpMapViewOfSection` | `NtMapViewOfSection` |
| `0x2a` | `NpUnmapViewOfSection` | `NtUnmapViewOfSection` |
| `0x33` | `NpOpenFile` | `NtOpenFile` |
| `0x4a` | `NpCreateSection` | `NtCreateSection` |

- PDB 에만 이름이 있고 export 는 아니다. 바이트 모양·번호는 export 스텁과 같다. 누가 부르는지는 **안 봤다.**
- 비유: 관리실에 **같은 단축 번호가 저장된 전화기가 한 대 더** 있는 셈이다.
- 에뮬레이터가 "돌아갈 주소 → 스텁 이름" 으로 로그를 찍는다면, 이 6개 주소 (결과서 질문 3 표에 rva) 도 이름표에 넣어야 같은 번호가 다른 이름으로 안 찍힌다 `[추측]`.

#### 한 스텁에 이름 셋 `[정적]`

- `0x36` 스텁 (rva `0x161470`) = `NtQuerySystemInformation` + `ZwQuerySystemInformation` + `RtlGetNativeSystemInformation`.

### 2.9 번호 풀기와 범위 검사 `[정적]`

- `KiSystemServiceStart +0x7 ~ +0xc` `EDI = (EAX >> 7) & 0x20` — 번호의 **비트 12 (`0x1000`)** 가 서 있으면 서술자 `[1]` (win32k 번호부), 아니면 `[0]`.
- `+0xf AND EAX,0xfff` — 번호부 안 번호.
- `+0x14` (`Repeat`) 기본 = `KeServiceDescriptorTable`. GUI 스레드 (`KTHREAD+0x78` bit 7) 면 `…Shadow`, bit 21 이면 `…Filter`.
- `+0x3e CMP EAX,[R10+RDI+0x10]` (칸 수와 비교) → 넘치면 `+0x43 JNC +0x907`.
  - win32k 번호면 `+0x91f KiConvertToGuiThread` 뒤 `+0x940` 에서 `+0x14` 로 다시.
  - 아니면 `+0x967 MOV EAX,0xc000001c` (STATUS_INVALID_SYSTEM_SERVICE) 로 돌아간다.
- **ntdll 스텁은 `0x1000` 이상 번호를 하나도 안 쓴다** (2.8). 그러니 test.exe 의 ntdll 길에선 늘 기본 번호부다.
- 비유: 단축 번호 앞자리에 "1" 이 붙으면 **옆 건물 (그래픽 쪽) 번호부**를 편다. 번호부에 없는 번호를 누르면 "없는 번호입니다" (`0xC000001C`) 로 끊긴다.

### 2.10 핵심 ③ 돌아갈 때 레지스터 — 보통 출구 `SYSRET` (질문 4)

#### 새 말 — `SYSRET`

- `SYSCALL` 의 **짝**이다. 커널에서 유저로 돌아갈 때 쓰는 명령으로, `RCX` 에 든 자리로 가고 `R11` 에 든 값을 RFLAGS 로 되살리는 것으로 알려져 있다 `[추측]` (일반적으로 알려진 설명).
- 이번 코드도 그 모양과 맞는다 `[정적]`: `SYSRET` 바로 전에 `RCX` ← 출발 메모 `Rip`, `R11` ← 출발 메모 `EFlags` 를 싣는다 (조각 `+0x60`·`+0x67`).
- 비유: 창구에 들어올 때 **"돌아갈 문" 쪽지**를 `RCX` 주머니에 넣고 (`SYSCALL`), 나갈 때 그 주머니 쪽지대로 나간다 (`SYSRET`). 그래서 `RCX` 주머니엔 인자를 넣을 수 없다 (2.6).
- run15·run29 의 `IRETQ` (**순간 이동**) 와는 다른 문이다. `IRETQ` 는 출발 메모의 다섯 칸 (`Rip`·`SegCs`·`EFlags`·`Rsp`·`SegSs`) 을 꺼내 나가고 ([run15 해설 2.6](../02_sprint/run15-user-thread-startup-해설.md)), 이번 `SYSRET` 은 주머니 두 개 (`RCX`·`R11`) 에 실어 둔 값으로 나간다.

#### 휘발 레지스터 — 다시 짧게

- **휘발 레지스터** = 함수를 부를 때 "불린 쪽이 마음대로 써도 되는 칸" `[추측]` (일반적으로 알려진 호출 규약, [run15 해설 2.4](../02_sprint/run15-user-thread-startup-해설.md)). `RAX`·`RCX`·`RDX`·`R8 ~ R11`·`XMM0 ~ XMM5` 가 여기에 든다고 알려져 있다 `[추측]`.
- 그러니 시스템 콜에서 돌아온 뒤 이 칸에 **무엇이 남아 있는지는** 규약이 정해 주지 않는다. 코드를 봐야 안다. 이번에 그 코드를 봤다.

#### 유저가 받는 값 (인스트루먼테이션 콜백 없음) `[정적]`

| 레지스터 | 값 | 근거 (`KiSystemServiceStart`) |
|---|---|---|
| `RAX` | 커널 함수의 **NTSTATUS** (범위 밖 번호면 `0xC000001C`) | `+0x391` 출발 메모 `Rax` 칸에 둠 → 조각 `+0x34` |
| `RCX` | 돌아갈 유저 RIP = 스텁 `+0x14 RET` | 조각 `+0x60` (출발 메모 `Rip`) |
| `R11` | 유저 RFLAGS (SYSCALL 때 값) | 조각 `+0x67` |
| `RDX` | **0** | 조각 `+0x46 XOR EDX,EDX` |
| `R8` | 유저 RSP (SYSCALL 때 값) | 조각 `+0x38`, `+0x7e MOV RSP,R8` |
| `R9` | **0** (`KiKvaShadow` 꺼짐) / **유저 RBP** (켜짐) | 꺼짐: 조각 `+0x81 XOR R9,R9`. 켜짐: `KiKernelSysretExit` 는 `R9` 를 안 지움 |
| `R10` | **0** | 본문 `+0x309 XOR R10,R10` |
| `XMM0 ~ XMM5` | **0** | 조각 `+0x48 ~ +0x5c PXOR` |
| `RBX`·`RSI`·`RDI`·`RBP`·`RSP`·MXCSR | 들어올 때 값 그대로 | `+0x1a0 ~ +0x1ae`, `+0x305`, 조각 `+0x7b`·`+0x7e` |
| `R12 ~ R15`, `XMM6 ~ XMM15` | 이 길에 쓰는 줄 없음 → 커널 함수가 규약대로 지켜 준다고 봄 | `[추측]` |

표를 읽는 법 — 세 무리로 나뉜다:

1. **답과 돌아갈 문** (`RAX`, `RCX`, `R11`) — 꼭 쥐여 보내는 것.
2. **운반에 쓰고 남은 것** (`R8`, `R9`) — `R8` 은 유저 RSP 를 되살리는 데 쓴 칸 (`+0x7e MOV RSP,R8`) 이라 그 값이 남는다. `R9` 도 유저 RBP 운반 (`+0x7b`) 에 쓰고, 보통 문은 뒤에서 지우지만 보안 검색대 문 (`KiKernelSysretExit`) 은 안 지운다.
3. **지워서 보내는 것** (`RDX`, `R10`, `XMM0~5`) — 0.
   - **왜 지우는지는 근거 문서에 없다.** 커널 안에서 쓰던 값이 유저에게 새지 않게 하려는 것으로 일반적으로 알려져 있다 `[추측]`.
   - 비유: 창구 직원이 일하면서 쓴 **메모지 몇 장**을 손님에게 그대로 들려 보내지 않고, 깨끗이 지워서 돌려준다.

#### `R9` 가 문에 따라 다른 이유 — 단계별로

1. `[정적]` 조각 `+0x7b` 에서 `RBP = R9` (유저 RBP 를 `R9` 로 운반해 온 것).
2. `[정적]` `KiKvaShadow` 꺼짐 (보통 문): 조각 `+0x81 XOR R9,R9`. 그 뒤 `+0x84 ~ +0x93` 에서도 결국 0 → **`R9 = 0`**.
3. `[정적]` 켜짐 (보안 검색대 문): 조각 `+0x6e / +0x75` 에서 `KiKernelSysretExit` 로 뛴다. 그 안은 `+0x44 MOV RBP,R9` 만 하고 `R9` 을 **안 지운다** → **`R9` = 유저 RBP**.
4. 그래서 이 VM 의 `R9` 값은 `KiKvaShadow` 하나에 달렸다. 실행 때 값이라 정적으로 못 정한다 → Q107 (3).

- 이 변수는 run15 (첫 스레드 출구) 와 run29 (`NtContinueEx` 출구) 의 문 고르기와 **같은 변수**다. 다만 그 둘은 `KiKernelExit` (`IRETQ`) 이고, 이번 길은 `KiKernelSysretExit` (`SYSRET`) 다. **함수는 다르고 변수는 같다** `[정적]`. 한 번 읽으면 세 곳이 같이 정해진다.

#### 덤 — 인스트루먼테이션 콜백 `[정적]`

- `KPROCESS +0x168` (`InstrumentationCallback`) 칸이 0 이 아니고 `CS = 0x33` (유저 64비트) 이면 (`+0x30c ~ +0x34c`):
  - `R10` = **원래 돌아갈 RIP**, 실제로 돌아가는 곳 = **콜백 주소**.
- 비유: 가게 문 앞에 "**나가면 먼저 ○○실 들르세요**" 표지가 붙어 있으면, 직원은 창구 앞이 아니라 그 방으로 간다. 원래 가려던 곳은 `R10` 쪽지에 적혀 있다.
- test.exe 에서 이 칸 값은 **안 봤다.** 보통은 비어 있을 것으로 보이지만 확인 아님 `[추측]`.

#### 덤 — 사이에 끼어든 나눗셈 `[정적]`

- 조각 `+0x1b ~ +0x31` 은 `GS:[0x858] & 0x100` 이면 `DIV RCX` 를 한다. 이때 `RAX`·`RDX`·`RCX` 가 바뀌지만, **바로 뒤에서 셋 다 다시 채운다.** 위 표엔 영향이 없다.

#### 표에 안 든 길 (이름만) `[정적]`

- 유저 APC (`+0x248 KiInitiateUserApc`), `+0x2d3 KiRestoreSetContextState` (스레드 플래그 `0x8000000`), 피코 프로세스 `KiSystemServiceExitPico`, 커널 모드 호출자 `+0x5be RET`, `INT 0x2e` 갈래.
- 이 길들에선 값이 다를 수 있다. `KiRestoreSetContextState` 는 문맥을 통째로 바꾸는 쪽으로 보인다 `[추측]`.

### 2.11 로더 끝 `NtContinue` 는 이 표를 안 쓴다

헷갈리기 쉬운 곳이라 따로 뗐다. [run29 해설 2.3](../02_sprint/run29-continue-start-해설.md) 의 이야기를 이번 결과로 다시 본다.

1. `[정적]` (run29) 성공한 `NtContinue` 는 `NtContinueEx` 가 **반환하지 않고**, 출발 메모에서 휘발 레지스터까지 되살린 뒤 (`NtContinueEx +0x3be ~ +0x3ee`) **`IRETQ`** 로 바로 유저에 간다.
2. `[정적]` (run56) 그러니 `KiSystemServiceStart +0x195` 로 돌아오지 않는다 → 위 2.10 의 보통 출구 (`RDX`·`R10` 지우기, `SYSRET`) 를 **안 탄다**.
3. 그래서 로더 끝 `NtContinue` 뒤 유저가 받는 레지스터는 **맡긴 문맥 값** (`Rcx` = 진입점, `Rdx` = PEB …) 이다 (flow.md 2.10).
4. `[정적]` (run29 + run56) **실패할 때만** (`NtContinueEx +0x47a RET`) 보통 출구로 와서 위 표대로 돌려받는다.

- 즉 run29 해설 2.3 의 "보통 시스템 콜은 창구 앞으로 돌아온다" 는 그때 `[추측]` 이었는데, 이번에 그 **보통 출구 코드**를 읽었다 `[정적]`. 그리고 "`NtContinue` 는 그 길을 안 탄다" 와 나란히 놓으니 둘의 차이가 레지스터 수준까지 보인다:
  - 보통 창구: **답 봉투 (`RAX`) + 돌아갈 문 (`RCX`)**, 메모지는 지워서.
  - `NtContinue` 창구: 사물함 메모에 적힌 대로 **왼손에 진입점, 오른손에 PEB**.
- `[정적]` `[0x43]` 의 스택 인자 수는 0 이다. 인자 2개 (맡긴 문맥, `TestAlert`) 는 `R10` (→`RCX`)·`RDX` 로만 간다.
- 실제로 어느 길로 나가는지는 실행으로 확인 → Q107 (5) (Q29·Q57 과 같이).

### 2.12 콜스택 `CopyEnd+0x28` vs 파일 `+0x25` — 3바이트 차이

run 문서가 **고르지 않고 둘 다 둔** 곳이다. 왜 그런지 단계별로.

1. **근거** `[관찰]` (run3, run44): 커널 `Nt*` 바로 위 프레임 = **`KiSystemServiceCopyEnd+0x28`**. 예: run44 K1 콜스택 `PspAllocateThread` ← `NtCreateUserProcess+0xe5c` ← `KiSystemServiceCopyEnd+0x28` ← `ntdll!NtCreateUserProcess+0x14`.
2. **근거** `[정적]` (run56): 파일 바이트 `0x6c1d50` = `49 8b c2 | ff d0 | 0f 1f 00` → `MOV RAX,R10` / `CALL RAX` (2바이트) / `NOP` (3바이트).
3. **그래서** 파일대로라면 돌아올 자리 = `CALL RAX` 다음 = `+0x195` = **`CopyEnd+0x25`**. 관찰 `+0x28` 은 `NOP` 의 **끝** (`+0x198`) 이다.
4. **짐작** `[추측]`: 메모리에서 `CALL RAX` (2바이트) + `NOP` (3바이트) = **5바이트 자리**가 **5바이트짜리 직접 `CALL`** 로 바뀌었다고 보면 숫자가 맞아떨어진다. 결과서는 이걸 "retpoline 류" 라고 적었다.
   - retpoline 류 = 간접 호출 (`CALL RAX` 처럼 레지스터에 든 주소로 가는 호출) 을 보안상 다른 꼴로 바꾸는 장치로 알려져 있다 `[추측]` (일반적으로 알려진 설명).
   - 비유: 번호부 칸을 보고 전화를 돌리는 줄 (`CALL RAX`) 과 그 뒤 빈칸 (`NOP`) 을 합쳐, **"○○실로 바로 연결"** 이라고 고쳐 쓴 스티커를 붙였다면 — 스티커 끝이 3바이트 더 뒤라서 돌아올 자리도 3바이트 뒤가 된다.
5. **아직 확인 아님**: 이 빌드에서 그렇게 고쳐 쓰는 코드는 이번에 **안 찾았다**.

- 그래서 run 문서는:
  - 파일 값 `+0x25` 와 관찰 값 `+0x28` 을 **둘 다** 적었다.
  - 에뮬레이터가 실제 콜스택과 맞추려면 **관찰값 `+0x28`** 을 쓰는 게 맞다고 했다 (결과서 판단, 이유는 `[추측]`).
  - 확인 → Q107 (2) `u nt!KiSystemServiceCopyEnd+0x20 L3`.
- 칸 풀기·인자 수 답에는 **영향 없다.**

#### 덤 — 콜스택의 유저 쪽 한 줄은 맞아떨어졌다

- `[관찰]` run44 + `[정적]` run56: 같은 콜스택 맨 아래 `ntdll!NtCreateUserProcess+0x14` = 스텁 `+0x12 SYSCALL` 다음 `+0x14 RET` 자리다. 2.10 표의 출구 `RCX` (돌아갈 자리) 와 같다.

#### 덤 — 입구는 Ghidra 가 못 잡았다 (도구 이야기)

- `[정적]` `KiSystemCall64` (rva `0x6c1840`) 는 PDB 엔 함수인데 **Ghidra 함수가 아니어서** `.asm` 이 없다. 결과서가 `objdump` 로 봤다. 둘레엔 9바이트짜리 가짜 함수 31개 (결과서: RSB 채우기 사다리) 가 잡혀 있었다.
- `[정적]` Ghidra 11.3.2 는 CET 명령 둘을 **잘못 읽는다**: 바이트로는 `RDSSPQ R9` / `CLRSSBSY [R9]` 인데 `RDSSPD ECX` / `XSAVEOPT [R9]` 로 나온다. 그대로 읽으면 "`RCX` (돌아갈 자리) 를 덮어쓴다" 로 **잘못** 읽게 된다. 2.10 표의 `R9` 는 objdump 기준이다.
- `[추측]` `SYSCALL` 이 `KiSystemCall64` 로 오게 하는 설정 줄 (CPU 의 MSR) 은 안 봤다. `_refs/KiSystemCall64.tsv` 에 주소를 집는 줄 셋 (`KiInitializeBootStructures +0x391 LEA` 등) 이 있다. 보안 검색대 문이 켜진 기계면 입구가 `KiSystemCall64Shadow` (rva `0xbcb200`) 일 수 있다 `[추측]` — 안 읽음.

### 2.13 정정 — 틀린 게 아니라 덧붙임 둘

**(1) run29·run34 의 "489칸 모두 함수 시작과 맞음"**

- **인쇄본 (PE 파일) 기준으로는 맞다.** `>> 4` 없이 rva 로 읽은 게 파일 꼴에 맞는 방법이다.
- 다만 부팅 뒤 메모리 칸은 고쳐 쓴 꼴이다. WinDbg 로 `dd nt!KiServiceTable` 을 보면 **파일 값과 다르게** 나올 것이다.
- 이전 문서 (run29·run34) 는 틀린 게 아니라서 손대지 않았다. flow.md 의 같은 문장 셋 (기준 메모, 2.1 `NtCreateUserProcess`, 2.2 스텁 절, 2.10 `ntdll!NtContinue`) 에 "**파일 기준**" 과 run56 을 붙였다.

**(2) 결과서의 오프셋 하나**

- `KeCompactServiceTable` 루프 첫 줄 `MOVZX EAX,byte [RBX]` 는 결과서의 `+0x17` 이 아니라 **`+0x1b`** 다.
  - `.asm` 줄: `+0x1b` 의 주소가 `1405b5a17`, 루프 끝 `+0x3d JNZ 0x1405b5a17`. 결과서는 **주소 끝자리 `…a17`** 을 오프셋으로 옮겨 적은 것으로 보인다.
- run 문서·flow.md·이 글은 `+0x1b ~ +0x3d` 로 썼다. 뜻은 같다. 결과서는 고치지 않았다.

### 2.14 정리: 비유로 한 번 더

1. 관리사무소의 번호부 **인쇄본** (PE 파일 `KiServiceTable`) 엔 담당자 **번지**만 있다. 끝자리는 모두 0.
2. **문 여는 날** (부팅, `KiInitializeKernel +0x257`) 직원 (`KeCompactServiceTable`) 이 옆의 **"서류 몇 장" 표** (`KiArgumentTable`) 를 보며 칸마다 "**번호부에서 거리**" 로 고쳐 쓰고, 한 자리 밀어 **끝자리에 장수**를 적는다.
3. 직원이 관리실 전화기 (ntdll 스텁) 로 단축 번호를 누른다. 첫 서류는 `RCX` 주머니 대신 `R10` 에 든다 — `RCX` 주머니엔 "돌아갈 문" 쪽지가 들어가니까.
4. 창구 (`KiSystemServiceStart`) 는 번호부 칸을 **한 번** 읽고, 끝자리를 떼면 **담당자 자리**, 끝자리만 보면 **가방에서 꺼낼 장수**.
5. 가방 맨 위 "돌아갈 곳 쪽지" 와 빈 주머니 4개를 건너뛰고 (`RSP+0x28` 부터), 장수만큼 **14칸 사다리** 아래쪽으로 옮겨 담는다. 그리고 담당자를 부른다.
6. 끝나면 **답 봉투** (`RAX`) 와 **돌아갈 문 쪽지** (`RCX`) 를 쥐여 주고, 메모지 (`RDX`·`R10`·`XMM0~5`) 는 지워서 `SYSRET` 문으로 내보낸다.
7. 단, 로더 끝 `NtContinue` 손님은 이 문으로 안 나간다. 사물함 메모대로 **순간 이동** (`IRETQ`) 한다.

| 내부 스텁 `Np*` 6개를 누가 부르나 | 범위 밖 | 대기열 번호 없음 (같은 줄) |
| `0x5a` `NtQuerySystemTime` 이 정말 공용 게시판 시계를 읽고 끝나나 | `RtlQuerySystemTime` 안은 안 봤다 `[추측]` | 대기열 번호 없음 |
| `KiLockServiceTable` 이 하는 일 | 이름만 봤다 (`[추측]` 표를 잠금) | 대기열 번호 없음 |
| `R12 ~ R15`, `XMM6 ~ XMM15` 가 정말 그대로인가 | 이 길엔 쓰는 줄이 없어서 "커널 함수가 규약대로 지킨다" 는 `[추측]` | 대기열 번호 없음 (Q107 (4) 에서 `r` 을 찍으면 같이 보인다 `[추측]`) |

- 추천 멈춤점 (run 문서, dast-mentor 참고): `nt!KiSystemServiceCopyEnd+0x20` (`MOV RAX,R10`, `R10` = 함수 주소, 복사 끝난 뒤), `nt!KiSystemServiceStart+0x5b` (`ADD R10,R11` 바로 뒤), ntdll `Nt*` 스텁 `+0x14`.
