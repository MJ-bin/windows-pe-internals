2. **요청 쪽 숫자는 에뮬레이터 것이다.**

3. **오프셋이 네 가지다.** 앞 셋은 run 문서와 같은 규칙이다.
   - 나무 (`├─ +0x..`) 의 숫자 = **ret 자리** (콜스택에 찍힐 값).

### 비유 — 그대로 이어 쓴다

- 프로세스 = **가게**, 커널 = **관리사무소**, syscall = 관리사무소 **신청 창구**, 핸들 = **손잡이**.
- run99 · run129 의 그림 그대로:
  - rpcrt4 = 가게 안 **전화 부서**, ALPC 포트 = **전화선 끝**.
  - winnsi = 전화 신청을 맡기는 **신청 담당**. 번호 없이 회사 이름만 든 **연락 카드** 를 갖고 있다.
  - epmapper = **114 안내**, nsisvc = **nsi 사무실**.
- 이번에 새로 붙는 그림 (run 문서 "결과" 비유를 따름 — run 문서는 이 비유를 `[추측: 비유]` 로 둔다):
  - 전화선으로 오가는 것은 **메시지 한 장** 이다. 맨 앞엔 관리사무소가 보는 **겉칸**, 그 뒤엔 전화 부서끼리 보는 **속칸** 이 있다.
  - bind = 전화마다 맨 처음 하는 **첫인사** — "저 이 사무실 찾고요, 이 **말투** (전송 문법) 들 할 줄 알아요".
  - 호출 ID = 본론마다 붙이는 **문의 번호**. 답장에 같은 번호가 없으면 "엉뚱한 답장" 으로 버린다.
    - run 문서는 이걸 "번호표" 라 불렀다. 이 글은 run129 의 **접수 번호표** (컨텍스트 핸들) 와 헷갈리지 않게 **문의 번호** 로 부른다. 같은 것이다.
  - Context 속성의 `MessageContext` = 메시지에 매다는 **반송 꼬리표** — "이 답장은 우리 부서 누구에게" 라고 적어 보내면, 답장에 그대로 매달려 돌아와야 한다.
  - 비동기 대화 = 말을 건네자마자 **수화기를 내려놓는** 방식. 답이 오면 일꾼 사무실로 **"답 왔어요" 알림** 이 오고, 그때 **답을 따로 받으러** 간다. (run 문서 비유의 "벨" 이 이것이다.)

### 한 줄로 먼저 — 무엇을 얻었나

> **전화 부서 (rpcrt4) 의 대화는 늘 같은 꼴이다. 첫인사 (bind, 0x70 B) 로 "이 말투들 할 줄 알아요" 를 내밀고, 상대가 "그중 이 하나로" 라고 체크 한 칸만 돌려주면 된다. 전화 부서는 그 답에서 딱 세 칸만 본다.**
> **본론 (요청) 엔 문의 번호 (`+0x34`) 와 메뉴 번호 (`+0x3c`) 를 붙인다. 답장 (응답) 은 종류 3 + 같은 문의 번호 + 반송 꼬리표 그대로면 받아들인다.**
> **winnsi 가 하는 대화 넷 (114 첫인사 · 114 질문 · nsi 첫인사 · 메뉴 5) 은 모두 "보내고 끊기" 다. 답은 보내기 syscall 이 아니라, 나중에 따로 부르는 "받기만" syscall 로 온다. 서버 흉내는 이 둘째 부름에 답을 실어 줘야 한다.**
> **nsi 사무실은 번호를 정하지 않는다. 전화국 (rpcrt4) 이 `LRPC-` + 무작위 18자를 지어 주고, 사무실은 그걸 114 에 올린다. 그래서 손님은 114 에 물을 수밖에 없다.**

- 첫째 · 둘째 · 넷째 줄은 `[정적]`.
- 셋째 줄: "비동기면 이 길로 답이 온다" 는 `[정적]`. 다만 **bind 가 정말 비동기로 불리는지** 는 부르는 쪽 인자 전달을 안 읽어서 `[추측]` 이다 (2.3 끝, 동적 1).

## 1. 이번 바퀴의 질문

### 큰 그림에서 어디인가

run124 ~ run129 와 같은 자리, **초기화 밖** 이다. `main` 뒤 프로그램 코드가 웹을 쓸 때의 옆길이고, run129 가 "전화를 건다" 까지 따라간 그 전화의 **속 내용** 을 이번에 연다.

```
cmd.exe 의 부탁 (CreateProcess)
 │  커널: 프로세스 · 주소 공간 · PEB · 첫 스레드
 │  ntdll: LdrInitializeThunk → LdrpInitializeProcess → DLL 들이기 · 전원 켜기
 └─ NtContinue (은퇴) → exe 진입점 → (CRT 점선 상자) → main
                                                        │
      test.exe 는 여기서 RPC 를 안 쓴다 [소스]          │ 웹을 쓰는 프로그램이라면 (요청 쪽 에뮬레이터 로그):
                                                        └─ WinHttpSendRequest                                   (run128)
                                                             └─ F1 작업실 문 열기 → 비서 NotifyIpInterfaceChange
                                                                  └─ 신청 담당 winnsi → 전화 부서 rpcrt4          (run129: 연결 · 상태표)
                                                                       ├─ 114 (epmapper): 첫인사 · ept_map 질문    ← 이번 (선 위 형식)
                                                                       └─ nsi 사무실 (nsisvc): 첫인사 · 메뉴 5 · 7   ← 이번 (선 위 형식 + 서버 쪽)
```

### 왜 이 질문이 지금 왔나

- PE_emulator 에서 샘플 212 개 (악성 203) 가 winnsi 알림 등록에서 멈춘다 (요청 쪽 에뮬레이터 로그).
- run129 가 준 **싼 길** — epmapper 연결을 `0xc0000034` 로 실패시키면 → 1722 → `WinHttpSendRequest` 0 — 은 "깨끗하게 실패" 다. 멈추지는 않지만, 그 뒤 (진짜 HTTP 요청) 는 못 본다.

### 무엇이 궁금했나

1. **bind** — 첫인사 메시지의 칸 (오프셋 · 크기 · 값) 과, 답에서 무엇을 검사하고 틀리면 무슨 오류가 되나.
2. **요청 · 응답 머리** — 본론 메시지의 칸, 답장에서 보는 칸, 그리고 ALPC 오류 (`0xc0000008` 핸들 무효 등) 가 어떤 RPC 오류로 바뀌나.

4. **nsisvc** — 끝점 이름, 프로시저 5 가 입력을 어떻게 검사하고 컨텍스트 핸들을 어떻게 만드나.

### 2.2 한 줄씩 읽는 법

같은 syscall `NtAlpcSendWaitReceivePort` 가 나무에 **네 번** 나온다. 이름은 "보내고 · 기다리고 · 받기" 지만, 인자를 어떻게 주느냐에 따라 보내기만 할 수도, 받기만 할 수도 있다. 두 줄을 골라 읽어 보자.

#### 줄 ①: `├─ +0x62d  NtAlpcSendWaitReceivePort   bind 0x70 B · Flags 동기 0x20000 / 비동기 0`

- **누가**: `rpcrt4!LRPC_CASSOCIATION::Bind` — 연결 객체 (전화선 하나, run129 2.9) 의 "첫인사 하기" 함수.
- **어디서**: call `+0x626`, 돌아올 자리 `+0x62d`.
- **누구를**: `NtAlpcSendWaitReceivePort` — 관리사무소 창구에 "이 메시지 전화선으로 보내 주세요".
- **무엇을 위해**: 0x70 B 첫인사 (bind) 를 보낸다.
  - 동기면 Flags `0x20000` 에 **받을 칸 = 보낸 버퍼 그대로** — 같은 종이에 답이 덮여 온다.
  - 비동기면 Flags `0` 에 **받을 칸 NULL** — 보내기만 하고 곧바로 돌아온다.

#### 줄 ②: `├─ +0xcf   NtAlpcSendWaitReceivePort   받기만` (`IoCompleted` 아래)

- **누가**: `rpcrt4!LRPC_CASSOCIATION::IoCompleted` — "답 왔어요" 알림을 받은 쪽.
- **어디서**: call `+0xc8`, 돌아올 자리 `+0xcf`.
- **누구를**: 같은 `NtAlpcSendWaitReceivePort`.
- **무엇을 위해**: 이번엔 **보낼 메시지 NULL · 보낼 속성 NULL**, 받을 칸만 준다 — 도착한 답장을 꺼내 온다.

정리하면 이번 이야기의 주인공 자리는 **보내기 셋 (bind `+0x626` · 동기 요청 `DoSendReceive +0x14d` · 비동기 요청 `AlpcSend +0x128`) + 받기 하나 (`IoCompleted +0xc8`)** 다 `[정적]`. (그 밖에 얇은 감싸개 `LRPC_CASSOCIATION::AlpcSendWaitReceivePort +0xbb`, 쓸모없는 속성을 버리는 `ValidateCallbackReply +0x146` 도 같은 syscall 을 부른다.)

### 2.3 ★ 대화 넷은 "보내고 끊기" — 답은 둘째 부름으로 온다 `[정적]` (bind 의 동기 / 비동기는 `[추측]`)

run 문서 "요약" 첫 줄 · 2-4. 서버 흉내를 짤 때 **가장 먼저 알아야 할 구조** 다.

#### 새 말 — 받기만 하는 부름 · 완료 통지

- **받기만 하는 부름** = 보낼 메시지 없이 `NtAlpcSendWaitReceivePort` 를 불러, 전화선에 와 있는 답장 한 장을 꺼내는 것 (줄 ②).
- **완료 통지** = 전화선에 답이 도착했다는 알림. rpcrt4 는 비동기 연결 때 `TpAllocAlpcCompletionEx(포트, LrpcIoComplete, …)` 로 이 알림을 스레드 풀 (일꾼 사무실) 에 걸어 둔다 (run129 6절) `[정적]`.
  - 알림이 관리사무소에서 일꾼에게 **어떻게** 가는지 (ntdll `TpAllocAlpcCompletionEx` → `NtAlpcSetInformation` 쪽) 는 안 읽었다 `[공백]` → Q246 ②.

#### 한 걸음씩

1. **보내기** — 비동기 요청은 `AlpcSend +0x128` 이 `NtAlpcSendWaitReceivePort(포트, Flags, 메시지, 속성, 0, 0, 0, 0)` 을 부른다. 받기 칸이 다 0 이다.
   - Flags = `[호출+0x244] & 0x800000` 이면 `0xc00000`, 아니면 0 (상수 이름 모름).
   - 비동기 bind 는 보내기가 0 이면 버퍼를 곧바로 풀고 (`Bind +0x7d0`) **보류 `0xc0021018`** 을 돌려준다 (`+0x7c5`) — run129 2.9 의 "번호표 받고 앉아 계세요".
   - **돌아오는 순간 답은 없다.**
2. **알림** — 답이 도착하면 완료 통지 → `LrpcIoComplete +0xc3` 간접 호출 → `IoCompleted` (`[추측: 간접 대상]`).
3. **받기** — `IoCompleted +0xc8` 이 `NtAlpcSendWaitReceivePort(포트, Flags, NULL, NULL, 새 버퍼, &길이, &받기속성, NULL)`.
   - Flags = 완료 문맥이 있으면 **`0x1000000`** (그때 받기 버퍼 `MessageId` `+0x18` · `CallbackId` `+0x20` 에 문맥 값을 미리 씀, `+0x277 ~ +0x285`), 없으면 0.
   - 버퍼 길이 = `IsPortWithSharedSection` 참이면 `0x1000`, 거짓이면 `0xff00`. 받기 속성 Allocated = **`0xfa000000`**.
4. **나눠 주기** — 받은 메시지의 ALPC 종류 (`+0x04` 아래 바이트) 가 **2** 이고 LRPC 종류 (`+0x28`) 가 1 · 2 · 3 이면 `+0x21c` 가상 호출 `HandleReply` → 응답이면 `UnpackResponse` (2.9), bind 답이면 `CompleteBind` (2.6).
5. **받기가 실패하면** — `0xc0` 은 버리고 끝, `0xc0000041` 은 따로, **그 밖은 `RpcpReportFatalError(2, 상태)` = 치명** (`+0x4a6`, 그 뒤 `+0x4ab` INT3).
   - → 에뮬레이터가 이 자리에서 **모르는 오류를 돌려주면 프로세스가 죽는다**.
   - "쌓인 답이 없을 때" 무엇을 돌려줘야 정상인지는 `[공백]` (동적).

#### 동기 길은?

- 코드엔 있다: Flags `0x20000` + 받을 칸 = 보낸 버퍼. 답이 같은 종이에 덮여 오고, `MessageReceived` → `CompleteBind` / `UnpackResponse` 로 바로 간다 `[정적]`.
- 이 길은 LSA 같은 다른 클라이언트가 쓴다고 짐작한다 `[추측]` (결과서 짐작, 동적 1 로 확인).

#### bind 가 정말 비동기로 불리나 — 짐작의 단계

- 근거: 동기냐 비동기냐는 `LRPC_BIND_CCALL::Bind` 의 첫 정수 인자에서 온다 (`+0x42 MOV R12D,EDX` → `+0x1d7 MOV R8D,R12D`) `[정적]`.
- 그런데 그 인자를 넘기는 `DriveStateForward` 의 인자 전달은 안 읽었다.
- 그래서: winnsi · epmapper 의 bind 가 비동기라는 건 `[추측]` 이다. 동적 1 (`Bind+0x62d` 에서 `edx` = 0 이냐 `0x20000` 이냐) 로 가린다.
- 반면 `ept_map` (EPM 프로시저 8) 과 프로시저 5 는 `Ndr64AsyncClientCall` 로 부르는 비동기 RPC 다 `[정적]` (run129).

비유: 전화 부서는 말을 건네자마자 수화기를 내려놓는다. 답이 도착하면 일꾼 사무실로 "답 왔어요" 알림이 오고, 일꾼이 전화 부서 창구 (`IoCompleted`) 로 가서 답장을 **따로 꺼내 온다**. 서버 흉내가 답을 "보내기" 쪽에 실어 주면 아무도 안 받는다. **꺼내러 오는 둘째 부름** 에 실어 줘야 한다.

- 참고: run129 의 **신호등** (winnsi 가 `WaitForSingleObject` 로 쳐다보는 이벤트) 은 이보다 위층 이야기다. 이번 완료 통지는 전화 부서 안쪽 이야기이고, 둘이 어떻게 이어지는지는 이번 문서들이 적지 않았다.

### 2.4 메시지 한 장의 꼴 — 겉칸 0x28 + 속칸 `[정적]`

run 문서 1-2 · 2-1 · 2-3. 칸 표에 들어가기 전에 공통 모양부터.

#### 새 말 — 겉칸 (`PORT_MESSAGE`) · LRPC 종류

- **겉칸** = ALPC 메시지 맨 앞 **0x28 B**. 문서들은 `PORT_MESSAGE` 라 부른다. 관리사무소 (커널 ALPC) 가 읽는 머리로 알려져 있다 `[추측]` (일반적으로 알려진 설명).
  - `+0x00` `DataLength` · `+0x02` `TotalLength` (각 u16), `+0x04` `Type`, `+0x08 ~ +0x27` `ClientId` · `MessageId` 등.
  - 코드의 셈: 요청 머리에서 `TotalLength = DataLength + 0x28` (`InitializeRequestAndAttributes +0x192 ~ +0x1a1` · `+0x1a7` · `+0x2ea`) `[정적]`. 즉 `DataLength` 는 겉칸을 뺀 길이다. 첫인사의 `0x48` · `0x70` 도 같은 모양이다.
  - `+0x04` 아래 바이트는 **ALPC 메시지 종류** 다 — 2 = 답장 (reply), 5 = 포트 닫힘, 1 = 서버의 콜백 요청, `0xb` 따로 (`IoCompleted +0x12f ~ +0x19d`) `[정적]` (이름은 `[이름 추측]`).
- **속칸** = 그 뒤, 전화 부서끼리 읽는 LRPC 머리. 맨 앞 **`+0x28` 이 LRPC 종류** 다 `[정적]`:

  | `+0x28` | 뜻 (이름은 `[이름 추측]`) |
  |---|---|
  | 0 | 요청 (본론) |
  | 1 | bind (첫인사) — 답도 1 |
  | 2 | fault (못 했어요) |
  | 3 | 응답 (본론 답) |
  | 6 | 콜백 (동기 `SendReceive` 가 `UnpackResponse` 앞에서 따로) |
  | 10 · 11 | 내부에서 바꿔 씀 |

#### 새 말 — fault

- 서버가 본론에 답하는 대신 "**못 했어요, 까닭은 이 번호**" 라고 돌려주는 답장. 오류 번호는 `+0x30` 에 든다 `[정적]`.
- 그 번호는 `SanitizeErrorCodeFromServer` 를 거친다 — **0 이거나 치명 예외 14종 이면 `0x6c0`** 으로 바꾸고, 그 밖은 그대로 호출의 RPC 오류가 된다 `[정적]` (14종은 run129 해설 2.11).

#### 조심 — `+0x30` 은 메시지마다 뜻이 다르다

- 요청의 `+0x30` = 깃발, fault 의 `+0x30` = 오류 번호, 응답 (3) 에선 `+0x30` 의 4 비트만 "큰 응답" 표시로 본다 `[정적]`.

비유: 메시지 한 장 = 편지지. 맨 위 0x28 칸은 관리사무소가 보는 **겉칸** (길이 · 종류 · 보낸 사람), 그 아래가 전화 부서끼리 보는 **속칸**. 속칸 첫 칸에 "이건 첫인사 (1) / 본론 (0) / 답 (3) / 못 했어요 (2)" 를 적는다.

### 2.5 첫인사 보내기 — bind 0x70 B `[정적]`

run 문서 1-1 · 1-2 (`Bind__4e330.asm`).

#### 새 말 — bind

- 본론을 말하기 전에 "**저는 이 사무실 (인터페이스) 을 찾고, 이 말투들을 할 줄 알아요**" 를 먼저 맞추는 단계로 알려져 있다 `[추측]` (일반적으로 알려진 설명).
- 코드에서는 LRPC 종류 1 의 메시지이고, `LRPC_CASSOCIATION::Bind` (rva `0x4e330`) 가 만든다 `[정적]`.

#### 새 말 — 전송 문법 (NDR 2.0 · NDR64)

- 함수 인자 값을 바이트로 줄 세우는 **규칙 (말투)** 으로 알려져 있다 `[추측]` (일반적으로 알려진 설명). 두 쪽이 같은 말투를 써야 서로 알아듣는다.
- rpcrt4 가 아는 말투는 셋이고, 비트 하나씩을 쓴다 `[정적]` (GUID rva `0xebaf8` · `0xebb10` · `0xebb88`, 비트 표 `0xeb9c0`):
  - **1 = NDR 2.0** (`8a885d04-1ceb-11c9-9fe8-08002b104860` v2)
  - **2 = NDR64** (`71710533-beba-4937-8319-b5dbef9ccc36` v1)
  - **4** = `b4537da9-3d03-4f6b-b594-52b2874ee9d0` v1

#### 새 말 — 제안 마스크 · 슬롯 번호

- **제안 마스크** (`+0x48`) = "할 줄 아는 말투" 비트를 OR 한 값. 인터페이스의 문법 표마다 비트를 켠다. 표에 없는 문법이면 `0x6c2` `[정적]`.
  - **winnsi · EPM 둘 다 3** (NDR 2.0 + NDR64).
- **슬롯 번호** (`+0x4c` · `+0x4e` · `+0x50`, u16 셋) = 말투 1 · 2 · 4 마다 붙이는 **줄 번호**. 연결 객체의 표 (`this+0x58`) 에서 그 문법 결합이 몇 번 칸인지다 `[정적]`.
  - 이 번호는 나중에 **본론 머리 `+0x38` 에 그대로** 간다 (2.7). 서버는 이걸 보고 "아, 이 본론은 그 말투로 왔구나" 를 안다 `[정적]`.

비유: 전화를 받자마자 "nsi 사무실 맞죠? 저는 **옛 말투 (1) · 새 말투 (2)** 둘 다 해요" 하고 체크박스 두 칸에 체크해 내민다. 말투 옆에는 "이 말투로 하면 몇 번 줄" 이라는 **줄 번호** 를 적어 둔다.

### 2.8 첨부물 — 반송 꼬리표 (`MessageContext`) 는 지어내면 안 된다 `[정적]`

run 문서 2-2.

#### 새 말 — 메시지 속성 · Context 속성

- **메시지 속성** = 메시지에 딸려 가는 **첨부물 칸** 들. run129 의 "빈 봉투" (들어오는 속성) 가 바로 이 첨부물을 받는 봉투였다.
  - 맨 앞 8 B = `{Allocated, Valid}`. 이름으로 보아 Allocated = 마련한 칸, Valid = 이번에 실제로 채운 칸 `[추측: 이름]`.
  - 이어서 켜진 속성이 이 차례로 붙는다 `[정적]`: **Security (`0x80000000`) → DataView (`0x40000000`) → Context (`0x20000000`) → Handle → Token → Direct → WorkOnBehalf (`0x02000000`)**.
  - 전체 크기 = `RpcpAlpcpGetHeaderSize(마스크)` = 8 + 켜진 속성 크기 합 (Security · Handle · Token `0x18`, DataView · Context `0x20`, Direct · WorkOnBehalf 8).
- 무엇이 켜지나:
  - 보통 요청: Allocated `0xfe000000`, Valid **`0xa2000000`** (Security + Context + WorkOnBehalf). 큰 view 가 있으면 DataView 를 더한다.
  - "빠른" 길 (`[바인딩+0x178] & 0x40` 등) 은 Security 없이 `0x20000000`.
  - 첫인사 (bind) 는 Context 하나 (2.5).
- **Context 속성** = 그 첨부물 중 하나. 안의 `MessageContext` 칸에 **클라이언트가 자기 호출 객체 포인터** 를 넣는다 `[정적]`.

#### 왜 지어내면 안 되나 — 단계로

1. 답장이 오면 `IoCompleted` 가 받기 속성의 Context 칸 (속성 칸 `+0x48`) 에서 호출 객체를 꺼낸다 (`+0x1ae ~ +0x1b6` · `+0x4c0 ~ +0x4c8`).
2. 그 값이 **0 이면 메시지를 버린다** (`+0x4cd` · `+0x4d0`).
3. 객체 `+0xc` 에 `0x1000` 비트가 있어야 호출 객체로 친다 (`+0x1b6`).
4. 그러니 서버 흉내는 **요청 때 받은 값을 그대로** 돌려줘야 한다. 다른 값을 지어 넣으면 엉뚱한 주소를 호출 객체로 읽게 된다.

#### 호출 ID 와 무엇이 다른가

- **반송 꼬리표** (`MessageContext`) = 이 답장을 **누구에게** 넘길지 (배달) — `IoCompleted` 가 본다.
- **문의 번호** (`+0x34` 호출 ID) = 넘겨받은 답장이 **내 질문의 답이 맞는지** (확인) — `UnpackResponse` 가 본다 (2.9).
- 둘 다 맞아야 답이 받아들여진다.

비유: 택배에 "**3번 창구 김 대리 앞**" 반송 꼬리표를 붙여 보내면, 상대는 답장에 그 꼬리표를 그대로 붙여 돌려줘야 한다. 꼬리표가 없으면 우편실이 답장을 버린다. 김 대리는 답장을 받은 뒤 **문의 번호** 가 맞는지 한 번 더 본다.

### 2.10 ALPC 오류 → RPC 오류, 그리고 "다시 시도" `[정적]`

#### 표 (요약 — 전체는 run 문서 2-5)

보내기 세 자리가 **표를 저마다 따로** 들고 있다.

| NTSTATUS (이름은 `[이름 추측]`) | bind (`Bind__4e330`) | 동기 요청 (`DoSendReceive`) | 비동기 요청 (`AlpcSend`) |
|---|---|---|---|
| `0` | 성공 (비동기 `0xc0021018`) | 성공 | 성공 |
| **`0xc0000008`** (핸들 무효) | **`0x6bf`** | **`0x6bf`** | **`0x6bf`** |
| `0xc0000017` · `0xc0000044` · `0xc000009a` | `0xe` | `0xe` | `0xe` |
| `0xc0000022` | `0x6bf` | `0x6f7` | `0x6f7` |
| `0x102` | `0x71a` | `0x71a` | `0x71a` |
| 그 밖 | `0x6bf` | **`0x6be`** | **`0x6be`** |

- RPC 오류 뜻: `0x6ba` 1722 서버 없음 · `0x6be` 1726 · `0x6bf` 1727 (실행 안 되고 실패) · `0x6c0` 1728 프로토콜 오류 · `0x71a` 1818 취소.

#### 요청서 짐작과 다른 곳 — `6` 이 아니라 `0x6bf`

- 요청서는 `RpcpStrictAlpcToRpcStatus` (rva `0x99d70`, 표 `0xed0d0` 15쌍) 를 짚었다. 그 표는 `0xc0000008 → 6` 이고, 표에 없으면 치명이다.
- 그런데 이 함수를 부르는 쪽은 **서버** (`HandleBindRequest` · `ReplyWithSmallData` …) 다. 클라이언트 길엔 안 쓰인다 `[정적]`.
- 그래서 RPCSS 22 샘플의 "핸들 0 으로 보내기 → `0xc0000008`" 뒤 rpcrt4 가 돌려주는 값은 **`0x6bf`** 다.
- 그게 combase `+0x55b5a` 의 "주소 `0x4` 읽기" 로 어떻게 이어지는지는 rpcrt4 쪽에서 알 수 없다 — combase 몫이다.

#### 새 말 — 다시 시도 종류

- 어떤 RPC 오류는 "한 번 더 해 보면 될지도" 로 분류된다 `[정적]`.
  - `GetErrorClass` 가 **`0x6ba` · `0x6bf`** 를 "다시 시도 가능" 으로 본다 (`+0x9 ~ +0x25`). `0x6be` 는 불가.
  - `AttemptRetry` 는 카운터 `+0x2d8` < 4 · `+0x2da` < `0x101` 일 때만 → **첫 시도 + 최대 3번 다시**.
- 다시 시도를 실제로 실행하는 길 (`HandleSendReceiveFailure → RetryCall → DriveStateForward → DoSendReceive`) 은 `[추측: 가상 호출 대상 안 확인]`, 정말 도는지는 `[공백]` (동적 6).
- 헷갈리지 말 것: run129 해설 2.8 의 "재시도는 거의 없다" 는 **`AlpcConnect` 안에서** 연결을 다시 거는 이야기 (`0xc00002a0` 하나) 였다. 이번 것은 그보다 위, **호출 하나 단위** 의 다시 시도다.
  - 그래서 run129 의 T1 (서버 모델 없는 포트에 `0xc0000034` → `0x6ba`) 은 그대로 맞지만, `0x6ba` 가 다시 시도 종류라 **한 호출에서 연결 요청이 최대 4번** 올 수 있다 (run 문서 "PE_emulator 쪽" 6, 실제로 도는지는 동적 6).

비유: 관리사무소가 "그 손잡이 없는데요" (`0xc0000008`) 라고 하면, 전화 부서는 손님에게 "**전화가 안 걸렸어요**" (1727) 라고 전한다. 이건 "다시 걸어 볼 만한" 실패라서, 최대 세 번 더 걸어 볼 수 있다.

### 2.11 114 에 내는 질문 탑 — 4층 70 B `[정적]`

run 문서 3-1 (`TowerConstruct.asm`, `ResolveEndpoint__59d38 +0xba`). run129 에서 탑을 "질문지 묶음" 이라고만 했는데, 이번에 층이 보였다.

#### 새 말 — 층 (floor) · LHS / RHS · 프로토콜 ID

- **층** = 탑을 이루는 한 칸. 한 층은 **[LHS 길이 u16][LHS][RHS 길이 u16][RHS]** 꼴이다 `[정적: 쓰는 줄의 모양]`.
  - LHS / RHS 는 "왼쪽 / 오른쪽" 이란 이름으로 알려져 있다 `[추측]` (일반적으로 알려진 설명). 코드에서 LHS 는 **프로토콜 ID 1 B 로 시작** 하고, RHS 엔 부 버전이나 끝점 이름 같은 값이 든다 `[정적]`.
- **프로토콜 ID** = 그 층이 무슨 층인지 알리는 번호 `[정적]`:
  - **`0x0d`** = UUID 층 (뒤에 GUID 16 B + 주 버전)
  - **`0x0c`** = ncalrpc 의 층 (`0x0b` = ncacn_*, `0x0a` = ncadg_*) — 이름은 `[이름 추측]`
  - **`0x10`** = ncalrpc 끝점 층

#### 질문 탑의 꼴

- 맨 앞 u32 `tower_length` (끝점 없을 때 **`0x42`**) + u16 층 수 **4** + 층 넷.

| 층 | LHS | RHS | 뜻 |
|---|---|---|---|
| 1 | 길이 `0x13` · **`0x0d`** · 인터페이스 GUID · 주 버전 | 길이 2 · 부 버전 | 찾는 사무실 (nsi `7ea70bcf…` 1.0) |
| 2 | 길이 `0x13` · **`0x0d`** · 전송 문법 GUID (`8a885d04-…`) · 2 | 길이 2 · 0 | 말투 NDR 2.0 v2.0 |
| 3 | 길이 1 · **`0x0c`** | 길이 2 · 0 | ncalrpc |
| 4 | 길이 1 · **`0x10`** | 길이 **2** + `00 00` | 끝점 — **비워 둠** |

- 총 **70 B** (4 + `0x42`).
- 끝점 문자열이 `0xffff` 를 넘으면 `0xe`, 프로토콜 문자열이 `ncalrpc` · `ncacn_` · `ncadg_` 가 아니면 `0x6a8`.
- 인자 출처: 인터페이스 ID = `[조회+0x44]`, 전송 문법 = `[조회+0x58]`. 조회 객체 `+0x40 ~ +0xa0` 은 클라이언트 인터페이스 구조체 (0x60) 의 복사라서, 2층은 인터페이스의 `TransferSyntax` = **NDR 2.0 하나** 다 (2.5 끝 "헷갈리지 말 것").

#### 이 탑을 어떻게 보내나

- `LookupNextChunk +0x11d` (ret `+0x122`) → `Ndr64AsyncClientCall(프록시 0xe11e8, 프로시저 8, …, 바인딩, 객체 UUID, 질문 탑, SID NULL, 끝점 핸들 in/out, **max_towers 4** (`+0xe6`), &탑 개수, 탑 포인터 4개 배열, &상태)` `[정적]`.
- 동기는 프로시저 3 (SID 없음) / 7 (SID 있음). MS-RPCE EPM 번호 (`ept_map` 3 · `ept_map_auth` 7 · `ept_map_auth_async` 8) 와 맞아 보인다 `[추측: 이름 대응]`.

비유: 114 에 내는 질문지를 **4층 탑** 으로 쌓는다. 1층 "찾는 사무실 이름표", 2층 "쓸 말투", 3층 "같은 건물 내선", 4층 "번호 칸 — **비워 둠** (그걸 물어보는 거니까)".

### 2.12 114 의 답 — 세 군데만 보고, 최소 탑 하나면 된다 `[정적]` (NDR 틀은 `[공백]`)

#### 답에서 보는 것 (요약 — 전체는 run 문서 3-2)

#### 서버 흉내가 돌려줄 최소 탑 (끝점 `LRPC-emu` 예, run 문서 3-3)

- `tower_length = 0x40 + 끝점 길이 (NUL 포함)` → `LRPC-emu` 는 `0x49`, 총 77 B.
- 층 수 4 · 1층 nsi `7ea70bcf…` v1.0 · 2층 NDR 2.0 v2.0 · 3층 `0x0c` · 4층 `0x10` + RHS 길이 9 + `"LRPC-emu\0"`.
- 4층만 바이트로 보면 이렇다 (결과서 3-3 의 한 줄):

  ```
  +0x3f  01 00  10  09 00  4c 52 50 43 2d 65 6d 75 00     4층 ← RHS 길이 9, "LRPC-emu\0"
  ```

  - 전체 바이트 배열은 결과서 3-3. GUID 는 메모리 모양 그대로 적혀서, 1층의 `7ea70bcf` 가 `cf 0b a7 7e` 로 시작한다.

#### 아직 모르는 것 — 탑을 싸는 겉봉 (NDR 틀)

- 이 탑은 `ept_map` 응답의 **스텁 데이터 안** 에 든다. 그 안의 차례 (`entry_handle` 20 B → 개수 → 탑 배열 → 상태) 는 **안 읽었다 `[공백]`**. 공개 EPM IDL 순서로 짐작할 뿐이다 `[추측]`.
- 프로시저 8 형식 문자열 (프록시 `0xe11e8` → 형식 `0xefeb2`) 을 풀어야 닫힌다 → Q246 ③, 진짜 바이트는 동적 4.

비유: 114 의 답장에서 전화 부서는 "**층이 4개인가, 3층이 내선인가, 4층 번호 칸이 제대로 끝나는가**" 만 본다. 1 · 2층에 뭐라고 썼는지는 읽지도 않는다. 번호 칸에 적힌 이름을 받아 들고, 그 이름으로 nsi 사무실에 전화를 건다.

### 2.13 nsi 사무실은 번호를 정하지 않는다 — 동적 끝점 `[정적]`

run 문서 4-1 (`ServiceMain.asm` · `NsiStartRpcServer.asm`). 이번에 처음 서버 쪽을 열었다. 서버 쪽 프로시저 5 · 6 · 7 구현은 **nsisvc 안에 있었다** (요청서의 "껍데기뿐이면 멈춤" 은 해당 없음).

#### 사무실 문 여는 차례

- `ServiceMain +0xed NsiServiceInitialize` → **`+0xf6 NsiStartRpcServer`** → `+0x166 NsiServiceNotifyStart` (`RtlPublishWnfStateData`).
- `NsiStartRpcServer`:
  1. `+0xac` 출입 명부 (SD) 만들기 (SDDL 원문은 결과서 4-1).
  2. **`+0x123 RpcServerUseProtseqW(L"ncalrpc", 10, SD)` — 끝점 인자 없음.**
  3. `+0x1a1 RpcServerRegisterIf3(&인터페이스 0x6420, …, Flags 9, MaxCalls 1234, 0, NsiSecurityCallBack, SD)` (Flags 9 = `AUTOLISTEN` + `ALLOW_SECURE_ONLY` `[이름 추측]`).
  4. 정리 이벤트 · 대기 (`+0x1fb` · `+0x28a`).
  5. `+0x2de RpcServerInqBindings` → **`+0x337 RpcEpRegisterW(&인터페이스, 벡터, NULL, L"NSI server endpoint")`**.
  6. 성공이면 전역 `RpcServerInitialized = 1`.

#### 새 말 — 동적 끝점

- 서버가 끝점 이름을 **정하지 않고**, RPC 런타임이 그때그때 **지어 주는** 끝점 `[정적: 코드의 모양]`.
- 짓는 곳은 rpcrt4 서버 쪽 `LRPC_ADDRESS::ServerSetupAddress` (rva `0x971d0`):
  - `L"LRPC-"` (rva `0xeced8`, `+0xc4` · `+0xd1`) + `+0xe8 ProcessPrng` 난수 9 B 를 **소문자 16진 18자** → 23자.
  - 이미 있으면 (`0x6cc`) 다시 짓는다.
  - (`RpcServerUseProtseqW` → `ServerSetupAddress` 사이는 안 읽었다 — run 문서 나무의 `⇒`.)

#### 그래서 run129 의 "번호 칸 빈 카드" 와 맞물린다

- 클라이언트 쪽: winnsi 카드엔 끝점이 없고, 인터페이스의 기본 끝점 수도 0 (run129 해설 2.4) `[정적]`.
- 서버 쪽: nsisvc 서버 인터페이스 (rva `0x6420`) 도 **기본 끝점 0개** 이고, 이름은 난수다 `[정적]`.
- → 번호를 미리 아는 사람이 없다. **114 에 물어야만** 한다. run129 의 "`ept_map` 을 건너뛸 길은 없다" 의 서버 쪽 까닭이다.

#### 서버 인터페이스 · 메뉴판

- `7ea70bcf…` v1.0, NDR 2.0, 깃발 `0x6000000`, 기본 끝점 0개.
- 디스패치 표 (`0x64f0`, 9개): 프로시저 0 ~ 6 · 8 = `NdrServerCall2` (동기), **7 = `NdrAsyncServerCall` (비동기)**.
- 서버 함수: 5 = `RpcNsiRegisterChangeNotification` (`0x27c0`), 6 = `RpcNsiDeregisterChangeNotification` (`0x16f0`, 안 읽음), 7 = `RpcNsiRequestChangeNotification` (`0x1010`).

#### 새 말 — 인터페이스 콜백

- 손님 호출이 서버 함수에 닿기 **전에** 먼저 불리는 **문지기 함수** — `RpcServerRegisterIf3` 에 넘긴 `NsiSecurityCallBack` (`0x2e80`) `[정적]`.
- 하는 일: `+0x5a RpcServerInqCallAttributesW` 가 실패면 그 오류. 성공이면 `AuthenticationLevel` 이 **6 미만 → `5`**, 6 이상 → 0 (`+0x83` · `+0x88` · `+0x8a`).
  - 결과서: 디컴파일이 이 검사를 빠뜨려서 `.asm` 으로 읽었다.
- 클라이언트 (`RpcBindingSetAuthInfoW(…, 6, 10)`, run129 해설 2.4) 가 수준 6 을 서버에 어떻게 알리는지는 `[공백]`. 첫인사 · 본론 머리엔 인증 칸이 없고, ALPC Security 속성 (요청 `Valid` 에 늘 있음) 으로 간다고 짐작 `[추측]`.
- 흉내는 "허용" 으로 두면 된다.

비유: nsi 사무실은 개업할 때 번호를 직접 정하지 않는다. 전화국 (rpcrt4) 이 "`LRPC-` + 무작위 18자리" 번호를 주고, 사무실은 그 번호를 "NSI server endpoint" 라는 메모와 함께 **114 에 올린다**. 문 앞엔 문지기 (인터페이스 콜백) 가 서서 "비밀 통화 등급 (6) 이상만" 들여보낸다.

- 변경이 쌓여 있으면 하나 꺼내 바로 완료한다 (`+0x19b` · `+0x256` · `+0x3fb`).
- → run129 2.13 ⑧ "프로시저 7 은 답하지 않는다" 가 **서버 코드와 맞다**.

1. 보내는 부름: `Flags & 0x20000` → 동기 (같은 버퍼에 답 덮어쓰고 0). 아니면 비동기 → **즉시 0**, 답은 나중 (2.3).

4. 답 `Valid`: Context 켜고, DataView · Handle 끄기.
5. 오류를 주고 싶으면 2.10 표의 NTSTATUS 만. 대화 오류는 fault (`+0x28` 2 + `+0x30`) 가 가장 안전.

### 2.18 flow-writer 대조 · 정정

### 2.19 정리 — 비유로 한 번 더

- 전화 부서 (rpcrt4) 의 대화는 늘 **첫인사 → 본론** 이다.
  - 첫인사 (0x70 B): "이 사무실 찾고요, 옛 말투 · 새 말투 할 줄 알아요 (마스크 3), 말투마다 줄 번호는 이거요". 상대는 **체크 한 칸** 만 돌려주면 된다. 전화 부서가 보는 건 세 칸뿐, 길이는 안 본다.
  - 본론: "본론 (0) · **문의 번호** · 줄 번호 · **메뉴 번호**" + `+0x68` 부터 내용물. 답장은 "답 (3) · 같은 문의 번호" + `+0x40` 부터 내용물.
  - 모든 메시지엔 **반송 꼬리표** 가 매달려 가고, 답장에 그대로 돌아와야 우편실이 버리지 않는다.
- winnsi 의 대화 넷은 다 **보내고 끊기** 다. 답은 일꾼이 알림을 받고 **따로 꺼내러 오는** 둘째 부름에 실린다. 그때 모르는 오류를 주면 가게가 죽는다.
- 114 에는 **4층 질문 탑** 을 낸다. 114 의 답장 탑에서 전화 부서는 층 수 · 3층 · 4층 이름만 본다.
- nsi 사무실은 번호를 **무작위로** 받아 114 에 올려 두니, 손님은 114 를 거칠 수밖에 없다.
- nsi 창구는 메뉴 5 신청서를 **읽지 않고** 위층에 올린 뒤 접수 번호표를 주고, 메뉴 7 은 **걸어 둔다**.
