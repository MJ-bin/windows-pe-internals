### 비유: 그대로 이어 쓴다

- 커널 = **관리사무소**, 스레드 = **직원**, CONTEXT = **업무 시작 메모**, `ContextFlags` = 메모 맨 위 **체크박스**.
- 유저 스택에 맡긴 원래 메모 = **사물함 메모** (run16). 유저 스택 = 직원 **작업대** (run11).
- CET 그림자 스택 = **경비실 장부** (run29), XState = 메모 뒤에 붙는 **별지** (run42).
- `KUSER_SHARED_DATA` = 관리사무소가 붙여 두는 **공용 게시판** (run18).
- run 문서가 이번에 쓴 그림 (그대로 가져온다):
  - 관리사무소가 원래 메모를 사물함에 넣기 전에 **"메모 크기"** 를 잰다.
  - 자를 빌려 주는 게 `Length2`, 실제로 재는 건 `Length3`.
  - `Length2` 는 자만 건네는 게 아니라 **공용 게시판 주소 한 장**을 같이 붙여 준다 (그게 `r9` 상수).
  - 직원이 경비실 장부 (CET) 를 안 쓰면, `Length3` 는 그 게시판을 **보지도 않고** 정해진 크기 `0x4ff` 를 낸다.

### 한 줄로 먼저: 무엇을 얻었나

| 질문 | 답 (run 문서 그대로) |
|---|---|
| 1. `Length2` 가 rva `0x495440` 맞나 | **맞다.** 24바이트, PDB 이름 그대로 `[정적]` |
| 2-(a). `rcx`·`rdx` 그대로 넘기나 | **예** `[정적]` |
| 2-(b). `r8`·`r9` 는 | `r8` = 호출자 값 **그대로**. `r9` = **상수 `0xFFFFF780000003D8`** 로 덮어씀 (`&SharedUserData->XState`) `[정적]` |
| 2-(c). 꼬리 호출인가 | **아니다. 보통 CALL** (`+0xe`). 돌아와서 스택 정리하고 RET 만. `eax` 그대로 `[정적]` |
| 3. `0x4ff` 가 그래도 나오나 | **비-CET 스레드면 예** (`ecx = 0x10001b`, `r8 = 0`). 이 길에선 `r8`·`r9` 를 안 읽어서, CPU·VM 설정과 무관한 상수 `[정적]` |
| (덤) CET 스레드면 | `0x4ff` **아님.** `0x32f + RtlpGetEntireXStateAreaLength2(…)`, 안 풂 `[정적]` |
| run44 사진과 | **어긋나지 않는다** (길이 하나를 집어내진 못함) `[관찰]`+`[정적]` |
| PE_emulator 쪽 | "인자 그대로" `[추측]` → `[정적]`. 단 문구를 "`rcx`·`rdx`·`r8` 그대로, **`r9` 는 상수**" 로 |

이 글에서 붙잡아 둘 세 줄:

> **(1) "그대로 넘긴다" 는 거의 맞았다. 딱 하나, 넷째 인자 `r9` 만 상수로 바꿔 끼운다.**
>
> **(2) 그래도 `0x4ff` 는 그대로다. 비-CET 길은 그 `r9` 를 읽기 전에 갈라져 나가기 때문이다.**
>
> **(3) run44 사진은 "`0x4ff` 와 안 어긋난다" 까지만 말한다. 16바이트 맞춤이 끝자리를 지워서다.**

## 1. 이번 바퀴의 질문

### 큰 그림에서 어디인가

```
cmd.exe 의 부탁 → 커널 NtCreateUserProcess → NtResumeThread
 test.exe 첫 스레드 (커널)
  KiStartUserThread → PspUserThreadStartup                     출근 도장 (run15)
   └─ +0xb3  PspInitializeThunkContext                         바꿔 끼우기 (run16)
        ├─ +0xa7  RtlGetExtendedContextLength2                 메모 크기 재기   ← 이번
        ├─ (+0x17a ~ +0x187)  사물함 자리 = 원래 Rsp − 크기
        └─ …  사물함에 원래 메모 넣기, 출발 메모 = LdrInitializeThunk
  ═▶ IRETQ
 test.exe 첫 스레드 (유저)
  ntdll!LdrInitializeThunk → 로더 … → NtContinue 은퇴 → (CRT) → main
```

- `+0x..` 는 ret 자리다. 괄호 친 `(+0x17a ~ +0x187)` 은 호출이 아니라 함수 안 줄이다.
- flow.md 로는 **2.3 `PspInitializeThunkContext` 절 3번** ("맡길 자리 `R15` = 원래 `Rsp` − 문맥 길이") 바로 아래다.
- run16 에선 "길이는 `+0xa2` 가 구한 값" 까지만 적었다. 이번엔 **그 자 안쪽**을 열었다.

### 왜 이 질문이 지금 왔나

- `../PE_emulator` (진짜 nt·ntdll 과 같은 이름·호출관계로 짓는 에뮬레이터) 가 이 길이를 **`0x4ff`** 로 쓰고 있다.
- 셈은 `Length3` 코드로 했다. 그런데 실제로 불리는 건 `Length2` 다.
- 그래서 "`Length2` 는 `Length3` 에 인자를 **그대로** 넘긴다" 를 `[추측]` 으로 달아 두었다 (요청서 "배경").
- 그 추측 한 줄의 근거를 `[정적]` 으로 올려 달라는 요청이다. 큰 분석은 아니다.

### 무엇이 궁금했나

요청서 질문 셋:

1. `RtlGetExtendedContextLength2` 의 주소가 rva `0x495440` 이 맞나?
2. 이 함수는 `Length3` 에 무엇을 넘기나?
   - (a) `rcx` (체크박스 값), `rdx` (길이를 받을 칸 주소) 를 그대로?
   - (b) 셋째·넷째 `r8`·`r9` 는 무엇으로?
   - (c) 꼬리 호출 (`JMP`) 인가, 보통 `CALL` 인가?
3. `PspInitializeThunkContext +0xa2` 가 넘기는 값으로 `Length3` 가 정말 `0x4ff` 를 내나?

### 바퀴 전에 알던 것

- `[정적]` (run16) `PspInitializeThunkContext +0xa2` 의 결과가 맡긴 문맥 길이다. 맡길 자리 `R15 = (원래 Rsp − 길이) & ~0xf`.
- `[정적]` (run29) `KiContinuePreviousModeUser +0x133` 은 `Length3` 를 **직접** 부른다 (`Length2` 를 안 거침).
- `[정적]` (run42) 체크박스는 비-CET 면 `0x10001b`, CET 면 `0x10005b`.
- `[추측]` (PE_emulator) `Length2` → `Length3` 인자 그대로, 길이 `0x4ff`.
- `[관찰]` (run44) 맡긴 문맥 주소가 `0x4ff` 셈과 맞는다.

## 2. 찾은 것

### 2.1 한눈에

run 문서 "호출 관계" 그대로, 조금 줄였다.

```
PspInitializeThunkContext
 │  +0x69 ~ +0x8d  _KTHREAD+0x74 bit20 → R14D (0 / 0x800), R12D (0x10001b / 0x10005b)
 ├─ +0xa7  RtlGetExtendedContextLength2   (ecx = R12D, rdx = &[RBP], r8d = R14D)
 │       │  +0x4   r9 = 0xFFFFF780000003D8 (&SharedUserData->XState)
 │       └─ +0x13  RtlGetExtendedContextLength3   (rcx·rdx·r8 그대로)
 │               ├─ +0x2f  RtlpValidateContextFlags2   분기 칸 [RSP+0x20] (비-CET 1)
 │               │  (XState 블록 +0x88 ~ +0xdf — 비-CET 는 건너뜀)
 │               ├─ +0xc6  RtlpRemoveArchDisallowedXStateFeatures
 │               ├─ +0xd6  RtlpGetEntireXStateAreaLength2
 │               │  +0xf1  *rdx = 길이 (비-CET 0x4ff)
 │  +0xb1  [RBP] 읽음
 │  +0x17a ~ +0x187  R15 = (원래 Rsp − 길이) & ~0xf   (맡길 자리, run16)
 └─ …
```

- 모두 `[정적]` 이다.
- 호출 기호 (`├─`, `└─`) 옆 `+0x..` 는 ret 자리, 기호 없이 들여쓴 `+0x..` 는 그 함수 안 줄이다.
- `Length3` 아래 둘째·셋째 호출 (`+0xc6`, `+0xd6`) 은 **XState 블록 안**이라 비-CET 스레드는 **안 탄다**. 그림엔 "있다" 는 것만 그렸다.

### 2.2 한 줄씩 읽는 법

#### 한 줄 읽기 ①: `├─ +0xa7  RtlGetExtendedContextLength2   (ecx = R12D, rdx = &[RBP], r8d = R14D)`

- **누가**: `PspInitializeThunkContext` — 관리사무소가 새 직원의 출발 메모를 바꿔 끼우는 중이다.
- **어디서**: `+0xa2` 에서 부르고, 돌아올 자리가 `+0xa7` 이다.
- **누구를**: `RtlGetExtendedContextLength2` (메모 크기를 재는 자).
- **무엇을 위해**: 원래 메모를 사물함에 넣기 전에 **사물함을 얼마나 비울지** 알려고.
  - `ecx` = 체크박스 값, `rdx` = "재고 나서 크기를 여기 적어 줘" 칸 주소 (`[RBP]`, `+0x53` 에서 미리 0 으로 비움), `r8d` = 별지 종류 표시.
- 태그 `[정적]`.

#### 한 줄 읽기 ②: `│  +0x4   r9 = 0xFFFFF780000003D8 (&SharedUserData->XState)`

- **누가**: `RtlGetExtendedContextLength2` 자신.
- **어디서**: 자기 안 `+0x4` (10바이트짜리 명령 하나, `+0x4 ~ +0xd`).
- **누구를**: 부르는 줄이 아니다. 레지스터 `r9` 에 값을 **넣는** 줄이다.
- **무엇을 위해**: 다음 줄에서 부를 `Length3` 의 **넷째 인자**를 채우려고. 값은 상수, 뜻은 "공용 게시판의 XState 칸 주소" (2.4).
- 태그 `[정적]`.

### 2.3 `Length2` 는 다섯 줄짜리다 — 질문 1·2

`Length2` 는 rva `0x495440`, **24바이트**다. 명령이 다섯 개뿐이다 (run 문서 표 그대로).

| 줄 | 하는 일 | 표시 |
|---|---|---|
| `+0x0` | 스택 `0x28` 잡기 (그림자 공간 + 정렬) | [정적] |
| `+0x4` | `r9` ← 상수 `0xFFFFF780000003D8` | [정적] |
| `+0xe` | **CALL** `RtlGetExtendedContextLength3` | [정적] |
| `+0x13` | 스택 되돌림 | [정적] |
| `+0x17` | RET — `eax` 안 건드림 | [정적] |

이걸 질문별로 읽으면:

- **질문 1** — 주소 **맞다**. `.asm` 머리, `_index.tsv`, `pdb_aliases.py` 셋이 같은 값이고, Ghidra 가 다른 이름으로 잡은 것도 아니다 `[정적]`.
- **질문 2 (a)** — `rcx`·`rdx` 는 **그대로**. 이유는 간단하다. `+0x0 ~ +0xe` 사이에 둘을 **건드리는 명령이 없다** `[정적]`.
  - 손대지 않은 레지스터는 다음 함수가 그대로 받는다. 그래서 "안 바꿨다" = "그대로 넘겼다" 가 된다.
- **질문 2 (b)** — `r8` 도 손대는 명령이 없으니 **그대로**. `r9` 만 `+0x4` 에서 **상수로 덮어쓴다** `[정적]`.
  - 호출자가 `r9` 에 뭘 넣었든 상관없다. 덮어쓰니까.
- 그래서 `Length2` 를 한 줄로 쓰면 (결과서 "한 줄 요약"):
  - `Length2(ecx, rdx, r8)` = `Length3(ecx, rdx, r8, r9 = 0xFFFFF780000003D8)` 을 CALL, 돌아온 `eax` 그대로.

참고로 Ghidra 의 `.c` (디컴파일) 는 이 넷을 못 보여 줬다.

- `.c` 엔 `RtlGetExtendedContextLength3();` 한 줄뿐이다. PDB 에 인자 정보가 없어서 Ghidra 가 레지스터를 인자로 못 잡았다 (결과서).
- 그래서 이번 근거는 **`.asm` 만** 썼다. 이런 짧은 함수는 `.c` 가 오히려 정보를 빼먹을 수 있다는 예다.

비유로: 자 빌려주는 사람 (`Length2`) 은 받은 쪽지 세 장 (`rcx`·`rdx`·`r8`) 을 손대지 않고 그대로 넘긴다. 다만 **넷째 자리에 늘 같은 종이 한 장** (게시판 주소) 을 끼워 넣는다.

### 2.4 `r9` 상수의 뜻 — `KUSER_SHARED_DATA` 와 XState

먼저 두 말을 짧게 다시 푼다.

- **`KUSER_SHARED_DATA`** = 커널이 모든 프로세스에 보여 주는 **공용 정보 페이지**로 알려져 있다 `[추측]` (일반적으로 알려진 설명, [run18 해설](../02_sprint/run18-proc-init-setup-해설.md)). 비유: 관리사무소가 동네 가게마다 붙여 두는 **공용 게시판**.
  - run18 에선 유저 쪽에서 보는 주소 (`0x7ffe0330` 같은 `0x7ffe…`) 로 만났다. 이번 상수는 **커널 쪽에서 보는 주소** (`0xFFFFF78000000000`, 결과서 "커널 매핑") 다.
  - 같은 게시판을 두 주소로 본다는 건 `[추측]` (일반적으로 알려진 설명). 이번 근거는 커널 주소 쪽만이다.
- **XState** = 업무 시작 메모 뒤에 붙는 **별지** ([run42 해설 2.3](../02_sprint/run42-continue-detail-해설.md)). 기본 칸 말고 CPU 의 덧붙은 기능 상태를 담는 자리다.
  - 게시판의 `XState` 칸 (`_XSTATE_CONFIGURATION`) 은, 그 별지를 **이 컴퓨터에선 어떻게 만드나** 적어 둔 **"별지 양식 안내"** 쯤으로 보면 된다. 어떤 기능이 켜졌는지 (`EnabledFeatures`) 같은 칸이 있다 (결과서 칸 이름).

이제 상수를 쪼개 보면 (run 문서·결과서 그대로):

| 조각 | 값 | 뜻 | 표시 |
|---|---|---|---|
| 앞 | `0xFFFFF78000000000` | `KUSER_SHARED_DATA` 커널 매핑 | [정적] |
| 뒤 | `+0x3d8` | 그 안 `XState` 칸 (`pdb_struct.py` 로 확인) | [정적] |
| 합 | `0xFFFFF780000003D8` | `&SharedUserData->XState` | [정적] |

- `.asm` 에는 이 값이 `-0x87ffffffc28` 로 찍혀 있다. 같은 64비트 값을 **음수로 읽은 것**이다 (64비트 2의 보수, flow-writer 가 다시 맞춤).

`Length3` 는 이 주소를 어디에 쓰나 `[정적]`:

- `+0x25` 에서 `RSI` 에 옮겨 두고, 게시판 칸으로 읽는다: `+0x94`, `+0x9b`, `+0xa7`, `+0xcb`.
- **이 네 줄은 모두 XState 블록 (`+0x88 ~ +0xdf`) 안이다.** 이게 2.7 의 열쇠다.

### 2.5 꼬리 호출이 아니라 보통 CALL — 질문 2 (c)

**새 말 다시 — 꼬리 호출 vs CALL** ([run17 해설 2.4](../02_sprint/run17-ldr-init-entry-해설.md#24-꼬리-점프--콜스택에서-함수-하나가-지워지는-원리))

- `CALL` = 스택에 **책갈피 (돌아올 주소)** 를 꽂고 간다. 일이 끝나면 그 책갈피로 돌아온다.
- 꼬리 호출 (`JMP`) = 책갈피를 **안 꽂고** 넘어간다. "저 안쪽으로 가세요" 하고 자리를 비키는 안내 데스크 (run17 비유).
  - 그래서 꼬리 호출한 함수는 콜스택에서 **빠진다**.

`Length2` 는 어느 쪽인가 `[정적]`:

- `+0xe` 는 **`CALL`** 이다. `JMP` 가 아니다.
- 돌아와서 하는 일은 `+0x13` 스택 되돌림, `+0x17` RET 뿐이다.
- `eax` 는 안 건드린다. 그래서 `Length3` 가 낸 `eax` 가 그대로 `PspInitializeThunkContext` 로 간다.

이게 왜 중요하나:

- "넘기는 값" 만 보면 꼬리 호출이든 CALL 이든 결과가 같다. 돌아와서 **아무것도 안 하니까.**
- 차이는 **콜스택 모양**이다. CALL 이라서 책갈피 `RtlGetExtendedContextLength2+0x13` 이 남는다.
  - 그래서 WinDbg 콜스택엔 `Length3` 위에 `Length2+0x13` 줄이 **보일 것**이다 `[추측: 꼬리 호출이 아니라서]`. 아직 실제로 본 적은 없다.
- PE_emulator 처럼 "진짜와 같은 호출관계" 를 짓는 쪽에선 이 한 줄 (프레임이 있나 없나) 이 달라진다.

**길이는 반환값이 아니다** `[정적]`

- 헷갈리기 쉬운 곳이다. `Length3` 의 반환값 `eax` 는 **성공/실패 상태**다 (`+0xf4` 에서 0 = 성공).
- 길이는 `rdx` 가 가리키는 칸에 **`Length3` 가 직접 쓴다**: `+0x16` 에서 `rdx` 를 `R14` 에 쥐고, `+0xf1` 에서 `[R14]` 에 쓴다.
- 그래서 `PspInitializeThunkContext` 는 돌아와서 두 가지를 따로 본다:
  - `+0xa7 ~ +0xab` 상태가 음수면 실패 길.
  - `+0xb1` `[RBP]` (= 길이) 를 읽는다.
- 비유: 자를 빌려 간 사람이 "다 쟀어요 (상태)" 라고 말로 대답하고, 숫자는 **처음에 건네준 메모지 (`[RBP]`)** 에 적어 둔다.

### 2.6 CET 비트 하나가 두 값을 같이 정한다

**새 말 다시 — CET 그림자 스택** ([run29 해설 2.9](../02_sprint/run29-continue-start-해설.md#29-cet-그림자-스택--미리-올려-둔-한-칸과-맞춰-보기))

- 돌아올 주소를 따로 한 벌 더 적어 두고 맞춰 보는 CPU 보안 장치로 알려져 있다 `[추측]` (일반적으로 알려진 설명).
- 비유: 직원 수첩 (보통 스택) 말고 **경비실 장부**에도 "다음에 갈 곳" 을 적는다. 수첩은 고쳐 쓸 수 있어도 장부는 아무나 못 고친다.
- 장부 쓰는 직원이면, 메모에 **장부 상태를 적을 별지 칸 (XState 의 CET_U 칸)** 이 하나 더 붙는다 (run42).

`PspInitializeThunkContext` 가 `Length2` 를 부르기 전에 하는 일 `[정적]`:

1. `+0x5c` `RSI` = 지금 스레드 (`GS:[0x188]`).
2. `+0x69 ~ +0x6c` 스레드 `_KTHREAD +0x74` 의 **bit 20** (`CetUserShadowStack`) 하나만 남긴다.
3. 그 비트 하나로 두 값이 **같이** 정해진다:

| 비트 20 | `R14D` (→ `r8d`, 별지 종류) | `R12D` (→ `ecx`, 체크박스) |
|---|---|---|
| 꺼짐 (비-CET) | `0` | `0x10001b` |
| 켜짐 (CET) | `0x800` | `0x10005b` |

- `R14D` 는 `+0x72 ~ +0x79`, `R12D` 는 `+0x84 ~ +0x8d` 에서 정한다.
- 호출 직전 `+0x98` `r8d` ← `R14D`, `+0x9b` `rdx` ← `&[RBP]`, `+0x9f` `ecx` ← `R12D`, `+0xa2` CALL.
- run42 의 "`0x10001b` = 비-CET, `0x10005b` = CET" 와 같은 결론이다.

그러니 이번 질문 3 은 사실 **두 갈래**다. 비-CET 면 어떻게 되나 (2.7), CET 면 어떻게 되나 (2.9).

### 2.7 비-CET 길: `0x4ff` 가 나오는 순서 — 질문 3

입력: `ecx = 0x10001b`, `r8 = 0`, `r9` = 게시판 주소.

**새 말 — 분기 칸 (`[RSP+0x20]`)**

- `Length3` 가 자기 스택에 마련한 **지역 칸 하나**다. 주소를 `RtlpValidateContextFlags2` 에 넘기면, 그 함수가 숫자를 적어 돌려준다.
- 그 숫자의 bit 1, bit 2 를 보고 `Length3` 가 갈 길을 고른다.
- 비유: 체크박스 검사원이 메모를 훑어보고 **확인 도장 칸**에 숫자를 찍어 준다. "별지 있음" 이면 bit 1 이 켜진 숫자, "아무것도 없음" 이면 1.

**① 검사원: `RtlpValidateContextFlags2`** (`Length3 +0x2a` 가 부름) `[정적]`

- `+0xa ~ +0x28`: `0x10001b` 의 아키텍처 비트 검사 **통과** → `+0x4d`.
- `+0x4d ~ +0x8e`: XState 비트 조합 (`0x400020`·`0x100040`·`0x10040`) 이 **하나도 안 맞는다** → `+0x9c` 로 건너뜀.
  - 여기서 중요한 것: 게시판 칸 `XState.EnabledFeatures` 를 **안 읽는다.**
- `+0x9c ~ +0xa7`: CET 커널 검사도 안 탄다 → `+0xbd`.
- `+0xc2` 분기 칸 **= 1**, `+0xc5` 반환 0 (성공).

**② 재는 사람: `Length3`** `[정적]`

| 단계 | 줄 | 무슨 일 | 값 |
|---|---|---|---|
| 1 | `+0x3a ~ +0x3e` | bit 16 없음 → `+0x4d` 로 | |
| 2 | `+0x4d ~ +0x58` | bit 20 있음 → `+0x53` 기본 크기 → `+0x78` 로 | `EBX = 0x4d0` |
| 3 | `+0x78` | 맞춤 단위 | `R11D = 0x10` |
| 4 | `+0x7e` | `+0x20` 더함 | `EBX = 0x4f0` |
| 5 | `+0x81 ~ +0x86` | 분기 칸 bit 1 꺼짐 → **XState 블록 (`+0x88 ~ +0xdf`) 건너뜀** | |
| 6 | `+0xe1 ~ +0xe9` | 분기 칸 bit 2 꺼짐 | `EAX = EBX = 0x4f0` |
| 7 | `+0xec ~ +0xee` | `− 1 + 0x10` | `0x4ff` |
| 8 | `+0xf1` / `+0xf4` | `*rdx` 에 씀 / 반환 0 | `*rdx = 0x4ff` |

- PE_emulator 가 이미 적어 둔 줄 (`+0x4d ~ +0x58`, `+0x7e`, `+0xe1 ~ +0xee`) 은 **맞다**.
- 이번에 보탠 건 **그 사이의 분기 두 곳** (5단계 `+0x81/+0x86`, 6단계 `+0xe1`) 이 읽는 "칸 값 1" 이 **어디서 왔나**다. 답은 ① 의 `RtlpValidateContextFlags2 +0xc2`.
  - 그래서 PE_emulator 근거 줄에 `RtlpValidateContextFlags2 +0x4d ~ +0xc2` 를 더하라고 했다 (run 문서 "PE_emulator 쪽에서 고칠 것").

### 2.8 왜 "`r9` 를 바꿔도 `0x4ff` 는 그대로" 인가 — 단계별로

이번 바퀴의 핵심 추론이다. 천천히 간다.

1. **근거** `[정적]`: `Length2` 가 바꾸는 건 `r9` 하나뿐이다 (2.3).
2. **근거** `[정적]`: `Length3` 안에서 `r9` (= `RSI`) 가 가리키는 게시판 칸을 읽는 줄은 `+0x94` 이후, **모두 XState 블록 안**이다 (2.4).
3. **근거** `[정적]`: `r8` (= `Length3` 의 `RBP`) 을 쓰는 줄도 XState 블록 안 `+0xb7` 하나뿐이다.
4. **근거** `[정적]`: 비-CET 길은 `+0x86` 에서 **XState 블록을 통째로 건너뛴다** (2.7 의 5단계).
5. **근거** `[정적]`: 검사원 `RtlpValidateContextFlags2` 도 이 길에선 게시판 칸을 안 읽는다 (2.7 ①).
6. **그래서**: 비-CET 길에선 `r8`·`r9` 가 무엇이든 **한 번도 안 읽힌다.** `Length2` 가 `r9` 를 바꿔 끼웠어도 결과는 같다.
7. **그래서 하나 더**: 게시판 내용 (어떤 CPU 기능이 켜졌나) 도 안 읽으니, **`0x4ff` 는 CPU·VM 설정과 무관한 상수**다 `[정적]`.

비유로: 별지가 없는 메모를 재는 사람은 "별지 양식 안내" 게시판을 **볼 일이 없다.** 게시판 주소가 바뀌든 게시판 내용이 바뀌든, 재는 크기는 늘 같다.

이 결론이 PE_emulator 에 주는 뜻 `[추측]`:

- 에뮬레이터가 비-CET 스레드만 다룬다면, 게시판 (`SharedUserData->XState`) 칸을 진짜처럼 채우지 않아도 이 길이는 `0x4ff` 로 같게 나온다. (run 문서는 "CPU 무관 상수" 까지만 말한다. 에뮬레이터 설계 쪽 판단은 내 짐작이다.)

### 2.9 `0x4ff` 는 무엇을 더한 값일까 `[추측]`

run 문서가 `[추측]` 으로 남긴 풀이다. 칸 이름으로 확인한 건 아니다.

| 조각 | 짐작한 뜻 | 짐작의 근거 |
|---|---|---|
| `0x4d0` | `CONTEXT` (업무 시작 메모 본문) 크기 | `PspInitializeThunkContext +0x101 ~ +0x10e` 가 지역 문맥을 `0x4d0` 바이트 `memset`, run44 도 맡긴 `_CONTEXT` 를 `0x4d0` 바이트로 비교 |
| `+0x20` | 확장 문맥 머리 (별지를 붙이는 클립 같은 것) | — |
| `−1 + 0x10` | 16바이트 맞춤 여유 | — |

- 마지막 `−1 + 0x10` 은 "나중에 16 단위로 맞춰도 모자라지 않게 조금 넉넉히" 로 읽힌다. 이게 2.11 에서 다시 나온다.

### 2.10 CET 길: `0x4ff` 가 아니다 `[정적]`

입력: `ecx = 0x10005b`, `r8 = 0x800`.

- 검사원 `RtlpValidateContextFlags2`: `0x10005b & 0x100040 = 0x100040` → "별지 요청" 으로 보고 `+0x90` 에서 게시판 `XState.EnabledFeatures` 를 **읽는다**.
  - 0 이면 `0xc00000bb` 를 돌려준다 → `Length3 +0x31` 에서 `+0xf6` 으로, **길이를 안 쓰고** 끝.
  - 아니면 분기 칸 **= 3** (bit 1 켜짐).
- 그러면 `Length3` 가 XState 블록을 **탄다**:
  - `+0xc1` `RtlpRemoveArchDisallowedXStateFeatures`, `+0xd1` `RtlpGetEntireXStateAreaLength2` 를 부르고,
  - `+0xd6 ~ +0xdf` `EBX = 0x4f0 − 0x10 − 0x1c0 + (그 반환값)`.
  - 최종 **`*rdx = 0x32f + RtlpGetEntireXStateAreaLength2(…)`**.
- 그 반환값은 게시판 내용 (CPU 마다 다른 런타임 값) 과 `r8` 에 달렸다. 함수 안은 범위 밖이라 **안 풀었다**.

비유로: 장부 쓰는 직원 (CET) 의 메모엔 별지가 붙는다. 별지 크기는 **이 컴퓨터의 별지 양식** 에 달렸으니, 게시판을 꼭 봐야 한다. 그래서 숫자 하나로 못 박을 수 없다.

### 2.11 run44 사진과 맞춰 보기 — 왜 "어긋나지 않음" 까지만인가

run44 사진에 test.exe 첫 스레드 값이 남아 있다 `[관찰]`:

- P1 의 맡긴 문맥 `ContextFlags` = **`0x10001b`** → 비-CET 길이다.
- P0 트랩 프레임 `Rsp` = `9b2fcfff48`, 맡긴 문맥 주소 = `9b2fcffa40`.

정적 셈 (run16 의 `R15 = (원래 Rsp − 길이) & ~0xf`) 에 `0x4ff` 를 넣으면 `[정적]`:

- `(0x9b2fcfff48 − 0x4ff) & ~0xf = 0x9b2fcffa40` — 사진 값과 **같다**.

그런데 run 문서는 이걸 "길이가 `0x4ff` 임을 확인했다" 고 쓰지 **않는다.** 왜일까.

**새 말 — 16바이트 맞춤 (`& ~0xf`)**

- 주소의 끝 16진수 한 자리 (16칸 단위 아래쪽) 를 **0 으로 지워 버리는** 셈이다. 늘 아래쪽으로 내린다.
- 비유: 사물함이 **16칸짜리 선반 단위로만** 열린다. 원래 자리에서 메모 크기만큼 내려간 뒤, 그 선반의 **맨 아래 칸**에 맞춰 넣는다.
- 쉬운 10진수 예 (설명용, 실제 값 아님): 10 단위로 내림하면 47 도 41 도 모두 40 이 된다. 결과 40 만 보고는 원래가 47 이었는지 41 이었는지 모른다.

그래서:

- 길이가 조금 달라도 (`0x4ff` 보다 몇 바이트 많거나 적어도) **같은 선반 맨 아래 칸**에 떨어질 수 있다.
- run 문서가 그 범위를 적어 뒀다: 길이가 **`0x4f9 ~ 0x508`** 이면 다 같은 주소 `9b2fcffa40` 이 나온다.
- 즉 사진이 말하는 건:
  - "`0x4ff` 라면 사진과 맞는다" — **예.**
  - "길이가 정확히 `0x4ff` 다" — **사진만으론 못 말한다.** 범위 안의 다른 값도 같은 그림을 낸다.
- 태그도 그래서 `[관찰]`+`[정적]` "앞뒤가 맞는다" 다. 길이 값 자체는 정적 셈 (2.7) 이 정한 것이고, 사진은 그걸 **반박하지 않는다**는 쪽의 증거다.

길이를 바이트 하나까지 직접 보고 싶다면, 돌아온 직후 `[RBP]` 를 읽으면 된다 (결과서 "선택" 멈춤점, 4절). 지금은 필요 없다고 판정했다.

### 2.12 정정 — 우리 문서엔 없고, PE_emulator 쪽 한 줄

- **우리 문서엔 틀린 곳이 없다.** run16 의 "길이 = `Length2` (`+0xa2`) 결과" 는 그대로 맞고, 이번에 그 안이 `[정적]` 으로 채워졌다.
- **PE_emulator 쪽** "`Length2` → `Length3` 인자 **그대로**" `[추측]` 은 정확히는:
  - "`rcx`·`rdx`·`r8` 그대로, **`r9` = `0xFFFFF780000003D8`** (`&SharedUserData->XState`), CALL 뒤 `eax` 그대로" `[정적] run55`.
- 같이 고칠 것 (run 문서 맨 위):
  - `0x4ff` 는 **비-CET** (`0x10001b`, `r8 = 0`) 값이라고 적기.
  - 근거 줄에 `RtlpValidateContextFlags2 +0x4d ~ +0xc2` (분기 칸 = 1) 더하기.

### 2.13 정리: 비유로 한 번 더

1. 관리사무소가 새 직원의 원래 메모를 사물함에 넣으려 한다. 먼저 **메모 크기**를 잰다 (`PspInitializeThunkContext +0xa2`).
2. 그 전에 직원 카드를 본다: "경비실 장부 써요?" (`_KTHREAD +0x74` bit 20). 답에 따라 체크박스와 별지 종류가 같이 정해진다.
3. 자 빌려주는 사람 (`Length2`) 은 받은 쪽지를 그대로 넘기면서, 넷째 자리에 **공용 게시판의 "별지 양식 안내" 주소**를 꼭 끼워 준다. 그리고 재는 사람이 돌아올 때까지 **기다린다** (CALL, 꼬리 호출 아님).
4. 재는 사람 (`Length3`) 은 검사원에게 확인 도장을 받는다. 장부 안 쓰는 직원이면 도장 = 1.
5. 도장 1 이면 별지 칸은 건너뛰고, 정해진 크기 `0x4ff` 를 메모지에 적는다. **게시판은 보지도 않는다.**
6. 관리사무소는 그 크기만큼 내려가 16칸 선반 맨 아래에 사물함을 연다. run44 사진의 사물함 위치와 맞는다. 다만 선반 단위라 크기를 1바이트까지 집어내진 못한다.

- 그러니 에뮬레이터가 이 길이를 틀리면 첫 유저 `Rcx`·`Rsp` 가 다 밀린다. 한 숫자지만 뒤로 길게 이어진다.
- 짐 지도 쪽에선 이번 바퀴가 칸을 새로 세지 않았다. 다음 항목은 **Q104** (PE_emulator 요청 2, 동적 한 번 실행 묶음) 이고, 그 뒤에 짐 지도 Q78d4 로 돌아간다.
