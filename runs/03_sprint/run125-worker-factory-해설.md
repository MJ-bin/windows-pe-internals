### 이번 바퀴에서 조심할 곳 다섯

1. **이번 이야기는 초기화 "안" 에 한 번 걸친다.**
   - 요청서는 "test.exe 초기화 범위 밖" 으로 잡았다.
   - 그런데 **첫 넣기 자체는 초기화 안에서 한 번 일어난다** — 로더 풀 첫 `TppWorkPost +0x4f3 NtReleaseWorkerFactoryWorker` (run72 `[정적]`). 일꾼 2개가 P1a ~ P1b 에 생긴다 (run44 `[관찰]`).
   - 그래서 flow.md 에도 화살표가 붙었다 (3절).
2. **칸 · 클래스 이름은 "우리 이름" 이다.**
   - PDB 에 일꾼 공장 구조체도, 정보 클래스 열거도 **없다** (`llvm-pdbutil` types 에 `WorkerFactory` 0건).
   - 그래서 칸의 **위치 · 동작은 `[정적]`**, **이름은 공개 헤더와 맞춘 `[추측: 이름]`** 이다.
3. **오프셋 두 가지.** 본문 "`+0x201 ExpWorkerFactoryCheckCreate`" 처럼 함수 이름 앞의 숫자는 **call 자리**, 트리 (`└─ +0x206`) 의 숫자는 **ret 자리** (콜스택에 찍힐 값) 다. run 문서와 같은 규칙. 콜스택으로 본 적은 아직 없다.
4. **"에뮬레이터 로그" 는 진짜 Windows 로그가 아니다.** 요청서의 "클래스 5 → 4 → 3 차례" 는 PE_emulator 가 흉내 낸 실행의 기록이다.
5. **`f` 와 `P` 두 글자가 계속 나온다.** 2.2 에서 먼저 푼다.

### 비유 — 그대로 이어 쓴다

- 프로세스 = **가게**, ntdll = 가게 안 **관리실**, 커널 = **관리사무소**, syscall = 관리사무소 **신청 창구**, 스레드 = **직원**.
- 스레드 풀 = **일꾼 사무실**. 일꾼 공장 = 그 사무실에 딸린 **파견소** — 진짜 파견소는 관리사무소 안에 있고, 사무실은 **번호표** 만 들고 있다 (run69 해설).
- **이번에 파견소 안을 처음 들여다봤다.** 파견소엔 이런 게 있다:
  - **우편함** 하나 (IO 완료 포트). 일꾼은 여기 앞에서 봉투를 기다린다.
  - **장부** (공장 몸 `f`) — 정원 · 지금 일하는 수 · 뽑는 중인 수 · 새 일꾼에게 줄 "업무 시작 메모" 값.
  - **작은 메모판** (덩어리 `P`) — "넣은 일감 수", "우편함 앞에서 기다리는 일꾼 수", "빈 쪽지가 우편함에 들어 있음", "문 닫는 중".
- 주의 — 이름이 비슷한 통이 셋이다.
  - run62 · run93 해설의 **우편함** = IO 완료 포트. 이번 글의 우편함도 이것이다.
  - run72 해설의 **우체통** = ntdll 풀 개체 안의 큐 (`TaskQueue`). 진짜 일감 (호출 버튼 편지) 은 여기 있다.
  - run 문서 "결과" 의 비유는 완료 포트를 "**우체통**" 이라 부른다. 이 글에서는 앞 해설들과 맞춰 **우편함** 으로 부른다. 그림만 다르고 사실은 같다.

### 한 줄로 먼저 — 무엇을 얻었나

## 1. 이번 바퀴의 질문

### 큰 그림에서 어디인가

```
cmd.exe 의 부탁 → 커널 NtCreateUserProcess → 첫 스레드 출발
 └─ ntdll LdrInitializeThunk → _LdrpInitialize → LdrpInitializeProcess
      ├─ +0x1a47 LdrpEnableParallelLoading     팀 사무실 + 파견소 차리기 (run69)
      ├─ (사진 P1a)
      ├─ +0x1aa4 LdrpMapAndSnapDependency      exe 가 import 하는 DLL 들이기
      │    └─ … LdrpQueueWork → TpPostWork ⇒ TppWorkPost
      │          └─ +0x4f3 NtReleaseWorkerFactoryWorker   "한 명 보내 주세요" (run72)
      │                ⇒ 커널: 파견소 안에서 무슨 일이?                        ← 이번 (run125)
      ├─ (사진 P1b — 일꾼 2개가 이미 있음 [관찰] run44)
      └─ … NtContinue 은퇴 (사진 P2) → main
```

- run72 는 관리실 쪽 (ntdll) 에서 **쪽지를 건네는 순간** 까지 봤다. 쪽지를 받은 **관리사무소 안쪽** 은 안 읽었다.
- 이번엔 그 안쪽이다. flow.md 에서는 **3장 끝 새 절** "일꾼 공장" 으로 들어갔다.

### 왜 이 질문이 지금 왔나

- PE_emulator 요청이다. 지금 에뮬레이터는 `NtReleaseWorkerFactoryWorker` 에서 핸들 · 접근 검사만 하고 멈춘다. 일꾼 스레드를 안 만들어서 **모두 잠든다** (run 문서 "목적").
- 진짜 커널은 무엇을 하는지, 코드 줄로 답해 달라는 요청이었다.

### 무엇이 궁금했나

요청서 질문 넷.

1. 넣기가 공장의 **어떤 칸** 을 바꾸나. **어떤 조건** 에서 일꾼을 만드나. 바로인가 미루나. 첫 넣기가 계기인가 (run72 `[추측]` 닫기).
2. 일꾼 스레드를 **만드는 길** — 시작 주소 · 인자 · 스택 크기가 어디서 오나, `NtCreateThreadEx` 와 같은 길인가, 누구 프로세스에서 도나.
3. **`NtWaitForWorkViaWorkerFactory`** — 일꾼이 일감을 받는 꼴, 기다림, 끝나는 길.
4. **설정 클래스 4 · `0xb`** 의 뜻 (= Q134 (b) 몫).

### 바퀴 전에 알던 것

- `[정적]` (run72) ntdll `TppWorkPost` 첫 넣기 = `NtReleaseWorkerFactoryWorker(풀 +0x38)` 한 번, 기다림 없음. 둘째 넣기부터는 syscall 0.
- `[추측]` (run72) 이 첫 넣기가 커널에서 일꾼을 새로 만드는 **계기일 수 있다**.
- `[정적]` (run62 · run69) 이 프로세스엔 **일꾼 공장이 둘** (기본 풀 · 로더 풀). `NtCreateWorkerFactory` · `NtSetInformationWorkerFactory` 클래스 2 · 3 · 5 · `0xd` 를 부르는 쪽 · 길이.
- `[정적]` (run69) 로더 풀만 클래스 `0xd` (값 1) 를 부른다 → 커널 공장 `+0x198` bit 11. **그 bit 의 뜻은 `[공백]`**.
- `[정적]` (run74) `NtCreateThreadEx` → `PspCreateThread` 길, `CreateFlags` → TEB 비트 대응표 (`0x10` → `0x80` → `LoaderWorker`).
- `[관찰]` (run44) P1a ~ P1b 사이에 일꾼 2개 (`ActiveThreads` 1 → 3).
- `[관찰 — 에뮬레이터 로그, 진짜 Windows 아님]` 공장 만들기 뒤 설정 클래스 5 → **4** → 3 차례. 클래스 4 와 `0xb` 가 "지원 안 함".

## 2. 찾은 것

### 2.1 한눈에 — 쪽지 한 장이 일꾼 한 명이 되기까지

flow.md 3장 새 절의 트리를 줄였다. 모두 `[정적]`. 숫자는 ret 자리.

```
nt!NtReleaseWorkerFactoryWorker                      "한 명 보내 주세요" 창구
 │  P+0x18 ++ · P+0x20 = 1 · 우편함에 빈 쪽지 (0 패킷)
 └─ +0x206  ExpWorkerFactoryCheckCreate(f, 0, 0)     둘러보기: 조건 일곱
     └─ +0x1a0  ExpWorkerFactoryCreateThread(f)      한 명 뽑기
         ├─ +0xea   RtlpCreateUserThreadEx
         │   └─ +0x151  ZwCreateThreadEx ⇒ nt!NtCreateThreadEx → PspCreateThread … (run74)
         └─ +0x158  ZwResumeThread                    멈춘 채 만든 직원을 바로 풀기
새 일꾼 (ntdll TppWorkerThread [추측: 안 읽음])
 ├─ NtWorkerFactoryWorkerReady                        "왔어요"
 └─ NtWaitForWorkViaWorkerFactory
     ├─ +0x6bf  IoRemoveIoCompletion (시간 제한 없음)  우편함에서 봉투 꺼내기
     └─ +0xa62  ExpWorkerFactoryCheckCreate            일을 집은 뒤 — 다음 일꾼이 필요한가
```

- 비유로 한 번: 가게 관리실이 파견소 창구에 "한 명 보내 주세요" 쪽지를 낸다. 파견소는 자기 우편함에 **빈 쪽지** 한 장을 넣고, 그 자리에서 둘러본다. "우편함 앞에 기다리는 사람 없고, 정원 남았고, 뽑는 중인 사람도 없네" → **바로 한 명 뽑아 일터로 보낸다**.
- 뽑힌 일꾼은 먼저 "왔어요" 를 하고, 우편함에서 쪽지를 꺼낸다. 쪽지엔 아무것도 안 적혀 있다 — 진짜 일감은 ntdll 풀 쪽 목록 (run72 해설의 우체통) 에서 찾는다 `[추측: TppWorkerThread 안은 안 읽음]`.

### 2.2 새 말 — 파견소 장부 `f` 와 작은 메모판 `P`

이 글 내내 나오는 두 글자다. 먼저 푼다.

- **`f`** = 일꾼 공장 개체의 몸. 크기 `0x2a0` (`NtCreateWorkerFactory +0x1c5 ObCreateObjectEx`) `[정적]`.
  - 비유: 파견소 **장부**.
- **`P`** = 공장 `+0x10` 이 가리키는 **`0x28` 바이트 덩어리** (꼬리표 `TpWc`, 0 으로 채운 할당) `[정적]`.
  - 비유: 장부에 끼워 둔 작은 **메모판**. 넣기 · 꺼내기 때 자주 바뀌는 칸이 여기 모여 있다.

자주 나오는 칸만 (run 문서 6절에서 골랐다. 위치 · 동작 `[정적]`, 이름 `[추측]`):

| 칸 | 뜻 | 비유 |
|---|---|---|
| `P+0x08` | 완료 포트 (`_KQUEUE`) | 우편함 |
| `P+0x10` | 풀어주기 패킷 (2.3) | 미리 만들어 둔 빈 쪽지 한 장 |
| `P+0x18` | **넣은 일감 수** | "넣은 쪽지 수" 숫자 |
| `P+0x1c` | **기다리는 일꾼 수** | 우편함 앞에 서 있는 사람 수 |
| `P+0x20` | 패킷이 포트에 있음 | "빈 쪽지 들어 있음" 표시 |
| `P+0x21` | **마감** | "문 닫는 중" 팻말 |
| `f+0x18` · `+0x20` | 새 일꾼의 시작 주소 · 시작 인자 | 업무 시작 메모 값 |
| `f+0x38` · `+0x40` | 스택 예약 · 커밋 | 작업대 크기 |
| `f+0x178` · `+0x17c` | 최소 · 최대 스레드 | 정원 (아래 · 위) |
| `f+0x180` | 움직이는 일꾼 수 | 지금 일하는 사람 수 |
| `f+0x188` | 만들었지만 `Ready` 전 수 | 뽑혔는데 아직 "왔어요" 안 한 사람 |
| `f+0x190` | 만드는 중 수 | 뽑는 중인 사람 |
| `f+0x198` | 상태 비트 (bit 11 = `LoaderWorker` 등) | 장부 맨 위 체크 칸 묶음 |

- 칸 전체와 상태 비트 16개는 결과서 "공장 객체 칸 표" 에 있다.
- 덤: PE_emulator 의 `TODO(VM)` "`[[공장+0x10]+0x21]` 바이트 뜻" → **마감 바이트**, 새 공장은 0 (결과서).

### 2.3 넣기 — `NtReleaseWorkerFactoryWorker` 가 하는 일, 차례대로 `[정적]`

#### 새 말 — 풀어주기 패킷 (0 패킷)

- 공장을 만들 때 미리 하나 만들어 두는 **완료 패킷** (`NtCreateWorkerFactory +0x182 IoAllocateMiniCompletionPacket`, 콜백 = `ExpWorkerFactoryCompletionPacketRoutine`) `[정적]`.
- 넣을 때 네 칸 (키 문맥 · APC 문맥 · 상태 · 정보) 을 **모두 0** 으로 채운다. 그래서 run 문서는 "0 패킷" 이라고도 부른다.
- 비유: **아무것도 안 적힌 빈 쪽지.** "일 있어요" 라는 뜻만 있다.

#### 차례 (run 문서 1절 그대로)

1. `+0x46` 핸들 → 공장 (접근 1).
2. `P` 락을 잡는다.
3. `+0xe0` **마감** (`P+0x21`) 이 켜졌으면 → 락 풀고 **`0x80`**. 둘러보기 (`CheckCreate`) 없음.
4. `+0xea ~ +0xf0` `P+0x18` 이 `-1` 이면 **`0xc0000001`** (넘침 막기).
5. `+0xfb` **`P+0x18` ++** (넣은 일감 수).
6. `+0x102` 빈 쪽지가 **이미 우편함에 있으면** (`P+0x20 ≠ 0`) → 락 풀고 **상태 0 으로 끝**. 새 쪽지도, 둘러보기도 없다.
7. `+0x10c` **`P+0x20 = 1`**. ("멀리 있기" 표시면 `+0x11f` 로 끄기 — 2.5 끝.) 락 풀기.
8. 쪽지 = `P+0x10`. 없으면 `+0x2c4` 새로 할당.
9. `+0x143 ~ +0x153` 쪽지 네 칸을 0 으로.
10. 우편함 락 (`+0x18b`). 우편함 앞에 **기다리는 일꾼이 있고** 조건이 맞으면 `+0x1be KiWakeQueueWaiter` 로 **그 손에 직접** 넘긴다. 아니면 봉투 줄 꼬리에 붙인다.
11. **`+0x201 ExpWorkerFactoryCheckCreate(f, 0, 0)`** — 둘러보기.
12. 상태 0 반환.

#### 한 줄 읽기 — `NtReleaseWorkerFactoryWorker +0x201` (call) / `+0x206` (ret)

| caller | call | ret | callee | 표시 |
|---|---|---|---|---|
| `nt!NtReleaseWorkerFactoryWorker` | `+0x201` | `+0x206` | `ExpWorkerFactoryCheckCreate(f, 0, 0)` | [정적] |

- **누가**: "한 명 보내 주세요" 쪽지를 받은 창구 `NtReleaseWorkerFactoryWorker`.
- **어디서**: 빈 쪽지를 우편함에 넣은 **바로 뒤** `+0x201` 에서 부르고, `+0x206` 으로 돌아온다.
- **누구를**: 파견소 둘러보기 담당 `ExpWorkerFactoryCheckCreate`.
- **무엇을 위해**: "지금 일꾼을 새로 뽑아야 하나" 를 그 자리에서 판단하려고. 둘째 인자 0 = 락을 스스로 잡으라는 뜻, 셋째 0 = 미룬 일 다시 하기가 아니라는 뜻 (run 문서).
- 이 줄 하나가 run72 의 `[추측]` 을 닫는 핵심이다. **기다림 없이, 같은 syscall 안에서** 둘러보기까지 간다.

#### 바뀌는 칸 정리

- `P+0x18` ++, `P+0x20` = 1, 우편함 `SignalState` ++ (또는 직접 넘김), 공장 bit 9 끔.
- **일꾼 수 칸 (`f+0x180` · `+0x184` · `+0x188` · `+0x190`) 은 이 함수가 직접 안 건드린다.** 둘러보기 · 뽑기 담당이 건드린다 (2.4 · 2.10).

#### "N 번 넣었는데 쪽지는 한 장" — 어떻게 맞아떨어지나

헷갈리기 쉬운 곳이라 단계별로 `[정적]`.

1. 6번 갈래 때문에, 빈 쪽지가 우편함에 이미 있으면 **숫자 (`P+0x18`) 만 올리고** 새 쪽지를 안 넣는다.
2. 일꾼이 쪽지를 꺼낼 때마다 콜백 `ExpWorkerFactoryCompletionPacketRoutine` 이 `P+0x18` 을 하나 내린다 (`+0x71`).
3. 내린 뒤 0 이 아니면 **같은 쪽지를 다시 우편함에 넣는다** (`+0x75 JNZ`).
4. 0 이 되면 `P+0x20 = 0` (`+0x7c`) — "쪽지 없음" 으로 돌아간다.
5. 그래서 → **N 번 넣으면 일꾼이 N 번 꺼낸다.** 쪽지는 한 장이 돌고 돈다.

- 비유: 우편함에 **한 장짜리 순환 쪽지** 가 있다. 뒷면에 "남은 횟수" 가 적혀 있고, 꺼낼 때마다 하나 빼고, 남았으면 도로 넣는다.
- 덧: ntdll 은 둘째 넣기부터 syscall 을 안 낸다 (run72). 그러니 test.exe 초기화에서는 이 창구에 쪽지가 한 번만 온다 `[정적]`.

### 2.4 일꾼을 뽑는 조건 일곱 — `ExpWorkerFactoryCheckCreate` `[정적]`

#### 새 말 — 우편함의 두 숫자

- **`SignalState`** — 우편함 줄에 **쌓여 있는 봉투 수**. 넣기가 줄 꼬리에 붙일 때 ++ 한다 (2.3 10번).
- **`CurrentCount`** — 이 우편함에서 일을 받아 **지금 돌고 있는 일꾼 수**. run 문서 조건 5 의 뜻 칸 "CPU 수만큼 이미 일하는 중이 아님" 에 맞춘 읽기다. 언제 오르내리는지는 안 읽었다 (Q227 ②).
- 둘 다 PDB `_KQUEUE` 칸이다 (결과서).

#### 새 말 — 기록판, 부드러운 최대

- **기록판** = 공장 `f+0x48 ~ +0x67` 의 **최근 일꾼 4명 칸**. `ExpCheckThreadHistory(f)` 가 이걸 보고 참/거짓을 낸다 `[정적]`. **무슨 기준인지 뜻은 `[공백]`** (Q227 ④).
  - 칸 4개가 다 비면 거짓이다 (결과서 1-3).
- **부드러운 최대** = `f+0x18c`. 최대 (`f+0x17c`) 와 별도로 둔 "가능하면 이만큼까지" 선 `[추측: 이름]`. 클래스 `0xe` 로 정한다 (2.13 표).

#### 조건 표 (run 문서 2절 그대로) — 모두 참일 때만 뽑는다

| # | 조건 | 줄 | 뜻 |
|---|---|---|---|
| 1 | `f+0x190 == 0` | `+0x8b` | 이미 뽑는 중이 아님 |
| 2 | `f+0x180 < f+0x17c` | `+0x94 ~ +0x9a` | 일하는 사람 < 정원 |
| 3 | `P+0x1c == 0` | `+0xa6` | 우편함 앞에 기다리는 사람 없음 |
| 4 | 우편함 `SignalState ≠ 0` 또는 `P+0x18 ≠ 0` | `+0x10c` · `+0x112` | 일이 있음 |
| 5 | 우편함 `CurrentCount < KeNumberProcessors` | `+0x128 ~ +0x133` | CPU 수만큼 이미 일하는 중이 아님 — **걸림 ①** |
| 6 | `ExpCheckThreadHistory(f)` 거짓 | `+0x148 ~ +0x14f` | 기록판 — **걸림 ②** |
| 7 | `f+0x18c == 0` 또는 `f+0x180 <= f+0x18c` | `+0x15e ~ +0x16c` | 부드러운 최대 — **걸림 ③** |

- 1 ~ 4 중 하나라도 아니면 `+0xac` 에서 상태 비트만 지우고 **그냥 돌아간다** (안 뽑음, 미룸도 없음).
- 5 ~ 7 은 **"걸림"** 이다. 걸리면 그냥 포기하지 않고 **미룬다** (2.5).
- 다 맞으면: bit 9 끔 → **`f+0x190` ++ (`+0x180`)** → 락 풀기 → **`+0x19b ExpWorkerFactoryCreateThread(f)`**.

#### ★ 새 공장의 첫 넣기 — 일곱이 다 맞나? 단계별로

1. 근거 `[정적]`: 새 공장은 일꾼 0 → 조건 1 (`f+0x190` 0), 2 (`0 < 최대`), 3 (기다리는 사람 0) 참.
2. 근거 `[정적]`: 방금 넣기로 `P+0x18 = 1`, 우편함에 쪽지 1 → 조건 4 참.
3. 근거 `[정적]`: 아무도 안 일하니 `CurrentCount 0` → 조건 5 참 (CPU 가 1개 이상이면).
4. 근거 `[정적]`: 기록판이 비었으니 `ExpCheckThreadHistory` 거짓 → 조건 6 참.
5. 근거 `[정적]`: 부드러운 최대 0 → 조건 7 참.
6. 그래서 → **전부 참 → 그 자리에서 만든다.** run72 `[추측]` "첫 넣기가 일꾼을 만드는 계기" → **맞다 `[정적]`**.
7. 아직 확인 아님: 실제로 그 자리에서 섰는지 (콜스택) 는 동적 **Q226** ①.

### 2.5 걸리면 — 미룸, 그리고 관리 스레드 `[정적]`

#### 새 말 — 미룸 · 관리 스레드

- **미룸** = 지금 안 뽑고, 타이머를 걸어 **조금 뒤에 다시 둘러보기**.
- **관리 스레드** `ExpWorkerFactoryManagerThread` = 부팅 때 커널이 만든 **시스템 스레드** (`ExpWorkerFactoryInitialization +0x1b9 PsCreateSystemThread`). 미룬 일을 맡는다.
  - 비유: 관리사무소의 **순찰 직원**. 타이머가 울리면 "아까 미룬 파견소" 를 다시 둘러본다.

#### 미루는 단계 — 30 ms → 120 ms → 그냥 뽑기

- 걸림 ① ② ③ 에 처음 걸리면: 단계 비트 (`0x40` / `0x10` / `0x1000`) 를 켜고 **타이머 종류 3 (30 ms)**.
- 다시 둘러볼 때 또 걸리면: 다음 단계 비트 (`0x80` / `0x20` / `0x2000`) · **종류 2 (120 ms)**.
- 그다음 다시 둘러볼 때는 **그 검사를 건너뛰고 뽑는다.**
- 미루기 공통 (`+0x24d ~ +0x28b`): bit 3 켜기 → 미룬 목록에 넣기 (`+0x27f`) → `+0x286 ExpSetWorkerFactoryDeferredCreateTimer(종류)`.
- 타이머 종류 (결과서): 3 = 30 ms, 2 = 120 ms, 1 = `ExpWorkerFactoryThreadCreationTimeoutInSeconds` 초 (파일 초기값 10). 한 번에 하나, 더 급한 종류가 이긴다.
- 순찰 직원이 처리하는 길: `+0x60 ExpWorkerFactoryDeferredThreadCreation` → `+0x59 CheckCreate(f, 락, 1)` (셋째 인자 1 = 미룬 일 다시 하기).

- 비유: "지금 CPU 자리가 다 찼네. 30 ms 뒤에 다시 와 볼게." → 또 찼으면 "120 ms 뒤에." → 그래도 찼으면 "그냥 한 명 보낼게."

#### 뽑기에 실패하면

- `f+0x190` -- (`+0x1b6`).
- 상태가 `0xc000000a` · `0xc000010a` · `0xc00000f2` · `0xc0000001` 이면 **조용히 포기**.
- 그 밖이면 bit 8 켜고 **종류 1 (길게)** 로 미룬다.

#### 새 말 — 멀리 있기 · 묶음 수 (짧게)

- **묶음 수** = `f+0x194`, 클래스 3 으로 바꾼다 `[추측: 이름]`.
- **멀리 있기** (`ExpTryEnterWorkerFactoryAwayMode`) = 묶음 수가 0 이 아니고 우편함이 비었으면 bit 9 · 10 을 켜고 **우편함에 알림을 걸어 둔다**. 일이 들어오면 순찰 직원이 둘러보기를 한다 (`Manager +0xc3`) `[정적]`.
  - 비유: 파견소가 잠깐 자리를 비우며 우편함에 "봉투 오면 순찰 직원 불러 주세요" 벨을 달아 두는 것.
- 넣기 창구는 먼저 이걸 끈다 (2.3 7번, `+0x11f`).

### 2.6 일꾼을 뽑는 계기 — 전부 `[정적]`

`CheckCreate` · `CreateThread` 를 부르는 곳을 `_calls.tsv` 로 다 모은 표 (run 문서 2절).

| 계기 | 줄 | 한 줄 |
|---|---|---|
| 넣기 | `NtRelease +0x201` → `CheckCreate` | 2.4 조건표 |
| 일꾼이 일을 집은 뒤 (연쇄) | `NtWait +0xa5d` → `CheckCreate` | 일하는 수 < 최대 · 기다리는 사람 0 이면 (2.10) |
| 설정 클래스 3 (묶음 0 → ≠ 0) | `Set +0x59a` → `CheckCreate` | 우편함에 이미 일이 있을 때뿐 |
| 설정 클래스 4 (최소 올림) | `Set +0x74f` → `CreateThread` **직접** | 조건 검사 없음 (2.12) |
| 설정 클래스 5 (최대) | `Set +0x513` → `CreateThread` **직접** | 옛 최대 0 · 일이 있을 때, 실패는 삼킴 |
| 관리 스레드 | `Manager +0xc3`, `DeferredThreadCreation +0x59` | 미룸 · 멀리 있기 |

- 그리고 **없는 것** 하나: `NtCreateWorkerFactory` 는 `CreateThread` · `CheckCreate` 를 **안 부른다** (`_calls.tsv` 에 없음) `[정적]`.
  - → **파견소를 차리는 것만으로는 일꾼이 안 생긴다.** 일감이 들어와야 생긴다.

### 2.7 뽑는 길 — `NtCreateThreadEx` 와 같은 길 `[정적]`

```
ExpWorkerFactoryCreateThread(f)
 ├─ +0x6a   ExAcquireRundownProtection(f+0x68)      (실패 → 0x80)
 │  +0x87   P+0x21 (마감) 이면 안 만듦 · +0x91 f+0x188 ++
 ├─ +0xea   RtlpCreateUserThreadEx
 │   └─ +0x151  ZwCreateThreadEx  ⇒ nt!NtCreateThreadEx → +0x2d2 PspCreateThread
 │                                    → +0x283 PspAllocateThread · +0x2ea PspInsertThread   (run74)
 ├─ +0x142  ZwSetInformationThread(3, …)              (f+0x19c ≠ 0 일 때만 — 2.12)
 ├─ +0x158  ZwResumeThread                            ← 멈춰 만든 스레드를 푼다
 └─ +0x164  ObCloseHandle
```

(run 문서 3절 나무에서 줄였다. ret 자리. `NtCreateThreadEx` 아래는 run74 의 ret.)

- 첫 줄 `ExAcquireRundownProtection` 은 공장이 치워지는 중이면 못 들어오게 막는 **문** 으로 알려져 있다 `[추측: 일반적으로 알려진 설명]`. 실패하면 `0x80` 이다 `[정적]`.

#### 한 줄 읽기 — `ExpWorkerFactoryCreateThread +0xe5` (call) / `+0xea` (ret)

- **누가**: 파견소의 "한 명 뽑기" 담당 `ExpWorkerFactoryCreateThread`.
- **어디서**: `+0xe5` 에서 부르고 `+0xea` 로 돌아온다. 돌아오면 `+0xea` 에서 상태를 `f+0x1a0` 에 적어 둔다 (마지막 만들기 상태).
- **누구를**: `RtlpCreateUserThreadEx` — 커널 안에서 **유저 스레드 하나를 만드는 도우미**. 이 도우미가 다시 `+0x14c ZwCreateThreadEx` 를 부른다.
- **무엇을 위해**: 장부 칸 (`f+0x18` · `+0x20` · `+0x38` · `+0x40`) 에 적힌 값으로 새 직원을 들이려고 (2.8).

#### 왜 "같은 길" 인가 — 그리고 다른 점 하나

- `ZwCreateThreadEx` 는 `NtCreateThreadEx` 로 들어간다. 사용자 `CreateThread` 가 타는 그 창구다 (run74 · run90). 그래서 그 아래 `PspCreateThread` → `PspAllocateThread` · `PspInsertThread` 도 똑같다 `[정적]`.
- 다른 점은 **부른 쪽이 커널** 이라는 것뿐이다.
  - **새 말 — `PreviousMode`**: 이 syscall 을 부른 쪽이 유저인지 커널인지 적힌 칸. 커널이 `Zw*` 안쪽 문으로 들어오면 `Kernel` 이 된다 `[추측: Zw 스텁 30B 는 안 읽음]`.
  - 비유: 같은 창구에 낸 신청서지만, **관리사무소 직원이 직접 낸** 신청서라 "손님 손잡이가 진짜인가" 같은 검사 몇 개를 건너뛴다.
  - 그 건너뜀이 보이는 줄 `[정적]`: `NtCreateThreadEx +0x86 ~ +0x8c` (핸들 쓸 곳 검사 건너뜀), `+0xcb ~ +0x12c` (속성 · 프로세스 핸들에 `PreviousMode` 넘김 → 커널 핸들 허용).

#### "멈춘 채 만들고 바로 푼다"

- 만들기 플래그 (`CreateFlags`) 에 늘 `0x1` (멈춘 채로) 이 들어간다 (2.9).
- 그래서 `PspInsertThread` 가 새 직원에게 **대기 팻말** 을 건다 (run74 해설 2.6 (바)).
- 그다음 **같은 호출 안에서** `+0x153 ZwResumeThread` 가 팻말을 뗀다.
- 왜 굳이 멈췄다가 푸는지는 run 문서 · 결과서에 없다 (모름).
- 앞뒤로 `KeEnterCriticalRegion` · `KeLeaveCriticalRegion` 으로 감싼다. 실패면 `f+0x188` -- (`+0x19f`) 하고 상태를 돌려준다.
- **공장을 만든 프로세스에서만** 돈다. `NtCreateWorkerFactory` 는 "공장을 만드는 스레드의 프로세스" 가 아니면 `0xc000000d` 로 거절한다 (`+0x130 ~ +0x137`) `[정적]`.

### 2.8 새 일꾼의 첫 값 — 장부에서 온다 `[정적]`

| 새 스레드 값 | 장부 칸 ← 어디서 | 0 이면 |
|---|---|---|
| 프로세스 | `f+0x28` ← `NtCreateWorkerFactory` 5번째 인자 (커널 핸들로) | — |
| **시작 주소** (`Rcx`; `Rip` = `RtlUserThreadStart`) | `f+0x18` ← 6번째 인자 | — |
| **시작 인자** (`Rdx`) | `f+0x20` ← 7번째 인자 | — |
| **스택 예약** (`MaximumStackSize`) | `f+0x38` ← 9번째 인자 | `0x10000` |
| **스택 커밋** (`StackSize`) | `f+0x40` ← 10번째 인자 | `0x1000` |
| `ZeroBits` | 0 | |
| **만들기 플래그** | `0x1` 또는 `0x11` (2.9) | |

그럼 ntdll 은 공장을 만들 때 무엇을 넘기나 (`TpAllocPoolInternal.asm`, 결과서) `[정적]`:

- 프로세스 `-1` (= 자기 가게, `+0x2ee`)
- **시작 = `TppWorkerThread`** (`+0x2e2`, rva `0x1a2e0`)
- **인자 = 풀** (`+0x2dd`)
- **스택 = exe 헤더 `SizeOfStackReserve` / `SizeOfStackCommit`** (`+0x76` · `+0x7a`)
- 최대 = 인자 (0 이면 KUSD `+0x3c0` × 4 — 이름 `[추측: ActiveProcessorCount]`), 512 미만이면 512 (`+0x2a5 ~ +0x2c0`)

→ 그래서 새 일꾼은 **`RtlUserThreadStart(TppWorkerThread, 풀)`** 로 시작한다. 업무 시작 메모는 run74 `NtCreateThreadEx +0x1bf ~ +0x236` 과 같은 모양이다 `[정적]`.

- 비유: 파견소 장부에 "새 사람이 오면 **본업 자리는 `TppWorkerThread`**, 손에 쥐여 줄 건 **사무실 주소 (풀)**, 작업대는 **가게 설계도에 적힌 크기**" 라고 미리 적어 두었다. 뽑을 때마다 그 칸을 그대로 옮겨 적는다.

### 2.9 ★ `CreateFlags` `0x1` / `0x11` — 로더 풀 일꾼만 `LoaderWorker`

run69 이 남긴 `[공백]` "bit 11 의 뜻" 이 여기서 닫혔다. 사슬이 길어서 단계별로.

1. 근거 `[정적]` (run125): `ExpWorkerFactoryCreateThread +0x1f` · `+0x36` · `+0x62` — 만들기 플래그 = `1` 에 `(f+0x198 & 0x800) >> 7` 을 OR 한 값.
   - `0x800` 은 bit 11. 이걸 7 칸 오른쪽으로 밀면 `0x10`.
   - 그래서 bit 11 이 꺼졌으면 **`0x1`**, 켜졌으면 **`0x11`**.
2. 근거 `[정적]` (run74): `CreateFlags` `0x10` → 내부 양식 `0x80` → TEB `SameTebFlags.LoaderWorker` (`0x2000`).
3. 근거 `[정적]` (run125): 공장 bit 11 은 설정 클래스 `0xd` 값의 bit 0 에서 온다 (`Set +0x2c6 AND ECX,1` · `+0x2c9 SHL ECX,0xb` · `+0x2d8`).
4. 근거 `[정적]` (run69): ntdll 은 **로더 풀에만** 클래스 `0xd` 를 부르고 (`TpAllocPoolInternal +0x443`), 그 값은 둘째 인자 `& 1` = 1. 기본 풀은 `0xd` 를 안 부른다.
5. 그래서 → **로더 풀 일꾼 = `CreateFlags 0x11` → `LoaderWorker`**, **기본 풀 일꾼 = `0x1`** (TEB 비트 없음) `[정적 사슬]`.
6. 덤 `[정적]`: `RtlpCreateUserThreadEx +0x73` 은 `& 0x77` 만 통과시킨다. 이 길에선 `0x2` (`SkipThreadAttach`) · `0x20` (`SkipLoaderInit`) 이 **안 켜진다**.

- 비유: run69 해설에서 "짐 들이기 팀용" 사무실 주문서엔 체크가 하나 더 있어서, 업체가 파견소에 **표시 하나** 를 붙여 줬다. 그 표시의 뜻이 이제 나왔다 — "**이 파견소에서 보내는 사람은 입사 서류에 '짐 들이기 일꾼' 체크를 해서 보내라**". 그 체크가 직원 안내판에 `LoaderWorker` 표시로 옮겨 적힌다.
- 아직 확인 아님: 실제 `NtCreateThreadEx` 입구에서 `0x11` 이 보이는지는 동적 **Q226** ②.

#### 결과서는 "동적" 이라 했는데 — flow-writer 대조

- 결과서 "동적으로 확인할 것" 3 은 ntdll 이 클래스 `0xd` 에 넣는 값을 "동적 값 필요" 로 남겼다.
- 그런데 그 값 칸 `[RSP+0xb8]` (`TpAllocPoolInternal +0x434 LEA R8`) 은 run69 `[정적]` 이 이미 "둘째 인자 `& 1`" 로 정했다.
- 그래서 run 문서는 "로더 풀 bit 11 = 1" 을 **정적으로 닫힘** 으로 적고, 동적은 확인용으로만 남겼다.

#### run54 정정 하나

- run54 는 "`SkipThreadAttach` · `LoaderWorker` · `SkipLoaderInit` … 로더 일꾼 (`NtCreateThreadEx` 길) 에서만 켜짐" 이라고 적었다.
- 이번 결과로 좁혀졌다: 일꾼 공장 길에서 켜질 수 있는 건 **`LoaderWorker` 하나** 다. `SkipThreadAttach` · `SkipLoaderInit` 은 그 플래그를 **직접 넘기는** `NtCreateThreadEx` 호출자에서만.
- run54 문서 맨 위에 한 줄로 붙었다 (run 문서 "정정").

### 2.10 일꾼 쪽 — "왔어요" 와 "봉투 기다리기" `[정적]`

#### `NtWorkerFactoryWorkerReady` — 일꾼 수 칸의 한살이

뽑힌 직원이 출근해서 맨 먼저 하는 "왔어요" 다 (접근 `0x10`). 칸이 이렇게 움직인다:

1. 둘러보기 (`CheckCreate`): `f+0x190` ++ (뽑는 중)
2. 뽑기 (`CreateThread`): `f+0x188` ++ (뽑혔는데 아직 안 옴)
3. "왔어요" (`Ready`, `+0x66 ~ +0x90`): `f+0x190` --, `f+0x188` --, `f+0x180` ++, `f+0x184` ++
   - `f+0x190 == 0` 이면 `0xc0000001`, `f+0x188 == 0` 이면 `0xc000010a`.
4. 줄일 때 (2.11): `Wait` 가 `f+0x180` · `f+0x184` 를 내린다.

- 비유: 파견소 장부의 "뽑는 중" → "가는 중" → "일하는 중" 칸으로 이름이 옮겨 간다.
- 이 차례 때문에 **"왔어요" 전에 둘째 넣기가 와도 일꾼을 더 안 뽑는다** — 조건 1 (`f+0x190 == 0`) 이 거짓이니까.

#### `NtWaitForWorkViaWorkerFactory` — 봉투 꺼내기

인자: `(핸들, 패킷 배열, Count, &꺼낸 수, DeferredWork)`.

| 단계 | 줄 | 내용 |
|---|---|---|
| 검사 | `+0x10d ~ +0x116` | `Count` 1 ~ `0x7ffffff`, 아니면 `0xc000000d` |
| 마감 | `+0x284` | `P+0x21 ≠ 0` → **`0x80`** |
| **기다림 표시** | `+0x2d8` | **`P+0x1c` ++** (우편함 앞에 한 명 섬) |
| **꺼내기** | `+0x6ba` | **`IoRemoveIoCompletion`** (시간 제한 NULL) |
| 뒤처리 | `+0x6ca` | `ExpWorkerFactoryFinishDeferredWork` |

(run 문서 4절 표에서 골랐다.)

- **출력 한 칸 = `0x20` 바이트**: `{ KeyContext, ApcContext, IoStatus 상태, IoStatus 정보 }`. 한 번에 `Count` 개까지.
- **빈 쪽지가 일꾼 눈에 어떻게 보이나**: 패킷 종류 4 → `IoRemoveIoCompletion +0x1d1 ~ +0x1ec` 에서 네 칸을 복사한 뒤 콜백 (2.3 "N 번 넣었는데") 을 부른다. → **일꾼은 "네 칸이 모두 0 인 항목 1개" 를 받는다.**
- **일감이 없으면 시간 제한 없이 잠든다** (`P+0x1c` 를 올린 채).
  - run93 해설 2.11 의 "시간 0 이면 `0x102` + 0개" 와 다르다. 이번 호출은 시간 칸이 **NULL** (= 끝없이) 이라 빈손으로 돌아오지 않는다.

#### 일을 집은 뒤 — 연쇄 `[정적]`

1. 봉투를 꺼내면 `P+0x1c` -- (우편함 앞에서 빠짐).
2. 기록판에 자기를 적는다.
3. 일하는 수 < 최대 · 기다리는 사람 0 이면 `+0xa5d CheckCreate`.
4. 그래서 → **일이 쌓여 있으면 일꾼이 하나씩 늘어난다.**

- 비유: 첫 사람이 봉투를 들고 자리를 뜨면서 우편함을 돌아본다. "아직 봉투가 남았는데 기다리는 사람이 없네" → 파견소에 한 명 더.

### 2.11 끝내는 신호 — `0x80` 과 `0x102` `[정적]`

#### 새 말 — 마감 · 줄이기 · 놀기 제한

- **마감** = 공장을 닫는 것. `NtShutdownWorkerFactory` 또는 마지막 핸들이 닫힐 때 (`ExpCloseWorkerFactory`) `ExpShutdownWorkerFactory` 가 `P+0x21 = 1` 을 켠다.
  - 비유: 파견소 문에 "**문 닫는 중**" 팻말.
- **줄이기** = 일꾼이 너무 많거나 너무 오래 놀았을 때 한 명을 돌려보내는 것.
- **놀기 제한** = `ExpWorkerFactoryThreadIdleTimeoutInSeconds` (파일 초기값 **67초**, `1 ~ 600` 으로 자름). 공장 `f+0x70` 에 음수 100ns 로 들어간다.

| 상태 | 언제 | 줄 |
|---|---|---|
| `0x80` | 들어올 때 이미 마감 | `+0x284` → `+0xbc6` |
| `0x102` ① | 루프 머리: 최대 < 일하는 수 (클래스 5 로 낮춤) 또는 마감 | `+0x2ff ~ +0x30e` → `+0x932` |
| `0x102` ② | 놀기 제한 지남 **이고** `WantsToCreate(f, 1)` 거짓 · 일하는 수 > 최소 · 이 스레드 `IrpList` 비었음 | `+0x726` → `+0xaa5 ~ +0xaf6` |

- 놀기 제한은 `Wait` 의 인자가 아니다. 순찰 직원이 공장 타이머 알림을 받고 `KeTimeOutQueueWaiters` 로 따로 깨운다 (`Manager +0x115`).
- 마감 길: 기다리는 일꾼이 있으면 쪽지를 넣어 (`+0x13b`) **한 명씩 연쇄로** 깨운다. 깨어난 일꾼은 빈 쪽지를 받고 성공으로 돌아가고, **다음 `Wait` 가 `0x80`** 을 받는다.
- 이 신호를 받은 일꾼이 정말 스레드를 끝내는지는 ntdll 쪽 일이다 `[추측]` — `TppWorkerThread` 안은 안 읽었다 (Q227 ①).

### 2.12 설정 클래스 4 · `0xb` `[정적]`

둘 다 입력 **4바이트**, 길이가 다르면 `0xc0000004`, 핸들 접근 4.

#### 클래스 4 — 최소 스레드 (`f+0x178`)

1. 마감이면 `0x80`.
2. 새 값 > 옛 `f+0x178` 이면 "올렸다" 표시, **`f+0x178 = 새 값`** (값 검사 없음).
3. 최대가 새 최소보다 작으면 최대를 끌어올림.
4. 안 올렸으면 끝 — **같거나 줄인 값은 칸만 바꾸고 상태 0**.
5. 올렸으면 **`f+0x188 + f+0x180 < f+0x178` 인 동안** `f+0x190` ++ → `+0x74f ExpWorkerFactoryCreateThread` (루프 `+0x724 ~ +0x768`).

- → **최소를 N 으로 올리면 그 호출 안에서 모자란 만큼 한꺼번에 뽑는다.** 일감 · CPU 수 · 기록판 검사 없음.
- 비유: "이 파견소엔 늘 최소 N 명" 이라고 고쳐 적으면, 모자란 만큼 **그 자리에서** 다 보낸다. 2.4 의 일곱 조건은 안 본다.
- 이름 `[추측: 공개 헤더 WorkerFactoryThreadMinimum]`.

#### 클래스 `0xb` — 일꾼 기본 우선순위 (`f+0x19c`)

- 점프 표 A 를 안 거친다: `+0x67 CMP EBX,0xb` · `+0x6a JNZ` 로 `0xb` 만 따로 간다.
- **`f+0x19c = 입력`** (값 검사 없음). 상태는 마감이면 `0x80`, 아니면 0. **마감이어도 칸은 이미 쓴다.**
- 지금 있는 스레드엔 아무 일도 안 한다. **앞으로 뽑는 일꾼에만** `CreateThread` 가 `ZwSetInformationThread(3, …, 4)` 를 건다 (2.7 나무의 `+0x142` 줄).
- 이름 `[추측: WorkerFactoryThreadBasePriority]`.

### 2.13 Q134 (b) — 클래스별 몸 자리 `[정적]`, 이름은 모두 `[추측]`

run69 때 Ghidra 가 **점프 표를 못 풀어서** 남은 공백이다. 이번엔 결과서가 `ntoskrnl.exe` 파일 바이트에서 점프 표 셋을 직접 풀었다.

- A = 클래스 → 길이 검사 (rva `0x3a77ac`, 16칸)
- B = 읽기 (`0x3a773c`, 14칸, 클래스 − 2)
- C = 락 안 몸 (`0x3a7774`, 14칸, 클래스 − 2)

run69 이 부른 넷 + 이번 둘만 (전체는 run 문서 5절 표):

| 클래스 | 이름 `[추측]` | 몸 | 한 줄 |
|---|---|---|---|
| 2 | 놀기 제한 | C[0] `+0x676` | `f+0x70` ← 값, `KeSetTimer2` — run69 "유휴 시간" 맞음 |
| 3 | 묶음 수 | C[1] `+0x3ff` | `f+0x194` ± 값, 0 → ≠ 0 이면 멀리 있기 → `CheckCreate` |
| 4 | 최소 스레드 | C[2] `+0x547` | 2.12 |
| 5 | 최대 스레드 | C[3] `+0x494` | `f+0x17c` ← 값, 조건이면 일꾼 1 직접 — run69 "최대 스레드" 맞음 |
| `0xb` | 기본 우선순위 | C[9] `+0x780` | 2.12 |

- 길이는 run69 표 (2 = 8 · `0xa` = `0x10` · `0xf` 가변 · 나머지 4) 와 같다.
- 클래스 이름은 PDB 에 열거가 없어서 **정적으로 더 닫을 길이 없다** (run 문서 맨 위).

### 2.14 ★ 한 장으로 — 일감을 넣었는데 일꾼이 0 이면 `[정적]`

PE_emulator 가 제일 궁금해한 물음이다. 새 풀의 첫 `TppWorkPost` 기준 (run 문서 7절).

1. **같은 syscall 안에서** `P+0x18 = 1`, `P+0x20 = 1`, 우편함에 빈 쪽지 1장 (`SignalState = 1`). 기다리는 일꾼이 없어 줄에 붙인다.
2. `CheckCreate(f, 0, 0)` — 조건 일곱 모두 참.
3. `f+0x190 = 1` → `ExpWorkerFactoryCreateThread`: 같은 프로세스에 **멈춘 채 만들고 바로 푼다**. `f+0x188 = 1`. 넣은 스레드는 그 뒤 syscall 에서 돌아온다.
4. 새 일꾼 (ntdll 쪽): `Ready` → `f+0x190 = 0` · `f+0x188 = 0` · `f+0x180 = f+0x184 = 1` → `Wait` 가 빈 쪽지를 꺼냄 (콜백이 `P+0x18 = 0` · `P+0x20 = 0`) → 풀의 일감 목록을 돈다 `[추측: TppWorkerThread 안은 안 읽음]`.
5. `Ready` 전에 둘째 넣기가 와도 더 안 뽑는다. 일꾼이 일을 집은 뒤 일이 남고 기다리는 사람이 없으면 **하나씩** 더 뽑는다. CPU 수만큼 이미 일하면 30 ms → 120 ms 미룬 뒤.

- PE_emulator 가 "아무것도 안 해서 모두 잠드는" 건 진짜와 다르다. 최소로 필요한 셋 (run 문서): (a) 칸 갱신 (b) 우편함에 빈 쪽지 (c) 조건 맞으면 `PspCreateThread` 다리 한 번. 미룸 · 기록판 · 부드러운 최대 · 놀기 제한은 나중.
- 파일별로 "맞음 / 모자람" 은 run 문서 "PE_emulator 쪽" 표에 있다. 고칠지는 사용자 결정이다. 눈에 띄는 것만:
  - `nt_wait_for_work_via_worker_factory.cpp` 의 **"큐가 비면 `stop`" 은 틀림** — 진짜는 시간 제한 없이 잠든다.
  - `worker_factory_set_length` 에 **`4 → 4` · `0xb → 4`** 가 빠졌다.

### 2.15 test.exe 와 맞물리는 곳

태그가 갈려서 하나씩.

- `[정적]` (run72 + run125) **로더 풀 첫 넣기가 일꾼을 만드는 계기다.** `TppWorkPost +0x4f3` → 커널 `NtReleaseWorkerFactoryWorker +0x201` → `CheckCreate +0x19b` → `CreateThread`. run72 의 `[추측]` 이 닫힌다.

  - run8 `[관찰]` "일꾼에서 `LdrInitializeThunk` 만, DllMain · TLS 콜백 안 불림" 과 run17 `[추측]` "`LoaderWorker` 면 `_LdrpInitialize` 가 첫 스레드를 안 기다림" 이 로더 풀 일꾼 쪽이면 맞물린다 `[추측: 일꾼 2개가 어느 풀 것인지는 동적 그대로]`.
- `[추측]` run44 `[관찰]` 일꾼 2개 (P1a ~ P1b, `ActiveThreads` 1 → 3) 와 **어긋나지 않는다**. 단계별로:
  1. 첫 넣기로 1명 (2.14).
  2. 그 일꾼이 일을 집은 뒤 연쇄 (`Wait +0xa5d`) 로 1명 (2.10).
  3. 로더 풀 최대는 3 (run69) 이라 정원 안이다.
  4. 그래서 "첫 넣기 1 + 연쇄 1" 이 한 모양이다.
  5. 아직 확인 아님: 다른 모양 (둘째 공장 · 미룸) 도 지울 수 없다 → 동적 **Q226** ①.

  - 이건 run62 D10 ("WNF 두 syscall 직후 일꾼 스레드가 생기나") 에 정적 기대로 **보탬** 이 됐다 (run62 문서 맨 위 한 줄).

### 2.16 결과서와 run 문서가 다르게 적은 곳 · 디버거 조심

flow-writer 가 `.asm` · `_calls.tsv` 로 다시 맞춘 곳이다. **뜻은 같다.**

- `ExpRemoveCurrentThreadFromThreadHistory` call 자리: 결과서 "`+0xb1b`" → `+0xb1b` 는 `MOV RCX,RSI`, CALL 은 **`+0xb1e`** (ret `+0xb23`).
- 결과서 "`+0x284 JNZ +0xbbc`": `+0x284` 는 `CMP byte [RCX+0x21],0`, 점프는 그다음 줄.
- 클래스 `0xd` 값 "동적" → run69 정적으로 이미 닫힘 (2.9).

디버거가 붙어서 달라질 수 있는 점 (run 문서 "디버거 메모", CLAUDE.md "따로 적기"):

- 미룸은 **시간** (30 / 120 ms 타이머) 과 우편함 `CurrentCount` 에 달려 있다.
- 커널 멈춤점에서 오래 서 있으면 타이머가 먼저 터지거나 다른 일꾼이 `CurrentCount` 를 붙들고 있어서, **"바로 뽑음" 이 "미뤄 뽑음" 으로 바뀔 수 있다** `[추측]`.
- 그래서 동적 1 · 6 은 조건부 멈춤점 + 바로 `g` 로 하자고 적혀 있다.
- 공장 구조체 타입이 PDB 에 없어서 `dt nt!_…` 로는 못 읽는다. `dq` / `dd` 로 위 오프셋을 직접 읽는다.
