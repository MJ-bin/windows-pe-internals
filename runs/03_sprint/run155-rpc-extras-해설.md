## 1. 이번 바퀴의 질문

### 큰 그림에서 어디인가

run128 ~ run150 과 같은 자리, **초기화 밖** 이다. `main` 뒤 프로그램이 웹을 쓸 때의 옆길이다.

```
cmd.exe 의 부탁 (CreateProcess)
 │  커널: 프로세스 · 주소 공간 · PEB · 첫 스레드
 │  ntdll: LdrInitializeThunk → LdrpInitializeProcess → DLL 들이기 · 전원 켜기
 └─ NtContinue (은퇴) → exe 진입점 → (CRT 점선 상자) → main
                                                        │
      test.exe 는 여기서 RPC 를 안 쓴다 [소스]          │ 웹을 쓰는 프로그램이라면 (요청 쪽 에뮬레이터 로그):
                                                        └─ WinHttpSendRequest                                    (run128)
                                                             └─ 신청 담당 winnsi → 전화 부서 rpcrt4            (run129 · run141)
                                                                  ├─ 메시지 꼴 · 답 배달 · 메뉴 5 내용물         (run133 · run137)
                                                                  ├─ 메뉴 6 · 7 의 내용물 (길이)                 ← 이번 (덤 1)
                                                                  ├─ 걸어 둔 7 을 클라이언트가 거두기 (취소)      ← 이번 (덤 2)
                                                                  └─ 종류 0 · 1 밖 메시지 (4 · 5)                ← 이번 (덤 3)
      ── 다른 가게: nsisvc (서비스) ─────────────────────────┼─────────────────────────
                                                                  └─ 걸린 7 을 서버가 끝낼 때의 답 (0x4c7)       ← 이번 (덤 1 끝)
```

- 이번엔 **신청 담당 (winnsi) 의 서식 설명서** 와 **전화 부서 (rpcrt4) 의 취소 · 정리 길** 을 읽었다. nsi 사무실 (nsisvc) 은 있던 `.asm` 세 개만 봤다.

### 왜 이 질문이 지금 왔나

PE_emulator 쪽 이야기다 (요청 쪽 에뮬레이터 로그 — 진짜 Windows 관찰 아님). 원문 말로 "지금 막는 곳 없음 · 작음". 세 가지가 남아 있었다.

1. **덤 1** — 에뮬레이터가 winnsi 메뉴 6 · 7 몸을 세울 때 스텁 꼴을 **규칙으로 지어** 썼다 (`nsi.cpp` 의 `TODO(VM)`). "6 요청 52 B · 응답 24 B 가 맞나, 7 완료 응답 칸은?"
2. **덤 2** — BG02 판: 6 이 fault → winnsi 가 `+0x302 RpcAsyncCancelCall(7, 1)` → 같은 스레드가 `NtAlpcSendWaitReceivePort(Flags 0x10000, 보내기만)` → 에뮬레이터 `svc_async_unsupported` → `NtDelayExecution(2 ms)` 가 **끝없이** (seq 2136 ~ 2143).
3. **덤 3** — BG03 판: 새 스레드가 이미 묶인 nsi 포트로 첫 메시지를 **종류 ≠ 0 · 1** 로 비동기 보냄 → `svc_lrpc_kind_unsupported` → 곧 프로시저 5 로 이어 감. "누가 무엇을 보내나?"

### 무엇이 궁금했나

### 2.2 한 줄씩 읽는 법

#### 줄 ①: `│  └─ +0xa1  NtAlpcSendWaitReceivePort   Flags 0x10000 · 0x40 B · +0x28 = 4 · 보내기만`

- **누가**: rpcrt4 의 `AlpcSendCancelMessage` (rva `0x62690`).
- **어디서**: call 은 `+0x9a`, 돌아올 자리 (ret) 가 `+0xa1`. 그 바로 앞 `+0x88 MOV EDX,0x10000` 이 둘째 인자 Flags 를 만든다.
- **누구를**: `NtAlpcSendWaitReceivePort` — 커널 ALPC 창구 (syscall).
- **무엇을 위해**: 0x40 B 짜리 "취소" 쪽지 (속칸 `+0x28` = **4**) 를 nsi 사무실 쪽 전화선에 **보내기만** 한다. 받기 칸 · 속성 칸은 다 NULL 이고, 돌아온 값도 안 본다 `[정적]`.

#### 줄 ②: `├─ +0xf5  Sleep(2)   Context MessageId · CallbackId 둘 다 0 인 동안 (끝없음)`

- **누가**: rpcrt4 의 `AlpcCancelMessage` (rva `0x94724`).
- **어디서**: `+0xe9 MOV ECX,2` 로 2 ms 를 넣고 `+0xee` 에서 call, ret `+0xf5`. 그 뒤 `+0xfa JMP +0x27` 로 **다시 칸을 읽으러** 간다.
- **누구를**: `Sleep` — 2 ms 잔다.
- **무엇을 위해**: 커널에 "그 편지 취소해 주세요" (`NtAlpcCancelMessage`, `+0x80`) 를 내려면 그 편지의 **발송 번호** 가 필요하다. 번호 칸이 아직 0 이면 자고 다시 본다. 횟수 · 시간 제한이 없다 `[정적]`.

#### 줄 ③: `└─ +0x73  RpcAsyncCompleteCall(걸린 7, &0x4c7)   일반 응답 32 B (fault 아님)`

- **누가**: nsi 사무실 (nsisvc) 의 `NsipUnsubscribeAndCompleteAsyncCall`.
- **어디서**: call `+0x6c`, ret `+0x73`. 이 함수는 `RpcNsiDeregisterChangeNotification +0x207` 에서 불리고, 그 앞 `+0x1fb MOV EDX,0x4c7` 이 값을 넘긴다.
- **누구를**: `RpcAsyncCompleteCall` — 걸어 둔 비동기 호출을 "끝났어요" 로 닫는 rpcrt4 함수.
- **무엇을 위해**: 손님이 메뉴 6 (해제) 을 내면, 창구에 걸어 둔 메뉴 7 을 **반환값 `0x4c7`** 로 닫아 준다. fault (못 했어요) 가 아니다 (2.7).

### 2.4 ★ 모듈 ID 는 24 B — 가름값이 한 번 더 나간다 (칸 `[정적]`, 사슬 `[추측]`)

run 문서 1-3. 이번 바퀴에서 길이가 갈린 **단 하나의 까닭** 이라 천천히 본다.

#### 새 말 — 공용체 · 팔

- **공용체** = 한 자리에 **여러 꼴 중 하나만** 들어가는 칸. 이번 것은 16 B 자리에 "GUID 16 B" 또는 "8 B 구조체 (LUID `[추측: 이름]`)" 중 하나가 든다 `[정적]` (`0x6ec2` 의 팔 2개).
- **팔** = 공용체가 고를 수 있는 꼴 하나하나. 여기선 값 1 → GUID 팔, 값 2 → LUID 팔.
- 비유: 부서 이름표의 **번호 칸**. 긴 번호 (GUID) 나 짧은 번호 (LUID) 중 하나만 적는다.

#### 새 말 — 가름값

- 공용체에 **지금 어느 팔이 들었는지** 알려 주는 번호. 이번엔 enum16 (2 B) 이다 `[정적]` (`0x6eb8` 의 "가름 종류 ENUM16").
- 비유: 번호 칸 옆 "**긴 번호 / 짧은 번호**" 표시.

#### 새 말 — 비캡슐 공용체

- 가름값이 공용체 **안이 아니라 밖** (둘러싼 구조체의 다른 칸) 에 있는 공용체. 이번 것은 "**구조체 안 4 B 앞 (`fc ff` = −4) 의 `Type`**" 칸을 가름값으로 쓴다 `[정적]` (`0x6eb8` = `FC_NON_ENCAPSULATED_UNION`).
- 비유: "긴 번호 / 짧은 번호" 표시가 번호 칸에 붙어 있지 않고, 이름표 위쪽 **"종류" 칸** 에 이미 적혀 있는 꼴.

#### 이름표의 꼴 (메모리)

| 자리 | 무엇 |
|---|---|
| `0x6eee` | 24 B 구조체: `Length` (SHORT) · 메모리 패딩 2 · `Type` (ENUM16) · 공용체 (`FC_EMBEDDED_COMPLEX` → `0x6eb8`) |
| `0x6eb8` | 비캡슐 공용체, 가름 종류 ENUM16, 가름값 = 앞 `Type` |
| `0x6ec2` | 메모리 16 B, 팔 2개 — 값 1 → GUID 16 B, 값 2 → 8 B |

#### 그런데 선 위에는 — 단계로

1. 서식 기계의 공용체 담당 함수 `NdrNonEncapsulatedUnionMarshall` (rva `0x15440`) 를 읽었다 `[정적]`.
2. `+0x20 NdrpComputeConformance` 에서 가름값을 구한다 (= 앞 칸 `Type` 의 값).
3. `+0x5d` 에서 "가름 종류별 쓰기 표" `[0xe33c0 + 종류 × 8]` 을 읽고 `+0x65` 에서 부른다. 종류 `0x0d` (ENUM16) 칸 = `0x1800900d0` = **`NdrpSimpleTypeEnum16Marshall`** (flow-writer 가 `pefile` · `pdb_aliases.py` 로 다시 확인).
4. 그 함수 바이트를 손으로 읽으면: 값 범위 검사 → 버퍼 2 정렬 → **2 B 쓰기 · 버퍼 포인터 +2** `[정적]`.
5. 그러니 이 함수가 불리면, `Type` 칸 (이미 2 B 나감) 과 **같은 값이 2 B 더** 나간다.
6. 그 뒤 GUID 구조체가 스스로 4 정렬을 하면서 패딩 2 가 생긴다고 읽었다 `[추측: 팔 구조체 함수 안 읽음]`.

→ 선 위 모듈 ID = `Length` 2 (+0) · `Type` 2 (+2) · **가름값 2 (+4)** · 패딩 2 (+6) · GUID 16 (+8) = **24 B** (LUID 면 16 B).

#### 아직 확인 아닌 것 — 사슬

- 위 1 ~ 4 는 **함수 하나 안의 코드** 다 `[정적]`.
- "복잡 구조체 담당이 **이 이름표의 공용체를 그 함수로 넘긴다**" 는 호출 줄은 따라가지 않았다 `[추측]` (결과서: run137 4절의 "NDR 2.0 이면 DCE 엔진" 과 함수 이름으로 이어 봤을 뿐).
- 공개 NDR 에서도 비캡슐 공용체는 "가름값 + 팔" 로 선 위에 나간다고 알려져 있다 `[추측: 기억]`.
- 그래서 진짜 길이는 VM 으로 본다 (4절 동적 1).

비유: 부서 이름표엔 "종류: 긴 번호" 칸이 이미 있다. 그런데 서식 기계는 번호 칸을 쓰기 직전에 **"긴 번호" 도장을 한 번 더** 찍고, 줄을 맞추려고 한 칸을 비운다. 그래서 이름표가 20 B 가 아니라 24 B 가 된다.

### 2.5 ★ run137 고쳐 읽기 — 왜 20 → 24 B, 40 → 44 B 가 생겼나

run 문서 "앞 run 고쳐 읽기". 같은 이름표를 run137 은 20 B 로, 이번엔 24 B 로 읽었다. 어디서 갈렸나.

#### run137 은 이렇게 읽었다 (run137 문서 3-2)

- 모듈 ID = `Length` u16 · 형 u16 (1 = GUID) · GUID 16 = **20 B** → 메뉴 5 요청 = 12 + 20 + 8 = **40 B**.
- 이 풀이는 형식 바이트를 **코드로 따라가지 않고**, "`FC_STRUCTPAD` 는 선 위에 안 나감" · "**비캡슐 공용체 가름값은 앞 멤버**" 같은 NDR 규칙에 기댔다 `[규칙]`. 그래서 표에 가름값 칸이 따로 없다.
- 근거 하나로 "클라이언트 상수 `0x18` 과 앞 12 + 8 = 20 이 맞아떨어짐" 을 들었다.

#### 이번엔 무엇이 새로 보였나

1. **서식 기계 코드를 직접 읽었다** — 가름값을 "앞 멤버에서 **가져오는**" 것은 맞다 (2.4 걸음 2). 그런데 가져온 값을 **버퍼에 한 번 더 쓴다** (걸음 3 · 4) `[정적]`.
2. **상수 근거가 힘을 잃었다** — 메뉴 5 의 클라이언트 상수 `0x18` 은 44 B 와도, 40 B 와도 같지 않다. 이번엔 상수로 선 위 길이를 정하지 않았다 (run 문서 1-1).
3. 그래서 "가름값은 앞 멤버" 규칙을 "선 위에 따로 안 나간다" 로 읽은 것이 4 B 를 빠뜨렸을 것이다.

#### 고쳐 읽기 (run137 문서 · 해설서 맨 위 한 줄씩 — 원문은 그대로)

- 모듈 ID **20 B → 24 B** (LUID 면 16 B).
- 메뉴 5 요청 **40 B → 44 B** (`+0x0c` 모듈 ID 24 · `+0x24` compartment 8) / LUID 면 36 B.
- 응답 24 B 는 그대로 맞다.
- 재미있는 덤: run137 정정 3 이 고쳐 쓴 **run133 의 옛 짐작 "모듈 ID 24 B"** 가 오히려 이번 값과 같다.
- 태그: 칸 · 형식 바이트 · 가름값 쓰는 줄은 `[정적]`, 사슬은 `[추측]` → **"확정 정정" 이 아니라 "고쳐 읽기 (VM 확인 전)"**.

비유: 지난번엔 서식 설명서의 "종류 표시는 위 칸 것을 쓴다" 를 "그러니 따로 안 찍는다" 로 읽었다. 이번에 서식 기계를 직접 열어 보니, 위 칸 것을 **베껴서 한 번 더 찍고** 있었다.

| **7 요청** | **20 B** | 번호표 20 B 하나 |
| **7 응답, 변화 없이 끝냄** | **32 B** | A (포인터 ID 0 · 길이 0) · B (enum16 0 · 패딩 · 포인터 ID 0 · LONG 0 · LONG 0) · 출력 enum16 0 · 패딩 · **`+0x1c` 반환 `c7 04 00 00`** |

- 한 줄 읽기 — **6 요청 56 B**: 앞 12 B 는 메뉴 5 와 같다 (예약 · 모듈 ID 포인터 ID · 객체 번호). 포인터 ID 가 0 이 아니니 `+0x0c` 부터 이름표 본문 24 B (2.4) 가 따라온다. 그 뒤 `+0x24` 부터 번호표 20 B. 12 + 24 + 20 = 56.
- 요청서의 52 B 는 이름표를 20 B 로 셈하면 나오는 수다 (12 + 20 + 20) `[추측: 요청 쪽 셈법은 안 봄]`. 4 B 차이가 2.4 의 가름값 · 패딩이다.
- 세 경우 (56 / 48 / 32) 모두 **끝 20 B 가 번호표** 다.
- "7 응답 출력 0 · 포인터 NULL" 은 서버 스텁이 출력 구조체를 0 으로 채워 돌려준다고 본 것 `[추측: 스텁 초기화]`.
- 배열 포인터가 NULL 이 아니면 32 B 뒤에 배열이 더 붙는다. A 는 `+0x04` 길이를 쓰고, B 의 개수 칸은 `[공백]`.

### 2.7 걸린 7 을 서버가 끝낼 땐 — fault 가 아니라 일반 응답 `[정적]`

run 문서 "요약" · 1-4.

- 손님이 메뉴 6 (해제) 을 내면 nsi 사무실의 `RpcNsiDeregisterChangeNotification` 이 `+0x1fb MOV EDX,0x4c7` → `+0x207 NsipUnsubscribeAndCompleteAsyncCall` → 그 안 `+0x6c RpcAsyncCompleteCall(상태, &[RSP+0x38])`.

#### 새 말 — 홈 칸

- 부른 쪽이 스택에 미리 비워 둔, **레지스터 인자를 받아 적어 두는 칸** `[추측: 일반적으로 알려진 설명 — x64 호출 규약]`.
- 이번엔 `NsipUnsubscribeAndCompleteAsyncCall +0x5 MOV [RSP+0x10],EDX` 로 받은 `0x4c7` 을 홈 칸에 적어 두고, 나중에 `+0x6c` 에서 그 칸 주소 (`&[RSP+0x38]`) 를 넘긴다. 두 자리가 같은 칸이다 `[정적]`. 숫자가 다른 건 그사이 스택 꼭대기가 내려갔기 때문으로 보인다 `[추측]`.
- 비유: 받은 메모를 책상 서랍 첫 칸에 넣어 뒀다가, 나중에 "서랍 첫 칸 걸 보세요" 하고 건네는 것.

#### 그래서

- `RpcAsyncCompleteCall` 의 둘째 인자는 **반환값 자리** 다. 그러니 걸린 7 은 "반환값 `0x4c7`" 로 **보통 답** (LRPC 종류 3) 을 받고 끝난다.
- fault (종류 2, "못 했어요") 였다면 손님 쪽에선 **RPC 오류 `0x4c7`** 이 된다. 진짜는 **RPC 오류 0 + 반환값 `0x4c7`** 이다 (run 문서 PE_emulator 표 `:98`).
- 비유: 걸어 둔 "소식 오면 알려 주세요" 신청을 사무실이 닫을 때, "**못 했어요**" 딱지가 아니라 평범한 답장에 "**결과: 해지됨 (`0x4c7`)**" 이라 적어 돌려준다.

### 2.8 ★ 취소 쪽지 — 종류 4, 0x40 B, 보내기만 `[정적]`

run 문서 2-1 · 2-2. 이제 덤 2. 6 이 **오류로** 돌아왔을 때 이야기다 (서버가 7 을 닫아 줄 기회가 없는 경우).

#### 새 말 — 취소 메시지 (LRPC 종류 4)

- 걸어 둔 호출을 **"그만둘게요"** 라고 서버에 알리는 짧은 메시지. 속칸 `+0x28` 이 **4** 다 `[정적]` (`AlpcSendCancelMessage +0x57`).
- run133 의 종류 표 (0 · 1 · 2 · 3 · 6 · 10 · 11) 에 없던 값이다.
- 비유: 창구에 던지는 "**제 신청 취소요**" 쪽지. 쪽지엔 신청할 때 쓴 **문의 번호** 만 적는다.

#### 거기까지 가는 길 — 단계로

1. winnsi `NsiRpcDeregisterChangeNotificationEx`: 6 이 오류로 돌아오고 (`+0x1b8 JNZ → +0x2ef`), 걸린 7 이 있으면 (`+0x1a9 CMP byte [RDI+0x80],1`) → **`+0x302 RpcAsyncCancelCall(7 의 상태, 1)`**. 그 뒤 `+0x1db` 에서 7 의 신호등을 **INFINITE** 로 기다린다.
2. `RpcAsyncCancelCall` (`0x61e40`) → `+0x7f` 가상 `[vtbl+0xa8]` = **`CancelAsyncCall`** (`0x61f30`).
3. `CancelAsyncCall`: `+0x65 [부름+0x120] |= 4` (취소 중 표시) → 상태 `[부름+0x108]` 가 **9 보다 크고 `0xc` 가 아니면** → **`+0x8a AlpcSendCancelMessage(연결, [+0x124] 호출 ID)`**.
4. 둘째 인자 (`1`) 가 0 이 아니면 `+0xab CancelCall` 로 이어진다 (2.9).

#### 쪽지 0x40 B 의 칸

| 칸 | 값 |
|---|---|
| 전체 | 먼저 0 으로 지움 |
| `+0x00` DataLength · `+0x02` TotalLength | `0x18` · `0x40` |
| `+0x04` Type | `0x4000` |
| **`+0x28` LRPC 종류** | **4** |
| **`+0x34` 호출 ID** | `[부름+0x124]` — 요청 `+0x34` 와 **같은 값** (run133 2.7 의 문의 번호) |
| **보내기** | `NtAlpcSendWaitReceivePort([연결+0x88], 0x10000, &쪽지, NULL × 5)` |
| 반환 | **안 본다** |

- `0x10000` 의 공개 이름은 `[추측: ALPC_MSGFLG_RELEASE_MESSAGE]`. 코드엔 숫자만 있다.

#### 서버는 답하지 않는다 (줄 `[정적]`, 비트 뜻 `[추측]`)

1. 서버 `ProcessIO` 는 ALPC 종류 3 (`[추측: 이름 LPC_DATAGRAM]`) 갈래에서 `+0x9fa` 로 TotalLength ≥ `0x40` 을 보고 → **`+0xa0e HandleCancelMessage(연결, [쪽지+0x34])`**. 이 길은 `+0x28` 을 읽지도 않는다.
2. 답은 `+0xa13 ~ +0xa1f` 에서 **`Type & 0x2000`** 일 때만 `+0xa44` 로 보낸다. 보내기만 한 쪽지는 이 비트가 꺼져 있을 것이라 **답 없음** `[추측: 비트 뜻]`.
3. `HandleCancelMessage` 는 문의 번호가 맞는 호출에 취소 표시 + 상태 바뀜 알림을 건다. 그런데 **취소 알림을 구독한 호출에만** 일이 생긴다.
4. nsi 사무실이 메뉴 7 에 건 구독은 **손님 끊김뿐** 이다 (`RpcNsiRequestChangeNotification +0xd6` EDX = 1 · `+0xdb` R8D = 5).
5. → **걸린 7 은 서버에서 안 끝난다.** 끝내는 쪽은 손님 전화 부서 자신이다 (2.9 · 2.10).

비유: 쪽지를 창구에 **던지고 돌아선다.** 창구 직원은 쪽지를 읽고 "그 신청에 '취소' 딱지" 만 붙인다. 그런데 nsi 사무실은 그 딱지를 보는 사람을 안 두었다. 그러니 신청은 창구에 그대로 걸려 있고, 정리는 손님이 스스로 해야 한다.

### 2.9 ★ 2 ms 잠 — 발송 번호가 적힐 때까지 `[정적]` (커널이 채움은 `[추측]`)

run 문서 2-3.

#### 새 말 — `MessageId` · `CallbackId` (발송 번호)

- run133 해설 2.8 의 **Context 속성** (반송 꼬리표 `MessageContext` 가 든 첨부물) 안의 다른 두 칸. `+0x14` = `MessageId`, `+0x18` = `CallbackId` `[정적: 자리]`.
- 이 글은 `MessageId` 를 **발송 번호** 라 부른다 — 편지를 보낼 때 관리사무소가 매겨 주는 번호로 짐작된다 `[추측]` (커널 안 읽음, 아래 "누가 채우나").
- 비유: 반송 꼬리표 옆에 비어 있는 "**발송 번호**" 칸. 관리사무소 창구가 편지를 받으면서 적어 줄 것으로 보인다.

#### 잠의 차례 (`AlpcCancelMessage`, rva `0x94724`)

1. `+0x15 ~ +0x24`: 인자로 받은 속성 칸의 첫 dword `& 0xc0000000` → `+0x1d RpcpAlpcpGetHeaderSize` → Context 속성 자리 = 칸 + 머리 크기 (Security · DataView 가 켜져 있으면 그만큼 뒤).
2. `+0x27 MOV EDX,[Context+0x14]` — `MessageId` 가 0 이 아니면 `+0x32` 로 진행.
3. 0 이면 `+0xdf` 에서 `[Context+0x18]` (`CallbackId`) 를 본다. 0 이 아니면 `+0xe3 JNZ +0x32` 로 진행.
4. **둘 다 0 이면** `+0xe9 MOV ECX,2` · **`+0xee Sleep(2)`** · `+0xfa JMP +0x27` — 처음으로 돌아가 다시 읽는다. **제한도, 탈출도 없다.**
5. 진행하면: 칸 다섯 `{[+0], [+8], [+0x10], MessageId, [+0x18]}` 을 스택에 베끼고 (`+0x3c ~ +0x5d`) → **`+0x80 NtAlpcCancelMessage(포트, 0, &사본)`** (ret `+0x87`).

#### 누가 그 칸을 채우나 — 단계로

1. 그 Context 속성은 `호출+0x128` 칸이다. 비동기 **요청을 보낼 때** 보내기 속성으로 커널에 넘어간 바로 그 칸이다 `[정적]`:
   - `InitializeRequestAndAttributes +0x1b LEA RSI,[RCX+0x128]`
   - `AlpcNonPipeSend +0x16 LEA R8,[RCX+0x128]` → `AlpcSend +0x10c MOV R9,R14` → `AlpcSend +0x128 NtAlpcSendWaitReceivePort`
2. 그러니 이 칸에 값을 쓸 수 있는 건 **그 syscall 안의 커널** 이다.
3. 커널이 그 안에서 `MessageId` 등을 써 준다는 것은 이 루프와 맞는 짐작이다 `[추측]` (커널 `AlpcpSendMessage` 안 읽음 → Q299).

#### 그래서 BG02 는 — 짐작

- 에뮬레이터는 비동기 요청을 받을 때 Context 속성의 `MessageContext` (`+8`) 만 읽고, `MessageId` 를 안 써 준다 (run 문서 PE_emulator 표).
- 그러면 위 걸음 4 가 영원히 돈다. 요청 쪽 로그의 `NtDelayExecution(2 ms)` 끝없음과 같은 꼴이다 `[추측: 로그 원본 없음]`.

비유: 전화 부서는 "그 편지 회수해 주세요" 를 관리사무소에 내려면 **발송 번호** 가 있어야 한다. 그래서 편지 사본의 발송 번호 칸을 2 ms 마다 들여다본다. 관리사무소가 번호를 안 적어 줬다면? 영원히 들여다본다.
