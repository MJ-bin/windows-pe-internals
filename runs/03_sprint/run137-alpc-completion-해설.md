### 비유 — 그대로 이어 쓴다

- 프로세스 = **가게**, 커널 = **관리사무소**, syscall = 관리사무소 **신청 창구**, 핸들 = **손잡이**.
- run133 의 그림 그대로:
  - rpcrt4 = 가게 안 **전화 부서**, ALPC 포트 = **전화선 끝**, 전화선으로 오가는 것 = **메시지 한 장** (답장도 메시지다).
  - 비동기 대화 = 말을 건네자마자 **수화기를 내려놓는** 방식. 답이 오면 일꾼 사무실로 **"답 왔어요" 알림** 이 오고, 그때 **답을 따로 꺼내러** 간다 (받기만 하는 부름).
  - bind = **첫인사**, 전송 문법 = **말투**, 호출 ID = **문의 번호**.
- run125 · run127 의 그림 그대로:
  - 일꾼 공장 = **파견소**, 그 안 완료 포트 = **우편함**. 일꾼은 우편함 앞에서 **쪽지** (패킷) 를 기다린다.
  - 쪽지엔 **꼬리표** (키) 가 붙는다. 일꾼은 꼬리표를 보고 "이게 누구 일인지" 안다.
- 이번에 새로 붙는 그림 (run 문서 "결과" 비유를 우편함 말로 바꾼 것 — run 문서는 이 비유를 `[추측: 비유]` 로 둔다):
  - 전화 부서는 전화선을 연 뒤 관리사무소에 **한 번** 부탁한다. "이 전화선 끝에 메시지가 오면, 저 우편함에 **이 꼬리표를 붙인 쪽지** 를 넣어 주세요." = **완료 포트 붙이기**.
  - 관리사무소는 **메시지 한 장마다 쪽지 한 장**. "아까 넣은 쪽지를 아직 안 꺼냈으니 이번엔 건너뛰자" 는 없다.
  - 일꾼은 쪽지 한 장에 전화선 끝을 **딱 한 번** 들여다본다 (받기만 하는 부름). 아무것도 없는데 들여다보면 관리사무소는 "없음" (`0xc0000001`) 만 말하고, 전화 부서는 그걸 **큰일** 로 보고 가게를 멈춘다.
  - 그래서 흉내 서버가 지킬 약속은 하나: **메시지 수 = 쪽지 수 = 들여다보는 수.**
- 헷갈리지 않게 — **메시지** 와 **쪽지** 는 다른 것이다.
  - 메시지 (답장) 는 **전화선 끝** (ALPC 포트) 의 줄에 쌓인다. 내용물이 들어 있다.
  - 쪽지 (패킷) 는 **우편함** (완료 포트) 에 쌓인다. 내용물 없이 "꼬리표 · 0 · 0 · 0" 뿐이다. "저 전화선에 뭔가 왔어요" 라는 **알림** 일 뿐이다.

### 한 줄로 먼저 — 무엇을 얻었나

> **전화 부서는 전화선을 연 직후 딱 한 번, `NtAlpcSetInformation(포트, 종류 2, {꼬리표 = TP_ALPC 포인터, 우편함 손잡이}, 0x10)` 으로 전화선을 일꾼 사무실 우편함에 붙인다. 그 뒤 다시 켜는 일은 없다.**
> **관리사무소는 전화선 끝에 메시지가 하나 쌓일 때마다 우편함에 쪽지 `{꼬리표, 0, 0, 0}` 한 장을 넣는다. 일꾼은 쪽지를 꺼내 `TppAlpcpExecuteCallback` → `LrpcIoComplete` → 썽크 → `IoCompleted` 로 가서 받기만 하는 부름을 정확히 한 번 한다.**
> **쌓인 메시지 없이 받기만 하면 관리사무소는 기다리지 않고 `0xc0000001` 을 돌려주고, 전화 부서는 그걸 치명으로 본다. 그러니 "메시지 수 = 쪽지 수 = 받기 수" 가 어긋나면 가게가 죽는다.**
> **EPM 프로시저 8 · nsi 프로시저 5 의 내용물 꼴 (NDR 2.0 판) 도 바이트로 풀었다. 프로시저 8 은 공개 `ept_map` 과 달리 포인터 ID 가 없다. 말투는 클라이언트가 고르지 않고 서버가 고른 비트 하나를 따른다.**

- 모두 `[정적]`. NDR 바이트 자리 · 패딩은 `[정적: 형식 문자열]` + `[규칙: 공개 NDR 2.0]`.

## 1. 이번 바퀴의 질문

### 큰 그림에서 어디인가

run128 ~ run133 과 같은 자리, **초기화 밖** 이다. run133 이 "전화선 위 메시지 꼴" 을 열었고, 이번엔 그 중 비어 있던 **"답이 어떻게 전화 부서까지 돌아오나"** 와 **내용물 바이트** 를 채운다.

```
cmd.exe 의 부탁 (CreateProcess)
 │  커널: 프로세스 · 주소 공간 · PEB · 첫 스레드
 │  ntdll: LdrInitializeThunk → LdrpInitializeProcess → DLL 들이기 · 전원 켜기
 └─ NtContinue (은퇴) → exe 진입점 → (CRT 점선 상자) → main
                                                        │
      test.exe 는 여기서 RPC 를 안 쓴다 [소스]          │ 웹을 쓰는 프로그램이라면 (요청 쪽 에뮬레이터 로그):
                                                        └─ WinHttpSendRequest                              (run128)
                                                             └─ 신청 담당 winnsi → 전화 부서 rpcrt4         (run129)
                                                                  ├─ 보내기: 첫인사 · 본론 메시지 꼴       (run133)
                                                                  ├─ 답 배달: 전화선 → 우편함 → 일꾼 → 받기   ← 이번 (나머지 반쪽)
                                                                  └─ 내용물: ept_map (8) · nsi 5 의 NDR 바이트 ← 이번
```

### 왜 이 질문이 지금 왔나

- PE_emulator 에서 샘플 199 (악성 197) 가 `WinHttpSendRequest` 0 에서 막힌다 (요청 쪽 에뮬레이터 로그).
- 지금 에뮬레이터는 epmapper (114) 연결을 `0xc0000034` 로 답해서 이 길에 아예 안 들어간다 (run129 의 "싼 길").
- 서버 흉내 (114 의 `ept_map` · nsi 프로시저 5) 를 진짜로 돌리려면 run133 이 남긴 두 구멍이 필요했다:
  - **답 배달의 나머지 반쪽** — run133 해설 2.3 에서 "알림이 관리사무소에서 일꾼에게 **어떻게** 가는지는 `[공백]`" 이었다.
  - **내용물 바이트** — run133 해설 2.12 에서 "탑을 싸는 겉봉 (NDR 틀) 은 `[공백]`" 이었다.
- 에뮬레이터 `NtAlpcSetInformation` 은 종류 5 밖이면 멈춘다 (`:602`). 완료 포트 · 일꾼 공장 · 기다림 패킷 몸은 이미 있다 (run93 · run125 · run127).
- 같은 비동기 틀을 RPCSS (`CoInitializeSecurity`, 요청 쪽 21 샘플) 도 쓴다 (원 요청 말).

### 무엇이 궁금했나

1. **완료 포트 붙이기** — `CreateAlpc +0x66` 뒤에 어떤 syscall 이 어떤 차례로 오나, `NtAlpcSetInformation` 의 종류 번호 · 입력 칸 · 길이, 커널이 무엇을 검사하고 무슨 status 로 거절하나.
2. **통지 한 번의 꼴** —
   - (a) 커널이 우편함에 넣는 쪽지의 네 칸과, 메시지마다 하나인지.
   - (b) 일꾼이 쪽지를 받아 `LrpcIoComplete` 를 **어떤 인자로** 부르나. 다시 켜는 syscall 이 있나.
   - (c) 쌓인 메시지 없이 받기만 하면 무슨 status 가 오나, rpcrt4 는 어떻게 다루나, 쪽지 하나에 받기가 몇 번 오나.
3. **NDR 본문 바이트** — EPM 프로시저 8 · nsi 프로시저 5 의 요청 · 응답 내용물.
4. **bind 에서 고르는 말투** — 서버 흉내가 하나만 고를 때 어느 쪽이 안전한가.

### 바퀴 전에 알던 것

- `[정적]` (run129) 비동기 연결이면 `EnableAsync → CreateAlpc → TpAllocAlpcCompletionEx(&결과, 포트, LrpcIoComplete, …)` 로 완료 통지를 건다. 그 안 (ntdll) 은 안 읽었다 (= Q232 ①).
- `[정적]` (run133) 대화 넷은 "보내고 끊기" 다. 답은 `IoCompleted +0xc8` 의 **받기만 하는 부름** 으로 온다. 받기 실패는 `0xc0` · `0xc0000041` 밖이면 **치명**.
  - `[추측]` `LrpcIoComplete +0xc3` 간접 호출의 대상이 `IoCompleted` 라는 것.
  - `[공백]` "쌓인 답이 없을 때" 무엇을 돌려줘야 정상인지.
  - run133 은 받기 Flags 를 "완료 문맥이 있으면 `0x1000000`, 없으면 0" 으로 적었다.
- `[정적]` (run133) bind 답의 수락 마스크는 **비트 하나** 여야 한다. 코드는 NDR 2.0 · NDR64 **둘 다 받는다**. 어느 쪽을 쓰나는 `[추측]` ("`Ndr64AsyncClientCall` 을 쓰니 NDR64 가 자연스러워 보인다").
- `[정적]` (run125) 일꾼은 `NtWaitForWorkViaWorkerFactory` 로 우편함에서 쪽지를 꺼낸다 (한 칸 0x20 B `{KeyContext, ApcContext, 상태, 정보}`). 일꾼 쪽 ntdll `TppWorkerThread` 안은 `[추측: 안 읽음]`.
- `[정적]` (run127) 파일을 우편함에 묶는 `NtSetInformationFile 0x1e` — 꼬리표 · 접근 2 참조 · "이미 묶임" 거절. 이번 ALPC 판과 비교할 짝이다.
- 몰랐던 것: ntdll · 커널 쪽 붙이기 길 전부, 쪽지 칸, 빈 받기 status, NDR 바이트.

### 2.1 한눈에 — 붙이기 · 쪽지 넣기 · 꺼내서 받기 `[정적]`

flow.md 3장 새 절의 나무를 장면 셋으로 나눠 줄였다. 숫자는 ret 자리.

```
장면 1 — 붙이기 (전화선을 연 직후 한 번)
```

### 2.2 한 줄씩 읽는 법

#### 줄 1: `├─ +0x1d6 NtAlpcSetInformation(포트, 2, {키 = TP_ALPC, 풀+0x40 완료 포트 핸들}, 0x10)` (장면 1)

- **누가**: ntdll `TppAllocAlpcCompletion` (rva `0xc95a4`).
- **어디서**: call `+0x1d1`, ret `+0x1d6` (콜스택에 찍힐 값).
- **누구를**: syscall `NtAlpcSetInformation` → 커널 `nt!NtAlpcSetInformation` 이 `+0x13b` (ret `+0x140`) 에서 `AlpcpAssociateIoCompletionPort` 를 부른다.
- **무엇을 위해**: 전화선 (ALPC 포트) 을 일꾼 사무실의 우편함 (풀의 IO 완료 포트) 에 붙인다. 인자 넷:
  - 포트 핸들 — rpcrt4 가 `[연결객체+0x88]` 에서 넘긴 전화선 손잡이.
  - **2** — 정보 종류. `+0x1ca LEA EDX,[R9-0xe]` 로 만든다.
  - 입력 16 B 의 주소 — 꼬리표 (`+0x00`) 와 우편함 손잡이 (`+0x08`).
  - **0x10** — 길이 (`+0x1bf`).
- 이 줄 하나가 이번 질문 1 의 답 전부다. **같은 포트 · 같은 우편함에 대한 syscall 은 이것 하나뿐** 이다 `[정적]`.

#### 줄 2: `└─ +0xc8 ⇢ LrpcCAssociationConnectIoHandler (RCX −= 0xe0, RDX = 0) ⇢ IoCompleted` (장면 3)

- **누가**: rpcrt4 `LrpcIoComplete` (rva `0x53510`).
- **어디서**: call `+0xc3`, ret `+0xc8`. 대상이 코드에 적혀 있지 않은 **간접 호출** (`[R14]`).
- **누구를**: `[R14]` = 문맥의 첫 칸 = 썽크 `LrpcCAssociationConnectIoHandler` (rva `0x96a70`). 썽크는 두 줄만 하고 `IoCompleted` (rva `0x57800`) 로 **꼬리 점프** 한다 (돌아오지 않고 그대로 건너감).
- **무엇을 위해**: 일꾼이 들고 온 "문맥" 을 전화선 하나의 메모판 (연결 객체) 으로 되돌려 `IoCompleted` 에 넘긴다. 2.7 에서 한 걸음씩.
- 이 줄은 run133 에서 `[추측]` 이었다 ("대상이 `IoCompleted` 인 건 `[추측]`"). 이번에 **`[정적]`** 이 됐다 — 다만 직접 대상은 `IoCompleted` 가 아니라 **썽크** 다 (2.15).

### 2.3 장면 1 — 붙이기 차례 `[정적]`

run 문서 1-1 · 1-2.

#### 새 말 — 정보 종류 2 (완료 포트 붙이기)

- `NtAlpcSetInformation` 은 "포트에 무엇을 설정하나" 를 **종류 번호** 로 가른다. run127 해설의 `NtSetInformationFile` 종류 표와 같은 꼴이다.

#### 새 말 — TP_ALPC 객체

- ntdll 이 `RtlAllocateHeap(0x128)` 로 만드는 **0x128 B 덩어리**. "이 전화선의 알림을 일꾼 사무실이 어떻게 처리하나" 를 적어 둔다 `[정적]`.
- 비유: 일꾼 사무실이 전화선마다 만드는 **작업 카드**. 쪽지 꼬리표엔 이 카드의 주소가 적힌다.
- 카드에 적는 칸 (run 문서 1-1):

  | 칸 | 값 | 비유 |
  |---|---|---|
  | `+0x38` | `TppAlpcpExecuteCallback` 주소 | "이 카드는 ALPC 종류" 표시 겸 처리 담당 |
  | `+0x98` | 콜백 = `LrpcIoComplete` | 쪽지가 오면 부를 전화 부서 창구 |
  | `+0xa0` | 문맥 = `&[연결객체+0xe0]` | 어느 전화선 메모판인지 |
  | `+0xd8` | 풀 | 어느 일꾼 사무실인지 |
  | `+0x110` | 포트 핸들 | 전화선 손잡이 |
  | `+0x120` 비트 0 | **Ex** | 아래 |

#### 새 말 — Ex 비트

- `TpAllocAlpcCompletionEx` (29 B) 는 **여섯째 인자에 1 (Ex 깃발) 만 얹고** `TppAllocAlpcCompletion` 으로 넘기는 얇은 함수다 (`+0x9` · `+0x13`) `[정적]`.
- 그 1 이 카드 `+0x120` 비트 0 이 된다. 나중에 콜백을 **4 인자** (뒤에 `ApcContext` 를 하나 더) 로 부르느냐, 3 인자로 부르느냐를 가른다 (2.6).
- rpcrt4 는 Ex 판을 부르니 이 길은 **4 인자** 다.

#### 차례 (run 문서 1-1 줄임)

1. **`AlpcConnect +0x388 IsPortWithSharedSection`** → `NtAlpcQueryInformation(포트, 0, &버퍼, 0x10, NULL)`.

2. **`Connect +0x3b1 EnableAsync`** → 연결 객체 `+0xe0` 칸에 **썽크 주소를 먼저 쓰고** (`+0x64`), `CreateAlpc(포트, …, 문맥 = &[연결객체+0xe0], …)`.

   - 콜백 인자가 코드 줄로 보인다 — `+0x42 LEA R8,[0x180053510]` = `LrpcIoComplete` 시작 (flow-writer 보탬).
   - `PrivatePool` 이 0 이면 환경 = NULL → **전역 풀** (켜는 함수는 안 읽음 `[추측: 안 켜면 NULL]`).
   - 붙이기가 어떤 이유로든 실패하면 `CreateAlpc` 는 **14** 로 바꿔 돌려준다 (`+0x87` → `+0xb6`).
4. **`TppAllocAlpcCompletion`**:

   - **syscall 바로 앞에서 한 번 더** — 풀 NULL · 종료 중 → `0xc000000d` (flow-writer 보탬, `+0x18d` ~ `+0x1a7` → `+0x22a`).
   - **`+0x1d1 NtAlpcSetInformation(포트, 2, &{키, [풀+0x40]}, 0x10)`.**

   - 성공이면 `*결과 = 카드`. 실패면 카드를 치우고 그 status.

| CompletionKey (꼬리표) | `+0x00` | 8 | **TP_ALPC 카드 포인터** — 일꾼이 쪽지 `KeyContext` 로 돌려받는다 |
| CompletionPort (우편함) | `+0x08` | 8 | 풀의 IO 완료 포트 **핸들** (`[풀+0x40]`, run125 의 `TpAllocPoolInternal +0x292 NtCreateIoCompletion` 이 만든 것) |

- 비유: "우편함 열쇠 (`+0x08`) 와, 쪽지에 붙일 꼬리표 (`+0x00`)". run127 의 파일 묶기 (`0x1e`) 와 **칸 순서가 반대** 다 — 그쪽은 `+0x0` 포트 핸들 · `+0x8` 키였다 ([run127 해설 2.5](run127-file-completion-해설.md)). 에뮬레이터가 두 길을 같은 코드로 짜면 여기를 조심해야 한다.
- 꼬리표가 왜 카드 포인터인가 — 일꾼이 쪽지를 꺼냈을 때 꼬리표 하나만 보고 "어느 카드 (= 어느 전화선 · 어느 콜백)" 인지 바로 찾게 하려는 것으로 읽힌다 `[추측]` (2.6 의 `[키+0x38]` · `[키+0x98]` 을 보면 실제로 그렇게 쓴다 `[정적]`).

#### 덤 — 풀어 줄 때도 syscall 이 없다

- `TpReleaseAlpcCompletion` → `TppAlpcpFree` 는 붙인 걸 푸는 `NtAlpcSetInformation` 없이 `TpAdjustBindingCount(풀, −1)` 만 한다 `[정적]`.
- 연결은 포트를 닫을 때 사라진다 `[추측: 닫는 쪽 커널 안 읽음]`.

### 2.4 ★ 장면 1 커널 쪽 — 검사 차례와 실패 status `[정적]`

run 문서 1-3 (`nt!NtAlpcSetInformation` → `AlpcpAssociateIoCompletionPort`). **에뮬레이터가 그대로 따라 할 표** 라 차례를 줄이지 않고 옮긴다.

| 차례 | 검사 | 실패 status |
|---|---|---|
| 1 | 포트 핸들 0 | `0xc000000d` |
| 2 | 입력 NULL | `0xc000000d` |
| 3 | 사용자 모드 · 길이 > 0x48 | `0xc0000004` |
| 4 | 포트 핸들 참조 (접근 1, ALPC 포트 종류) | 그 status (`0xc0000008` · `0xc0000024` · `0xc0000022`) |
| 5 | **길이 ≠ 0x10** | **`0xc0000004`** (종류 5 는 `0xc000000d` — 다름) |
| 6 | 완료 포트 핸들 0 | `0xc000000d` |
| 7 | 포트 잠금 아래 **`[포트+0x20] ≠ 0` (이미 붙음)** | **`0xc0000048`** |
| 8 | `[포트+0x168]` 완료 목록 있음 | `0xc00000bb` |
| 9 | 완료 포트 핸들 참조 (**접근 2**, IO 완료 종류) | 그 status |
| 10 | 꼬리표 저장 + 패킷 쌈 만들기 | 못 만들면 `0xc000009a` |
| 11 | 이미 쌓인 메시지마다 쪽지 하나 | |
| 12 | 성공 | 0 |

(줄 번호는 run 문서 1-3 표.)

읽는 법 — 한 걸음씩:

- **차례 1 ~ 4 는 모든 종류가 같이 지나는 앞부분** 이다. 에뮬레이터의 공통 앞부분이 이미 이 차례 · 값과 맞다 (2.18).
- **차례 5 부터가 종류 2 몫** 이다. 길이가 틀리면 `0xc0000004`. 같은 함수의 종류 5 는 길이가 틀리면 `0xc000000d` 라서, "길이 틀림 = 늘 같은 status" 가 아니다.
- **차례 7 이 차례 9 보다 앞** 이다. 그래서 run 문서의 두 문장이 나온다:
  - "이미 붙은 포트에 **틀린** 완료 포트 핸들을 줘도 `0xc0000048`" — 핸들을 열어 보기도 전에 "이미 붙음" 에서 걸린다.
  - "완료 포트 핸들 0 은 그보다 앞 `0xc000000d`" — 차례 6 이 7 보다 앞이니까.
- 비유: 관리사무소 창구는 "전화선 손잡이 있어요? → 종이 크기 맞아요? → 우편함 열쇠 있어요? → **이 전화선 이미 다른 우편함에 붙어 있지 않아요?** → 우편함 진짜 맞아요?" 순으로 본다.

#### run127 (파일 묶기) 와 다른 점

flow.md 3장 run127 절에 이번에 붙은 한 줄이다.

| | 파일 `0x1e` (run127) | ALPC 종류 2 (이번) |
|---|---|---|
| 우편함 참조 | 접근 2 | 접근 2 (같음) |
| 이미 묶임 | `0xC000000D` (먼저 봄), 경주면 `0xC0000048` | **`0xc0000048`** (잠금 아래 한 번) |
| 쪽지 | 일이 끝날 때 조건에 따라 (성공 · 오류 · PENDING 따라 다름) | **메시지마다** `{키, 0, 0, 0}` — 구분 없음 (2.5) |

#### 새 말 — 완료 목록

- `[포트+0x168]` 칸. PDB `_ALPC_PORT.u1` 비트 16 이름이 `EnableCompletionList` 다 `[정적]`.
- 이 글에서 필요한 건 두 가지뿐이다: 이 장치가 이미 있으면 붙이기가 **`0xc00000bb`** 로 거절되고, 메시지를 이 목록에 올렸을 때만 쪽지 `ApcContext` 가 −1 이 된다 (2.5).
- 이 장치의 본문은 이번에 안 읽었다. rpcrt4 클라이언트 연결 길은 이걸 안 쓴다.

#### 새 말 — 패킷 쌈

- 성공하면 커널이 포트에 남기는 칸 셋 (PDB `_ALPC_PORT` 이름):
  - `+0x20 CompletionPort` — 우편함 **객체** (핸들 아님)
  - `+0x28 CompletionKey` — 꼬리표
  - `+0x30 CompletionPacketLookaside` — **패킷 쌈**
- 패킷 쌈 = 쪽지를 빨리 넣으려고 **미리 만들어 묶어 둔 쪽지 묶음** (`min(4, 동시성)` 개). 묶음 속 쪽지 하나 = `_IO_MINI_COMPLETION_PACKET_USER` 0x50 B `[정적]`.
- 이 칸들은 유저에게 안 보인다. 결과서 말로, 에뮬레이터가 따라 할 건 **"포트에 (완료 포트, 꼬리표) 두 칸"** 뿐이다.

### 2.5 ★ 장면 2 — 쪽지 한 장의 값, 그리고 "메시지 하나 = 쪽지 하나" `[정적]`

run 문서 2-1.

#### 새 말 — 메시지 줄 (`MainQueue`)

- 전화선 끝 (ALPC 포트) 에 도착한 메시지가 쌓이는 줄. `MainQueue` (포트 `+0x90`), 길이는 `MainQueueLength` (`+0x1c0`) `[정적]`.
- 받기만 하는 부름은 이 줄 머리에서 한 장을 꺼낸다.

#### 차례

1. `AlpcpCompleteDispatchMessage` (보내기 · 답 · 닫기 · 연결 요청 처리의 끝) 가 **먼저 메시지를 줄에 넣는다** (`+0x541 INC [포트+0x1c0]`).
2. 대상 포트에 우편함이 붙어 있으면 (`+0x470 CMP [포트+0x20]`) 쪽지를 넣는다. 두 갈래:
   - 보통 → **바로** `+0xeb4 AlpcpQueueIoCompletionPort`.
   - 동기 요청 (`Flags & 0x20000`) 이거나 보내기 길 (`Flags & 4`) 이면 → 표시만 해 두고, `NtAlpcSendWaitReceivePort` 끝 (`+0x176 AlpcpSignal`) 에서 **같은 쪽지** 를 넣는다. 보내는 syscall 이 돌아가기 직전이다.
3. 취소 · 끊기 (`AlpcpSignalPortAndUnlock`) 도 우편함이 있으면 쪽지 하나 (결과서, 디컴파일 첫 갈래).

#### 쪽지 네 칸 (PDB `_IO_MINI_COMPLETION_PACKET_USER`)

| 칸 | 값 | 어디서 |
|---|---|---|
| `KeyContext` (`+0x18`) | 꼬리표 = TP_ALPC 카드 포인터 | 포트 `+0x28` |
| `ApcContext` (`+0x20`) | **0** (완료 목록에 올렸을 때만 −1) | 둘째 인자 |
| `IoStatus` (`+0x28`) | **0** | 상수 |
| `IoStatusInformation` (`+0x30`) | **0** | 상수 |

- 그러니 rpcrt4 클라이언트 길에서 일꾼이 받는 쪽지는 **`{카드 포인터, 0, 0, 0}`** 이다.
- run125 해설 2.10 의 "풀어주기 쪽지" 는 네 칸이 다 0 이었다. 이번 쪽지는 **꼬리표만 채워진** 쪽지다. 일꾼 쪽 `TppPrepareDirectParams` 는 키 ≠ 0 항목을 골라 자기 몫으로 잡는다 (2.6).

#### "메시지 하나 = 쪽지 하나" — 왜 그렇게 말할 수 있나

- 근거 1: `AlpcpQueueIoCompletionPort` 는 **부를 때마다** 쌈에서 한 장 꺼내 넣는다 (`+0x91 ~ +0x97`). 쌈이 가득이면 새 쪽지를 만든다 (`AlpcpQueueIoCompletion`, `+0x2ff ~ +0x31b`).
- 근거 2: 새 쪽지마저 못 만들면 셈 칸 (`PendingNullCount` 등) 을 올려 두었다가, 쪽지가 반납될 때 **대신 넣는다**. 건너뛰지 않는다.
- 근거 3: "이미 넣은 쪽지가 아직 안 꺼졌으면 건너뛰기" 같은 검사 칸이 **없다**.
- 근거 4: 메시지 종류와 상관없다 — 답 (ALPC 종류 2) · 요청 (1) · 닫기 (5) 각각 하나.
- 그래서 → **메시지 k 장 = 쪽지 k 장. 합치지도 빼먹지도 않는다.**
- 덤: 붙이기 **전에** 이미 쌓인 메시지가 있으면, 붙이는 순간 그 개수만큼 쪽지가 한꺼번에 들어간다 (2.4 차례 11). rpcrt4 는 연결 직후에 붙이니 보통 0 장이다.

#### 순서 — 메시지가 먼저, 쪽지가 나중

- 쪽지는 메시지를 줄에 넣은 **뒤** 에 들어간다.
- 그래서 일꾼이 쪽지를 받고 전화선을 들여다볼 때, 메시지는 이미 줄에 있다. 빈 받기 (2.8) 가 정상 길에서는 안 생기는 이유다.

비유: 관리사무소는 답장을 전화선 끝 받침에 **먼저 놓고**, 그다음 우편함에 "저 선에 뭐 왔어요" 쪽지를 넣는다. 답장 한 장마다 쪽지 한 장. 미리 접어 둔 쪽지가 떨어지면 새로 접고, 그마저 안 되면 "나중에 넣을 것" 숫자만 적어 뒀다가 꼭 넣는다.

### 2.6 장면 3 (앞) — 일꾼이 쪽지를 받아 콜백까지 `[정적]`

run 문서 2-2 표 1 ~ 4행.

| 단계 | 하는 일 | 줄 |
|---|---|---|
| 1 | `NtWaitForWorkViaWorkerFactory` 로 쪽지 받기 — 항목 0x20 B `{키, ApcContext, 상태, 정보}` | `TppWorkerThread +0x379` |
| 2 | `TppPrepareDirectParams` — **마지막 (키 ≠ 0) 항목** 을 이 일꾼 몫으로 스택에, 나머지는 풀 일감 줄에 | `+0x46e` |
| 3 | **`[키+0x38]` 함수 주소로 종류 가름** — `TppAlpcpExecuteCallback` 이면 ALPC 갈래 | `+0x536 ~ +0x556` · **`+0x55e`** |
| 4 | `TppAlpcpExecuteCallback` — 참조 · 카운터 · 활성화 문맥 · ETW 뒤 **콜백** | **`+0x449`** |

#### 새 말 — 인스턴스

- 일꾼이 "지금 이 일" 을 처리하는 동안 쓰는 기록. 일꾼 스택 위에 있고, 콜백 첫 인자로 넘어간다 (`RCX = &[RSP+0x198]`) `[정적]`.
- 비유: 일꾼이 일 하나를 잡을 때 책상에 펴는 **작업 메모**.

#### 읽는 법

- 단계 3 이 이 글의 핵심 연결 고리다. 쪽지의 꼬리표 = TP_ALPC 카드 포인터 (2.3) → 카드 `+0x38` = `TppAlpcpExecuteCallback` (2.3 카드 표) → 그래서 일꾼이 "아, ALPC 일이구나" 를 안다.
  - 다른 종류 (`TppIopExecuteCallback` · `TppWaitCompletion` · 간접) 도 같은 칸으로 가른다.
- 단계 4 의 콜백 부름은 카드의 Ex 비트로 갈린다:
  - **Ex 켜짐 (rpcrt4 길)** → `콜백(인스턴스, [TP_ALPC+0xa0], TP_ALPC, ApcContext)` — 4 인자 (`+0x449`).
  - Ex 꺼짐 → 3 인자 (`+0x7e0`) — 이 길 아님.
- 콜백 = 카드 `+0x98` = `LrpcIoComplete`, 둘째 인자 = 카드 `+0xa0` = `&[연결객체+0xe0]`.
- 항목이 여럿 와도 하나씩 와도 결과는 같다 — 일꾼이 마지막 것을 자기가, 나머지는 풀에 맡긴다.

#### 콜백 뒤 "다시 켜기" 는 없다

- 요청서가 물은 것: 콜백이 끝나면 알림을 다시 켜는 syscall 이 있나?
- 답: **없다** `[정적]`.
  - `TppAlpcpExecuteCallback` 안의 `NtAlpcSetInformation` 은 `+0x684` (종류 8, 길이 4) 하나인데, `[TP_ALPC+0x120] & 3 == 3` 일 때만 간다. `TppAllocAlpcCompletion` 은 비트 0 만 쓰므로 이 길에선 안 간다 (비트 1 을 켜는 건 완료 목록 쪽 함수 `[추측]`).
  - 커널 포트에도 켜고 끄는 칸이 없다.
- 그래서 → 2.3 의 붙이기 **한 번** 이 전화선이 살아 있는 동안 계속 간다.

### 2.7 ★ 장면 3 (가운데) — `LrpcIoComplete` 와 썽크 `[정적]`

run 문서 2-2 표 5 · 6행. **run133 의 `[추측]` 하나가 `[정적]` 으로 바뀌는 곳** 이라 천천히 간다.

#### 한 걸음씩

1. `EnableAsync` 가 연결 객체 `+0xe0` 칸에 **썽크 주소를 써 둔다** (`+0x4c LEA R14,[RBX+0xe0]` · `+0x53` 썽크 주소 · `+0x64 MOV [R14],RAX`).
2. 그 칸의 **주소** (`&연결객체+0xe0`) 를 "문맥" 으로 `CreateAlpc` → 카드 `+0xa0` 에 적는다 (2.3).
3. 쪽지가 오면 일꾼이 `LrpcIoComplete(인스턴스, 문맥, TP_ALPC, ApcContext)` 를 부른다 (2.6).
4. `LrpcIoComplete` 는 스레드 객체 `[+0xc0]` 에 인스턴스를 적고, **문맥이 가리키는 칸의 함수** (= 1 에서 써 둔 썽크) 를 `(문맥, ApcContext)` 로 부른다 (`+0xc3`).
5. 썽크 `LrpcCAssociationConnectIoHandler` 는 두 줄만 한다:
   - `RCX −= 0xe0` — 문맥 = `&연결객체+0xe0` 이었으니, 0xe0 을 빼면 **연결 객체 맨 앞** 이 된다.
   - `EDX = 0` — 둘째 인자 (`ApcContext` 가 들어 있던 자리) 를 **0 으로 지운다**.
   - 그리고 `IoCompleted` 로 꼬리 점프.
6. 그래서 `IoCompleted` 는 **`(연결객체, NULL)`** 로 불린다.

- 근거 (run 문서 "확인된 것"): `EnableAsync +0x53 · +0x64` 가 쓰는 칸 · `TppAllocAlpcCompletion` 의 `+0xa0` · `TppAlpcpExecuteCallback +0x43b` · `LrpcIoComplete +0xba` 의 데이터 흐름. 썽크 바이트 (`0x96a70`: `48 81 c1 20 ff ff ff 33 d2 e9 …`) 는 flow-writer 가 `pefile` 로 다시 읽었다.
- 비유: 일꾼이 들고 온 작업 카드엔 "전화선 메모판의 **0xe0 번째 줄**" 주소가 적혀 있다. 그 줄엔 "이 번호로 전화하세요" 메모 (썽크) 가 있다. 썽크는 "0xe0 줄 위로 올라가 메모판 맨 위부터 보세요, 그리고 손님이 맡긴 메모 (`ApcContext`) 는 버리세요" 하고 전화 부서 창구 (`IoCompleted`) 로 넘긴다.

#### 그래서 — 받기 Flags 는 늘 0

- `IoCompleted` 의 둘째 인자 (PDB 형 이름 `RPCP_ALPC_CONTEXT_ATTR*`) 가 NULL 이면 "완료 문맥 없음" 이다.
- run133 은 받기 Flags 를 "완료 문맥이 있으면 `0x1000000`, 없으면 0" 으로 적었다. 이번에 **클라이언트 연결 길에선 썽크가 늘 NULL 을 넘기니 늘 0** 이라는 게 정해졌다.
  - `0x1000000` 갈래 (`IoCompleted +0x277 ~ +0x288`) 는 이 길에서 안 쓰인다.
  - 서버 쪽 (`ServerStartingToListen`) 의 문맥은 다른 썽크일 수 있다 `[공백: 안 읽음]`.
- 그 형의 `+0x14` · `+0x18` 이 ALPC 컨텍스트 속성 (`MessageId` · `CallbackId`) 모양과 맞다 `[추측: 모양 대조]`.

### 2.8 ★ 장면 3 (끝) — 빈 받기는 `0xc0000001`, 그리고 치명 `[정적]`

run 문서 2-3.

#### 새 말 — 빈 받기

- 받기만 하는 부름을 했는데 전화선 끝 줄에 **메시지가 하나도 없는** 경우. 이번 질문 2 (c) 의 대상이다.
- 부름 꼴 (`IoCompleted +0xc8`): `(포트, Flags 0, NULL, NULL, 새 버퍼, &길이 0x1000 / 0xff00, &받기 속성 (Allocated 0xfa000000), 타임아웃 NULL)`.
  - 타임아웃 NULL 은 보통 "끝없이 기다림" 이다. 그런데 이번 길에선 기다리지 않는다 — 아래 표.

#### 경우별 (run 문서 2-3 표 줄임)

| 경우 | status | 쓰는 것 |
|---|---|---|
| 줄에 메시지 있음 | 0 | 헤더 0x28 + 데이터 · 받기 속성 |
| **줄 빔 + 우편함 붙음 (이 길)** | **`0xc0000001`, 기다리지 않음** | **아무것도 안 씀** |
| 줄 빔 + 우편함 없음 | 기다림 (끝나면 `0x102` 등) — 이 길 아님 | — |
| 포트 닫힘 | `0xc0000700` | 안 씀 |
| 연결 거절 | `0xc0000041` | 안 씀 |
| 버퍼 < `0x28 + DataLength` | `0xc0000023`, 메시지는 줄에 남음 | `*길이` 에 필요한 크기 |

- 핵심 줄: `AlpcpReceiveMessagePort` 가 줄 셋이 빈 걸 보고 (`+0xd4 ~ +0x107`), 완료 목록도 없고 (`+0x10d ~ +0x117`), 우편함이 붙어 있으면 (`+0x197 / +0x19c`) → **`+0x1ba MOV EDI,0xc0000001`** `[정적]`.
- 왜 기다리지 않게 만들었나 — 코드엔 이유가 안 쓰여 있다. 우편함이 붙은 포트는 "기다리기" 를 우편함 쪽 (일꾼이 쪽지를 기다림) 이 맡으니, 전화선 앞에서 또 기다릴 까닭이 없다는 뜻으로 읽힌다 `[추측]`.
- 헷갈리지 않게: run125 해설 2.10 에서도 `0xc0000001` 이 나왔다 (`NtWorkerFactoryWorkerReady`, "뽑는 중 수" 0 일 때). **숫자만 같고 다른 함수 · 다른 뜻** 이다.

#### rpcrt4 가 이 값을 받으면 — 한 걸음씩

1. `IoCompleted +0xd4` 에서 status 를 받는다.
2. `+0x486 CMP ESI,0xc0` → 맞으면 버리고 끝.
3. `+0x492 CMP ESI,0xc0000041` → 맞으면 연결 끊김 처리.
4. 그 밖 → **`+0x49e ~ +0x4a6 RpcpReportFatalError(2, 상태)` + `INT3`**.
5. `0xc0000001` 은 2 · 3 어디에도 없다 → **4 로 간다 = 치명** `[정적]`.

- run133 해설 2.3 걸음 5 의 "`[공백]` — 쌓인 답이 없을 때 무엇을 돌려줘야 정상인지" 가 여기서 닫혔다. 답은 "**정상인 값이 없다. 그 상황이 생기면 안 된다.**"

#### 쪽지 하나에 받기는 정확히 한 번

- `IoCompleted` 안 받기 부름은 `+0xc8` **하나뿐** 이다 `[정적]`.
- `+0x481 JMP +0x98` 은 버퍼를 못 얻었을 때 **비상 버퍼로 같은 받기를 하러** 가는 길이라 횟수는 그대로 1 이다.
- 메시지 하나를 다 처리하면 (`+0x22c MessageReceived`) 끝. 더 꺼내려고 도는 줄은 **없다**.
- 받은 메시지의 ALPC 종류가 2 면 답, 5 면 포트 닫힘, 1 이면 서버가 보낸 콜백 요청 (run133 1-3).

### 2.9 ★ 불변식 — 메시지 수 = 쪽지 수 = 받기 수

#### 새 말 — 불변식

- 일이 어떻게 흘러가든 **늘 참이어야 하는 약속** 이다. 결과서 5절 · run 문서 5절 맨 위에 적힌 말이다.
- 비유: 가게 장부에서 "들어온 돈 − 나간 돈 = 금고 안 돈" 처럼, 어긋나면 어딘가 사고가 난 것.

#### 셋이 맞물리는 이유 — 앞 절을 한 줄씩 이으면

1. 메시지 한 장이 줄에 들어갈 때마다 쪽지 한 장 (2.5) → **메시지 수 = 쪽지 수**.
2. 쪽지 한 장마다 일꾼 한 번 → `IoCompleted` 한 번 → 받기 **딱 한 번** (2.6 ~ 2.8) → **쪽지 수 = 받기 수**.
3. 쪽지는 메시지를 줄에 넣은 **뒤** 들어가니 (2.5), 받기 때 줄엔 늘 메시지가 있다.

#### 어긋나면

- **쪽지가 메시지보다 많으면** (예: 흉내 서버가 답 없이 쪽지만 넣음) → 받기가 빈 줄을 본다 → `0xc0000001` → **치명**.
- **쪽지가 메시지보다 적으면** (예: 답을 줄에 넣고 쪽지를 안 넣음) → 아무도 안 꺼내러 온다 → 답이 줄에 남고, 클라이언트는 영원히 기다린다 `[추측: 결과에서 이어 짐작 — 기다리는 쪽 동작은 이번에 안 읽음]`.
- 그래서 에뮬레이터 흉내의 규칙은 한 줄: **답을 줄에 넣을 때, 같은 동작 안에서 쪽지 하나를 같이** (2.17 의 빠진 것 ②).

### 2.10 NDR 본문 — 어디서 읽었나 `[정적]`

run 문서 3-0. 여기부터는 질문 3 — 메시지 **내용물** (스텁 데이터) 의 바이트 꼴이다.

#### 새 말 — 형식 문자열

- rpcrt4 · winnsi 파일 안에 들어 있는, **"이 프로시저의 인자를 이 차례 · 이 꼴로 줄 세워라" 를 적은 바이트 목록**. NDR 엔진이 이걸 읽으며 인자를 바이트로 바꾼다 `[정적: 바이트 자체]`.
- 비유: 말투 (전송 문법) 별로 따로 있는 **서식 설명서**. "1번 칸엔 16 B 이름표, 2번 칸엔 크기 적고 그만큼 바이트 …" 같은 것.
- 이번엔 프로그램을 돌리지 않고 이 설명서를 **읽어서** 바이트 꼴을 풀었다. 설명서 자체는 `[정적]`, 풀이 (패딩 자리 등) 는 `[규칙]` 이다 (위 "조심할 곳" 5).

| 모듈 | NDR 2.0 프로시저 | NDR64 (머리만) |
|---|---|---|
| rpcrt4 EPM (`e1af8308…` v3.0) | 시작 `0xefeb2` + 396 → **프로시저 8 = `0xf003e`** (3 = `0xeff42`) | 8 = `0xe7870` |
| winnsi (`7ea70bcf…` v1.0) | 시작 `0x70c2` + 336 → **프로시저 5 = `0x7212`** | 5 = `0x66e0` |

- 짚을 것 (run 문서 3-0):
  - run133 이 적은 EPM "`0xefeb2`" 는 NDR 2.0 프로시저 설명서의 **시작** 이다. 프로시저 8 은 거기서 +396.
  - winnsi `0x66e0` · `0x6590` · `0x6360` 은 **NDR64** 판 프로시저 5 · 6 · 7 이다.

### 2.11 ★ EPM 프로시저 8 — 공개 `ept_map` 과 다른 점: 포인터 ID 가 없다 `[정적]`

run 문서 3-1.

#### 파라미터 여덟 (형식 머리 · 차례는 `[정적]`, 이름은 `[추측]`)

① 객체 UUID (입력 · 참조, 16 B) ② 질문 탑 (입력 · 참조) ③ SID (입력, **`FC_UP`**) ④ 끝점 핸들 (입력 · 출력, 컨텍스트 핸들 20 B) ⑤ `max_towers` (값, 0 ~ 500) ⑥ 탑 개수 (출력) ⑦ 탑 배열 (출력) ⑧ 상태 (출력).

- `LookupNextChunk +0x11d` 의 인자 순서 (run133 3-1) 가 이 스택 자리와 그대로 맞는다.
- 이름 `ept_map_auth_async` 도 `[추측: 이름 대응]` 이다.

#### 새 말 — 참조 포인터 · 고유 포인터 · 전체 포인터 · 포인터 ID

- NDR 은 포인터 인자를 **종류에 따라 다르게** 줄 세운다. 형식 문자열에 종류가 적혀 있다 `[정적]`.
  - **참조 포인터** — 이번 ① · ② 가 이것 (형식 문자열의 "참조").
  - **고유 포인터** (`FC_UP`) — 이번 ③ SID, ⑦ 배열 원소.
  - **전체 포인터** (`FC_FP`) — 공개 `ept_map` (프로시저 3) 의 객체 · 탑.
- **포인터 ID** = 선 위에서 포인터 자리에 먼저 쓰는 4 B 값 (NULL 이면 0).
- 일반적으로 알려진 설명 `[추측]`: 참조 포인터는 "절대 NULL 이 아님" 을 약속한 포인터라 "있다 / 없다" 를 알릴 필요가 없어 **ID 를 안 쓰고 내용만 바로** 쓴다. 고유 · 전체 포인터는 NULL 일 수 있어서 ID 를 먼저 쓴다.
- 비유: 택배 상자에 "**내용물 있음 / 없음**" 스티커 (포인터 ID) 를 붙이느냐. "늘 들어 있음" 이 약속된 상자 (참조 포인터) 엔 스티커가 없다.

#### 그래서 — 왜 중요한가

- run 문서: "**3 은 객체 · 탑이 전체 포인터 (`FC_FP`) 라 포인터 ID 4 B 가 앞에 붙고, 8 은 참조 포인터라 ID 가 없다 — 공개 명세 그대로 쓰면 안 된다**" `[정적]`.
- 공개 명세의 `ept_map` 꼴을 보고 흉내 서버가 요청을 읽으면, 객체 UUID 앞 4 B · 탑 앞 4 B 가 **있는 줄 알고 건너뛰어** 모든 칸이 밀린다.
- run133 이 "공개 EPM IDL 순서로 짐작" 한 것 중 **순서는 맞았고**, 이 ID 유무가 달랐다 (2.15 고쳐 읽기 4).
- 반대로 ③ SID 는 고유 포인터라 ID 가 **있다** (아래 표 `+0x5c`).

### 2.12 EPM 프로시저 8 — 요청 120 B · 응답 128 B (칸 · 크기 `[정적]`, 패딩 자리 `[규칙]`)

#### 새 말 — conformance · 패딩

- **conformance** = 크기가 실행 때 정해지는 배열 앞에 쓰는 "**이 배열 몇 칸?**" 숫자 (u32). 받는 쪽은 이걸 먼저 읽고 그만큼 읽는다 `[규칙]`.
- **패딩** = 다음 4 B 값을 4 의 배수 자리에 두려고 끼우는 빈 바이트 `[규칙]`.
- 비유: 줄 공책에 글을 쓰다가 "다음 숫자는 새 칸 맨 앞에서 시작" 규칙 때문에 남는 빈칸.

#### 요청 스텁 (메시지 `+0x68` 부터, 질문 탑 octets 66 일 때 **120 B**)

| 스텁 오프셋 | 크기 | 뜻 |
|---|---|---|
| `+0x00` | 16 | 객체 UUID (없으면 16 B 0) — **ID 없이 바로** |
| `+0x10` | 4 | 질문 탑 conformance (= 66) |
| `+0x14` | 4 | `tower_length` (= 66) |
| `+0x18` | 66 | 탑 octets (층 수 u16 + 4층, run133 3-1) |
| `+0x5a` | 2 | 패딩 |
| `+0x5c` | 4 | SID 포인터 ID (NULL = 0) |
| `+0x60` | 20 | 끝점 핸들 (처음엔 20 B 0) |
| `+0x74` | 4 | `max_towers` (= 4) |

- 한 줄 읽기 — `+0x5a` 2 B 패딩: 바로 앞 탑 octets 가 `+0x18` 부터 66 B 라 `+0x5a` 에서 끝난다. 다음 칸은 4 B 값 (SID 포인터 ID) 이라 4 의 배수 자리 `+0x5c` 로 밀린다 `[규칙]`.
- 서버 흉내는 이 요청을 깊이 읽을 필요가 크지 않다. 응답이 더 중요하다.

#### 응답 스텁 (메시지 `+0x40` 부터, 탑 1개 · octets 73 일 때 **128 B**)

| 스텁 오프셋 | 크기 | 뜻 |
|---|---|---|
| `+0x00` | 20 | 끝점 핸들 — **20 B 0 이면 "더 없음"** (다음 조각을 안 물음, run133 3-2) |
| `+0x14` | 4 | `num_towers` |
| `+0x18` | 4 | 배열 max_count (= 요청의 `max_towers`) |
| `+0x1c` | 4 | 배열 offset (0) |
| `+0x20` | 4 | 배열 actual_count (= `num_towers`) |
| `+0x24` | 4 × n | 원소 포인터 ID (0 이 아닌 값) |
| `+0x28` | 4 | 탑 1 conformance (`0x49`) |
| `+0x2c` | 4 | 탑 1 `tower_length` (`0x49`) |
| `+0x30` | 73 | 탑 1 octets (run133 3-3 의 `LRPC-emu` 탑) |
| `+0x79` | 3 | 패딩 |
| `+0x7c` | 4 | 상태 (0) |

- 탑 0개면: 끝점 핸들 0 · `num_towers` 0 · 배열 `4 · 0 · 0` · 상태 → **40 B** `[규칙]`. 응답 머리 `TotalLength = 0x40 + 스텁`.
- 읽는 법:
  - 배열 머리가 숫자 셋 (max · offset · actual) 인 건 형식 문자열의 `FC_BOGUS_ARRAY` — 크기 = `max_towers`, 실제 = `*num_towers` 에서 온다 `[정적]`.
  - 원소가 고유 포인터 (`FC_UP`) 라 **원소마다 포인터 ID** 가 먼저 오고, 그 뒤에 탑 본체가 온다.
  - run133 해설 2.12 의 최소 탑 (`LRPC-emu`, `tower_length 0x49`) 이 `+0x30` 의 73 B 자리에 들어간다 (run 문서 3-1).
- `[공백]` 클라이언트가 응답의 max_count 를 자기 `max_towers` 와 맞춰 보는지는 안 읽었다 (NDR 해석기 본문). 그래서 **같게 보내는 게 안전** 하다 (run 문서).

비유: 114 의 답장 내용물은 "**접수 번호표 (20 B, 비우면 '끝') → 탑 몇 장 → 묶음 머리 (최대 · 시작 · 실제) → 장마다 '들어 있음' 스티커 → 탑 본체 → 빈칸 → 결과 도장**" 차례다.

### 2.13 nsi 프로시저 5 — 응답 24 B · 요청 40 B `[정적]` + `[규칙]`

run 문서 3-2.

- 형식 머리: 프로시저 5 · 파라미터 4개 (입력 구조체 · compartment 8 B · 출력 컨텍스트 핸들 · 반환 LONG) · `0xc6` (반환값 있음 · 비동기 핸들).
- **응답 스텁 24 B** — 서버 흉내가 돌려줄 것:
  - `+0x00` 컨텍스트 핸들 20 B (속성 u32 0 + 0 이 아닌 GUID) — run133 해설 2.14 의 **접수 번호표**.
  - `+0x14` 반환 DWORD (0 = 성공).
  - 실패 대답은 핸들 20 B 0 + 반환에 오류 값 (run133 4-2 의 `0x490` · `8` · `0x139f` …).
- 요청 스텁 40 B (서버 흉내는 안 읽어도 됨): 예약 u32 · 모듈 ID 포인터 ID · 객체 번호 · 모듈 ID (`Length` u16 · 형 u16 · GUID 16) · compartment 8.
  - 해석은 NDR 규칙에 기댄다 `[규칙]`. 클라이언트 상수 0x18 과 앞 12 + 8 = 20 이 맞아떨어진다.
- run133 이 `[추측]` 으로 둔 꼴과 비교 (2.15 고쳐 읽기 3):
  - 요청 "입력 24 B + 모듈 ID 24 B + compartment 8 B" → **40 B** (12 + 20 + 8).
  - 응답 "컨텍스트 핸들 20 B + DWORD 0 (정렬로 24 B)" → **24 B** 로 맞았다.

#### NDR64 판은?

- 프로시저 머리만 읽었다 `[정적]` — 파라미터 수 · 스택은 NDR 2.0 판과 같다.
- **타입 서술자는 바이트로 안 풀었다 `[공백]`.** 규칙상 포인터 ID · conformance 류가 8 B 라 EPM 8 은 자리가 다 바뀐다. nsi 5 응답은 NDR 2.0 과 같은 24 B 일 가능성이 크다 `[추측]` → Q259 ①.

### 2.14 ★ 말투는 서버가 고른다 — 비트 하나, 둘 다 켜면 거부 `[정적]`

run 문서 4절. run133 해설 2.5 · 2.6 의 **말투 · 수락 마스크** 를 이어서 본다.

#### 한 걸음씩

1. 클라이언트는 첫인사에 할 줄 아는 말투를 **비트 1 → 2 → 4 순으로 OR** 해서 낸다 (`Bind__4e330 +0x4e0` · `+0x713` · `+0x8a5`). winnsi · EPM 은 3 (NDR 2.0 + NDR64).
2. 서버가 `+0x48` 에 돌려준 수락 마스크를 `CompleteBind` 가 본다:
   - 0 → `0x6c2`
   - 제안에 없는 비트, 또는 비트가 **정확히 하나가 아님** → `0x6c0`
   - 그래서 **둘 다 켠 답 (3) 은 거부** 된다.
3. → **클라이언트는 고르지 않는다.** 서버가 고른 비트 하나를 그대로 쓴다.

### 2.17 ★ 에뮬레이터에서 빠진 두 가지 (결과서 6절 판정)

run 문서 "PE_emulator 쪽". `../PE_emulator` 코드는 flow-writer 가 안 읽었다. 결과서가 읽은 시점 기준이고, **고칠지는 사용자 결정** 이다.

#### 빠진 것 ① — `NtAlpcSetInformation` 종류 2 (`nt_alpc_create_port.cpp:602` `stop`)

- 지금은 종류 5 밖이면 멈춘다. rpcrt4 비동기 연결은 **전화선을 열자마자** 종류 2 를 부르니, 이 길에 들어서는 순간 멈춘다.
- 넣을 것 (2.4 표 차례 그대로):
  1. 길이 ≠ 0x10 → **`0xc0000004`**
  2. 입력 `{키 @0, 핸들 @8}` (run127 파일 묶기와 칸 순서 반대 — 2.3)
  3. 핸들 0 → `0xc000000d`
  4. **이미 붙음 → `0xc0000048`** (핸들 참조보다 앞)
  5. 완료 목록 → `0xc00000bb`
  6. IO 완료 객체로 참조 (**접근 2**, 실패 status 그대로)
  7. 포트에 `completion_port` · `completion_key` → 0. `AlpcPort` 에 두 칸이 없으면 늘린다.

#### 빠진 것 ② — 답을 줄에 넣을 때 쪽지 하나 (`:612 ~ :626`)

- 비동기 보내기 = "받기 칸 0 이면 곧바로 0" 은 **맞다**. 커널도 받을 메시지 포인터가 0 이면 `AlpcpReceiveMessage` 를 건너뛴다 (`+0x112 ~ +0x11d`).
- 그런데 **답을 줄에 넣을 때 쪽지를 같이 넣는 길이 없다.** 그래서 일꾼이 안 깨고, 답은 아무도 안 꺼낸다 (2.9 "쪽지가 적으면").
- 넣을 것: 같은 우편함 (`src/threadpool/nt_io_completion.cpp`) 에 `{키 = completion_key, apc 0, status 0, information 0}` 한 줄. 결과서 판정 "**맞는 틀**" — 우편함 몸은 이미 있고, 넣는 길만 새로 내면 된다. `NtWaitForWorkViaWorkerFactory` 출력 0x20 칸 간격도 커널과 맞다.

### 2.19 정리 — 비유로 한 번 더

- 전화 부서 (rpcrt4) 는 전화선을 열자마자 관리사무소에 **딱 한 번** 부탁한다: "이 선에 뭐 오면 일꾼 사무실 우편함에, **작업 카드 주소를 꼬리표로** 붙인 쪽지를 넣어 주세요" (종류 2, 16 B). 이미 붙은 선이면 `0xc0000048`, 종이 크기가 틀리면 `0xc0000004`.
- 관리사무소는 답장을 전화선 받침에 **먼저** 놓고, 답장 한 장마다 쪽지 `{꼬리표, 0, 0, 0}` **한 장** 을 넣는다. 건너뛰지 않는다.
- 일꾼은 쪽지의 꼬리표로 작업 카드를 찾고, 카드에 적힌 창구 (`LrpcIoComplete`) 로 간다. 거기 메모 (썽크) 가 "메모판 맨 위로, 손님 메모는 버리고" 하며 `IoCompleted` 로 넘긴다. `IoCompleted` 는 전화선을 **한 번** 들여다본다.
- 빈 전화선을 들여다보면 "없음" (`0xc0000001`) → 전화 부서는 **가게를 멈춘다**. 그러니 **답장 수 = 쪽지 수 = 들여다보는 수**.
- 답장 내용물 꼴 (NDR 2.0) 도 풀었다. 114 의 프로시저 8 은 공개 `ept_map` 과 달리 **"들어 있음" 스티커가 없는** 상자를 쓴다.
- 말투는 서버가 **하나만** 체크해 주면 클라이언트가 따른다. 흉내는 옛 말투 (마스크 1) 가 안전하다.

### 큰 그림에서 어떻게 이어지나

- 흐름도 본선 (프로세스 생성 → `NtContinue` 은퇴 → `main`) 엔 **변화가 없다**. 이번도 `main` 뒤 옆길의 지도다.
- **run128 → run129 → run133 → run137** 로 "웹 요청 하나가 망 안내 쪽에 묻는 전화" 가 끝까지 내려왔다.
  - run129: 전화를 건다 (연결 · 상태표). 비동기면 `TpAllocAlpcCompletionEx` 로 알림을 건다.
  - run133: 전화선 위 메시지 꼴 (첫인사 · 본론 · 답장 머리). 답은 둘째 부름으로 온다.
  - run137: 그 **둘째 부름이 어떻게 불려 오는지** (붙이기 → 쪽지 → 일꾼 → 받기) 와 내용물 바이트.
  - → 서버 흉내 차례 표 (2.16) 의 칸이 이제 **NDR64 판 빼고 다 찼다**.
- **일꾼 사무실 쪽 지도와 이어졌다.** run125 (파견소 · 우편함), run127 (파일을 우편함에 묶기), run93 (기다림 쪽지) 에 이어, **ALPC 전화선도 같은 우편함에 묶인다** 는 게 보였다. 우편함 하나에 파일 · 기다림 · 전화선 쪽지가 같이 들어오고, 일꾼은 꼬리표의 `+0x38` 로 종류를 가른다.
  - test.exe 의 로더 풀 일꾼도 같은 `TppWorkerThread` 몸이다. 이번에 그 몸의 갈래 하나가 처음 `[정적]` 으로 보였다.
- **공통 몫** — 붙이기 · 쪽지 · 빈 받기 규칙은 rpcrt4 LRPC 클라이언트 공통 몫이고, 원 요청 말로 RPCSS (`CoInitializeSecurity`) 도 같은 비동기 틀을 쓴다 `[추측: RPCSS 쪽 연결 객체가 같은 썽크를 쓰는지는 안 읽음]`.
