### 이번 바퀴에서 조심할 곳 다섯

1. **test.exe 는 이 호출을 안 쓴다 (본 적이 없다).**
   - test.exe 초기화 지도 (flow.md) 에 `NtSetInformationFile` 이 0건이다. "안 불린다" 가 아니라 "**본 적이 없다**" 는 뜻이다.
   - `sample/*.c` 에 완료 포트 · 겹침 I/O · 소켓 API 가 없다 `[소스]` (`grep -il 'completion\|overlapped\|socket'` 0건).
   - 그래서 이번 이야기도 "**소켓을 쓰는 다른 프로그램 (여기선 Go 프로그램) 이라면**" 이다. 그림 · 짐 지도는 그대로다.
2. **"Go 가 새 소켓마다 부른다" 는 에뮬레이터 로그다.** 진짜 Windows 에서 본 게 아니다. 그래서 `[관찰]` 로 안 쓴다 (flow.md 기준 줄).
3. **종류 번호를 십진수로도 부른다.** 에뮬레이터 코드는 십진수 (`30` · `41`), run 문서는 16진수다.

   | 16진 | 10진 | 이름 (공개 문서) | 한 줄 |
   |---|---|---|---|
   | **`0x1e`** | 30 | `FileCompletionInformation` | 이 손잡이를 **우편함에 묶기** |
   | **`0x29`** | 41 | `FileIoCompletionNotificationInformation` | 끝났을 때 **알림을 어떻게 받을지 스위치** |

4. **오프셋 두 가지.** 트리 (`├─ +0x..`) 의 숫자는 **ret 자리** (콜스택에 찍힐 값), 본문 "`+0x8de IopCompleteRequest`" 처럼 함수 이름 앞의 숫자는 **call 자리**, 그냥 "`+0xa53`" 은 함수 안 **줄** 이다. run 문서와 같은 규칙. 콜스택으로 본 적은 없다.
5. **비트 이름은 "우리 이름" 이다.** `_FILE_OBJECT` · `_IRP` · `_IO_COMPLETION_CONTEXT` 의 **칸 이름 · 오프셋은 PDB 타입** 이라 `[정적]`. 그런데 파일 객체 `Flags` 의 비트 이름 (`FO_SYNCHRONOUS_IO` · `FO_SKIP_COMPLETION_PORT` …) 은 PDB 에 없어서 공개 헤더 값으로 맞춘 **`[추측: 이름]`** 이다. 비트 **값과 그 값을 다루는 줄** 은 `[정적]`.

### 비유 — 그대로 이어 쓴다

- 프로세스 = **가게**, 커널 = **관리사무소**, syscall = 관리사무소 **신청 창구**, 핸들 = **손잡이**.
- run124 · run126 의 그림 그대로:
  - afd = 관리사무소 안 **우체국 창구** 상담실, 소켓 하나 = **사서함** 하나.
  - I/O 관리자 = 관리사무소의 **접수 사무실**. 주문서를 상담실에 건네고, 끝나면 전표를 손님 칸에 넣고 신호등을 켜는 쪽이다.
  - IRP = **배달 봉투**, IOSB = **전표**, 이벤트 = **신호등**, 완료 포트 = **우편함**.
  - status 도장 색 = 초록 (성공 `0x0…`) · 노랑 (경고 `0x8…`) · 빨강 (오류 `0xC…`) (run126 해설 2.16).
- 이번에 새로 붙는 그림 (run 문서 "결과" 비유를 따름):
  - 파일 객체 = 접수 사무실이 사서함마다 가진 **사서함 카드**. 그 카드의 `+0xb0` 칸 = **서랍**.
  - `0x1e` = 창구에 "이 사서함 소식은 저 **우편함** 으로 보내 주세요" 하고 **우편함 열쇠 (포트 핸들) 와 꼬리표 (키)** 를 맡기는 것.
  - `0x29` = 사서함 카드에 달린 **스위치** 를 켜는 것.
  - 완료 패킷 = 우편함에 넣는 **"끝났어요" 쪽지** (run126 해설 2.16 그림, run93 해설의 "봉투").
- 주의 — 이름이 겹치는 곳:
  - run 문서 "결과" 의 비유도 "우편함 · 서랍 · 쪽지 · 스위치" 다. 이 글은 그것과 같은 이름을 쓴다.
  - 다만 IRP 는 앞 해설들처럼 **배달 봉투**, 완료 패킷은 **"끝났어요" 쪽지** 로 나눠 부른다. 둘 다 "봉투" 라고 부르면 헷갈려서다.

### 한 줄로 먼저 — 무엇을 얻었나

> **`0x1e` 와 `0x29` 는 우체국 창구 (afd) 까지 안 간다. 접수 사무실 (I/O 관리자) 이 사서함 카드에 스스로 적고 끝낸다.**
> **`0x1e` = 카드 서랍 (`+0xb0`) 에 쪽지 `{우편함, 꼬리표, 쓰는 중 수}` 를 넣고 우편함 열쇠를 쥔다. 이미 서랍이 찼거나 "서서 기다리는 손님" (동기 손잡이) 이면 `0xC000000D`.**
> **`0x29` = 스위치 셋 (`0x2000000 / 0x4000000 / 0x8000000`) 을 켜기만 한다. 끄는 길은 없다.**
> **빨강 도장 (오류) 이면 전표를 안 쓴다. 묶인 사서함의 일이 "접수했어요" 없이 바로 빨강으로 끝나면 우편함에 쪽지도 없다.**

모두 `[정적]`. 단 "afd 가 `ConnectEx` 를 '접수했어요' 없이 끝내나" 는 정적으로 못 정해서 `[공백]` 이다 (2.13).

요청서 질문에 대한 답 (run 문서 "요약" 기준):

| 요청 질문 | 답 | 이 글 |
|---|---|---|
| 1 `0x1e` 검사 차례 · status | 길이 < 16 → `0xC0000004` · **이미 묶임 `0xC000000D`** → **동기 손잡이 `0xC000000D`** → 포트 핸들 (접근 2) → 풀 `0x18` B → 경주면 `0xC0000048` `[정적]` | 2.4 · 2.5 |
| 1 `0x1e` 쓰는 칸 · 참조 · IOSB | `FileObject+0xb0` = `_IO_COMPLETION_CONTEXT {Port, Key, UsageCount}`, `Flags &= ~0x400`, **참조는 파일 객체가 사라질 때 놓음**, IOSB `{0, 0}` `[정적]` | 2.6 · 2.7 |
| 1 드라이버로 내려가나 | **안 내려감** — `IopCallDriverReference` 를 안 지나 `IopCompleteRequest` 로 스스로 끝 `[정적]` | 2.3 |
| 2 `0x29` 비트 · 칸 · 끄기 · 순서 | 비트 `1/2/4` → `Flags` `0x2000000/0x4000000/0x8000000` 켜기만, 다른 비트 무시, 묶기 전 가능, 동기 손잡이만 거절 `[정적]` | 2.8 |
| 3 패킷 조건 · `ConnectEx` | 바로 오류 → 없음 · 바로 성공 + 스위치 1 → 없음 · `ApcContext` 0 → 없음 · 경고 / PENDING 뒤 → 있음. `ConnectEx` 바로 오류면 없음이 **맞다** (afd 쪽은 `[공백]`) `[정적 + 공백]` | 2.11 ~ 2.13 |

## 1. 이번 바퀴의 질문

### 큰 그림에서 어디인가

run124 · run126 과 같은 자리, **초기화 밖** 이다. `main` 뒤 프로그램 코드가 소켓을 쓸 때의 옆길이다.

```
cmd.exe 의 부탁 (CreateProcess)
 │  커널: 프로세스 · 주소 공간 · PEB · 첫 스레드
 │  ntdll: LdrInitializeThunk → LdrpInitializeProcess → DLL 들이기 · 전원 켜기
 └─ NtContinue (은퇴) → exe 진입점 → (CRT 점선 상자) → main
                                                        │
      test.exe 는 여기서 소켓을 안 쓴다 [소스]           │ 소켓을 쓰는 프로그램이라면 (요청 쪽: Go 런타임, 에뮬레이터 로그):
                                                        ├─ 소켓 열기                                     (run124)
                                                        ├─ NtSetInformationFile(소켓, 0x1e)  우편함에 묶기   ← 이번 (run127)
                                                        ├─ NtSetInformationFile(소켓, 0x29)  알림 스위치     ← 이번
                                                        └─ ConnectEx (0x120c7)                            (run124 2.15)
                                                             끝날 때 우편함에 쪽지가 가나?               ← 이번
                                                             (IRP 길 / 빠른 길 완료 — 커널 공용, run126)
```

- flow.md 에서는 **3장 끝 새 절** "파일을 완료 포트에 묶기" 다. run126 의 "AFD 주소 목록 묻기 · IOCTL 완료" 절 **바로 다음 이야기** 다.
- run126 해설 3절에서 "2.16 표의 '우편함' 칸 다음 이야기" 라고 예고한 바퀴가 이것이다.

### 왜 이 질문이 지금 왔나

- PE_emulator 요청이다 (요청서 "왜", 에뮬레이터 로그 — 진짜 Windows 아님).
  - Go 런타임이 새 소켓마다 `NtSetInformationFile(소켓, …, 종류 0x1e)` · `(…, 종류 0x29)` 를 부른다.
  - 에뮬레이터는 두 종류를 몰라서 "**성공인데 아무것도 안 함**" 기본 대답을 준다.
  - 그 뒤 `ConnectEx` 는 망 없는 PC 정책 실패 (`0xC000023C`) 로 바로 돌아온다.
- 요청한 쪽이 이미 알던 것: 종류 이름과 입력 크기 (공개 문서). 값 · 길이 검사 · 커널 칸은 몰랐다.
  - ReactOS 의 "이미 묶였거나 동기 핸들이면 `STATUS_INVALID_PARAMETER`" 는 Windows 11 에서 확인 안 된 것이었다.
- 사용자 결정 2026-11-21: "**이것들부터 먼저**".

### 무엇이 궁금했나

요청서 질문 셋 (run 문서 "목적").

1. `0x1e` — 검사 차례 · status · 파일 객체에 쓰는 칸 · 포트 참조 · IOSB · 드라이버로 내려가나.
2. `0x29` — 받는 비트 · 옮기는 칸 · 묶기 전에 되나 · 끌 수 있나.
3. 묶인 파일의 I/O 가 끝날 때 우편함 쪽지가 가는 조건 — "**`ConnectEx` 가 바로 오류면 쪽지 없음**" 이 맞나.

### 바퀴 전에 알던 것

- `[정적]` (run126, sast/124) IRP 길 완료 `IopCompleteRequest`: **빨강 도장 + PENDING 없음 → 전표 · 신호등 · 우편함 다 안 건드림.** 성공 · 경고면 전표 → 신호등 → (APC 또는 우편함) ([run126 해설 2.16](run126-afd-addrlist-해설.md)).
- `[정적]` (run126) 그 표에서 우편함 칸은 "`CompletionContext` 가 있으면 …" 까지만 있었다. **동기 손잡이에 우편함이 붙는지는 `[공백]`** 이었다.
- `[정적: 줄 읽기]` (run126 11절) 빠른 길 `IopXxxControlFile +0xbb4 ~ +0xbbc`: "파일 객체 `+0xb0` 이 있으면 **다른 갈래로 (안 읽음)**". 그리고 신호등을 켜는 조건에 "비트 `0x8000000` 이 꺼져 있을 때" 가 있었는데, **누가 그 비트를 켜는지** 몰랐다.
- `[정적]` (run124, sast/121) `ConnectEx` = 주문서 `0x120c7` (`AfdSuperConnect`). `ApcContext` = `hEvent` 맨 아래 비트가 0 이면 `OVERLAPPED*` (우편함으로 감), 1 이면 0 ([run124 해설 2.15](run124-afd-socket-해설.md)).
- `[정적]` (run125, sast/122) 우편함 (`_KQUEUE`) 칸 ([run125 해설](run125-worker-factory-해설.md)).

## 2. 찾은 것

### 2.1 한눈에 — 세 장면

run 문서 "호출 관계" 를 줄였다. 모두 `[정적]`. 트리 숫자는 ret 자리, 들여쓴 `+0x..` 는 그 함수 안 줄.

```
(장면 1: 묶기 — Go 런타임이 새 소켓마다, 요청 쪽 로그)
nt!NtSetInformationFile                         공통 검사 (길이 · IOSB · 정렬 · 파일 핸들 · IRP 0 부터)
 │  +0x7d5 ~ +0x845  비교 사슬
 │    ├─ 0x1e  +0xa53 이미 묶임 / +0xa61 동기 → 0xC000000D
 │    │    ├─ +0xa9a  ObReferenceObjectByHandle      포트, 접근 2 (참조 +1, 안 놓음)
 │    │    ├─ +0xab4  ExAllocatePool2                 쪽지 0x18 B
 │    │    │  +0xaf8 FileObject+0xb0 = {Port, Key, UsageCount}
 │    ├─ 0x29  +0xceb 동기 → 0xC000000D · Flags |= 0x2000000 / 0x4000000 / 0x8000000 (켜기만)
 │    └─ 그 밖 → +0x86c  IopCallDriverReference      ← 0x1e · 0x29 는 여기 안 옴
 └─ +0x8e3  IopCompleteRequest                   성공이면 IOSB {0,0}, 오류면 안 씀, 쪽지 없음

(장면 2: 묶인 사서함의 다음 일이 끝날 때)
nt!IopCompleteRequest      +0xbf 오류 + PENDING 0 → 우편함 안 봄
 └─ +0x3b9  KeInsertQueueEx                      "끝났어요" 쪽지 (조건 맞을 때만)
nt!IopXxxControlFile (빠른 길)  +0xe82 스위치 · +0xe9c 오류 → +0x10e4 쪽지 넣기

(장면 3: 사서함 카드가 사라질 때)
nt!IopDeleteFile
 └─ +0x2a2  ObfDereferenceObject                 묶을 때 쥔 우편함 열쇠를 여기서 놓음
```

- 장면 1 = 창구에 "**이 사서함 소식은 저 우편함으로**" 를 맡기는 순간.
- 장면 2 = 그 뒤 사서함 일이 끝날 때 **우편함에 쪽지가 가나** 를 정하는 순간. run126 의 완료 길을 "우편함" 칸만 펼친 것이다.
- 장면 3 = 맡겨 둔 열쇠를 **언제 돌려주나**.

#### 새 말 — `NtSetInformationFile` 과 정보 종류 표

- `NtSetInformationFile` = "이 파일 (손잡이) 의 정보를 바꿔 주세요" syscall. 인자로 **정보 종류 번호** 를 받아 무엇을 바꿀지 고른다 (run41 해설의 정보 클래스와 같은 꼴).
- 종류마다 정해진 값이 **표 셋** 에 있다 `[정적]` (run 문서 "방법", PE 파일 `PAGE` 구역 바이트로 직접 읽음):
  - 길이표 `IopSetOperationLength` — 입력이 최소 몇 바이트여야 하나
  - 정렬표 `IopQuerySetAlignmentRequirement` — 입력 주소가 몇 바이트 단위로 맞아야 하나
  - 접근표 `IopSetOperationAccess` — 파일 손잡이에 어떤 권한이 있어야 하나
- 표는 `0x54` 칸이다. 이번 두 종류의 값: **`0x1e` = 16 / 4 / 0, `0x29` = 4 / 4 / 0** (길이 / 정렬 / 접근) `[정적]`.
- 결과서가 이 표 셋을 PE_emulator 쪽 같은 표와 **84칸 전부** 맞춰 봤더니 같았다. 두 곳에서 따로 읽은 값이 맞으니 표 값은 믿을 만하다.
- 비유: 신청 창구 벽에 붙은 "**신청서 종류별 규격표**" — 종이 크기 · 접는 법 · 필요한 도장.

#### 새 말 — 파일 객체

- 손잡이 (핸들) 가 가리키는 **커널 쪽 기록 한 장** 이다. 소켓 손잡이도 뒤에 파일 객체가 있다 (run124 해설 2.10 의 "손잡이 뒤 파일 객체").
- 이번에 나오는 칸 (PDB `_FILE_OBJECT` 이름 · 오프셋) `[정적]`:
  - `+0x50` `Flags` — 이 사서함의 **성질 비트 묶음** (동기인가, 스위치 셋 …)
  - `+0xb0` `CompletionContext` — **서랍** (우편함 쪽지 자리, 2.6)
  - `+0xb8` — 서랍을 다룰 때 잡는 스핀락 (결과서는 `IrpListLock`)
  - (run126) `+0x98` 손잡이 신호등 · `+0x38` `FinalStatus`
- 비유: 접수 사무실이 사서함마다 하나씩 가진 **사서함 카드**.

### 2.2 한 줄씩 읽는 법

run 문서 "정적 — 호출 지점" 표에서 두 줄을 골라 "누가 / 어디서 / 누구를 / 무엇을 위해" 로 읽는다.

#### 줄 1: `nt!NtSetInformationFile` · call `+0xa95` · ret `+0xa9a` · `ObReferenceObjectByHandle` (`0x1e` 포트 핸들, 접근 2, `IoCompletionObjectType`)

- **누가**: `NtSetInformationFile` (rva `0x3ab2d0`, 4323B) 의 **`0x1e` 갈래**.
- **어디서**: 함수 시작에서 `+0xa95` 에서 부르고 `+0xa9a` 로 돌아온다. 콜스택엔 `+0xa9a` 로 찍힐 것이다.
- **누구를**: `ObReferenceObjectByHandle` — 손잡이를 **커널 객체 포인터로 풀어 주는** 공용 부품.
- **무엇을 위해**: 손님이 입력 `+0x0` 에 준 **포트 핸들** (우편함 손잡이) 을 진짜 우편함 객체로 바꾸려고.
  - 요구 접근 = **2** (`IO_COMPLETION_MODIFY_STATE` `[추측: 이름]`), 요구 종류 = 완료 포트 (`IoCompletionObjectType`).
  - 풀리면 우편함의 **참조 수가 1 오른다.** 이 참조를 이 갈래는 **안 놓는다** (2.7).
  - 못 풀리면 그 status 를 **그대로** 돌려준다 (2.5 · 4절).
- 비유: 손님이 내민 "우편함 손잡이" 를 보고 접수 사무실이 **진짜 우편함 열쇠 사본** 을 하나 받아 쥔다.

#### 줄 2: `nt!IopDeleteFile` · call `+0x29d` · ret `+0x2a2` · `ObfDereferenceObject` (`ctx.Port`)

- **누가**: `IopDeleteFile` — 파일 객체를 **지울 때** 부르는 함수.
- **어디서**: `+0x29d` 에서 부르고 `+0x2a2` 로 돌아온다.
- **누구를**: `ObfDereferenceObject` — 참조 수를 1 내리는 공용 부품.
- **무엇을 위해**: 줄 1 에서 쥐었던 **우편함 열쇠 사본을 돌려주려고**. 대상이 서랍 쪽지의 `Port` 칸 (`ctx.Port`) 이다.
  - 바로 앞 `+0x285` 에 `KeBugCheckEx` 가 있다 — 쪽지의 `UsageCount` 가 0 이 아니면 (아직 누가 쓰는 중이면) 멈춘다.
  - 뒤 `+0x2ab` 에서 쪽지 자체 (`ctx`) 를 풀에 돌려준다 (`ExFreePoolWithTag`).
- 줄 1 과 줄 2 는 **짝** 이다. 쥐는 곳과 놓는 곳이 서로 다른 함수, 다른 때다 (2.7).

이제 장면 1 을 **들어가는 순간 → 갈래 → 끝맺음** 차례로 따라간다.

### 2.3 ★ 두 종류는 창구까지 안 간다 — 드라이버를 안 부름 `[정적]`

먼저 결론부터. 이게 요청 쪽에 가장 중요한 답이다.

#### 새 말 — 비교 사슬

- 종류 번호로 갈 곳을 고를 때, **표 (점프표) 로 한 번에 뛰지 않고** "`0x10` 인가? `0x1e` 인가? `0x3d` 인가? …" 하고 **하나씩 견주며 내려가는** 꼴이다 (`+0x7d5 ~ +0x845`) `[정적]`.
- 비유: 서류 더미를 칸막이 선반 (점프표) 에 꽂지 않고, 창구 직원이 "이거 A 서류? 아니면 B?" 하고 차례로 묻는 것.

#### 근거 → 그래서

1. **근거** `[정적]`: `NtSetInformationFile` 안에서 드라이버를 부르는 `IopCallDriverReference` 는 **`+0x867` 한 곳** 뿐이다. 그 줄로 들어오는 길은 **`+0x84b` 하나** 다.
2. **근거** `[정적]`: `0x1e` 갈래 (`+0x815 → +0xa4a`) 와 `0x29` 갈래 (`+0x827 → +0xce2`) 는 끝에서 **`+0x86f` 로 뛴다.** `+0x84b` 를 안 지난다.
3. **그래서**: `+0x86f` 뒤 `+0x8de IopCompleteRequest` 로 **같은 스레드에서 스스로** 끝낸다. IRP (배달 봉투) 는 만들긴 하지만 **상담실에 안 건넨다.**
4. **그래서**: 소켓이든 보통 파일이든, **afd 는 이 두 호출을 모른다.** 에뮬레이터는 afd 흉내 쪽이 아니라 **I/O 관리자 쪽** 에서 처리하면 된다.

비유:

- 손님이 신청 창구에 "이 사서함 소식은 저 우편함으로" 를 냈다.
- 접수 사무실은 배달 봉투를 하나 만들긴 하지만, 우체국 창구 직원은 **부르지도 않는다.** 사서함 카드에 스스로 적고, 봉투는 그 자리에서 닫는다.

#### 드라이버를 안 부르는 종류 — 목록 `[정적]`

이번 두 종류 말고도 비교 사슬에서 접수 사무실이 스스로 끝내는 종류가 있다 (run 문서 4절).

- **안 부름**: `0x10` (`+0x7d5`) · **`0x1e`** (`+0x815`) · `0x3d` (`+0x81e`, `IopReplaceCompletionPort` — 안 묶였으면 `0xC000000D`) · **`0x29`** (`+0x827`) · `0x2a` (`+0x830`, `IopSetFileObjectIosbRange`) · `0x2b` (`+0x839`) · `0x45` (`+0x842`).
- 앞에서 따로: `0xe` (동기 핸들만, IRP 앞 `+0x2ba ~ +0x38d`) · `0x24` (`+0x63a → +0xd50`).
- **부름 (이름만)**: `0xa / 0xb / 0x1f / 0x41 / 0x48` (`+0x7de` 비트 마스크), `0x28`, `0xd / 0x40`, 그 밖 모두 → `+0x84b`.

### 2.4 들어가는 길 — 두 종류가 같이 지나는 공통 검사 `[정적]`

run 문서 1절. 비교 사슬에 닿기 전에 모든 종류가 지나는 앞부분이다.

| 차례 | 하는 일 | 걸리면 |
|---|---|---|
| 1 | 호출자가 **커널** 이면 2 ~ 5 건너뜀 (`Thread+0x232`, `+0x69`) | — |
| 2 | 종류 번호 ≥ `0x54` 또는 길이표 0 | `0xC0000003` |
| 3 | `Length` < 길이표 (`0x1e` 16 · `0x29` 4) | **`0xC0000004`** |
| 4 | IOSB 첫 4 B 를 읽고 되써 봄 (`+0xb1 ~ +0xc7`) | 예외 → 5 의 착지 |
| 5 | 입력 정렬 (둘 다 4) · 버퍼 끝 검사 | 예외 코드가 반환값 `[추측]` (아래) |
| 6 | 파일 손잡이에 요구하는 접근 — **둘 다 0** (손잡이이기만 하면 됨) | — |
| 7 | 파일 손잡이 풀기 (`+0x19a`) | 실패 status 그대로 |
| 8 | AppContainer + 파일 객체 확장 `+0xd0` 비트 4 | `0xC0000910` |
| 9 | **동기 손잡이** (`Flags & 2`) 면 파일 객체 락 · 사용자 IOSB 를 IRP 에 바로. 비동기면 스택에 임시 신호등 · 임시 전표 | — |
| 10 | IRP 만들기 → 입력을 풀 (태그 `IoSB`) 에 복사 → 스레드 IRP 목록에 걸기. **IRP 는 0 부터** | IRP 실패 `0xC000009A` |
| 11 | 종류별 갈래 — 비교 사슬 (2.3) | |

읽을 곳 셋:

- **차례 10 의 "IRP 는 0 부터"** 가 나중에 중요하다 (2.9). `IopAllocateIrpPrivate +0x192` 가 IRP 를 통째로 0 으로 채운다 → `ApcRoutine` (`+0x58`) · `ApcContext` (`+0x60`) · `PendingReturned` (`+0x41`) 가 다 0 이다 `[정적]`. 이 IRP 는 `ApcRoutine` 도 `+0x6d6` 에서 0 으로 둔다.
- **차례 5 의 예외** 는 확실하지 않다. 착지 `+0x157` 이 원본 바이트로 `jmp +0x3c7` (함수 끝) 이고 EAX 를 안 건드리니 "예외 코드가 그대로 반환값이 된다" 고 **짐작** 한다 `[추측]` (run 문서 표 그대로). 실행해 봐야 안다.
- **차례 9 의 동기 손잡이** — run124 해설 2.3 의 "창구 앞에 서서 기다리는 손님" 이다. 이 손잡이는 이 앞부분에서 **락까지 잡고** 들어간다 (`+0x271 KeAbPreAcquire`). 그런데 두 종류 다 갈래 안에서 곧 거절한다 (2.5 · 2.8).

에뮬레이터와 견주면 (결과서 "지금 우리 맞나"): **앞쪽 순서 · 표 값은 이미 맞다.** 작은 차이 둘 — 진짜는 IOSB 를 첫 4 B 만 시험하고, 커널 호출자면 길이 · 정렬을 건너뛴다. 에뮬레이터가 늘 사용자 호출자면 상관없다.

### 2.5 ★ `0x1e` 의 검사 차례 — 어느 것이 먼저 걸리나 `[정적]`

run 문서 2절. 갈래 시작 `+0x815 CMP EDI,0x1e / +0x818 JZ → +0xa4a`. 입력 복사본 = `Irp+0x18` (`+0x0` 포트 핸들 · `+0x8` 키).

#### 새 말 — 키

- 입력 `+0x8` 의 8 바이트 값. 우편함에 쪽지가 들어갈 때 **같이 붙는 꼬리표** 다 — 2.11 표의 "있음" 칸에서 쪽지의 키 = `ctx.Key` `[정적]`.
- 커널은 이 값을 **해석하지 않고** 그대로 옮긴다 `[추측]` (이번 줄에서 키를 견주는 곳이 안 나옴). 보통 프로그램이 "어느 소켓 것인지" 알아보려고 쓴다고 알려져 있다 `[추측]` (일반적으로 알려진 설명).
- 비유: 우편함 하나를 여러 사서함이 같이 쓸 때, 쪽지에 붙이는 **"3번 사서함" 꼬리표**.

#### 차례

| 차례 | 조건 | status |
|---|---|---|
| 1 | **이미 묶임** — `FileObject+0xb0` ≠ 0 (`+0xa53`) | **`0xC000000D`** |
| 2 | **동기 손잡이** — `Flags & 0x2` (`FO_SYNCHRONOUS_IO` `[추측: 이름]`) (`+0xa61`) | **`0xC000000D`** |
| 3 | 포트 핸들 풀기 — 접근 2, 완료 포트 종류 (2.2 줄 1) | 실패 status 그대로 |
| 4 | 쪽지 `0x18` B 풀 할당 (비페이지, 태그 `IoCc`) | 실패 → 참조 되돌림 · `0xC000009A` |
| 5 | 스핀락 `FileObject+0xb8` 잡고 `+0xb0` **다시 봄** | 차 있으면 풀 해제 · 참조 되돌림 · `0xC0000048` |
| 6 | **성공** — 2.6 | `0` |
| 7 | 끝맺음 — 드라이버 없이 `+0x86f` → `IopCompleteRequest` | 위 status |

읽는 법:

- 요청 쪽이 걱정한 ReactOS 의 "이미 묶였거나 동기 핸들이면 `STATUS_INVALID_PARAMETER`" — Windows 11 26100.9457 에서도 **둘 다 `0xC000000D`** 다 `[정적]`. 순서는 **"이미 묶임" 이 먼저**, "동기" 가 다음이다.
- 비유: "이미 서랍에 쪽지가 있어요" 이거나 "**서서 기다리는 손님**" 이면 "안 돼요" (`0xC000000D`).
  - 서서 기다리는 손님에게 우편함으로 알릴 일이 없으니 거절하는 것으로 읽힌다 `[추측]` (이유는 코드에 안 쓰여 있다).

#### 새 말 — 경주

- 두 스레드가 **같은 칸을 거의 동시에** 고치려 할 때를 말한다.
- 차례 1 에서 "서랍 비었음" 을 본 뒤 차례 5 의 자물쇠를 잡기 전 사이에, **다른 스레드가 먼저 쪽지를 넣었을 수** 있다. 그래서 자물쇠를 잡고 **한 번 더 본다** `[정적]` (`+0xad3 / +0xadb`).
- 그때 나오는 status 가 `0xC0000048` (`STATUS_PORT_ALREADY_SET` `[추측: 이름]`) 이다.
- **차례대로 부르면 이 값은 안 나온다** — 두 번째 호출은 차례 1 에서 이미 `0xC000000D` 로 걸러진다 (run 문서 표).
- 비유: 서랍이 빈 걸 보고 쪽지를 쓰러 간 사이 다른 직원이 먼저 넣었다. 그래서 **서랍을 잠그고 다시 열어 본다.**

### 2.6 ★ `0x1e` 성공 — 서랍에 넣는 쪽지 `[정적]`

#### 새 말 — `CompletionContext` · `_IO_COMPLETION_CONTEXT`

- `FileObject+0xb0` (`CompletionContext`) = 이 파일이 **어느 우편함에 묶였나** 를 가리키는 칸. 0 이면 안 묶임.
- 가리키는 것 = `_IO_COMPLETION_CONTEXT` 덩어리 (PDB 타입, 크기 `0x18`):

  | 칸 | 오프셋 | 넣는 값 | 비유 |
  |---|---|---|---|
  | `Port` | `+0x0` | 포트 객체 (2.2 줄 1 에서 푼 것) | 우편함 (열쇠 사본) |
  | `Key` | `+0x8` | 입력 `+0x8` | 꼬리표 |
  | `UsageCount` | `+0x10` | (0 으로 시작 `[추측]`, 결과서: 0 채운 할당으로 보임) | **지금 이 쪽지를 보고 있는 사람 수** |

- 비유: 사서함 카드 서랍 (`+0xb0`) 에 넣는 **쪽지 한 장** — "소식은 이 우편함으로, 이 꼬리표 붙여서".

#### 성공 갈래가 하는 일 — 줄 차례

1. `+0xae1` — `Flags &= ~0x400` (비트 `0x400` 끔). 이름은 `FO_QUEUE_IRP_TO_THREAD` `[추측: 이름]`. 결과서는 "묶이면 IRP 를 스레드 말고 파일 객체 목록에 걸게 함" 이라고 짐작했다 `[추측]`.
2. `+0xaed` · `+0xaf4` — 쪽지에 `Port` · `Key` 적기.
3. `+0xaf8` — **서랍에 쪽지 넣기** (`FileObject+0xb0` = ctx).
4. `+0xaff` — status 0.
5. `+0xb05` — 스핀락 놓기.
6. 끝맺음 → `IopCompleteRequest` → 전표 `{Status 0, Information 0}` (2.9).

### 2.7 ★ 우편함 열쇠는 언제 돌려주나 — 손잡이 닫을 때가 아니다 `[정적]`

- **근거** `[정적]`: 성공 갈래 줄에 참조를 내리는 `Dereference` 가 **없다.** 2.2 줄 1 에서 쥔 참조를 쪽지 (`ctx.Port`) 에 쥔 채 둔다.
- **근거** `[정적]`: 놓는 곳은 `IopDeleteFile +0x29d` (2.2 줄 2). 그 앞 `+0x285` 는 `UsageCount` ≠ 0 이면 `KeBugCheckEx`, 뒤 `+0x2ab` 는 쪽지 해제.
- **그래서**: 우편함 열쇠는 **파일 객체가 사라질 때** 돌려준다. 손잡이를 닫는 순간이 아니다.
  - 일반적으로 손잡이를 닫아도 다른 쪽이 그 객체 참조를 아직 쥐고 있으면 객체는 남아 있다고 알려져 있다 `[추측]` (일반적으로 알려진 설명). 그래서 "닫기" 와 "사라짐" 이 다른 때일 수 있다.
  - 실제로 손잡이를 닫은 뒤에도 참조 수가 그대로인지는 동적 (→ Q235 6).
- 따로, **완료 때마다 잠깐** 더 쥐었다 놓는 참조도 있다 — `IopCompleteRequest +0x109` 로 쥐고 `+0x29e` 로 놓는다. `UsageCount` 는 `+0x52c` 에서 올리고 `+0x4ad` 에서 내린다 `[정적]`.
- 비유: 접수 사무실은 우편함 **열쇠 사본** 을 서랍에 넣어 두고, 사서함 카드를 **폐기할 때** 비로소 사본을 반납한다. 반납하기 전에 "지금 이 쪽지 보는 사람 있나?" (`UsageCount`) 를 확인하고, 있으면 큰일 난 것 (버그체크) 으로 본다.

PE_emulator 쪽에 주는 뜻: 묶기 성공이면 **포트 참조를 쥐어야** 한다 (run 문서 "PE_emulator 쪽"). 안 쥐면 손님이 우편함 손잡이를 닫았을 때 우편함이 먼저 사라질 수 있다 `[추측: 참조 수가 0 이 되면 치운다는 일반 규칙에서]`.

### 2.8 `0x29` — 스위치 셋, 켜기만 `[정적]`

run 문서 3절. 갈래 시작 `+0x827 CMP EDI,0x29 / +0x82a JZ → +0xce2`. 입력 = dword 하나.

| 입력 비트 | 켜는 `Flags` 비트 | 이름 `[추측: 이름]` | 줄 | 스위치 뜻 (비트를 읽는 곳에서) |
|---|---|---|---|---|
| (동기 손잡이) | — | — | `+0xceb ~ +0xcf1` | **`0xC000000D`**, 비트 안 바꿈 |
| `0x1` | `0x2000000` (비트 25) | `FILE_SKIP_COMPLETION_PORT_ON_SUCCESS` → `FO_SKIP_COMPLETION_PORT` | `+0xcfa ~ +0xd04` (`BTS ECX,0x19`) | 바로 성공이면 **우편함 쪽지 건너뛰기** (`IopCompleteRequest +0x366` · `IopXxxControlFile +0xe82`) |
| `0x2` | `0x4000000` (비트 26) | `FILE_SKIP_SET_EVENT_ON_HANDLE` → `FO_SKIP_SET_EVENT` | `+0xd07 ~ +0xd11` (`BTS ECX,0x1a`) | **손잡이 신호등** (파일 객체 이벤트) 안 켬 (`IopCompleteRequest +0x2a5`), 호출 앞에 안 끔 (`IopXxxControlFile +0x721`) |
| `0x4` | `0x8000000` (비트 27) | `FILE_SKIP_SET_USER_EVENT_ON_FAST_IO` → (헤더 이름 `[공백]`) | `+0xd14 / +0xd18 → +0x104c ~ +0x1050` (`BTS ECX,0x1b`) | 빠른 길에서 **손님 신호등** 안 켬 (`IopXxxControlFile +0xbc7`. 우편함이 있고 경고면 켬 `+0x1651 ~ +0x165b`) |
| `0x8` 이상 | — | — | 마스크 비교 없음 | **검사 없이 무시, status 0** |

`BTS` = "이 비트를 1 로" 명령이다. 그래서 세 줄 모두 **켜기** 다.

읽는 법 — 요청서 질문 둘의 답:

- **끌 수 있나 → 못 끈다.** 세 곳 다 `BTS` 뿐, 끄는 `BTR` · `AND` 가 없다 `[정적]`. 입력 비트가 0 이면 "끄기" 가 아니라 "**그냥 둠**" 이다.
- **묶기 (`0x1e`) 전에 불러도 되나 → 된다.** 이 갈래에 서랍 (`+0xb0`) 을 읽는 줄이 없다 `[정적]`.
- 끝맺음은 `0x1e` 와 같은 길 (`+0xd1e ~ +0xd26` → `+0x874 ~ +0x8de`), 전표 `{0, 0}`.

비유:

- 사서함 카드에 **스위치 세 개** 가 달려 있다. "잘 끝난 건 우편함에 안 넣어도 돼요" · "손잡이 표시등은 켜지 마세요" · "즉석 답이면 손님 신호등 안 켜도 돼요".
- 손님이 할 수 있는 건 **켜는 것뿐** 이다. 한 번 켠 스위치는 끄는 손잡이가 없다.
- 모르는 스위치 번호를 줘도 창구는 화내지 않고 **그냥 넘긴다** (status 0).

왜 "바로 성공이면 우편함 쪽지 건너뛰기" 같은 스위치가 있을까 — 일반적으로 "호출이 바로 성공으로 돌아왔으면 프로그램이 반환값으로 이미 결과를 알았으니, 우편함 쪽지를 또 받을 필요가 없다" 는 쓰임으로 알려져 있다 `[추측]` (일반적으로 알려진 설명). Go 가 `1|2 = 3` 을 줄 것이라는 기억도 `[추측]` (결과서) 이고, 실제 값은 동적 (→ Q235 1).

### 2.9 끝맺음 — 빨강 도장이면 전표를 안 쓴다 `[정적]`

두 종류 다 갈래 끝에서 같은 길을 탄다 (`+0x86f` → `+0x874` · `+0x88e / +0x89a` → `+0x8de IopCompleteRequest`). 이 길은 run126 해설 2.16 의 IRP 길 완료와 **같은 함수, 같은 줄** 이다.

| 결과 | 전표 (IOSB) | 근거 줄 |
|---|---|---|
| 성공 (`0`) | **`{Status 0, Information 0}`**, `Information` 먼저 | `IopCompleteRequest +0x125 ~ +0x142` |
| 오류 (`0xC000000D` · `0xC0000004` 등) | **안 씀** — IRP 에만 적힘 | `IopCompleteRequest` 오류 + PENDING 0 갈래 |

- 왜 안 쓰나: 이 IRP 는 0 부터 시작해서 `PendingReturned` = 0 이다 (2.4 차례 10). 그래서 "빨강 + PENDING 아님" → 전표 · 신호등 · 우편함 다 안 건드림 (run126 해설 2.16 표 마지막 줄) `[정적]`.
- 반환값은 위 status 그대로 (`+0x940 ~ +0x947 → +0x3c4 → +0x3d9`).
- 비유: 접수 사무실은 "안 돼요" 를 **도장으로만** 돌려준다. 손님 전표 칸은 손님이 써 둔 그대로 남는다.

#### 묶은 바로 그 봉투는 쪽지를 안 보낸다

- 방금 서랍에 쪽지를 넣었으니, `IopCompleteRequest` 가 서랍을 **읽기는 한다** (`+0xce` · `+0x52c`) `[정적]`.
- 그런데 이 IRP 의 `ApcRoutine` = 0 · `ApcContext` = 0 이라 `+0x35b / +0x360 JZ → +0x244` 로 **쪽지 없이** 끝난다 `[정적]`.

#### 새 말 — `ApcContext`

- IRP `+0x60` 칸. 손님이 I/O 를 낼 때 "끝나면 이 값을 같이 돌려주세요" 하고 맡기는 값이다.
- `ConnectEx` 에서는 `hEvent` 맨 아래 비트가 0 이면 `OVERLAPPED*` 가 들어간다 ([run124 해설 2.15](run124-afd-socket-해설.md)) `[정적]`.
- 이번 규칙의 핵심 `[정적]`: **`ApcContext` 가 0 이면 우편함 쪽지는 절대 안 간다** (2.11 표).
- 비유: "끝났어요" 쪽지에 붙여 달라고 손님이 맡긴 **메모**. 메모를 안 맡긴 손님 몫으로는 쪽지를 안 쓴다.

### 2.10 run126 의 `[공백]` 하나가 닫힌다 — 동기 손잡이엔 못 묶는다 `[정적]`

- run126 해설 2.16 표 "성공 / 동기 손잡이" 줄의 우편함 칸: "`CompletionContext` 가 있으면 비동기와 같음 (**동기 손잡이에 붙는지는 `[공백]`**)".
- 이번 답: **`NtSetInformationFile 0x1e` 로는 못 붙인다** — 동기 손잡이면 `+0xa61` 에서 `0xC000000D` `[정적]`.
- 단 **다른 길** (예: 만들 때 붙이는 길이 있다면) 은 안 봤다. 그래서 "어떤 길로도 동기 손잡이엔 우편함이 없다" 까지는 아니다 (run 문서 "정정").

### 2.11 ★ 묶인 사서함의 일이 끝날 때 — 우편함 쪽지 조건 `[정적]`

run 문서 5절. run126 해설 2.16 표의 "우편함" 칸을 **펼친** 것이다. 포트에 묶인 비동기 파일, `NtDeviceIoControlFile` IRP 길. 줄은 `IopCompleteRequest.asm`.

#### 새 말 — `PendingReturned`

- IRP `+0x41` 칸. 드라이버가 처리 도중 "**접수했어요 (`0x103`), 나중에 끝낼게요**" 라고 표시했으면 1 이다.
- 비유: 배달 봉투에 찍힌 "**접수증 발급함**" 도장. 손님이 접수증만 받고 이미 자리를 떴다는 뜻이다.

#### 새 말 — 완료 패킷

- 우편함 (완료 포트) 줄에 넣는 한 건. 이 글에서는 **"끝났어요" 쪽지** 라고 부른다.
- 넣는 함수는 IRP 길이면 `IopCompleteRequest +0x3b4 KeInsertQueueEx`, 빠른 길이면 `IopXxxControlFile +0x10df` (2.12) `[정적]`.
- 쪽지 모양 (꺼낼 때 무엇이 나오나) 은 이번에 안 봤다 → Q236 ③. 우편함 줄 자체는 [run93 해설](run93-wait-packet-해설.md) · [run125 해설](run125-worker-factory-해설.md).

#### 표

| 일이 끝난 꼴 | 쪽지 | 줄 |
|---|---|---|
| **바로 빨강** (`0xC…`, `PendingReturned` 0) | **없음** — 서랍도 안 읽음, 전표 · 신호등도 안 건드림 | `+0xb3 ~ +0xbf → +0x426 / +0x42a → +0x445` |
| 바로 초록 + 스위치 1 (`0x2000000`) **켜짐** | **없음** | `+0x366 → +0x5ac / +0x5b0` · `+0x5b6 ~ +0x5be` · `+0x5c9 → +0x376 / +0x378 → +0x244` |
| 바로 초록 + 스위치 1 꺼짐 | `ApcRoutine` 0 · `ApcContext` ≠ 0 이면 **있음** (꼬리표 = `ctx.Key`) | `+0x2d0 → +0x23b` · `+0x35b / +0x360` · `+0x37e ~ +0x383` · `+0x3b4` |
| 바로 노랑 (`0x8…`) | **있음** (스위치 1 켜져 있어도) | `+0x5b6 ~ +0x5c3 → +0x373` |
| `ApcContext` = 0 | **없음** (어느 경우든) | `+0x35b / +0x360 JZ → +0x244` |
| `ApcRoutine` ≠ 0 | 쪽지 대신 사용자 APC | `+0x2c9 ~ +0x351` |
| **접수증 뒤 완료** (`PendingReturned` 1), 초록 · 빨강 다 | **있음** (`ApcContext` ≠ 0 이면, 스위치 무시) | `+0x426 / +0x42a` 안 탐 · `+0x5ac JNZ → +0x373` |

(`ApcRoutine` ≠ 0 줄: 포트 손잡이엔 `ApcRoutine` 을 못 주게 막는 줄이 따로 있다 — sast/124 `IopXxxControlFile +0xd3b ~ +0xd55`.)

#### 한 줄씩 — 표를 어떻게 읽나

이 표는 **"손님이 아직 결과를 모르나?"** 로 읽으면 한 번에 들어온다. 이건 표를 외우기 쉽게 하는 **읽는 법** 이고, 코드에 그 이유가 쓰여 있지는 않다 `[추측: 읽는 법]`.

1. **접수증 없이 바로 끝남** — 손님은 syscall 반환값으로 결과를 **이미 안다.**
   - 빨강이면: 아무것도 안 건드리고 도장만 (run126 해설 2.16 과 같음). 쪽지도 없다.
   - 초록이면: 쪽지를 보내는 게 기본. 단 손님이 스위치 1 ("잘 끝난 건 안 넣어도 돼요") 을 켰으면 생략.
   - 노랑이면: 스위치 1 이 켜져 있어도 **보낸다.** 스위치 1 은 "성공" 몫만 건너뛴다.
2. **접수증 뒤 끝남** — 손님은 "접수했어요" 만 받고 **떠났다.** 결과를 알 길은 우편함뿐이다.
   - 그래서 초록이든 빨강이든, 스위치와 상관없이 **보낸다.**
3. **어느 경우든 `ApcContext` 가 0 이면 안 보낸다.** 메모를 안 맡긴 손님이다.

### 2.12 빠른 길도 같은 규칙으로 따로 넣는다 `[정적]`

run 문서 5절 끝 · "flow-writer 대조". run126 해설 2.17 에서 "**(안 읽음)**" 으로 남았던 `+0xbbc` 뒤를 이번에 읽었다.

`IopXxxControlFile` 빠른 길 (창구 즉석 답, run126 해설 2.2) 이 TRUE 를 돌려준 뒤 (`+0x70f → +0xb16`):

1. `+0xbb4 / +0xbbc` — 서랍 (`FileObject+0xb0`) 이 있으면 `+0xe82` 로.
2. `+0xe82 ~ +0xe96` — 스위치 1 (`0x2000000`) 켜짐이면 **노랑일 때만 계속**, 아니면 `+0xbc2` 로 건너뜀.
3. 스위치 1 꺼짐이면 `+0xe9c ~ +0xea9` — **빨강이면** `+0xbc2` 로 건너뜀.
4. 아니면 `+0xec7 IopIncrementCompletionContextUsageCountAndReadData` — 서랍에서 우편함 · 꼬리표 읽기.
5. `+0xc10 / +0xc13 → +0x10a9` — `ApcContext` (`[RSP+0x288]`) 가 0 이면 쪽지 없이 (`+0x10b1 / +0x10b4`). 아니면 **`+0x10df` 쪽지 넣기**.
   - 넣기 실패면 status `0xC000009A`, 노랑이면 `0x103` 으로 바꿈 (`+0x10e4 ~ +0x1101`) → `+0x110e → +0xc19`.

여기서 중요한 한 가지 (flow-writer 가 `.asm` 으로 맞춤):

- 2 · 3 에서 건너뛰는 목적지가 **둘 다 `+0xbc2`** (손님 신호등 단계) 다.
- 그래서 빠른 길에서 건너뛰는 건 **쪽지만** 이다. 전표 · 신호등은 run126 해설 2.17 대로 **빨강이어도 쓴다.**

| | 빠른 길 (창구 즉석 답) | IRP 길 (배달 봉투) |
|---|---|---|
| 바로 빨강 — 전표 · 신호등 | **씀** (run126) | 안 씀 (run126) |
| 바로 빨강 — 우편함 쪽지 | **없음** (이번) | **없음** (이번) |
| 바로 초록 + 스위치 1 | 쪽지 없음 | 쪽지 없음 |
| 노랑 | 쪽지 있음 | 쪽지 있음 |

비유: 창구가 즉석에서 "안 돼요" 라고 한 일은, 전표엔 "안 돼요" 를 적어 주지만 **우편함엔 아무것도 안 넣는다.**

### 2.13 ★ 답 — "`ConnectEx` 가 바로 오류면 쪽지 없음" 이 맞나 `[정적 + 공백]`

run 문서 6절. 요청 쪽이 가장 알고 싶었던 것.

근거 → 그래서 → 아직 확인 아님:

1. **근거** `[정적]`: 2.11 표 첫 줄 — 바로 빨강 (`PendingReturned` 0) 이면 IRP 길은 `IopCompleteRequest +0xbf → +0x426 → +0x445` 로 서랍조차 안 읽는다.
2. **근거** `[정적]`: 2.12 — 빠른 길도 `+0xe9c ~ +0xea9` 에서 빨강이면 쪽지를 건너뛴다.
3. **그래서 → 예.** afd 가 **접수증 없이** 빨강 (syscall 반환이 `0xC000023C` 같은 오류, `0x103` 아님) 으로 끝내면 쪽지는 없다. 에뮬레이터가 지금 그 경우 쪽지 넣기를 안 부르는 건 **맞다.**
4. **반례** `[정적]`: afd 가 `IoMarkIrpPending` 뒤 `0x103` 을 먼저 돌려주고 나중에 빨강으로 끝내면, `ApcContext` ≠ 0 일 때 **쪽지가 간다** (2.11 표 마지막 줄).
5. **아직 확인 아님** `[공백]`: afd `AfdSuperConnect` (`0x120c7`) 가 둘 중 **어느 쪽** 인지는 정적으로 못 정했다. afd 를 이번에 안 읽었다. → 정적 Q236 ①, 동적 Q235 4 (= run124 동적 ⑤ 와 같은 질문).

비유: "바로 '안 돼요' 라고 돌려준 일은 우편함에 아무것도 안 넣는다. '접수했어요' 라고 한 뒤 나중에 실패하면 넣는다" — 남은 건 **창구 직원 (afd) 이 연결 실패를 어느 말투로 하느냐** 다.

### 2.14 flow-writer 대조 — 결과서와 다르게 적은 곳 (뜻은 같음)

run 문서 "flow-writer 대조". run 문서를 따른다.

1. 결과서 "`IopReplaceCompletionPort` 를 `+0x33aefe` 에서 부름" → `_calls.tsv` 는 조각 표기 `frag:FUN_1406e61bb+0x13` (ret `+0x18`). `.asm` 에 `(= NtSetInformationFile +0x33aefe)` 로 같은 자리다. run 문서는 둘 다 적었다.
2. 결과서 "`+0x10df IoSetIoCompletionEx` (PDB 별칭 `IoSetIoCompletionEx2`)" → `_calls.tsv` 이름은 `alias:IoSetIoCompletionEx`, `pdb_aliases.py --lookup` 으로 같은 주소 이름 2개 (`IoSetIoCompletionEx2` · `IoSetIoCompletionEx`). run 문서는 "**쪽지 (패킷) 넣기**" 로 적고 후보 둘을 붙였다. 이 글도 그렇게 부른다.
3. 결과서 빠른 길 "켜짐 → 경고일 때만 계속, 아니면 건너뜀" → 건너뛰는 곳을 `.asm` 으로 맞추니 `+0xe96 JNZ` · `+0xea9 JZ` 둘 다 `+0xbc2`. 그래서 건너뛰는 건 **쪽지만** (2.12).
4. 결과서 `alias:RtlCopyMemory` (`+0x72a`) → run 문서는 하는 일 "입력을 풀에 복사" 로 적었다.

### 2.15 정리 — 비유로 한 번 더

- 손님 (Go 프로그램) 이 사서함 (소켓) 을 열자마자 신청 창구에 두 장을 낸다.
- 첫 장 (`0x1e`): "이 사서함 소식은 **저 우편함** 으로, **이 꼬리표** 붙여서."
  - 접수 사무실이 받아서, 서랍이 비었고 "서서 기다리는 손님" 이 아니면, 우편함 **열쇠 사본** 을 하나 받아 쪽지 `{우편함, 꼬리표, 보는 사람 수}` 를 서랍에 넣는다.
  - 우체국 창구 직원 (afd) 은 **부르지도 않는다.**
  - 열쇠 사본은 사서함 카드를 **폐기할 때** 반납한다.
- 둘째 장 (`0x29`): "잘 끝난 건 우편함에 안 넣어도 돼요 …" 스위치를 **켠다.** 끄는 길은 없다.
- 두 장 다 "안 돼요" 면 **도장만** 돌려준다. 전표는 손님이 써 둔 그대로.
- 그 뒤 사서함 일이 끝날 때:
  - 접수증 없이 바로 끝났으면 손님은 이미 결과를 안다 → 빨강이면 쪽지 없음, 초록이면 (스위치 1 이 꺼졌을 때만) 쪽지.
  - 접수증을 받고 떠났으면 → 초록이든 빨강이든 쪽지.
  - 메모 (`ApcContext`) 를 안 맡긴 손님 몫으로는 늘 쪽지 없음.
