### 비유 — 그대로 이어 쓴다

- 프로세스 = **가게**, 커널 = **관리사무소**, syscall = 관리사무소 **신청 창구**, 핸들 = **손잡이**.
- run124 의 그림 그대로:
  - afd = 관리사무소 안 **우체국 창구** 상담실, 소켓 하나 = **사서함** 하나.
  - mswsock = 가게 안 **우편 담당 직원**, ws2_32 = 가게 **계산대**, tcpip = 창구 뒤 **배송 회사**, nsi = 관리사무소의 **망 안내 데스크**.
  - IOCTL = **번호 붙은 주문서**, IRP = 주문서를 담는 **배달 봉투**, IOSB = **전표**, 이벤트 = **신호등**, 완료 포트 = **우편함**.
- 이번에 새로 붙는 그림:
  - 출력 버퍼 = 손님이 내미는 **답장 종이**. run124 해설 2.7 의 "질문지 한 장을 내밀면 창구가 그 종이에 답을 적는다" 와 같은 그림이다.
  - I/O 관리자 = 관리사무소의 **접수 사무실**. 주문서를 상담실에 건네고, 끝나면 전표를 손님 칸에 넣고 신호등을 켜는 쪽이다.
- 주의 — 이름이 겹치는 곳:
  - run 문서 "결과" 의 비유는 출력 버퍼를 "**봉투**", IRP 를 "**접수증**", IOSB 를 "**결과 쪽지**", 이벤트를 "**벨**" 이라 부른다.
  - 이 글은 앞 해설들과 맞춰 출력 버퍼 = **답장 종이**, IRP = **배달 봉투**, IOSB = **전표**, 이벤트 = **신호등** 으로 부른다. 그림만 다르고 사실은 같다.

### 한 줄로 먼저 — 무엇을 얻었나

> **창구 (afd `AfdAddressListQuery`) 는 답장 종이가 4 바이트 이상이면 맨 앞에 "주소 N 개" 를 꼭 적는다 — 0 개여도, 종이가 모자라도.**
> **직원 (mswsock `WSPIoctl`) 은 그 N 하나만 보고 "이만한 종이가 필요해요" (`8 + N × (16 + A)`) 를 셈한다. 전표 아래 칸 (`Information`) 은 안 본다.**
> **그래서 에뮬레이터가 N 을 안 적으면, 종이에 원래 묻어 있던 쓰레기가 N 이 된다.**
> **망 없는 PC 의 정직한 대답 = status 0 · `Information` 4 · 종이 맨 앞 `00 00 00 00`.**

모두 `[정적]`. 단 "쓰레기가 N 이 되어 64 MiB 를 잡았다" 는 이어 붙인 짐작이라 `[추측]` 이다 (2.10).

또 하나, 커널 쪽 (sast/124):

> **배달 봉투 (IRP) 로 간 주문서가 PENDING 없이 "오류 (`0xC…`)" 로 끝나면, 접수 사무실은 전표도 안 쓰고 신호등도 안 켠다. 성공 · 경고면 전표를 쓰고 신호등을 켠다.**
> **반대로 창구가 즉석에서 답한 주문서 (빠른 길) 는 오류여도 전표를 쓰고 신호등을 켠다.**

IRP 길은 `[정적]`, 빠른 길은 flow-writer 가 줄을 이어 읽은 `[정적: 줄 읽기]` 이고, "afd 즉시 처리 주문서가 늘 이쪽" 은 `[추측]` 이다 (2.17).

## 1. 이번 바퀴의 질문

### 큰 그림에서 어디인가

run124 와 같은 자리, **초기화 밖** 이다. `main` 뒤 프로그램 코드가 소켓을 쓸 때의 옆길이다.

```
cmd.exe 의 부탁 (CreateProcess)
 │  커널: 프로세스 · 주소 공간 · PEB · 첫 스레드
 │  ntdll: LdrInitializeThunk → LdrpInitializeProcess → DLL 들이기 · 전원 켜기
 └─ NtContinue (은퇴) → exe 진입점 → (CRT 점선 상자) → main
                                                        │
      test.exe 는 여기서 소켓을 안 쓴다 [관찰][소스]      │ 소켓을 쓰는 프로그램이라면 (예: WinHttp 길):
                                                        ├─ socket() / connect()                       (run124)
                                                        └─ WSAIoctl(SIO_ADDRESS_LIST_QUERY)
                                                             (ws2_32 → mswsock 다리는 [공백])
                                                             └─ mswsock!WSPIoctl                       ← 이번 (run126)
                                                                  └─ NtDeviceIoControlFile(0x120b3)
                                                                       ⇒ I/O 관리자 → afd!AfdAddressListQuery   ← 이번
                                                                         (IRP 길 완료 규칙 — 커널 공용)          ← 이번
```

- flow.md 에서는 **3장 끝 새 절** "AFD 주소 목록 묻기 · IOCTL 완료" 다. run124 의 "소켓 장치 AFD" 절 **바로 다음 이야기** 다.

### 왜 이 질문이 지금 왔나

- PE_emulator 요청이다. run124 덕분에 에뮬레이터에서 소켓이 열리게 되자, WinHttp 길에서 **새 멈춤** 이 났다 — `UC_ERR_WRITE_UNMAPPED` (`ntdll!RtlpAllocateHeap+0x7ed`) (요청서, 에뮬레이터 로그).
- 소켓 하나의 차례가 이랬다 (요청서, 에뮬레이터 로그 — 진짜 Windows 아님):
  - 열기 → (`0x1207b` ×2) → `0x12047` → `0x120bf` → `0x12047` → **`0x120b3` ×3** → `0x120bf` (출력 8 B 힙) → 닫기.
  - `0x120b3` 세 번의 답장 종이: **N B 힙 → 4 B 스택 → 8 B 힙** (N = `0x200` 또는 `0xc98`).
- 요청한 쪽 짐작 `[추측]`: 우리 기본 대답이 "성공" 만 주고 종이 · 전표에 아무것도 안 적어서, 부른 쪽이 **안 쓴 칸에서 개수를 읽어** 크기를 잘못 셈했다 → 64 MiB 넘는 할당.
- 그래서 핵심 질문이 하나로 모였다: **"어느 칸이 다음 크기를 정하나?"**
- 사용자 결정 2026-11-17: "**다른 것보다 이거 먼저**".

### 무엇이 궁금했나

요청서 둘의 질문 (run 문서 "목적").

1. (R1 · R2) `0x120b3` — 창구가 종이에 무엇을 적나, 종이가 작을 때 · 주소가 0 개일 때 정직한 대답은, 직원은 그걸 어떻게 읽어 다음 크기를 셈하나.
2. (R3 · R4 · R5) 곁가지 — `0x120bf` 의 출력, `AfdBind` 의 출력, `SOCKADDR_SIZE` 표.
3. (R6) 배달 봉투 (IRP) 로 간 IOCTL 을 드라이버가 PENDING 없이 끝냈을 때, 전표 · 신호등 · 우편함 · APC 는 어떻게 되나 — status 별, 손잡이 종류별.

### 바퀴 전에 알던 것

- `[정적]` (run124, sast/121) `0x120b3` → `AfdAddressListQuery`, **즉시 처리 표** (`AfdImmediateCallDispatch`). `0x120bf` → `AfdTliIoControl` · `0x12003` → `AfdBind` 는 IRP 길 (`AfdIrpCallDispatch`).
- `[정적]` (요청서 "이미 아는 것") 즉시 처리 길: 표 찾기 → `&Information` = IoStatus + 8 → 처리 함수 → `IoStatus.Status` = 반환값 → TRUE (`AfdFastIoDeviceControl.asm +0xff ~ +0x114, +0x15d9 ~ +0x160a`). 그 뒤 전표 16 B 복사 · `KeSetEvent` (`IopXxxControlFile.asm +0xb38 ~ +0xb66, +0xbc2 ~ +0xbe4`).
- `[정적]` 처리 함수 인자 꼴 = (파일 객체, 코드, 요청 모드, 입력, 입력 길이, 출력, 출력 길이, `&Information`). 코드는 모두 `METHOD_NEITHER`.
- `[정적]` (sast/121) mswsock 은 PENDING 이 아니면 전표 · 신호등을 안 본다 (`SockDoConnectReal.asm +0x420, +0x46f, +0x471`, [run124 해설 2.15](run124-afd-socket-해설.md)).
- `[정적]` IRP 길: 신호등은 드라이버 앞에서 끄고 (`IopXxxControlFile +0x2db`), 그 뒤 `IopSynchronousServiceTail` (`+0x997`). **그 안은 몰랐다.**
- `[추측]` run124 해설 3절: "끝나면 세운다 (`+0xbe4/+0xbe9 KeSetEvent`). 어느 갈래에서 세우는지는 안 읽었다." — 이번에 풀린다 (2.18).
- 에뮬레이터 지금 (갈래 K, K02): IRP 길 IOCTL 에 "status 만 돌려줌 · 전표 안 씀 · 신호등 꺼 둔 채" (요청서 sast/124).

#### 새 말 — `SIO_ADDRESS_LIST_QUERY`

- 프로그램이 `WSAIoctl` 로 소켓에 "**이 PC 의 내 주소 목록을 주세요**" 하고 묻는 제어 코드다. mswsock 안에서 값은 **`0x48000016`** 이다 `[정적]` (`WSPIoctl +0xb20 ~ +0xb26 → +0xce8`).
- 이 이름 자체는 값과 공개 이름을 맞춘 것이다 `[추측: 이름]` (PDB 에 상수 이름 없음).
- 이 갈래가 afd 에 내는 주문서 번호가 **`0x120b3`** 이다.
- 비유: 손님이 우편 담당 직원에게 "우리 사서함 쪽에서 쓸 수 있는 **보내는 주소** 가 뭐뭐 있어요?" 하고 묻는 것.

### 2.2 새 말 — 빠른 길 / IRP 길

이번 글 전체가 이 둘의 차이 위에 서 있어서, 먼저 푼다.

- **IRP 길** = 접수 사무실 (I/O 관리자) 이 주문서를 **배달 봉투 (IRP)** 에 넣어 상담실 (드라이버) 로 넘기는 길. 상담실이 일을 끝내면 "봉투 다 됐어요" (`IoCompleteRequest`) 를 하고, 접수 사무실이 **봉투를 열어 결과를 손님에게 돌려준다** `[정적]` (`IopXxxControlFile +0x997 IopSynchronousServiceTail`).
- **빠른 길** = 봉투를 안 만들고, 상담실 창구가 **그 자리에서 바로** 답하는 길. 드라이버가 "제가 처리했어요" (TRUE) 를 돌려주면 접수 사무실은 봉투 없이 결과를 손님에게 옮긴다 `[정적]` (`IopXxxControlFile +0x70f → +0xb16`).
  - 공식 이름은 fast I/O 로 알려져 있다 `[추측]` (일반적으로 알려진 설명). afd 에선 `AfdFastIoDeviceControl` 이 이 입구다.
- afd 는 주문서 번호마다 둘 중 한 길을 정해 둔다 — run124 해설 2.6 의 "**바로 끝나는** 주문 = 즉시 처리 표" 가 빠른 길 쪽이다.
  - `0x120b3` · `0x1207b` · `0x12047` → 즉시 처리 (빠른 길)
  - `0x120bf` · `0x12003` → IRP 길
- 왜 중요한가: **"결과를 손님에게 돌려주는 규칙" 이 두 길에서 다르다.** 특히 오류일 때 (2.16 · 2.17).
- 비유:
  - IRP 길 = 주문서를 **봉투에 넣어 안쪽 방으로** 보내고, 다 되면 접수 사무실이 봉투를 열어 전표를 손님 칸에 넣는다.
  - 빠른 길 = 창구 직원이 **그 자리에서** 답을 적어 주고, 접수 사무실은 그 답을 그대로 베껴 넘긴다.

### 2.3 한 줄씩 읽는 법

run 문서 "정적 — 호출 지점" 표에서 세 줄을 골랐다.

**줄 ①** `| mswsock!WSPIoctl | +0xe1d | +0xe24 | NtDeviceIoControlFile (0x120b3) | [정적] |`

- **누가**: mswsock 의 `WSPIoctl` (rva `0x191b0`, 8547 B). `WSAIoctl` 이 공급자 (mswsock) 로 넘어오면 닿는 함수로 보인다 `[추측: ws2_32 안 봄]`.
- **어디서**: `SIO_ADDRESS_LIST_QUERY` 갈래 안, `+0xe1d` 에서 call, 돌아올 자리 `+0xe24`.
- **누구를**: `NtDeviceIoControlFile` syscall.
- **무엇을 위해**: 창구에 주문서 `0x120b3` 을 내서, 답장 종이에 **주소 목록** 을 받으려고.
  - 인자: 손잡이 = 소켓, 이벤트 = 스레드 자료 `+0x10`, APC 0, 전표 = `RSP+0xf8`, 입력 2 B, 출력 · 길이 (2.4).
- 디버거로 보면 콜스택에 `mswsock!WSPIoctl+0xe24` 가 찍힐 자리다.

**줄 ②** `| afd!AfdFastIoDeviceControl | +0x1603 | +0x1608 | 간접 (즉시 처리 표 — 44번 칸 AfdAddressListQuery) | [정적] |`

- **누가**: 커널 afd 의 빠른 길 입구 `AfdFastIoDeviceControl`.
- **어디서**: `+0x1603` 에서 call, ret `+0x1608`.
- **누구를**: 이름이 아니라 **표의 칸** 을 부른다 (간접 호출). 칸 번호 = `(0x120b3 >> 2) & 0x3ff = 0x2c` = **44번 칸**, 그 칸이 `AfdAddressListQuery` 다. 결과서가 sast/121 의 표와 같다고 맞춰 봤다.
- **무엇을 위해**: 주문서를 처리 함수에 넘기고, 그 반환값을 `IoStatus.Status` 에 쓰려고 (요청서 `+0x15d9 ~ +0x160a`).

**줄 ③** `| nt!IopCompleteRequest | +0x3d5 | +0x3da | KeSetEvent (사용자 이벤트) | [정적] |`

- **누가**: 커널 I/O 관리자의 `IopCompleteRequest` (rva `0x214750`). 배달 봉투를 마지막으로 정리하는 함수.
- **어디서**: `+0x3d5` 에서 call, ret `+0x3da`.
- **누구를**: `KeSetEvent`.
- **무엇을 위해**: 손님이 들고 온 **신호등** 을 켜려고. 단 이 줄은 **오류 (`0xC…`) 가 아닐 때만** 지난다 (2.16).
- run124 해설이 "어디서 켜나 모름" 으로 남겼던 자리 중 IRP 길 몫이 바로 이 줄이다.

### 2.4 직원이 주문서를 내는 법 — `WSPIoctl` 내는 줄 `[정적]`

run 문서 5절 "내는 줄" 그대로.

| 줄 | 하는 일 |
|---|---|
| `+0xcf3 ~ +0xd0f` | 전표 (`RSP+0xf8`, 16 B) 0 · **4 B 스택 칸 (`RSP+0x110`) 0** · 입력 칸 0 |
| `+0xd17 ~ +0xd1f` | `*lpcbBytesReturned = 0` |
| `+0xd22 ~ +0xd3c` | `cbInBuffer ≠ 0` → WSAEINVAL (`0x2726`) |
| `+0xd41 ~ +0xd72` | 손님이 종이를 줬으면 **`cbOutBuffer` B 힙** 을 따로 잡음 (플래그 0 = **0 으로 안 채움**). 못 잡으면 WSAENOBUFS (`0x2747`) |
| `+0xda0 ~ +0xdc0` | 종이가 없으면 "**크기만 묻기**" — 출력 = 4 B 스택 칸, 길이 4 |
| `+0xdc7 ~ +0xdcb` | **입력 2 B = 소켓 구조체 `+0x1c` (만들 때의 계열)** |
| `+0xdd3 ~ +0xe1d` | `NtDeviceIoControlFile(…, 0x120b3, 입력 2 B, 출력, 길이)` |

읽는 법:

- **입력은 딱 2 바이트, 주소 계열 하나.** 예를 들어 AF_INET 소켓이면 2. "이 계열의 주소만 주세요" 라는 뜻이다.
- **답장 종이는 두 종류** 다. 여기가 뒤에서 중요해진다.
  - 손님이 종이를 줬으면 → 직원이 **같은 크기의 새 종이** 를 힙에 잡아 창구에 낸다. 이 종이는 **안 지운 종이** 다 (0 으로 안 채움).
  - 손님이 종이를 안 줬으면 → 직원 주머니의 **4 바이트 쪽지** (스택 칸) 를 낸다. 이 쪽지는 **미리 0 으로 지워 둔다** (`+0xcf3 ~ +0xd0f`).
- 창구에 낸 종이 (힙) 와 손님 종이는 **다른 종이** 다. 직원은 창구 답을 읽어 손님 종이에 **다시 옮겨 적는다** (2.9).
- 요청 쪽 로그의 "입력 길이 2 · 전표 = 입력 + `0x10` · 스레드 이벤트 · APC 0" 과 모두 같다. 스택 칸 자리 (입력 `RSP+0xe8` · 전표 `RSP+0xf8` · 4 B 칸 `RSP+0x110`) 까지 로그 모양과 맞아서, 결과서는 이걸 "**같은 빌드라는 증거**" 로 썼다 (run 문서 "환경" 버전 대조).

### 2.5 창구의 검사 차례 — `AfdAddressListQuery` `[정적]`

rva `0x25840`, 1237 B. run 문서 1절 표를 줄였다. 줄은 모두 `ms/disassemble/afd/AfdAddressListQuery.asm`.

| 차례 | 조건 | status | `Information` | 종이 | 줄 |
|---|---|---|---|---|---|

| 1 | 입력 길이 < 2 | `0xC000000D` | 0 | 안 씀 | `+0x86 ~ +0x89` |
| 2 | **출력 길이 < 4 (0 포함)** | `0xC000000D` | 0 | 안 씀 | `+0x8f ~ +0x99` |

| **8** | 계열 읽기 · **종이 `+0` = 0** · 쓴 크기 = 4 | — | — | **`+0` DWORD 0** | `+0xeb` · `+0xfe` · `+0x109` |
| 9 ~ 11 | 컴파트먼트 번호 · 만들기 · 첫 채우기 실패 | 그 status / `0xC000009A` | 0 | 개수 0 남음 | `+0x12a` · `+0x3c4` · `+0x46a` |

### 2.6 ★ 답장 종이에 적히는 모양 `[정적]`

run 문서 2절 그대로.

| 오프셋 (종이 시작 기준) | 크기 | 뜻 | 값 · 줄 |
|---|---|---|---|
| `+0x00` | 4 | **개수** | 0 으로 시작 (`+0x109`), 칸 하나마다 +1 (`+0x31d ~ +0x322`) — **본문이 안 들어가도 센다** |
| `+0x04` | 2 | 첫 칸 `AddressLength` | IPv4 `0x0e` · IPv6 `0x1a` |
| `+0x06` | 2 | 첫 칸 `AddressType` (계열) | 2 · `0x17` · `0x11` |
| `+0x08` | 길이 B | 주소 본문 | IPv4: 포트 2 B (0) · 주소 4 B · 0 8 B. IPv6: 포트 2 · flow 4 · 주소 16 · 범위 4 |
| 다음 칸 | — | 빈틈 없이 바로 뒤 (정렬 없음) | 복사 위치 = 종이 + 누적 크기 (`+0x240 ~ +0x24b`, `+0x324`) |

#### 새 말 — `TA_ADDRESS` 칸

- "길이 2 B + 계열 2 B + 주소 본문" 한 덩어리. run 문서가 이 모양을 **`TA_ADDRESS`** 라 부른다 — 이름은 TDI 문서의 같은 모양과 맞아서 붙였다 `[추측: 이름]`.
- 칸 하나 크기 = `AddressLength + 4` → **IPv4 18 B, IPv6 30 B** `[정적]`.
- 비유: 종이 맨 위 "N 개" 아래로, **주소 딱지** 를 빈틈 없이 이어 붙인 모양. 딱지마다 앞에 "길이" 와 "종류" 가 적혀 있다.

읽는 법:

- **포인터 칸이 없다.** 종이 안의 다른 자리를 가리키는 주소 값은 없다. 손님에게 줄 "주소 가리키는 칸" (`lpSockaddr`) 은 직원 (mswsock) 이 따로 만든다 (2.9).
- 포트는 늘 0 — 칸을 만드는 `AfdNsiAddressChangeEventAtPassive` 가 포트 자리를 0 으로 둔다 (`+0x19b ~ +0x1a7`, `+0x276 ~ +0x281`) `[정적]`.
- **개수가 0 이면 `+4` 부터는 안 건드린다.** 종이 나머지는 원래 있던 그대로다.

#### 새 말 — 이중 모드 (짧게)

- IPv6 소켓 하나로 IPv4 상대와도 말할 수 있게 켜 두는 모드로 알려져 있다 `[추측]` (일반적으로 알려진 설명).
- 이번 코드에서 확인한 것 `[정적]`: 계열 `0x17` 로 물었고 엔드포인트 `+8` 비트 `0x14` 가 켜져 있으면, IPv4 칸을 `::ffff:a.b.c.d` 꼴 IPv6 칸 (30 B) 으로 바꿔 보낸다 (`+0x27e ~ +0x286`, `+0x1f1 ~ +0x21a`, `+0x21a IN6ADDR_SETV4MAPPED`).
  - 이 비트는 `0x120bf` 로 레벨 `0x29` · 옵션 `0x1b` 를 값 0 으로 설정해 성공했을 때 켜진다 (`AfdCompleteTliIoControlCore +0x1d2 BTS` / `+0x226 BTR`). **새 엔드포인트는 꺼짐.**
- 에뮬레이터 입장: 새 소켓이면 이 갈래는 안 탄다.

### 2.7 ★ 종이가 작을 때 — "개수는 늘 적는다" `[정적]`

run 문서 3절 표.

| 출력 길이 | 주소 0 개 | 주소 1 개 IPv4 (필요 22 B) |
|---|---|---|
| 0 ~ 3 | `0xC000000D`, Info 0, 안 씀 | 같음 |
| 4 | status 0, Info 4, `+0` = 0 | **`0x80000005`, Info 22, `+0` = 1** (본문 없음) |
| 8 | status 0, Info 4, `+0` = 0 (`+4 ~ +7` 그대로) | **`0x80000005`, Info 22, `+0` = 1** (`+4 ~ +7` 그대로) |
| 22 이상 | status 0, Info 4 | status 0, Info 22, 본문 18 B |

왜 이렇게 되나, 단계별로 `[정적]`:

1. 종이 < 4 바이트면 "**개수 칸조차 못 적는다**" → 처음부터 `0xC000000D` (서식 틀림). 종이도 전표 아래 칸도 0.
2. 종이 ≥ 4 바이트면 `+0x109` 에서 개수 칸에 0 을 먼저 쓴다.
3. 목록을 돌며 **칸마다 개수를 +1** 한다 (`+0x31d`). 이건 **본문이 들어가든 말든** 한다.
4. 본문이 들어갈 자리가 있을 때만 칸을 복사한다 (`+0x24b`).
5. 끝에 `Information` = **누적 크기** 를 쓴다 (`+0x2bd ~ +0x2c1`). 넘쳤어도 누적 크기를 그대로 쓰니, 이 값이 곧 "**필요한 전체 크기**" 가 된다.
6. 하나라도 안 들어갔으면 status = `0x80000005`.

- 22 는 어디서 왔나: 개수 4 + IPv4 칸 18 = 22 (`0x16`). 2.5 표의 "4 + Σ(칸 길이 + 4)" 식에 칸 하나를 넣은 것이다.
- 비유: 종이가 작아도 창구는 맨 위에 "**주소 1 개 있어요**" 는 적어 준다. 그리고 "종이가 작아요 (`0x80000005`), 22 바이트짜리 가져오세요 (`Information`)" 라고 전표에 적는다.

### 2.8 목록은 어디서 오나 — 그리고 "0 개" 는 정상이다 `[정적 + 추측]`

run 문서 4절.

#### 새 말 — 컴파트먼트 (망 구획)

- run 문서 말로 "**망 구획**". afd 안에서 주소 목록을 담아 두는 객체다 `[정적]`: 목록 = **컴파트먼트 객체 `+0xa8` 의 연결 목록**.
- 컴파트먼트는 엔드포인트 `+0x58` 에 달린다. 없으면 처음 물을 때 만든다 (`AfdGetCompartment`).
- 번호는 `AfdQueryCompartmentId` 가 정한다 — 조건이 맞으면 TL 에 `SO_COMPARTMENT_ID` (레벨 `0xffff` · 옵션 `0x3004`) 를 묻고, 아니면 **1 (기본)** `[추측: 옵션 이름은 값 기준]`.
- 비유: 우체국 안의 **구역별 주소록**. 보통 PC 는 기본 구역 (1번) 하나를 쓴다고 보면 된다.

#### 주소록을 채우는 사람

- **처음 한 번** (`AfdInitializeAddressList`, 계열마다 한 번, `AfdAddressListQuery +0x45f` 에서 부름) `[정적]`:
  1. 기본 컴파트먼트면 `TdiRegisterPnPHandlers` (`+0x170`).
  2. IPv4 · IPv6 각각 `NsiRegisterChangeNotificationEx` (`+0x1f9` · `+0x277`) — 콜백 = `AfdNsiAddressChangeEvent`.
  - 실패는 **물은 계열 것만** 오류로 올린다.
- **채우는 쪽** = 그 NSI 콜백 `[정적]`. 알림 종류 3 = 처음 전부 읽기 (`NsiAllocateAndGetTable`), 2 = 지움, 그 밖 = 추가 · 바뀜. 지금 IRQL 이 PASSIVE 가 아니면 작업 항목으로 미룬다.
- TDI 쪽 처리기 `AfdAddAddressHandler` 는 계열 2 · `0x17` 을 버린다 (`+0xa ~ +0x1e`) → IPv4 · IPv6 주소는 **NSI 로만** 들어온다 `[정적]`.
- 비유: 창구는 처음 주소록을 열 때 **망 안내 데스크 (nsi)** 에 "주소가 생기거나 없어지면 알려 주세요" 하고 연락처를 남긴다. 안내 데스크가 알려 줄 때마다 주소록에 적는다.

#### 새 말 — 루프백 · 주소 범위 · 선호 상태

- **루프백** = 망에 안 나가고 **자기 자신에게 돌아오는** 주소. `127.0.0.1` · `::1` 이 그것이다 `[추측]` (일반적으로 알려진 설명).
- **주소 범위 (scope)** = 그 주소가 어디까지 통하는지의 단계 값. 이번 코드는 `Ipv4UnicastAddressScope` · `Ipv6UnicastAddressScope` 로 이 값을 얻는다 (`AfdNsiGetAddressProperties +0x161` · `+0x176`) `[정적]`.
- **선호 상태** = 주소 중복 검사를 마치고 "**써도 되는**" 상태. 칸 이름 (`DadState`) 은 `[추측]`.

#### 주소록에서 빼는 것 `[정적]`

(`AfdNsiGetAddressProperties +0x150 ~ +0x18a`, `AfdNsiAddressChangeEventAtPassive +0x1be`)

- 인터페이스 칸 `+4` 가 **`0x18`** 이고 주소 범위가 3 보다 작으면 뺀다 → **루프백 `127.0.0.1` · `::1` 은 안 들어간다.**
  - `0x18` = `IF_TYPE_SOFTWARE_LOOPBACK` (24) 와 같은 값 `[추측: 칸 이름은 PDB 에 없음]`.
- 중복 검사 상태가 **4 (선호)** 인 것만 넣는다 `[추측: 칸 이름]`.

#### 그래서 "0 개" 는?

- 근거 `[정적]`: 목록이 비면 루프 (`+0x1a2 ~ +0x1ac`) 가 바로 `+0x298` 로 가서 **status 0 · Information 4** 로 끝난다. 이건 오류 갈래가 아니라 **보통 끝내는 길** 이다.
- 그래서 → **주소 0 개는 정상 대답** 이다. 루프백이 빠지니 **망 없는 PC 는 0 개일 수 있다.**
- 아직 확인 아님 → 망 없는 PC 에 **실제로 무엇이 남나** (끊긴 어댑터, 링크 로컬 `169.254.x.x` · `fe80::` 등) 는 NSI · tcpip 몫이라 `[공백]`. 정적으로 말할 수 있는 건 "루프백 인터페이스의 주소는 안 들어간다" 까지다 (→ Q233 1).

### 2.9 ★ 직원은 답을 어떻게 읽나 — 다음 크기 셈 `[정적]`

run 문서 5절 "읽는 줄" · "다음 크기 셈".

| 무엇 | 보는 것 | 줄 |
|---|---|---|
| 반환 `EAX` | `0x103` 이면 기다린 뒤 전표 `Status`, 아니면 반환값 그대로. **PENDING 이 아니면 전표를 안 읽는다** | `+0xe29 ~ +0xe58` |
| status | **`0` 또는 `0x80000005` 만 계속.** 그 밖 → `NtStatusToSocketError` → `*lpErrno` · −1 (`*lpcbBytesReturned` 는 0 그대로) | `+0xe5f ~ +0xe76` |
| 종이 `+0` | **개수** | `+0xe7b` |
| 전표 `Information` | **읽지 않는다** (함수 전체에 `[RSP+0x100]` 읽기 없음 — 결과서 `grep`) | |
| 소켓 도우미 정보 `+0x24` | `MaxSockaddrLength`, 8 로 올림 = **A** | `+0xe8a ~ +0xe9d` |

#### 새 말 — `MaxSockaddrLength` (A)

- 소켓 도우미 정보에 적힌 "**이 계열 주소 쪽지의 최대 길이**" 다. 레지스트리 값 `"MaxSockaddrLength"` 에서 읽는다 (`SockLoadHelperDll +0x2e8 RegQueryValueExW`) `[정적]`.
- 이걸 8 의 배수로 올린 값을 run 문서는 **A** 라 부른다.
- IPv4 보통 16 · IPv6 보통 32 `[추측: 레지스트리 값은 PC 마다]`.

#### 다음 크기 셈 (`+0xe7b ~ +0xedd`)

> **`*lpcbBytesReturned = 8 + 개수 × (16 + A)`**

- 8 = 손님 종이의 머리, 16 = `SOCKET_ADDRESS` 한 칸 (포인터 8 + 길이 4 + 빈칸 4), A = 계열별 주소 쪽지 자리.
- **이 식에 들어가는 창구 값은 "개수" 하나뿐** 이다. 이게 요청 쪽의 "어느 칸이 크기를 정하나" 에 대한 답이다.
- 보호 하나: 곱셈이 `0x7fffffff` 를 넘으면 크기를 안 쓰고 WSAEFAULT 로 간다 (`+0xeb3 ~ +0xec9` → `+0xfb2`).
- 크기를 쓴 뒤 오류로 가는 갈래 (`*lpcbBytesReturned` = 필요 크기 + **WSAEFAULT** `0x271e`): status `0x80000005` · 종이 없음 · 필요 > `cbOutBuffer` (`+0xedf ~ +0xef7`). → 이것이 "**크기 묻기**" 의 정직한 대답이다.
- **재시도 고리 없음** — `WSPIoctl` 은 `0x120b3` 을 **한 번만** 낸다.

#### 새 말 — `SOCKET_ADDRESS_LIST`

- 손님 종이에 다시 적는 모양이다. 창구 종이 (`TA_ADDRESS` 칸) 와 **모양이 다르다** `[정적]`:
  - `[out+0]` = 개수 (`+0xf27`)
  - `[out + 8 + 16·i]` = `lpSockaddr` — **손님 종이 안의 절대 주소** (가리키는 칸)
  - `[out + 0x10 + 16·i]` = `AddressLength + 2`
  - 본문은 창구 칸의 `AddressType` 부터 복사 (`+0xf46 ~ +0xf7d`)
- 이름은 공개 구조체 이름과 맞춘 것이다 `[추측: 이름]`.
- 숫자로 맞춰 보면: IPv4 칸 `AddressLength` `0x0e` (14) + 2 = 16, IPv6 `0x1a` (26) + 2 = 28. 계열 2 B 부터 복사하니 "길이 + 2" 가 되는 것이다 — 2.15 의 `SOCKADDR_SIZE` 값 (16 · 28) 과 같은 숫자다 (이 글이 숫자를 맞춰 본 것).
- 비유: 직원은 창구가 준 **딱지 줄** 을 보고, 손님 종이에는 "**목차** (몇 번째 주소는 이 종이 몇 쪽에 있음) + 본문" 꼴로 **새로 정리해서** 적어 준다. 목차의 "몇 쪽" 이 포인터다.

#### 정리 — 무엇을 꼭 맞춰야 하나

- **꼭**: status (`0` 또는 `0x80000005`), 종이 `+0` **개수**, (개수 > 0 이면) 칸 본문.
- **안 봄**: 전표 `Information` (PENDING 이 아니면 전표 자체를 안 봄).
- 이 꼴은 run124 해설 2.9 의 "직원은 대답에서 무엇을 보나" 표와 같은 종류다. 주문서마다 "보는 칸" 이 다르다는 것.

### 2.10 ★ 에뮬레이터는 왜 64 MiB 를 잡았나 — 근거 → 그래서 → 아직 확인 아님

여기가 이번 요청의 핵심 질문이다. 단계별로.

1. **근거** `[정적]`: 직원은 손님이 종이를 주면 **안 지운 힙 종이** 를 창구에 낸다 (2.4, `+0xd41 ~ +0xd72`).
2. **근거** `[정적]`: 직원은 status 가 0 이면 종이 `+0` 을 **개수로 읽는다** (2.9, `+0xe7b`). 전표 `Information` 은 안 본다.
3. **근거** (결과서 "지금 우리 맞나" — run 문서 "PE_emulator 쪽"): 지금 에뮬레이터의 afd 갈래 기본 대답 (`fake()` / `device_control_code_unverified`) 은 **"성공" 만 주고 개수 · Information 을 안 쓴다.**
4. **그래서**: 창구가 개수를 안 적으면, 힙 종이에 **원래 묻어 있던 쓰레기** 가 개수가 된다 `[추측: 쓰레기 값은 동적]`.
5. **그래서**: 그 쓰레기 개수로 `8 + 개수 × (16 + A)` 를 셈한다. 곱셈이 `0x7fffffff` 보다 작은 쓰레기면 보호를 지나, **큰 크기를 쓴 뒤** WSAEFAULT 로 간다. 부른 쪽은 그 크기로 새로 할당한다 `[추측]`.
   - 예: 개수가 약 `0x200000` 이면 `8 + 32 × 개수` ≈ 64 MiB `[추측]` (run 문서 5절).
6. **아직 확인 아님**:
   - 에뮬레이터 힙에 실제로 무엇이 있었는지 → Q233 7 (`WSPIoctl+0xe7b` 직전 `[r13]`). 힙이 0 으로 오는지는 에뮬레이터 `RtlAllocateHeap` 몫 `[공백]`.
   - 부른 쪽 (ws2_32 · 앱) 이 정말 그 크기로 할당하는지는 안 봤다 → Q234 ①.

덧붙여 이 글의 짐작 하나 `[추측]` — 로그의 "4 B 스택 → 8 B 힙" 이 어떻게 이어지나:

- 근거 `[정적]`: 종이 없는 호출의 4 B 스택 칸은 **미리 0 으로 지워 둔다** (2.4). 그리고 표 (run 문서 6절) 에서 "버퍼 없음 + 개수 0" 이면 `*lpcb` = **8** + WSAEFAULT.
- 그래서 → 창구가 아무것도 안 적어도 둘째 호출은 개수 0 → "8 바이트 가져오세요" → 셋째 호출이 **8 B 힙** 이 된 모양과 맞는다.
- 아직 확인 아님 → 부른 쪽이 세 번을 어떤 순서로 부르는지는 안 봤다. run 문서도 "세 번은 부른 쪽 몫 `[추측]`" 이라고만 한다.

비유로:

- 직원은 창구에 낼 때 **새 종이를 안 닦고** 낸다.
- 창구가 맨 위 "N 개" 를 안 적고 "됐어요" 도장만 찍어 주면, 직원은 종이 맨 위에 **원래 묻어 있던 낙서** 를 N 으로 읽는다.
- 그 N 으로 "**이만한 종이가 필요해요**" 를 셈하니, 터무니없이 큰 종이를 사러 가게 된다.

### 2.11 ★ 망 없는 PC 의 정직한 대답 — 최소 응답 `[정적 + 추측]`

run 문서 6절. 입력 2 B = 계열, 입력 길이 2, 요청 모드 유저.

| 출력 길이 | 반환 status | 전표 `Status` | 전표 `Information` | 종이 | mswsock 결과 |
|---|---|---|---|---|---|
| `0x200` (힙) | 0 | 0 | 4 | `00 00 00 00`, 나머지 그대로 | 성공, `*lpcb` = 8 |
| 4 (종이 없음) | 0 | 0 | 4 | `00 00 00 00` | `*lpcb` = 8 + WSAEFAULT |
| 8 (힙) | 0 | 0 | 4 | `00 00 00 00`, `+4 ~ +7` 그대로 | 성공, `*lpcb` = 8 |

- 주소 1 개 (IPv4 `192.168.0.5`, 계열 2) 일 때 예:
  - `0x200` → status 0 · Info `0x16` · `01 00 00 00 0e 00 02 00 00 00 c0 a8 00 05` + 0 8 B.
  - 4 · 8 → `0x80000005` · Info `0x16` · `+0` = 1 만.
  - mswsock 크기 = `8 + 1 × (16 + 16)` = 40 (A = 16 가정 `[추측]`).
- 한 줄 바이트를 풀어 읽으면: `01 00 00 00` 개수 1 → `0e 00` 길이 14 → `02 00` 계열 2 → `00 00` 포트 0 → `c0 a8 00 05` = 192.168.0.5 → 그 뒤 0 8 B (2.6 의 IPv4 본문 꼴).
- 전표는 **빠른 길이 정한다** — `IoStatus.Status` = 반환값, `Information` = 위 값을 `IopXxxControlFile +0xb38 ~ +0xb48` 이 16 B 통째로 복사 (2.17).
- "망 없는 PC = 선호 상태의 비루프백 주소 없음" 은 `[추측]` — 진짜 VM 에서 비는지는 Q233 1.
- 비유: "주소 0 개요" 라고 **맨 위에 0 을 적은 종이** 와 "됐어요" 도장, 그리고 전표 아래 칸 "4 바이트 적었음". 이게 정직한 대답 한 벌이다.

### 2.12 다른 부르는 곳 하나 — 여기는 `Information` 을 본다 `[정적]`

- `0x120b3` 을 내는 mswsock 줄은 **둘** 이다. 즉치 바이트 `b3 20 01 00` 을 mswsock 코드 구역 전체에서 훑어 찾았다 (결과서).
  - `WSPIoctl +0xe1d` — WinHttp 로그 길 (위 2.4 ~ 2.9).
  - `SockpCreateV6AddressMap +0xbe` (구역 `SANONTCP`) — 계열 `0x17` 고정.
- 둘째 쪽은 **`0x80000005` 면 전표 `Information` 만큼 다시 잡아 또 부르는 고리** 가 있다 (`+0xca ~ +0xcf → +0x3b`). 여기선 `Information` 이 필요 크기여야 끝난다.
- 그래서 → 에뮬레이터가 "넘침" 을 줄 때 `Information` = 필요 크기를 **정직하게** 적어 두면 두 길 다 맞는다. 2.7 의 창구 동작이 원래 그렇다.
- WinHttp 로그 길은 아니다 `[추측: 부르는 곳 안 봄]`.
- 비유: 같은 주문서라도 **다른 직원** 은 전표 아래 칸을 본다. 창구는 누가 오든 똑같이 정직하게 적으면 된다.

여기부터는 곁가지 셋 (`0x120bf` · `0x12003` · `SOCKADDR_SIZE`) 이다. 모두 run124 의 connect 앞 차례 ([run124 해설 2.11](run124-afd-socket-해설.md)) 에 나왔던 주문서다.

### 2.13 `0x120bf` — 창구는 답장 종이에 아무것도 안 적는다 `[정적]`

run 문서 7절. `0x120bf` → `AfdIoctlTable` 47번 칸 → **IRP 길** (`AfdIrpCallDispatch`). 처리 = `AfdTliIoControl` (rva `0x26430`, 3144 B).

**입력 `0x20`** (64 비트; 32 비트는 `0x18` 꼴):

| 오프셋 | 크기 | 뜻 | 줄 |
|---|---|---|---|
| `+0x00` | 4 | **종류**: 1 = 설정 (`WSPSetSockOpt`) · 2 = 읽기 (`WSPGetSockOpt`) · 3 = 소켓 ioctl (`WSPIoctl`). 그 밖 `0xC000000D` `[추측: 이름]` | `AfdAllowedUserIOControlRequest +0xb ~ +0x2d` |
| `+0x04` | 4 | 레벨. 종류 1 · 2 는 `0xfffc` · `0xfffd` 거절, 종류 3 은 0 만 | `+0x13 ~ +0x2d` |
| `+0x08` | 4 | 옵션 이름 / ioctl 코드 | `WSPIoctl +0x1fa9` |
| `+0x0c` | 1 | **반드시 1** | `AfdAllowedUserIOControlRequest +0x6 ~ +0x9` |
| `+0x10` · `+0x18` | 8 · 8 | 값 포인터 · 길이 (읽기는 0 · 0) | |

창구가 스스로 하는 것 · 배송 회사로 넘기는 것:

- **스스로**: 입력 검사 (TL 엔드포인트 아님 `0xC0000010` · 길이 < `0x20` 또는 허용 표 밖 `0xC000000D` · 정렬 `0xC00002C5` · 못 읽음 `0xC0000005` · 묶는 중 / 종류 안 맞음 `0xC0000184`), `AfdHandleISBIoctls` (안 읽음 `[공백]`), QoS 두 코드 앞처리 (안 읽음).
- **그 밖은 TL (tcpip)** 로 넘긴다 (`+0x7eb` 일반 등). 답장 종이는 **잠가서 TL 에 건넬 뿐** (`+0x147 ~ +0x1df`, `+0x77d ~ +0x7b1`) — **afd 는 종이에 안 쓴다.**
- 완료 (`AfdCompleteTliIoControlCore`): status = TL status, 단 **`0xC0000206` → `0xC0000023`** 로 바꿈 (`+0xa6 ~ +0xb5`). `Information` = TL 이 준 값 (안 주면 0).
- → 종이 내용 · `Information` · 작은 종이 status 는 **TL 몫** `[공백]`.

**어느 직원이 냈나** — 전표 자리로 셋이 갈린다 `[정적]`:

| 내는 줄 (ret) | 종류 | 전표 | 종이 | 보는 것 |
|---|---|---|---|---|
| `WSPSetSockOpt +0x1fd` (`+0x204`) | 1 | 입력 `+0x20` | 없음 | status 부호만 |
| `WSPGetSockOpt +0x7c4` (`+0x7cb`) | 2 | 입력 `−0x10` | `optval` · `*optlen` | 음수면 오류, **`Information` → `*optlen`** |
| `WSPIoctl +0x2007` (`+0x200e`) | 3 | 입력 **`+0x30`** | `lpvOutBuffer` · `cbOutBuffer` | 0 → `*lpcbBytesReturned = Information` 등 |

- 요청 쪽 로그 "입력 `0x20` · 출력 8 B 힙 · 전표 = 입력 + `0x30`" 은 **`WSPIoctl` (종류 3) 만** 맞는다.
- 어떤 ioctl 코드인지는 로그의 입력 `+0x08` DWORD 를 보면 안다. 정적으로는 앱이 고른 값이라 못 가린다 `[공백]` (→ Q233 8).
- 비유: 이 주문서는 창구가 **서식만 보고 배송 회사로 넘긴다.** 답장 종이도 배송 회사가 채운다. 창구가 스스로 고쳐 주는 말은 딱 하나 — 배송 회사의 `0xC0000206` 을 `0xC0000023` 으로.

### 2.14 `0x12003` `AfdBind` — "접수했어요 (`0x103`)" 뒤 배송 회사가 끝낸다 `[정적]`

run 문서 8절. rva `0x39160`, 2997 B. TL 모드 갈래만 풀었다 (TDI 모드 갈래는 `[공백]`).

검사 차례 (줄였다):

| 차례 | 조건 | status |
|---|---|---|
| 1 | 엔드포인트 `+5` 비트 `0x10` 과 `+6` 비트 1 이 둘 다 켜짐 | `0xC0000022` |
| 2 · 3 · 4 | 입력 < 6 · 출력 < 2 · 출력 < 입력 − 4 | `0xC000000D` |
| 5 | `[ep+0x170]` 0 → 3 바꾸기 실패 (다른 TL 요청 중) | `0xC000000D` |
| 6 | 엔드포인트 종류 `[ep+2]` 가 1 · 2 아님 (**이미 묶임 · 연결됨**) | **`0xC0000238`** |
| 9 | 계열 (입력 `+4` WORD) ≥ `0x23` | **`0xC0000141`** |
| 10 | 주소 쪽지 바이트 (입력 − 4) < `SOCKADDR_SIZE(계열)` | **`0xC0000141`** |
| 12 | **성공 갈래** | **`0x103` (PENDING)** — 결과는 TL 완료가 냄 |

(7 · 8 정렬 · 못 읽음, 11 출력 MDL 실패는 run 문서 8절.)

성공 갈래 사슬 `[정적]`:

```
AfdBind ─ +0x3a9 AfdTLBindSecurity            (공유 방식 1 · 3 이면 TL 에 재사용 · 독점 옵션 먼저)
            └─ +0x14a AfdTLBind ─ +0xa3 [간접] TL 제공자 bind   ⇢ 콜백 AfdTLBindComplete
AfdTLBindComplete ─ +0xd2 AfdTLBindComplete2   성공: [ep+2] ← 3, TL 에 로컬 주소 묻기
            └─ +0x143 AfdTLIoControl            ⇢ 콜백 AfdTLBindGetAddrComplete
AfdTLBindGetAddrComplete ─ +0x5b TdiCopyBufferToMdl (종이 +0 에 로컬 sockaddr) ─ +0xd8 IofCompleteRequest
```

- 종이 `+0` 에 **로컬 sockaddr**, `Information` = TL 이 준 바이트 수, Status = 복사 결과 (보통 0), `[ep+0x170]` ← 0.
- `[ep+2]` ← 3 (연결 객체가 붙는 소켓은 4).

#### 새 말 — 임시 포트

- bind 할 때 프로그램이 포트를 0 으로 주면, 시스템이 **빈 번호 하나를 골라** 붙여 주는 포트로 알려져 있다 `[추측]` (일반적으로 알려진 설명). run124 해설 2.11 의 "빈 번호 아무거나" 가 이것이다.
- 이번 코드에서 확인한 것 `[정적]`: **afd 에는 포트 칸을 쓰는 줄이 없다** → 임시 포트는 **TL (tcpip) 이 고른다.**

곁 이야기 — 요청 쪽 로그의 입력 길이 `0x10`:

- 입력 `0x10` 이면 주소 쪽지가 `0x10 − 4` = 12 B 다. AF_INET 이면 `SOCKADDR_SIZE(2)` = 16 보다 작으니 **차례 10 에 걸린다** `[정적]`.
- mswsock `WSPBind` 의 TL 모드 입력은 `namelen + 4` (`+0x229`) 라 IPv4 정상값은 **`0x14`** 다.
- 로그의 `0x10` 이 어떤 호출인지는 `[공백]` (→ Q233 11).

mswsock `WSPBind` 쪽 (sast/121 `.asm`): 성공이면 **`Information` = 묶인 주소 길이** 만큼 종이에서 소켓 로컬 주소 칸 `[sock+0xa8]` 로 복사 (`+0x45b` · `+0x4bf`). run124 해설 2.11 의 "이 주문서는 **전표 아래 칸까지 본다**" 와 같은 줄이다.

- 비유: 사서함에 보내는 주소를 붙여 달라고 하면, 창구는 서식만 보고 "**접수했어요**" (`0x103`) 를 먼저 준다. 배송 회사가 빈 번호를 골라 붙이고 나면, 그 주소를 **답장 종이 맨 앞** 에 적고 전표에 길이를 적어 봉투를 닫는다.

### 2.15 `SOCKADDR_SIZE` — 계열별 주소 쪽지 길이 표 `[정적]`

run 문서 9절. rva `0x5b40`, 29 B. 계열 < `0x23` 이면 afd `.rdata 0x7ad80` 표 한 바이트, 아니면 표 `[0]`.

| 계열 | 길이 |
|---|---|
| 0 | 0 |
| 1 (AF_UNIX) | 110 |
| **2 (AF_INET)** | **16** |
| **`0x17` (AF_INET6)** | **28** |
| `0x22` | 36 `[추측: AF_HYPERV 와 같은 번호]` |
| 3 ~ `0x16`, `0x18` ~ `0x21` | 0 (길이 검사가 늘 통과) |
| ≥ `0x23` | 표 `[0]` = 0 — 부르는 쪽이 먼저 `0xC0000141` |

- 부르는 곳: `AfdBind +0x24a` · `AfdConnect +0x514` (run124) · `AfdSuperConnect +0x1d3` 등.
- [run124 해설](run124-afd-socket-해설.md) 2.12 의 `AfdConnect` 검사 "`입력 − 0x18 ≥ SOCKADDR_SIZE(family)`" 에서 이름만 나왔던 그 함수다. 이제 값이 정해졌다.
- 비유: 계열마다 "**주소 쪽지는 최소 이만큼은 돼야 해요**" 를 적은 한 장짜리 표.

이제 아래 줄기 — 배달 봉투 길의 마무리 — 다. 여기는 afd 만이 아니라 **모든 상담실** 에 해당한다.

### 2.16 ★ IRP 길 완료 — 오류면 아무것도 안 건드린다 `[정적]`

run 문서 10절. `nt!IopSynchronousServiceTail` (rva `0x8eb0e0`) · `IopfCompleteRequest` (`0x2b2318`) · `IopCompleteRequest` (`0x214750`).

#### 새 말 — 성공 · 경고 · 오류 (`NT_ERROR`)

- status 는 맨 앞 자리로 세 무리로 나뉜다. 이번에 나오는 것만:
  - **성공** = `0x0…` (예: 0)
  - **경고** = `0x8…` (예: `0x80000005`)
  - **오류** = `0xC…` (예: `0xC000000D`)
- 이번 코드가 쓰는 오류 검사 = **`(Status & 0xC0000000) == 0xC0000000`** (`IopCompleteRequest +0xb3 ~ +0xbf`) `[정적]`. 맨 앞 두 비트가 **둘 다 1** 인 것만 오류다.
- 그래서 경고 (`0x8…`) 는 "음수" 이긴 해도 ([run94 해설 2.6](run94-bcrypt-resolve-해설.md)) 이 검사에선 **오류가 아니다.** 성공과 같은 길을 탄다.
- 비유: 도장 색이 셋 — 초록 (성공), 노랑 (경고), 빨강 (오류). 접수 사무실은 **빨강만** 따로 다룬다.

#### 새 말 — DEFER (완료를 누가 하나)

- 배달 봉투를 마무리하는 일 (`IopCompleteRequest`) 을 **언제 · 어디서** 하나를 정하는 표시다. `Irp.Flags 0x800` 비트 `[추측: 비트 이름 DEFER_IO_COMPLETION]`.
- `NtDeviceIoControlFile +0x13` 이 마지막 인자에 **1** 을 쓴다 (`NtFsControlFile` 은 0) `[정적]`. 그래서:
  1. `IopXxxControlFile` 이 DEFER 비트를 **안 세운다** (`+0x937 ~ +0x93b`).
  2. → 드라이버가 `IoCompleteRequest` 를 부르는 **그 자리에서** `IofCompleteRequest +0xe` → `IopfCompleteRequest` → `IopCompleteRequest` 를 **바로** (`+0x62d`) 부르거나,
  3. → **특수 커널 APC 로 미뤄** 부른다 (`+0x684` · `+0x3eb`).
- (비교) `NtFsControlFile` 길은 DEFER 라 `IopSynchronousServiceTail +0x39c` 가 직접 부른다. **효과는 같다.**
- 비유: 봉투 정리를 "상담실이 일을 끝낸 **그 자리에서** 바로" 할지, "손님 보내기 직전에 접수 사무실이 **몰아서**" 할지의 차이. IOCTL 은 앞쪽이다.

#### 새 말 — 특수 커널 APC

- [APC](../02_sprint/run13-resume-thread-해설.md) 는 "다음에 돌 때 이것 좀 해" 하고 맡겨 두는 쪽지다. 그 가운데 **커널 안에서 처리되는 쪽지** 의 한 종류로 보면 된다.
- 언제 미루나 `[정적]` (`IopfCompleteRequest +0x5be ~ +0x5ef`): IRP 를 만든 스레드가 지금 스레드가 아님 · 모든 APC 꺼짐 · 다른 프로세스에 붙음 · 취소됨.
- 어느 쪽이든 **같은 스레드가 유저로 돌아가기 전에 끝난다** `[추측: 특수 커널 APC 는 IRQL 이 내려갈 때 배달되는 보통 동작]`. 어느 갈래를 타는지는 동적 (→ Q233 12).
- 비유: 봉투를 연 손님 본인이 아니면, 그 손님 앞으로 "**돌아가기 전에 이 봉투 정리하세요**" 쪽지를 붙여 둔다.

#### 새 말 — 파일 객체 이벤트 · `FinalStatus`

- 손님이 들고 온 신호등 (사용자 이벤트) 말고, **손잡이 쪽에 달린 신호등** 이 하나 더 있다 — 파일 객체 `+0x98` `Event` `[정적]` (PDB 타입).
- `FinalStatus` (`+0x38`) = 그 손잡이의 "**마지막 결과 도장**" 칸.
- **동기 손잡이** ([run124 해설 2.3](run124-afd-socket-해설.md) 의 "창구 앞에 서서 기다리는 손님") 는 PENDING 이면 이 신호등을 기다린다 (`IopSynchronousServiceTail +0x3e1 IopWaitForSynchronousIo`).
- 비유: 사서함 문에 달린 **작은 표시등** + "마지막 처리 결과" 메모 칸.

#### 표 — PENDING 없이 끝났을 때 (`Irp+0x41 PendingReturned` = 0)

| | 반환 | 전표 | 손님 신호등 | 손잡이 신호등 · `FinalStatus` | 우편함 | 사용자 APC |
|---|---|---|---|---|---|---|
| **성공 / 동기 손잡이** | 드라이버 status | **씀** (`+0x125 ~ +0x142`) | 줬으면 **켬** (`+0x3d5`) | **켬** + `FinalStatus` (`+0x2ba` · `+0x2c1`) | `CompletionContext` 가 있으면 비동기와 같음 (동기 손잡이에 붙는지는 `[공백]`) | `ApcRoutine ≠ 0` 이면 (`+0x351`) |
| **성공 / 비동기 손잡이** | 드라이버 status | **씀** | 줬으면 **켬** | 손님 신호등을 **안 줬을 때만** 켬 | 우편함 + `ApcRoutine == 0` + `ApcContext ≠ 0` 이면 패킷 (`+0x3b4`) | 같음 |
| **경고 / 동기** | 드라이버 status | **씀** | 켬 | 성공 / 동기와 같음 | 같음 | 같음 |
| **경고 / 비동기** | 드라이버 status — **우편함 연결 손잡이면 `0x103`** | **씀** | 켬 | 성공 / 비동기와 같음 | `FO_SKIP_COMPLETION_PORT` 여도 **경고는 넣음** | 같음 |
| **오류 / 동기 · 비동기** | 드라이버 status | **안 씀** | **안 켬** (참조만 풂, `+0x4c1 ~ +0x4ec`) | **안 켬**, `FinalStatus` 그대로 | 없음 | 없음 |

(칸 · 줄은 run 문서 10절 표 그대로. 성공 / 비동기의 `FO_SKIP_*` 조건은 run 문서 참고.)

읽는 법:

- **성공 · 경고** 면 접수 사무실이 할 일을 다 한다 — 전표 → 신호등 → (손잡이 신호등) → APC 또는 우편함.
  - 전표는 **`Information` 먼저** (`+0x133` / `+0x12f`), **`Status` 나중** (`+0x142`) 에 쓴다.
  - 전표 쓰기는 **예외를 삼킨다** — 필터가 늘 1 을 돌려주고 착지가 신호등 단계로 이어진다 (결과서가 `+0x146 ~ +0x169` 원본 바이트로 확인). 전표 주소가 나빠도 syscall 은 안 죽는다.
- **오류** 면 **아무것도 안 건드린다.** 전표도, 신호등도, 손잡이 신호등도, APC 도, 우편함도.
  - 손님 신호등은 호출 **앞에서** 이미 꺼 뒀다 (`IopXxxControlFile +0x2db`). 그래서 오류일 때 신호등은 "**꺼 둔 채**" 로 남는다.
- **반환은 대부분 드라이버 status 그대로** 다. 달라지는 경우 (run 문서 10절 "찾은 것 전부"):
  1. 동기 + PENDING → 기다린 뒤 `FileObject->FinalStatus`
  2. 비동기 + 우편함 + 경고 → `0x103`
  3. IoRing → `0x103` (범위 밖)
  4. AppContainer + 특정 파일 객체 → 드라이버 안 부르고 `0xC0000910` `[추측: 대상은 정적으로 모름]`
- **PENDING 일 때** (참고): 동기 손잡이는 손잡이 신호등 (`FileObject+0x98`) 을 기다린다 — 호출 앞 `IopXxxControlFile +0x730` 에서 꺼 둔 것과 짝. 비동기 손잡이는 바로 `0x103`.

비유로:

- 봉투가 **초록 · 노랑 도장** 으로 돌아오면: 접수 사무실이 전표를 손님 칸에 넣고, 손님 신호등을 켜고, (필요하면) 우편함에 "끝났어요" 쪽지를 넣는다.
- 봉투가 **빨강 도장** 으로 돌아오면: 전표도 신호등도 없이 "**안 됐어요**" 도장만 손님에게 돌려준다.

### 2.17 빠른 길 완료 — status 를 안 본다 `[정적: 줄 읽기]` + `[추측]`

run 문서 11절. 요청서 · 결과서가 "비교용" 으로만 짚은 줄을 **flow-writer 가 이어 읽었다** (`ms/disassemble/ntoskrnl/IopXxxControlFile.asm`).

차례:

1. 빠른 길 호출 (`+0x6dc PiCMFastIoDeviceDispatch`, 또는 떨어진 조각의 간접 호출 — 드라이버 FastIoDeviceControl `[추측]`) 의 반환 바이트 (`+0x6e4`) 가 0 이 아니면 `+0x70d ~ +0x70f` 에서 **`+0xb16` 으로**.
2. `+0xb16 ~ +0xb66`: 32 비트 표식이 없으면 **`IoStatus` 16 B 를 손님 전표로 통째로 복사** (`+0xb38 ~ +0xb48`), 있으면 4 + 4.
3. `+0xbb4 ~ +0xbbc`: 파일 객체 `+0xb0` (`CompletionContext`) 가 있으면 다른 갈래로 (안 읽음).
4. `+0xbc2 ~ +0xbe4`: 손님 신호등이 있으면 (파일 객체 `+0x50` 비트 `0x8000000` 꺼짐일 때) **`KeSetEvent`** → 참조 풂.
5. `+0xc30`: 반환 = `IoStatus.Status`.

근거 → 그래서 → 아직 확인 아님:

- **근거** `[정적: 줄 읽기]`: 이 구간 (`+0xb16 ~ +0xbe4`) 에 **status 를 견주는 줄이 없다.**
- **그래서**: 빠른 길이 TRUE 면 **오류여도 전표를 쓰고 신호등을 켠다.** IRP 길 (2.16) 과 정반대다.
- **이어서** `[추측]`: afd 는 즉시 처리 코드에서 처리 함수 반환값을 `IoStatus.Status` 에 쓰고 TRUE 를 돌려준다 (요청서 `AfdFastIoDeviceControl +0x15d9 ~ +0x160a`). 그러니 `0x120b3` 이 `0xC000000D` 를 내도 전표 = (`0xC000000D`, 0) 이 써지고 신호등이 켜질 것이다.
- **아직 확인 아님**: afd 가 **어떤 경우 FALSE 를 돌려 IRP 길로 넘기는지** 는 안 읽었다 → Q234 ⑩. 실제로 오류 때 전표가 써지는지는 → Q233 13.

비유로 두 길을 나란히:

| | 빠른 길 (창구 즉석 답) | IRP 길 (배달 봉투) |
|---|---|---|
| 초록 · 노랑 도장 | 전표 베껴 넣음 · 신호등 켬 | 전표 씀 · 신호등 켬 · (APC / 우편함) |
| **빨강 도장** | **그래도 전표 베껴 넣음 · 신호등 켬** | **전표 · 신호등 없이 도장만** |

### 2.20 정리 — 비유로 한 번 더

- 손님 (프로그램) 이 계산대 (ws2_32) 를 거쳐 우편 담당 직원 (mswsock) 에게 "우리 쪽 **보내는 주소** 목록 주세요" (`SIO_ADDRESS_LIST_QUERY`).
- 직원은 **안 닦은 새 종이** (또는 손님이 종이를 안 줬으면 **닦아 둔 4 바이트 쪽지**) 를 들고 우체국 창구 (afd) 에 주문서 `0x120b3` 을 낸다.
- 창구는 **즉석에서** 답한다 (빠른 길). 종이 맨 위에 "**N 개**" 를 먼저 0 으로 적고, 구역 주소록 (컴파트먼트) 에서 주소 딱지 (`TA_ADDRESS`) 를 찾을 때마다 N 을 올린다. 자기 자신에게 돌아오는 주소 (루프백) 는 처음부터 주소록에 없다.
- 종이가 작으면 N 은 적고 "종이가 작아요 (`0x80000005`), 몇 바이트 필요해요 (`Information`)".
- 접수 사무실은 창구 답을 **도장 색과 상관없이** 전표에 베껴 넣고 신호등을 켠다.
- 직원은 **N 하나만** 보고 "이만한 종이가 필요해요" (`8 + N × (16 + A)`) 를 셈하고, 손님 종이에 **목차 + 본문** (`SOCKET_ADDRESS_LIST`) 으로 다시 정리해 준다.
- 창구가 N 을 안 적으면 → 직원은 종이의 **낙서** 를 N 으로 읽는다 → 터무니없는 크기 `[추측]`.
- 한편 **배달 봉투로 가는 주문서** (`0x120bf` · `0x12003` …) 는, 빨강 도장이면 접수 사무실이 **전표도 신호등도 없이** 도장만 돌려준다.

  13. ★ 빠른 길 완료 — `nt!IopXxxControlFile+0xb38` 이 `0x120b3` **오류** (출력 길이 3 등) 에도 걸리나. 2.17 의 `[추측]` 을 닫는다.
- 디버거 조심: 커널 멈춤점은 모든 프로세스에 걸린다 → 소켓 프로그램일 때만 멈추게 조건을 붙인다 (CLAUDE.md "방법").
