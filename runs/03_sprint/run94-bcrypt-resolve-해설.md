### 이번 바퀴에서 조심할 곳 다섯

1. **test.exe 는 bcrypt 를 안 올린다** (run92 와 같다 — run44 사진 모듈 6개 `[관찰]`, sample 에 암호 API 없음 `[소스]`).
   - 그래서 이번 이야기도 **"이 DLL 을 올리고 암호 API 를 부르는 다른 프로세스라면"** 이다. 흐름도 **그림은 그대로** 다.
2. **"로그" 는 진짜 Windows 로그가 아니다.**
   - 입력 `0x38` · `0x30`, 출력 `0x180`, 결과 `0xc00000e5` 는 PE_emulator 가 흉내 낸 실행의 로그다 `[관찰 — 에뮬레이터 로그, 진짜 Windows 아님]`.
   - 이 글의 결론은 전부 코드를 읽은 것 `[정적]` 이다. 진짜 KsecDD 가 무슨 답을 주는지는 **아직 아무도 안 봤다** (→ Q179).
3. **오프셋이 두 종류 나온다. 섞으면 길을 잃는다.**
   - `BCryptResolveProviders +0x4b0` 처럼 **함수 이름 뒤 `+0x`** = 그 함수 **코드 안 자리** (명령 줄).
   - "출력 `0x18`", "공급자 칸 `+0x28`" 처럼 **답·칸 안의 자리** = 데이터 **바이트 자리**.
   - 이 글에서는 앞의 것은 늘 함수 이름을 같이 쓰고, 뒤의 것은 "출력 ○○", "칸 +○○" 처럼 무엇 안인지 같이 쓴다.
4. **출력 칸 이름 (`pszFunction` · `pUM` 등) 은 `[추측]` 이다.**
   - PDB 에 이 구조체 정의가 **없다** (결과서 `pdb_struct.py --list` 0건).
   - 칸의 **오프셋 · 크기 · 검사는 `[정적]`** (`IoUnpack_*` 의 오프셋), **이름은 공개 헤더 기억 `[추측]`**.
5. **결과서와 run 문서가 다르게 적은 곳이 있다 → run 문서를 따른다** (2.14).
   - 결과서의 `+0x74b` 는 주소 끝자리다. 함수 오프셋으로는 `+0x39b`. 결론은 같다.

이미 푼 말은 **링크만** 건다.

- 오프셋, call/ret, 콜스택, 태그, 시스템 콜 → [run9 해설](../02_sprint/run9-create-user-process-해설.md) 2절, [핸들](../02_sprint/run9-create-user-process-해설.md#핸들) = **손잡이**
- 드라이버 = 관리사무소 건물 안 **전문 상담실**, IOCTL = **번호 붙은 주문서** → [run66 해설 2.7](run66-apphelp-cache-해설.md)
- **`\Device\KsecDD`**, 주문서 **`0x390400`**, **기능 번호** (입력 `+0x4` 칸 = 용건 번호), **`-1` "없음" 도장**, 입력 머리 `0x1a2b3c4d`, **`STATUS_PENDING` (`0x103`)**, 핸들 칸 **`g_hIoDevice`** (손잡이 걸이), **C++ 꾸민 이름** → [run92 해설](run92-bcrypt-ksecdd-해설.md) 2.3 · 2.6 · 2.7 · 2.16
- **출력 칸** (반환값 말고 부르는 쪽이 건넨 칸에 써 주는 대답 = 바구니), status = 결과 **도장** → [run91 해설 2.3](run91-bcrypt-init-해설.md)
- bcryptprimitives (암호 부품 건물, 그 `DllMain` 최소 조건) → [run91 해설](run91-bcrypt-init-해설.md)
- 크리티컬 섹션 (임계영역) = 한 번에 한 명만 들어가는 방의 **열쇠** → [run68 해설 2.7](run68-dll-init-rest-해설.md#27-락--새-말-크리티컬-섹션)
- "최소 조건 표" 라는 꼴 → [run85 해설](run85-user32-init-해설.md) 2.6

### 비유 — 그대로 이어 쓴다

- 프로세스 = **가게**, 커널 = **관리사무소**, syscall = 관리사무소 **신청 창구**, ntdll = 가게 안 **관리실**.
- DLL = 가게에 들이는 **건물**. DLL 전역 = 건물마다 가진 **수첩**. 핸들 = **손잡이**, 핸들 칸 = 벽의 **손잡이 걸이**.
- 드라이버 = 관리사무소 건물 안 **전문 상담실**, IOCTL = 상담실에 넣는 **번호 붙은 주문서**. 주문서 양식은 하나 (`0x390400`), 맨 위 **용건 번호** 칸 (기능 번호) 으로 일이 갈린다.
- bcrypt = **암호 앞쪽 건물** (run92), bcryptprimitives = **암호 부품 건물** (run91).
- 이번에 새로 붙는 그림:
  - 이번 용건 번호는 **`0x20000`** — "**AES 일은 어느 건물이 맡나요?**" 를 묻는 주문서다 (2.0).
  - 상담실은 대답을 **답장 한 장** 으로 바구니 (출력 버퍼) 에 넣어 준다. 답장과 함께 **전표** (IOSB) 도 한 장 온다 (2.6).
  - 답장 안의 "어디에 무엇이 있다" 는 진짜 위치가 아니라 **쪽 번호** 로 적혀 있다. bcrypt 가 쪽 번호를 진짜 위치로 고쳐 읽는다 (2.8). (flow.md 3장 새 하위 절도 "쪽 번호" 비유를 썼다.)

### 한 줄로 먼저 — 무엇을 얻었나

**이번 글의 중심은 이 한 줄이다 (사용자에게 가장 중요한 줄).**

> **에뮬레이터가 이 IOCTL 을 통과시키려면: status 0 + 전표의 `Information` = N (`0x10` 이상 `0x180` 이하) + 답장 N 바이트를 정해진 모양대로. 공급자 하나짜리 가장 작은 답장은 `0x98` 바이트 한 장이다. 공급자 "0 개" 답장은 쓰면 안 되고 (크래시), "그런 알고리즘 없음" 은 IOCTL 을 음수 status 로 끝내서 알린다.** `[정적]`

그리고 로그의 수수께끼 넷이 **코드로 한 줄도 안 어긋나게** 풀렸다 `[정적]`:

| 로그에 보인 것 | 코드로 본 정체 | 이 글 |
|---|---|---|
| 입력 `0x38` | 이름 하나 (3 글자 이하, `AES` 등) 를 묻는 주문서. 길이 = `0x30 + Σ((글자수 × 2 + 9) & ~7)` | 2.4 |
| 입력 `0x30` | 이름 없이 "난수 담당 (인터페이스 6) 누구?" 를 묻는 주문서 (`BCryptGenRandom` 길) | 2.3 · 2.4 |
| 출력 `0x180` | 첫 시도용 **고정** 크기 (`+0x7a8`) | 2.5 |
| 결과 `0xc00000e5` | 기본 대답 (`Information` 0, 또는 0 으로 채운 답장) 이 머리 검사에서 걸림 → Win32 `0x54f` → `0xc00000e5` | 2.7 |

## 1. 이번 바퀴의 질문

### 큰 그림에서 어디인가

**DLL 전원 켜기가 끝난 뒤** 다. 그것도 test.exe 에는 없는 건물이라 **옆길** 이다. run92 가 본 bcrypt `DllMain` (전원 켜기) 의 **바로 다음 걸음** 이다.

```
cmd.exe 의 부탁 (CreateProcess)
 │  커널: 프로세스 · 주소 공간 · PEB · 첫 스레드
 │  첫 스레드 출발 → ntdll!LdrInitializeThunk
 │    └─ LdrpInitializeProcess
 │         ├─ (2.6) import DLL 들이기
 │         └─ (2.7) DLL 전원 켜기
 │               └─ (bcrypt 를 올리는 프로세스라면) bcrypt!DllMain  ← run92: KsecDD 손잡이를 걸이에 건다
 └─ … → NtContinue (은퇴) → exe 진입점 → main
                                        │
                                        └─ (그 프로그램이 암호 API 를 부르면)
                                             BCryptOpenAlgorithmProvider / BCryptGenRandom
                                               └─ BCryptResolveProviders → IOCTL 0x390400 (기능 0x20000)  ← 이번 (run94)
                                                    └─ 답장에 적힌 DLL 을 LoadLibraryExW
```

- 위치를 한 번 더: 이 IOCTL 은 **프로그램이 암호 API 를 부를 때** 일어난다. 초기화 (은퇴 전) 에 꼭 일어나는 일은 아니다.
  - 어느 때 부르는지는 그 프로그램 마음이다. 그림의 `main` 아래에 둔 것은 "예를 들어" 다.
- flow.md 3장 "bcrypt 시작 함수" 절 아래에 **하위 절** "attach 뒤 첫 사용 — 공급자 찾기 IOCTL" 로 놓였다.

### 왜 이 질문이 지금 왔나

- run92 덕에 PE_emulator 에서 bcrypt `DllMain` 은 이제 **통과** 한다 (KsecDD 손잡이를 걸이에 걸어 주고, 기능 `0x10500` 주문서에 status 0).
- 그다음 벽이 이것이다 `[관찰 — 에뮬레이터 로그]`:
  - **같은 손잡이** 로 같은 주문서 `0x390400` 이 **다른 모양** 으로 온다.
    - 입력 `0x38` · 출력 `0x180` (12 줄, `BCryptOpenAlgorithmProvider` 길)
    - 입력 `0x30` · 출력 `0x180` (3 줄, 다른 샘플 · `BCryptGenRandom` 길로 보임)
  - 엔진은 이 모양을 몰라 **기본 대답** 을 준다 → 부른 쪽이 **`0xc00000e5`** 로 끝난다. 악성 샘플 **36 개** 가 여기서 막힌다.
- 사용자가 이번 바퀴를 연 계기: PE_emulator 쪽 외부 피드백 "**Q173 ② 아직 기다리는 중**".
  - 그래서 Q173 을 둘로 나눠, ② 만 **Q173a** 로 지금 먼저 했다. 나머지는 Q173b.

### 무엇이 궁금했나

요청서 질문 다섯 (run 문서 "원문 질문이 어디서 답해졌나").

1. **누가 이 IOCTL 을 부르나** — 입력 `0x38` · `0x30` 은 어느 길 · 어떤 인자에서 나오나, 출력 `0x180` 은 어디서 정해지나. `BCryptGenRandom` 길도 같은 함수로 오나.
2. **답을 어떻게 읽나** — status 를 어떻게 보나 (다시 부르나), 답장 칸 표, 쪽 번호를 진짜 위치로 고치나 · 범위 검사가 있나.
3. **`0xc00000e5` 는 어디서 나오나** — 그리고 다른 실패 status 들.
4. **최소 조건 (가장 중요)** — 성공으로 가려면 바깥이 줘야 하는 status · 전표 · 답장 칸 값. 그 뒤 어떤 DLL 을 올리나. 공급자 "0 개" 답이면 어디로 가나.
5. (작게) **캐시** — 같은 프로세스에서 IOCTL 이 몇 번 나나 가늠하려고.

### 바퀴 전에 알던 것

- `[관찰 — 에뮬레이터 로그, 진짜 Windows 아님]` 위 "왜 지금" 의 입력 `0x38` · `0x30`, 출력 `0x180`, 결과 `0xc00000e5`.
- `[정적]` (run92) `0x390400` 은 CNG 의 **만능 통로** 다. 용건은 입력 `+0x4` 의 기능 번호. `BCryptResolveProviders` 는 기능 **`0x20000`** 을 쓰고 (`+0x590`), attach 와 달리 **출력을 읽는다** (`+0x4fb IoUnpack_ProviderRef`).
- `[추측]` (에뮬레이터 쪽) 로그에 기능 번호가 안 찍혀서, 입력 `0x38` · `0x30` 이 정말 기능 `0x20000` 인지는 짐작이었다.
- `[추측]` (요청서) 출력 `0x180` 은 첫 시도용 고정 크기이고, 모자라면 크기를 받아 다시 부를 것.
- `BCryptResolveProviders` 는 이미 `.asm` 으로 뽑혀 있었지만 **본문은 아무도 안 읽었다** (요청서).

## 2. 찾은 것

### 2.0 새 말 — 공급자 (provider)

먼저 이 말 하나를 잡고 가자. 이번 글 전체가 이 말 위에 있다.

- **공급자** = 실제로 암호 일 (AES 계산, 난수 만들기 등) 을 해 주는 **DLL** 이다.
  - flow.md 3장 새 하위 절: bcrypt 가 커널에 "**이 알고리즘은 어느 DLL 이 맡나**" 를 묻고, 답에 적힌 그 DLL 을 `LoadLibraryExW` 로 올린다 `[정적]`.
  - 이번 결과서가 가장 작은 답의 예로 쓴 이름이 **`bcryptprimitives.dll`** 이다 (run91 의 그 DLL). 이것이 bcrypt 의 기본 공급자라는 건 결과서 `[추측]` 이다.
- 비유:
  - 암호 앞쪽 건물 (bcrypt) 은 **접수처** 다. 손님 (프로그램) 이 "AES 해 주세요" 하면, 직접 하지 않고 **KsecDD 상담실** 에 주문서를 낸다: "**AES 일은 어느 건물이 맡나요?**"
  - 상담실이 답장에 "**암호 부품 건물 (bcryptprimitives) 이 맡아요**" 라고 적어 준다.
  - 접수처는 그 건물을 가게에 들인다 (`LoadLibraryExW`).
- 이 "어느 건물이 맡나요?" 를 묻는 함수가 **`BCryptResolveProviders`** ("공급자 찾기") 다.

### 2.1 한눈에 — 공급자 찾기 줄기

run 문서 "호출 관계" 를 줄였다. 전부 `[정적]`. ★ = 이번 막힘에 직접 닿는 줄.

```
bcrypt!BCryptOpenAlgorithmProvider (rva 0x9410)  (phAlgorithm, pszAlgId, pszImplementation, dwFlags)
```

### 2.2 한 줄씩 읽는 법

#### 줄 1: `├─ (2) +0x5eb  NtDeviceIoControlFile([g_hIoDevice], 0,0,0, &IOSB, 0x390400, 입력, 길이, 출력, 0x180)` (`BCryptResolveProviders` 아래)

- **누가**: `bcrypt!BCryptResolveProviders` (공급자 찾기).
- **어디서**: 그 함수 `+0x5eb` 에서 부른다 (돌아올 자리 `+0x5f2`) `[정적]`.
- **누구를**: ntdll `NtDeviceIoControlFile` → 신청 창구 → **KsecDD 상담실**.
- **무엇을 넘기나** (run 문서 보탬 ④, `+0x5b7 ~ +0x5e6`):
  - 손잡이 = 걸이 `[g_hIoDevice]` 에 걸린 것 (`+0x5d0`). run92 의 attach 가 건 **바로 그 손잡이** 다.
  - Event · APC · APC 문맥 = 0 (`+0x5d7` · `+0x5cd` · `+0x5c6`).
  - IOSB = 지역 `[RSP+0x78]`, 16 바이트를 **0 으로 비우고** 시작 (`+0x571`).
  - 주문서 번호 `0x390400` (`+0x5de`).
  - 입력 = 칸을 채운 그 버퍼 (`+0x56e`), 출력 = 방금 할당한 그릇, 길이 `0x180`.
- **무엇을 위해**: "이 알고리즘은 어느 DLL 이 맡나요?" 를 묻고, 답장을 받으려고.
- 비유: 접수처가 걸이에서 손잡이를 꺼내, 상담실에 **주문서 한 장 + 빈 답장 종이 (`0x180` 크기)** 를 같이 넣는다.

#### 줄 2: `│  +0x7f8 MOV R12D,0x54f → +0x39b (출력 free) → +0x3ba WinErrorToNtStatus → 0xc00000e5` (`BCryptResolveProviders` 아래)

- **누가**: 같은 `BCryptResolveProviders`.
- **어디서**: `+0x7f8` 에서 "실패 번호" 칸 (`R12D`) 에 `0x54f` 를 적고, `+0x7fe JMP` 로 함수 `+0x39b` 로 간다 `[정적]`.
- **그다음**: `+0x39b` 에서 **자기가 할당한 답장 그릇을 버리고** (`+0x3a9 BCryptFree`), `+0x3ba` 에서 `WinErrorToNtStatus(0x54f)` 를 부른다 → **`0xc00000e5`** `[정적]`.
- **무엇을 위해**: "답장이 망가졌다" 를 status 로 바꿔 위로 돌려주려고.
- 이것이 **로그의 `0xc00000e5` 가 나온 그 줄** 이다 (2.7).

### 2.3 누가 부르나 — 두 길이 한 함수로 모인다 (질문 1)

#### 길 A — `BCryptOpenAlgorithmProvider` (입력 `0x38` 쪽) `[정적]`

| # | 길 | `BCryptResolveProviders` 에 넘기는 것 |
|---|---|---|
| A1 → A2 | `BCryptOpenAlgorithmProvider +0x259` → `BcoapCached +0x11b` (캐시 미스) | `(NULL, 0, 이름, NULL, 1, 2, &cb, &refs)` |
| A3 | `BcoapCached +0xcf` | `(NULL, 0, 이름, 공급자, 1, 플래그, &cb, &refs)` |

- `BcoapCached` 는 `BCryptResolveProvidersForBcoapCached` 를 줄여 부른 이름이다 (run 문서 표기).
- A2 와 A3 의 갈림: 공급자 이름이 NULL **그리고** 플래그 2 면 A2 (캐시를 쓰는 길), 그 밖은 A3 (`+0x23 ~ +0x2c`).
  - `BCryptOpenAlgorithmProvider(&h, L"AES", NULL, 0)` 처럼 공급자를 안 정해 주면, attach 가 끝난 뒤 (`g_fLoadCNGDone ≠ 0`) 엔 플래그 2 로 A2 를 탄다 (`+0x201 ~ +0x229`).

#### 새 말 — 인터페이스 번호 (`dwInterface`)

- 둘째 인자 `0` / `6` 이 **인터페이스 번호** 다. "**어떤 종류의 일**" 을 찾는지 적는 칸이다.
  - 코드로 본 번호 `[정적]`: **6 = 난수**, **2 = hash**, **3 = 비대칭 암호화**.
  - **1 = 암호** 는 `[추측]` (공개 헤더 기억).
  - 길 A 는 `0` 을 넘긴다 — 이름으로 찾으니 종류는 안 정한다는 뜻으로 읽힌다 `[추측: 읽는 법]`.
- 비유: 주문서의 "**일 종류**" 칸. 길 A 는 "AES 담당" 처럼 이름으로 묻고, 길 B 는 "난수 담당 아무나" 처럼 종류로 묻는다.

#### 길 B — `BCryptGenRandom` (입력 `0x30` 쪽) `[정적]`

| # | 길 | 넘기는 것 |
|---|---|---|
| B1 → B2 → B3 | `BCryptGenRandom +0x157` → `GetSystemPreferredRngHandle +0x78` → `OpenSystemPreferredAlgorithmProvider +0xf7` | `(NULL, 6, NULL, NULL, 1, 0, &cb, &refs)` — **이름 없이** 인터페이스 6 |
| B4 | `OpenSystemPreferredAlgorithmProvider +0x47` → A1 | 이름 = B3 답장의 첫 공급자 이름 |

- 그래서 **`BCryptGenRandom(NULL, …, 플래그 2)` 첫 호출은 IOCTL 이 둘 이어진다** `[정적]`:
  1. B3 — "난수 담당 누구?" (입력 `0x30`)
  2. B4 → A1 → A2 — 답장에 적힌 그 이름으로 다시 "이 이름 담당 누구?" (입력 `0x30 + 이름`, 3 글자 이하면 `0x38`)
- 에뮬레이터 로그와 맞춰 보면: "`0x30` 3줄" 이 ①, "`0x38` 12줄" 이 ② 와 `BCryptOpenAlgorithmProvider` 직접 호출 — **맞춤은 `[정적]`, 실제 횟수는 동적** 으로 봐야 한다.
- 지금 엔진은 ① 에서 이미 `0xc00000e5` 로 끝나니 ② 가 안 보였을 것이다. **고치면 IOCTL 이 둘 이어서 보일 것** (run 문서 판정 표).
- 작은 조건 둘 `[정적]`:
  - `GetSystemPreferredRngHandle` 은 캐시 칸 (rva `0x25ad0`) 이 0 일 때만 이 길을 탄다 (`+0x39 JZ`). 한 번 얻은 핸들은 그 칸에 넣어 둔다 (`+0x8a`) → **다음부터 IOCTL 없음**.
  - `OpenSystemPreferredAlgorithmProvider` 는 `g_fLoadCNGDone` 이 0 이면 질의 없이 바로 `L"RNG"` 로 `+0x47` 로 간다 (`+0x26` · `+0x30` · `+0x36`).

#### 두 IOCTL 길 — 어느 쪽을 타나 `[정적]`

`BCryptResolveProviders` 안에는 IOCTL 을 부르는 자리가 둘 있다. 8번째 인자 `ppBuffer` ("답장을 어디에 받을까") 하나로 갈린다.

| 길 | 언제 | 부르는 자리 |
|---|---|---|
| **직접** `NtDeviceIoControlFile` | `ppBuffer ≠ NULL` (`+0x253 TEST RAX` · `+0x256 JNZ +0x514`) | `+0x5eb` |
| `IoCallKernelDriver` (run92 의 그 함수) | `ppBuffer == NULL` — **크기만 묻기** | `+0x276` |

- 길 A · B 는 **둘 다** `&refs` 를 넘기니 `ppBuffer ≠ NULL` → **직접 길만** 탄다.
- `IoCallKernelDriver` 길은 `BCryptEnumProviders` · `BCryptEnumAlgorithms` 같은 쪽이 NULL 을 줄 때뿐이라고 결과서는 본다. 그 둘이 실제로 NULL 을 넘기는지는 안 읽었다 `[공백]` (→ Q178 ②).
- 또 하나: 이 길의 입력은 run92 의 `IoPack_*` 를 **안 쓰고** `BCryptResolveProviders` 가 직접 채운다. run92 attach 의 `0x10500` 입력 (`0x68`) 과 **칸 배치가 다르다** `[정적]`.

### 2.4 입력 — 주문서 칸, 그리고 `0x38` · `0x30` 이 나오는 계산 (질문 1)

#### 입력 칸 표 (기능 `0x20000`, run 문서 그대로)

| 칸 | 크기 | 뜻 | 출처 |
|---|---|---|---|
| `+0x00` | 4 | `0x1a2b3c4d` 표지 | `+0x58a` |
| `+0x04` | 4 | **`0x20000`** 기능 번호 | `+0x590` |
| `+0x08` | 8 | 컨텍스트 문자열 쪽 번호 / `-1` | `+0x223` · `+0x2b5` |
| `+0x10` | 4 | 인터페이스 (A 길 `0`, B3 `6`) | `+0x1ff` |
| `+0x14` | 4 | 안 씀 | — |
| `+0x18` | 8 | 알고리즘 이름 쪽 번호 / `-1` | `+0x233` · `+0x2c1` |
| `+0x20` | 8 | 공급자 이름 쪽 번호 / `-1` | `+0x243` · `+0x2cd` |
| `+0x28` | 4 | 모드 (모두 `1`) | `+0x209` |
| `+0x2c` | 4 | 플래그 (A2 `2`, A3 · B3 `0`) | `+0x213` |
| `+0x30` ~ | 가변 | 문자열 (UTF-16, NUL 포함, 각 8 바이트로 올림). 순서: 컨텍스트 → 이름 → 공급자 | `+0x313` · `+0x166` · `+0x1c3` |

- 표의 "쪽 번호" 는 run 문서의 "오프셋" 이다 — **입력 시작에서 몇 바이트째** 에 그 문자열이 있나. 자세한 뜻은 2.8 에서 푼다 (답장도 같은 방식이다).
- 모드 · 플래그 값의 이름 (`CRYPT_UM` 1 · `CRYPT_ALL_PROVIDERS` 2) 은 `[추측]` (공개 헤더와 같은 값).

#### 길이 계산식 — 한 단계씩 `[정적]`

run 문서: **길이 = `0x30 + Σ ((글자수 × 2) + 9) & ~7`** (`+0xb0 MOV R15D,0x30` · `+0xef LEA EAX,[9+RAX*2]` · `+0xf6 AND EAX,0xfffffff8` · `+0xf9 ADD ESI,EAX`).

읽는 법:

1. `0x30` — 칸 표의 **머리** 크기 (`+0x00` ~ `+0x2f`). 문자열이 없어도 늘 있다.
2. 문자열마다 `글자수 × 2` — UTF-16 은 글자 하나가 2 바이트.
3. `+ 9` 하고 `& ~7` — 풀어 보면 "끝 표시 NUL (2 바이트) 을 붙이고, 8 의 배수로 **올린다**" 이다. (`& ~7` 은 아래 세 비트를 지워 8 의 배수로 내리는 셈이라, 미리 7 을 더해 두면 올림이 된다. 9 = NUL 2 + 올림용 7.) run 문서의 "NUL 포함, 각 8 바이트로 올림" 과 같은 말이다.
4. 그 문자열들을 머리 뒤에 붙인다.

예 (run 문서 그대로):

| 묻는 것 | 문자열 | 길이 |
|---|---|---|
| `AES` · `RNG` · `MD5` (3 글자) | 하나 | **`0x38`** ← 로그 |
| `SHA1` · `SHA256` | 하나 | `0x40` |
| `ECDSA_P256` | 하나 | `0x48` |
| B3 (이름 없음) | 없음 | **`0x30`** ← 로그 |
| A3 + `AES` (공급자 `L"Microsoft Primitive Provider"`, 28 글자 → `+0x40`) | 둘 | `0x78` — 에뮬레이터 로그엔 아직 안 보인 모양 |

- `AES` 를 손으로 따라가 보면: 3 글자 → 6 바이트 → `+9` 는 15 → 8 의 배수로 내리면 8 → `0x30 + 8 = 0x38`.
- 실제 모양 둘 (run 문서):

| 실제 모양 | 길이 | `+0x10` | `+0x08` | `+0x18` | `+0x20` | `+0x28` | `+0x2c` | `+0x30` |
|---|---|---|---|---|---|---|---|---|
| `BCryptOpenAlgorithmProvider(L"AES", NULL, 0)` (A1 → A2) | `0x38` | 0 | -1 | `0x30` | -1 | 1 | **2** | `L"AES\0"` |
| `OpenSystemPreferredAlgorithmProvider` 질의 (B3) | `0x30` | **6** | -1 | -1 | -1 | 1 | **0** | (없음) |

- 첫 줄의 `+0x18` 값 `0x30` 을 보자. "이름은 입력 시작에서 **`0x30` 바이트째** 에 있다" 는 뜻이다. 실제로 `+0x30` 에 `L"AES\0"` 가 있다. **이것이 "쪽 번호" 방식이다.** 2.8 에서 답장 쪽에서도 똑같이 나온다.
- 길이가 `0x140` 을 넘으면 입력을 힙에, 아니면 스택에 만든다 (`+0x137 · +0x13d JA`).

**그래서**: 에뮬레이터 쪽 `[추측]` 이었던 "입력 `0x38` · `0x30` = 기능 `0x20000`" 이 **코드로 섰다** `[정적]`. 엔진 입장에선 입력은 **받는 그대로** 다. 만들 것은 **답** 이다.

### 2.5 출력 `0x180` — 첫 시도용 고정 그릇 (질문 1)

- `+0x514 MOV RCX,[RAX]` · `+0x51a JZ +0x7a8` — 부른 쪽이 "아직 그릇 없음 (`*ppBuffer == NULL`)" 으로 왔으면 → `+0x7a8 MOV R15D,0x180` → `+0x547 BCryptAlloc(0x180)` `[정적]`.
  - `BCryptAlloc` 은 "크기만큼 힙 할당" 공용 부품이다. 같은 주소에 이름이 셋 (`BCryptAlloc` · `MSCryptAlloc` · `SafeAllocaAllocateFromHeap`) 이라 run 문서는 `BCryptAlloc` 으로 부른다.
- 관찰된 두 호출자 (`BCryptOpenAlgorithmProvider` · `OpenSystemPreferredAlgorithmProvider`) 가 **둘 다** 그릇 없이 시작한다 → 둘 다 `0x180` `[정적]`. 로그와 맞다.
- 비유: 접수처는 답장 종이를 늘 **같은 크기 (`0x180`) 한 장** 으로 먼저 내민다. 모자라면 다시 받는 길이 있다 (다음 절).

### 2.6 ★ 답을 어떻게 읽나 (1) — 도장과 전표 (질문 2)

#### 새 말 — IOSB 와 `Information`

- **IOSB** (`IO_STATUS_BLOCK`) = IOCTL 을 부를 때 함께 건네는 **16 바이트 칸** 이다. 커널이 일을 끝내고 여기에 두 가지를 적어 준다:
  - `Status` — 결과 status (반환값과 같은 종류의 숫자).
  - **`Information`** — 이 IOCTL 에선 "**답장에 몇 바이트를 적었나**" 다. run 문서: bcrypt 는 이것을 "출력이 몇 바이트냐" 의 **유일한** 근거로 쓴다 `[정적]`.
  - (일반적으로 알려진 설명 — IOSB 의 두 칸 이름과 "몇 바이트 넘겼나" 라는 뜻 — 은 `[추측]` 이다. 이번 코드에서 확인한 것은 bcrypt 가 `Information` 칸을 길이로 쓴다는 것, `Status` 칸은 안 읽는다는 것이다.)
- 비유: 상담실은 답장과 함께 **전표** 한 장을 준다. 전표 위 칸엔 도장 (`Status`), 아래 칸엔 "**답장 ○ 바이트 적었음**" (`Information`).
  - 그런데 bcrypt 는 도장을 **반환값 (`EAX`) 쪽에서만** 본다. 전표의 도장 칸은 **안 본다**. 전표에서는 **아래 숫자만** 본다.

#### 무엇을 믿고 무엇을 안 보나 `[정적]`

| 대답 | bcrypt 가 보나 | 자리 |
|---|---|---|
| 반환 status (`EAX`) | **본다** — 부호로 갈림 | `+0x5fb JS` |
| IOSB `Information` | **본다** — 답장 길이의 유일한 근거 | `+0x601 MOV R15,[RBP-0x80]` |
| IOSB `Status` | **안 본다** | — |
| 답장 안 "전체 크기" 칸 · `0x1a2b3c4d` 같은 표지 | **없다** (그런 검사 줄 없음) | — |

#### status 처리 표 (`+0x5f7 ~ +0x7bd`, run 문서 그대로)

| IOCTL status | 자리 | 하는 일 |
|---|---|---|
| **≥ 0** (`0x103` 도) | `+0x5fb JS` 안 탐 → `+0x601` (`Information` 읽기) | 성공 길. 반환 status 는 0 (`+0x62b`) |
| 〃 그런데 `Information` > 그릇 크기 | `+0x60e CMP · +0x613 JC +0x725` | 자기가 할당한 그릇이면 **그 크기로 다시 할당해 IOCTL 다시** |
| `0xc0000023` | `+0x6b9 · +0x6be JZ +0x7bd` | **다시 안 함 → `0xc00000e5`** (`+0x664`) |
| `0x80000005` | `+0x6c4` · `+0x6d3 CMP EAX,4 · +0x6d6 JC` | `Information < 4` → `0xc00000e5`. 아니면 답장 첫 4 바이트 (`+0x6dc`) 로 갈림 ↓ |
| 〃 첫 4 바이트 = `0xc0000023` | `+0x6e0 ~ +0x6ef` | `Information` **정확히 8** 이어야. `+0x6f5` 에서 답장 `+4` 를 "필요한 크기" 로 읽어 다시 할당 · IOCTL 다시 (횟수 제한 없음) |
| 〃 첫 4 바이트 = 그 밖 | `+0x78e CMP EAX,4 · +0x791 JNZ` | `Information` **정확히 4** 이어야. 그 4 바이트를 진짜 status 로 반환 |
| 그 밖의 음수 | `+0x6c9 JNZ +0x7b3` → … → `+0x669` | **그대로 반환**. 그릇 버림 |

- `0xc0000023` · `0x80000005` 의 이름은 요청서가 쓴 `STATUS_BUFFER_TOO_SMALL` · `STATUS_BUFFER_OVERFLOW` 다 `[추측: 이름]` (일반적으로 알려진 이름).
- 음수인지 아닌지는 맨 앞 비트로 본다 ([run92 해설 2.7](run92-bcrypt-ksecdd-해설.md) `0x103` 이야기와 같다). `0x80000005` 도 맨 앞이 8 이라 **음수 쪽** 이다.

#### "다시 부르기" 는 정해진 말투로만 `[정적]`

여기가 헷갈리기 쉬운 곳이다. 단계별로.

1. "그릇이 모자라요" 를 알리는 **알아듣는 말투는 둘** 이다.
   - (가) status ≥ 0 인데 `Information` 을 그릇보다 크게 적기 → 그 크기로 다시.
   - (나) status `0x80000005` + 답장 8 바이트 `{0xc0000023, 필요한 크기}` + `Information` 정확히 8 → 그 크기로 다시.
2. 그런데 **status 를 그냥 `0xc0000023` 으로** 주면? → 다시 부르지 **않고** 곧장 `0xc00000e5` 다 (`+0x6be JZ +0x7bd`).
3. 그래서: "모자라요" 를 흔한 status 하나로 말하면 bcrypt 는 못 알아듣는다. 정해진 두 말투 중 하나여야 한다.
- 다만 공급자 하나짜리 답장은 `0x98` 바이트라 `0x180` 그릇에 **넉넉히 들어간다** (2.9). 엔진이 최소 답만 줄 거라면 다시 부르기를 신경 쓸 일이 없다.
- 비유: 접수처는 "종이가 작아요" 라는 말을 **딱 두 가지 서식** 으로만 알아듣는다. 다른 말로 하면 "상담실이 고장났나 보다" 하고 돌아선다.

### 2.7 ★ `0xc00000e5` 의 정체 — 기본 대답이 걸리는 두 줄 (질문 3)

#### 새 말 — Win32 오류 번호

- Windows 에는 오류 번호가 **두 집안** 있다:
  - **NTSTATUS** — 커널 · ntdll 이 쓰는 큰 수 (`0xc00000e5` 같은 것).
  - **Win32 오류 번호** — 그 위 API 층이 쓰는 작은 수 (`0x54f` 같은 것). run91 해설의 `GetLastError` 로 읽는 그 번호다.
  - (두 집안이 있다는 설명은 `[추측]` — 일반적으로 알려진 설명.)
- bcrypt 의 공급자 찾기 길은 안에서 **Win32 번호로 실패를 적고**, 끝에서 `WinErrorToNtStatus` 로 **NTSTATUS 로 바꿔** 돌려준다 `[정적]`.
  - `0x54f` → `0xc00000e5` (`WinErrorToNtStatus +0x57 ~ +0x70` — run 문서는 이 줄을 `0x491 + 0x4a + 0x74 = 0x54f` 로 맞췄다).
  - 이름: `0x54f` = `ERROR_INTERNAL_ERROR` `[추측: 이름]`, `0xc00000e5` = `STATUS_INTERNAL_ERROR` `[추측]`.
- 비유: 건물 안에서는 **건물 내부 고장 번호** 로 적고, 손님에게 내보낼 때 **관리사무소 공식 번호** 로 바꿔 적는다. "내부 고장 `0x54f` 번" → "공식: 내부 오류 `0xc00000e5`".

#### 기본 대답 두 모양 — 둘 다 같은 줄로 `[정적]`

엔진의 기본 대답은 "status 0" 이다. 그런데 답장 쪽은 두 모양이 있을 수 있다. **둘 다** `+0x7f8` 로 간다.

**모양 ① — `Information` 이 0** (답장에 아무것도 안 적음)

1. status 0 → `+0x5fb JS` 안 탐 → 성공 길.
2. `+0x601` 에서 `Information` = 0 을 길이로 읽는다.
3. `+0x4a0 CMP RCX,R15` · `+0x4b0 JA +0x7f8` — 머리 크기 `0x10` 보다 작다 → **머리조차 못 읽는 답장** → `+0x7f8`.

**모양 ② — `0x180` 을 0 으로 채움** (길이는 있는데 내용이 전부 0)

1. 머리 크기는 통과한다.
2. `+0x4ba` 에서 공급자 개수 = 답장 `0x00` = **0**.
3. `+0x4bd CMP RAX,-1` — 배열 쪽 번호 = 답장 `0x08` = **0**. `-1` (없음 도장) 이 **아니다**.
4. 그래서 bcrypt 는 "배열이 있다" 고 보고 `+0x7d4` 로 간다. 배열이 있으면 개수가 0 이 아니어야 한다.
5. `+0x7d4 TEST R13D` · `+0x7d7 JZ +0x7f8` — 개수 0 → **"배열은 있다면서 개수가 0?" 앞뒤가 안 맞는 답장** → `+0x7f8`.

**그다음 (공통)**: `+0x7f8 MOV R12D,0x54f` → `+0x7fe JMP` (함수 `+0x39b`, 그릇 버림) → `+0x3ba WinErrorToNtStatus(0x54f)` → **`0xc00000e5`**.

- run 문서: 로그의 결말과 같다 `[정적]`. 에뮬레이터가 실제로 ① ② 중 어느 쪽인지는 에뮬레이터 로그로 볼 일이다 (결과서).
- 모양 ② 에서 배운 것: **"0 = 없음" 이 아니다.** 이 양식에서 "없음" 은 늘 `-1` 이다. 0 은 "답장 맨 앞 (0 바이트째) 에 있다" 는 **진짜 쪽 번호** 로 읽힌다.
- 비유 (flow.md 3장 비유와 같은 뜻): 묶음 두께가 0 이면 bcrypt 는 "명함이 없다" 가 아니라 "**묶음이 망가졌다**" 로 본다.

#### 다른 실패 status (run 문서 "실패 status 표" 에서 줄임)

| status | 자리 | 조건 |
|---|---|---|
| **`0xc00000e5`** | `BCryptResolveProviders +0x7f8` → `+0x3ba` | `Information < 0x10` · 개수 / 배열 `-1` 짝 어긋남 · 배열 범위 밖 · `IoUnpack_*` 가 `0x54f` (**기본 대답은 여기**) |
| `0xc00000e5` | `+0x664` | IOCTL `0xc0000023`, 또는 `0x80000005` 인데 `Information` 이 4 / 8 아님 |
| IOCTL 음수 그대로 | `+0x6c9 JNZ +0x7b3 → … → +0x669` | 그 밖의 음수 |
| **`0xc0000008`** | `BCryptOpenAlgorithmProvider +0x3d4` | 첫 공급자 `dwInterface ∉ 1..8` |
| `0xc00000e5` | `LoadProviderEx +0x37` | `g_fLoaderInitialized` 0 (attach 의 `InitializeLoader +0x22` 가 1 로 씀) |
| `0xc00000e5` | `OpenSystemPreferredAlgorithmProvider +0x174` | `GenRandom` 질의 답 개수 0 |

- `BcoapCached` 는 **새 status 를 안 만든다** — 캐시 실패는 status 0 으로 두고 캐시만 안 한다.

### 2.8 ★ 답장 모양 — 쪽 번호와 포인터 고치기 (질문 2)

사용자에게 가장 낯설 곳이라 천천히 간다.

#### 새 말 — 상대 오프셋 ("쪽 번호")

- 답장 안에는 "이름은 여기 있어요", "공급자 칸은 여기 있어요" 를 가리키는 칸이 많다.
- 이 칸들에는 **진짜 메모리 주소가 아니라**, **답장 시작에서 몇 바이트째인가** 가 적혀 있다. 이것을 run 문서는 "**출력 시작 기준 오프셋**" 이라고 부른다 `[정적]`.
  - 예: 어떤 칸 값이 `0x60` 이면 "답장 시작에서 `0x60` 바이트째를 봐라" 다.
- 비유: 답장은 **작은 책** 이다. 목차에 "AES → **12쪽**" 처럼 **쪽 번호** 만 적혀 있다. 그 책이 지금 책상 위 어디에 놓였는지는 목차에 없다.
- 왜 진짜 주소가 아니라 쪽 번호로 적나 `[추측]` (일반적으로 알려진 설명): 답장을 만드는 쪽 (커널) 이 그 답장이 유저 쪽 **어느 주소에 놓일지** 에 기대지 않고 만들 수 있게. 이번 코드에서 확인한 건 "쪽 번호로 와서 bcrypt 가 고친다" 까지다.

#### 새 말 — 포인터 고치기

- bcrypt 는 답장을 받은 뒤, 쪽 번호 칸을 하나씩 **"답장 시작 주소 + 쪽 번호"** 로 바꿔 **그 칸에 다시 써 넣는다** `[정적]`.
  - 배열: `BCryptResolveProviders +0x7ec ADD RAX,R15`
  - 공급자 칸: `IoUnpack_ProviderRef +0x4f LEA RDI,[RAX+RDX]`
  - 문자열: `IoUnpack_ProviderRef +0x1c0 ADD RCX,RSI`
- `-1` ("없음" 도장) 칸은 **NULL** 로 바꾼다.
- 그 뒤로 bcrypt 의 다른 코드 (`BCryptOpenAlgorithmProvider` · `LoadProviderEx`) 는 그 칸을 **보통 포인터처럼** 그냥 따라간다.
- 비유: 책을 받은 사람이 목차의 "12쪽" 을 지우고 "**책상 왼쪽 서랍 셋째 칸**" 처럼 진짜 위치를 써 넣는다. 그다음부턴 누가 봐도 바로 찾아간다.

예를 들어 (값은 2.9 의 한 장에서):

| 칸 (답장 안 자리) | 받은 값 (쪽 번호) | 고친 뒤 |
|---|---|---|
| 답장 `0x08` (배열 쪽 번호) | `0x10` | 답장 시작 + `0x10` |
| 답장 `0x28` (공급자 이름) | `-1` | NULL |

- 답장 시작 주소는 bcrypt 가 할당한 그 `0x180` 그릇의 주소다 (실행마다 다르니 여기선 "시작" 으로만 쓴다).

#### 새 말 — 범위 검사

- 쪽 번호를 그냥 믿지 않는다. 고치기 전에 **"그 쪽이 이 책 안에 있나"** 를 본다 `[정적]`:
  - 쪽 번호 `< Information` (책 두께 안에서 시작하나)
  - 쪽 번호 + 칸 크기 `≤ Information` (끝까지 책 안에 들어오나)
  - 더하다 넘치지 않나 (넘침 검사)
  - 문자열이면 **NUL 로 끝나는 UTF-16 이 `Information` 안에** 있나
- 정렬 (8 의 배수 자리인가) 검사는 **없다**.
- 걸리면 Win32 `0x54f` (문자열이 안 끝나면 `0x7a`) → `0xc00000e5` (`0x7a` 는 `0xc0000023`).
- 여기서 **책 두께 = 전표의 `Information`** 이다. 그래서 `Information` 을 정확히 적어 주는 게 중요하다.

#### 답장의 다섯 덩어리 `[정적]`

run 문서 한 줄 요약: **머리 `0x10` · 포인터 배열 · 공급자 칸 `0x38` · 이미지 칸 `0x10` · 문자열**. 하나씩.

1. **머리 (`0x10` 바이트)** — 답장 맨 앞 (`+0x481 ~ +0x4fb`, `+0x7d4 ~ +0x7f8`).

   | 칸 | 크기 | 뜻 | 검사 |
   |---|---|---|---|
   | `+0x00` | 4 | 공급자 개수 | `Information < 0x10` → 실패 |
   | `+0x04` | 4 | 안 읽음 (성공 모드) | — |
   | `+0x08` | 8 | 포인터 배열 쪽 번호 / `-1` | `-1` 이면 개수 == 0. 아니면 개수 ≠ 0, 쪽 번호 `< Information`, 쪽 번호 + 개수 × 8 `≤ Information` |

2. **포인터 배열** — 8 바이트 × 개수. 칸마다 **공급자 칸의 쪽 번호**. (`-1` 도 되지만 개수 안에 끼면 뒤에서 크래시하니 쓰지 말 것.)
3. **공급자 칸 (`0x38` 바이트)** — 공급자 하나 = 이 칸 하나 (`IoUnpack_ProviderRef +0x39`).

   | 칸 | 크기 | 뜻 (이름은 `[추측]`) | 비고 |
   |---|---|---|---|
   | `+0x00` | 4 | `dwInterface` 인터페이스 번호 | 여기선 안 봄. `BCryptOpenAlgorithmProvider +0x3b7` 이 `1..8` 인지 봄 |
   | `+0x08` | 8 | `pszFunction` 알고리즘 이름 쪽 번호 / `-1` | NUL 로 끝나는 UTF-16 이 `Information` 안에 |
   | `+0x10` | 8 | `pszProvider` 공급자 이름 쪽 번호 / `-1` | 같은 검사 |
   | `+0x18` | 4 | `cProperties` 속성 개수 | — |
   | `+0x20` | 8 | `rgpProperties` 속성 배열 쪽 번호 / `-1` | `-1` 이면 개수 0 |
   | `+0x28` | 8 | **`pUM` 유저 이미지 칸** 쪽 번호 | **NULL (`-1`) 이면 `LoadProviderEx +0xb7` 널 역참조** |
   | `+0x30` | 8 | `pKM` 커널 이미지 칸 | 유저 길에선 안 읽음 |

4. **이미지 칸 (`0x10` 바이트)** — "올릴 DLL" 한 개 (`IoUnpack_ImageRef +0x31`): `+0x00` 이미지 이름 쪽 번호 / `-1`, `+0x08` `dwFlags` (안 봄).
   - (속성을 줄 때만 쓰는 **속성 칸 `0x18`** 도 있다: `+0x00` 이름, `+0x08` 값 크기, `+0x10` 값 쪽 번호. 최소 답엔 안 쓴다.)
5. **문자열** — UTF-16, NUL 로 끝남. 알고리즘 이름, DLL 파일 이름 등.

- 비유로 한 번 더: **책 (답장)** 맨 앞 **표지 (머리)** 에 "공급자 1명, 명단은 `0x10` 쪽" → **명단 (배열)** 에 "1번 공급자 소개는 `0x18` 쪽" → **소개 카드 (공급자 칸)** 에 "종류 1번, 이름은 `0x60` 쪽, 일하는 건물 안내는 `0x50` 쪽" → **건물 안내 (이미지 칸)** 에 "건물 이름은 `0x68` 쪽" → 그 쪽들에 **글자 (문자열)**. bcrypt 는 이 쪽 번호들을 하나씩 따라가며, 쪽마다 "책 안에 있나" 를 본다. (쪽 번호 값은 다음 절 한 장의 값 그대로다.)

### 2.9 ★ 가장 작은 답장 `0x98` 한 장 — 처음부터 따라 읽기 (질문 4)

**`BCryptOpenAlgorithmProvider(L"AES", NULL, 0)` 기준, 공급자 하나, `Information = 0x98`** (run 문서 "가장 작은 출력 한 장" = 결과서 4-b).

| `0x34` | 4 | 0 | 안 씀 | — |
| `0x38` | 8 | `-1` | `rgpProperties` 없음 (개수 0 이면 `-1` **필수**) | `+0x150 ~ +0x160` |
| `0x40` | 8 | `0x50` | `pUM` 이미지 칸 쪽 번호 (**NULL 불가**) | `IoUnpack_ImageRef +0x28 ~ +0x41` |
| `0x48` | 8 | `-1` | `pKM` 없음 | 같음 |
| `0x50` | 8 | `0x68` | 이미지 칸 `+0` = 이미지 이름 쪽 번호 | `IoUnpack_ImageRef +0xe1 ~ +0x12f` |
| `0x58` | 4 | `0` | 이미지 칸 `+8` `dwFlags` | 안 봄 |
| `0x60` | 8 | `L"AES\0"` | 알고리즘 이름 | `BCryptOpenAlgorithmProvider +0x4bb` 가 핸들 안에 복사 |
| `0x68` | 42 → 48 | `L"bcryptprimitives.dll\0"` + 0 | 이미지 이름 (**파일 이름만**) | `LoadProviderEx +0xb0` · `_LoadImage +0x2c ~ +0x45` |

#### bcrypt 의 눈으로 따라가기 — 단계별로

1. **전표**: `Information = 0x98`. `0x10` 이상이라 머리 검사 통과 (`+0x4b0` 안 탐).
2. **머리**: 개수 `1`. 배열 쪽 번호 `0x10` — `-1` 이 아니니 "배열 있음". 개수 ≠ 0 ✓. `0x10 < 0x98` ✓. `0x10 + 1 × 8 ≤ 0x98` ✓. → 배열 칸을 "시작 + `0x10`" 으로 고친다.
3. **배열 `[0]`**: `0x18` → 공급자 칸으로. 결과서가 적은 검사: `0x18 < 0x98`, `0x18 + 0x38 ≤ 0x98` ✓.
4. **공급자 칸** (`0x18` 에서 `0x38` 바이트 = 답장 `0x18` ~ `0x4f`):
   - 칸 `+0x00` (답장 `0x18`) = 인터페이스 `1`.
   - 칸 `+0x08` (답장 `0x20`) = `0x60` → 이름 `L"AES\0"` 가 NUL 로 끝나고 `0x98` 안에 있다 ✓.
   - 칸 `+0x10` (답장 `0x28`) = `-1` → NULL.
   - 칸 `+0x18` · `+0x20` (답장 `0x30` · `0x38`) = 속성 0 개 · `-1` — 짝이 맞다 ✓.
   - 칸 `+0x28` (답장 `0x40`) = `0x50` → 이미지 칸으로.
   - 칸 `+0x30` (답장 `0x48`) = `-1` → NULL (유저 길에선 안 씀).
5. **이미지 칸** (`0x50`): 칸 `+0` = `0x68` → `L"bcryptprimitives.dll\0"` 가 `0x98` 안에서 끝난다 ✓.
   - 결과서: 이 문자열은 `0x68 + 0x2a = 0x92` 에서 끝나고, 8 바이트로 올려 `0x98`.
6. 모든 검사 통과 → status 0, 고친 답장을 부른 쪽에 넘긴다.

- 결과서는 `IoUnpack_*` 검사 줄을 옮긴 파이썬 모델로 이 `0x98` 바이트를 돌려 **통과**, `Information 0` · `0x180` 영 채움은 `0x54f` 로 **걸림** 을 확인했다 (`[정적]` 손 검산, 임시 파일).
- 표에서 "칸 `+0x08`" 과 "답장 `0x20`" 처럼 **두 자리가 같이** 나오는 이유: 공급자 칸 자체가 답장 `0x18` 에서 시작하니, 칸 안 `+0x08` 은 답장 전체로는 `0x18 + 0x08 = 0x20` 이다. run 문서의 출력 칸 표 (칸 기준) 와 한 장 표 (답장 기준) 는 이렇게 맞물린다.

#### `dwInterface` 는 알고리즘에 맞아야 한다 `[정적]`

- 이 값은 bcrypt 가 돌려줄 알고리즘 핸들 `+0x24` 에 들어간다 (`BCryptOpenAlgorithmProvider +0x498`).
- 나중에 그 핸들을 쓰는 함수가 이 값을 본다. 예: `BCryptGenRandom +0x5a CMP [RAX+0x24],6` — 난수 함수는 **6** 이어야 한다.
- 코드로 본 번호: **6 = 난수** (`OpenSystemPreferredAlgorithmProvider +0xeb`), **2 = hash** (`+0xaa1` + 문자열 `HashBlockLength`), **3 = 비대칭 암호화** (`+0xb57` + `PaddingSchemes`). **1 = 암호** 는 `[추측]`.
- 범위 밖 (`1..8` 이 아님) 이면 `+0x3d4` `0xc0000008`.

#### `GenRandom` 질의 (입력 `0x30`, 인터페이스 6) 의 답 `[정적]`

- 같은 모양, `dwInterface = 6`.
- **`pszFunction` 이 NULL 이면 안 된다** — 그 문자열이 `BCryptOpenAlgorithmProvider` 의 알고리즘 이름으로 넘어간다 (B4). NULL 이면 `0xc000000d`.
- 이름은 `L"RNG"` 가 자연스럽다 `[추측]` — CNG 초기화 전 이 코드가 쓰는 이름이 `RNG` 이기 때문 (`+0x36 LEA RDX,[0x18001f128]`, PE 바이트).
- 그래서 엔진은 **입력 `+0x18` (이름 쪽 번호) 에서 알고리즘 이름을 읽어** 답의 `pszFunction` 과 `dwInterface` 를 맞춰 줘야 한다 (run 문서 "PE_emulator 확인거리"): `AES` → 1 `[추측]`, `RNG` → 6, `SHA256` → 2 등.

#### 최소 조건 표 (run 문서 그대로, attach 가 TRUE 로 끝난 전제)

전제: `g_hIoDevice ≠ 0` · `g_TrustedEnvironment & 1` · `g_fLoadCNGDone = 1` · `g_fLoaderInitialized = 1` (run92 attach 가 다 해 둔 것).

| # | syscall (또는 읽는 칸) | 기대 답 | 안 맞으면 |
|---|---|---|---|
| 1 | **`NtDeviceIoControlFile`** (공급자 질의, `0x390400`, 입력 `0x30` / `0x38` / …, 출력 `0x180`) | **status ≥ 0** (0 권장) | 음수 → 그대로 반환. `0xc0000023` → `0xc00000e5` |
| 2 | 그 IOCTL 의 IOSB (`[RSP+0x78]`) | **`Information` = N, `0x10 ≤ N ≤ 0x180`**. `Status` 칸은 안 읽음 | `N < 0x10` → **`0xc00000e5`** (지금 엔진). `N > 0x180` → 다시 할당해 IOCTL 다시 |
| 3 | 그 IOCTL 의 답장 | 처음 N 바이트 = 위 한 장 | 칸 어긋남 → `0xc00000e5`. `dwInterface ∉ 1..8` → `0xc0000008` |
| 4 | `LoadLibraryExW` (로더 몫) | 성공 + 그 DLL attach 통과 (bcryptprimitives — run91) | `0xc0000135` / `0xc000007b` → 다음 공급자 → 다 실패면 그 status |
| 5 | `GetProcAddress` (그 DLL 의 `Get…Interface`) | 내보내기가 있어야 — 이름 ↔ 번호 `[공백]` | 이름만 |
| 6 | 공급자 DLL 함수 표 검사 · 열기 함수 | 이름만 (공급자 몫) | 이름만 |

- `BcoapCached` 를 지나 성공 쪽으로 가는 최소 = **1 · 2 · 3 행**. 4 행부터는 "그 뒤 어떤 DLL 을 올리나" (2.11).

### 2.10 ★ 공급자 "0 개" 답장은 쓰면 안 된다 (질문 4)

"이 알고리즘은 맡는 건물이 없어요" 를 어떻게 알리면 될까? 직관적으로는 "개수 0 짜리 답장" 이 떠오른다. 그런데 **그게 제일 위험한 답** 이다.

#### 왜 크래시인가 — 단계별로 `[정적]`

1. 답장: status 0, `Information ≥ 0x10`, 개수 0, 배열 `-1`.
2. `BCryptResolveProviders` 는 이걸 **앞뒤가 맞는 답장** 으로 본다 ("배열 없음 + 개수 0" — 짝이 맞다). **status 0 으로 통과** (`+0x4c7 ~ +0x4da`).
3. `BcoapCached` 는 성공 답이니 **캐시에도 넣는다** (`+0x163 ~ +0x177`).
4. `BCryptOpenAlgorithmProvider` 로 돌아와 `+0x263 JNS` (성공이니 계속) → `+0x3a5 MOV RAX,[RAX+8]` · `+0x3a9 MOV RDX,[RAX]` — **첫 공급자 칸을 개수 검사 없이 읽는다**.
5. 결과서: 이때 `RAX = 0` → **널 역참조 (크래시)** `[정적: 읽기 — 실행은 안 봄]`.
   - `[RAX+8]` 의 `+8` 이 머리의 배열 칸 자리 (`-1` 이라 NULL 로 고쳐진 칸) 와 같다 — 그래서 0 이 나온다고 읽힌다 `[추측: 읽는 법]`.
6. 게다가 캐시에 박혔으니 **같은 이름은 계속** 같은 답을 받는다.

- `GenRandom` 질의 (B3) 에서는 다르다: `OpenSystemPreferredAlgorithmProvider +0x106 CMP [개수],1` · `+0x109 JC +0x174` 가 먼저 막아 **`0xc00000e5`** 로 끝난다 (크래시 아님).
- 비유: 접수처는 "명단에 0명" 이라는 답장을 **멀쩡한 답장** 으로 받아 철해 둔다. 그리고 명단을 안 세고 "1번 공급자 소개 카드" 를 꺼내려다 빈손으로 넘어진다.

#### 그럼 "없음" 은 어떻게? — 음수 status 로 `[정적]`

| 답 | 결과 |
|---|---|
| status 0 + 개수 0 + 배열 `-1` | **널 역참조 (크래시)**. 캐시에 박힘. **쓰지 말 것** |
| 〃 (`GenRandom` 질의) | `0xc00000e5` |
| 개수 0 + 배열 ≠ `-1` | `+0x7d7` → `0xc00000e5` |
| **IOCTL 자체를 음수 status 로** | 그대로 위로 (`BCryptOpenAlgorithmProvider +0x263 JNS` 안 탐). **실패는 이쪽이 정상 길** |

- 어떤 음수가 진짜인지는 `[추측]` — 결과서는 `STATUS_NOT_FOUND 0xc0000225` 가 자연스럽다고 봤다. 단 `0xc0000023` · `0x80000005` 는 2.6 의 특별한 뜻이 있으니 피한다.
- 성공 답만 캐시하니 (`+0x12c JS`), 음수로 답하면 **캐시에도 안 박힌다**.

### 2.11 그 뒤 — 어떤 DLL 을 올리나 (질문 4)

- **답장에서 나온다** `[정적]`:
  1. `BCryptOpenAlgorithmProvider +0x514` 에서 배열 `[i]` 공급자 칸을 꺼내 → `+0x518 LoadProviderEx` (공급자마다, 루프 `+0x4dd ~ +0xa84`).
  2. `LoadProviderEx +0x35` — `g_fLoaderInitialized` 가 0 이면 `+0x37` `0xc00000e5` (attach 가 1 로 써 둠).
  3. `LoadProviderEx +0xb0 · +0xb7` — 공급자 칸 `+0x28` → 이미지 칸 `+0` → 이름.
  4. `_LoadImage +0x59 _GetImagePath` — `GetSystemDirectoryW` (`+0x5e`) 로 시스템 폴더를 얻고 `\` 를 붙인다 (`+0x70`).
  5. `_LoadImage +0x7b RtlCompareUnicodeString` — 이름이 `bcrypt.dll` 이면 **안 올리고 자기 자신** (`+0x140 g_hInstance`).
  6. `_LoadImage +0x9d LoadLibraryExW(시스템 폴더 + "\" + 이름, 0, 0)`.
  7. 실패면 `+0x18c` `0xc0000135` / `+0x176` `0xc000007b` → **다음 공급자** → 다 실패면 그 status.
- 그래서 답장의 이미지 이름은 **파일 이름만** (`bcryptprimitives.dll`) 주면 된다. bcrypt 가 폴더를 붙인다.
- 엔진 쪽으로 보면: 여기서부터는 IOCTL 이 아니라 **로더 (`LoadLibraryExW`) 몫** 이다. bcryptprimitives 의 `DllMain` 최소 조건은 run91 에서 이미 봤다.
- 비유: 답장의 "건물 이름" 을 보고, 접수처가 **동네 표준 주소 (시스템 폴더)** 를 앞에 붙여 그 건물을 가게에 들인다.

### 2.12 캐시 — 이름 하나당 IOCTL 한 번 (질문 5) `[정적]`

- 전역 **`g_pResolveProviderCache`** (rva `0x25c10`). `BcoapCached` 만 읽고 쓴다 (`+0x2e` · `+0x16a` · `+0x177 CMPXCHG.LOCK`).
- 끈으로 엮은 목록 (연결 리스트) 이고, 새 것은 맨 앞에 단다.
- 키 = **알고리즘 이름** (대소문자 구분). 노드 `0x40`: `+0x00` 다음 · `+0x08` 답장 포인터 · `+0x10` 크기 · `+0x14` 이름 (19 글자 + NUL).
- 조건: 공급자 이름 NULL **그리고** 플래그 2 — 즉 `BCryptOpenAlgorithmProvider(&h, 이름, NULL, 0)` 이고 `g_fLoadCNGDone ≠ 0` 일 때만. **성공 답만** (`+0x12c JS`). 이름이 19 글자를 넘으면 캐시 안 함 (`+0x157 JNZ`). **지우는 코드는 없다**.
- IOCTL 횟수 가늠 (run 문서): 서로 다른 알고리즘 이름 수 (≤ 19 글자, 공급자 NULL) + `GenRandom` 이면 질의 한 번. 공급자 이름을 직접 주면 **매번**.
- 엔진에 주는 뜻: **한 번 틀린 성공 답을 주면 그 이름은 프로세스 끝까지 그 답** 이다.
- 비유: 접수처는 받은 답장을 **알고리즘 이름표를 붙여 철해 둔다**. 같은 이름을 다시 물으면 상담실에 안 가고 철에서 꺼낸다. 철은 한 번도 비우지 않는다.

### 2.14 결과서와 다르게 적은 곳 · 보탠 것 (짧게)

- ① **결과서의 `+0x74b` 는 함수 오프셋이 아니라 주소 끝자리다.** `+0x7fe JMP 0x18000674b` · `+0x505 JNZ 0x18000674b` 의 대상은 함수 오프셋으로 **`+0x39b`** 다. 또 결과서의 "`+0x500 JNZ`" 는 `+0x505 JNZ` (`+0x500` 은 `MOV R12D,EAX`). run 문서와 이 글은 `+0x39b` · `+0x505` 로 적었다. **길과 결론은 같다.**
- ② 결과서 머리의 "PE_emulator **요청 33** 의 다음 벽" — 요청 33 은 run93 (wait packet) 이다. 이번 일은 run92 (요청 32) 의 다음 벽이고, plan.md 결정 기록은 "PE_emulator 외부 피드백 — Q173 ②" 로 적었다. run 문서는 그쪽을 따랐다.
- ③ (flow-writer 보탬) **`BCryptResolveProviders` 도 IOCTL 앞에서 걸이를 다시 본다** — `+0x5a7 ~ +0x5b1` 에서 `g_hIoDevice` 가 0 이면 열쇠 (`EnterCriticalSection`) 를 쥐고 `+0x761 _IoOpenDevice` 로 다시 연다. run92 의 `IoCallKernelDriver` 와 같은 꼴 — **열기 status 만 보고 걸이 값은 안 본다**. attach 가 TRUE 였으면 걸이가 이미 차 있어 안 탄다.
- ④ (flow-writer 보탬) IOCTL 인자 줄 (2.2 줄 1 에 옮김). 출력 그릇이 8 바이트보다 작으면 제 지역 8 바이트를 쓰는 갈래도 있지만 (`+0x688` · `+0x68b`), 관찰된 호출자는 `0x180` 이라 안 탄다.
- 이전 run 이 틀린 것은 없다 — 정정 없음. run92 "아직 확인 필요" 정적 ② 줄에 `(해결됨 → run94)` 를 붙였다.

### 2.15 디버거 · 도구 메모

- **디버거가 붙어서 달라지는 점**: 이번에 읽은 줄 안에서 디버거 칸을 읽는 줄은 없다 `[정적: 읽은 줄 안에서]`. `_LogBCryptOpenProviderFailure` · WPP 줄은 실패 기록용이라 성공 / 실패 갈림에 안 닿는다.
- **C++ 꾸민 이름** (run92 와 같은 함정 — [run92 해설](run92-bcrypt-ksecdd-해설.md) 2.16): `IoUnpack_ProviderRef` · `WinErrorToNtStatus` · `IoCallKernelDriver` 는 PDB 에 꾸민 이름만 있다. WinDbg 에서 `x bcrypt!*IoUnpack_ProviderRef*` 로 먼저 확인하거나 rva (`bcrypt+0x6bd0`) 로 건다 `[추측]`.
- **결과서 오프셋 표기**: 점프 대상을 주소 끝자리로 적은 줄이 있었다 (2.14 ①). `JMP` / `Jcc` 대상은 `.asm` 주소에서 함수 시작을 빼 오프셋으로 적는 게 맞다 — decompiler 쪽 확인 습관 제안 (run 문서).

### 2.16 정리 — 비유로 한 번 더

1. 어떤 가게의 손님 (프로그램) 이 **암호 앞쪽 건물** (bcrypt) 접수처에 "AES 해 주세요" 한다 (`BCryptOpenAlgorithmProvider`).
2. 접수처는 먼저 **철** (캐시) 을 본다. "AES" 이름표 붙은 답장이 없다.
3. 주문서를 쓴다: 맨 위 표지 `0x1a2b3c4d`, 용건 번호 **`0x20000`** ("어느 건물이 맡나요?"), 이름 칸엔 "**`0x30` 쪽을 보세요**", `0x30` 쪽에 "AES". 합 `0x38` 바이트.
4. 답장 종이는 **`0x180` 한 장** 을 미리 마련한다.
5. 벽 걸이의 **KsecDD 손잡이** (run92 가 건 것) 로 상담실에 주문서와 빈 종이를 넣는다.
6. 상담실이 **도장** 과 **전표** ("○ 바이트 적었음") 를 돌려준다. 접수처는 도장의 부호와 전표 숫자만 본다.
7. 흉내 상담실은 "처리됐어요" 도장에 전표 **0** (또는 0 으로 칠한 종이) 을 준다 → 접수처: "**책이 망가졌다**" (`0x54f`) → 공식 번호로 바꿔 **`0xc00000e5`**. ← 지금 엔진
8. 진짜처럼 하려면: 도장 0, 전표 `0x98`, 종이에 **작은 책 한 권** — 표지 · 명단 · 소개 카드 · 건물 안내 · 글자 — 을 **쪽 번호** 로 엮어 적는다.
9. 접수처는 쪽 번호를 하나씩 **"책 안에 있나"** 확인하며 진짜 위치로 고쳐 적는다.
10. 소개 카드의 종류 번호 (`dwInterface`) 가 `1..8` 인지 보고, 건물 안내의 이름 (`bcryptprimitives.dll`) 앞에 **동네 표준 주소** 를 붙여 그 건물을 들인다 (`LoadLibraryExW`).
11. 답장은 **"AES" 이름표를 붙여 철해 둔다**. 다음에 AES 를 물으면 상담실에 안 간다.
12. "맡는 건물 없음" 을 알리고 싶으면 **명단 0명짜리 책** 이 아니라 **실패 도장 (음수 status)** 을 찍는다. 0명짜리 책은 철에 박힌 채 손님을 넘어뜨린다.
