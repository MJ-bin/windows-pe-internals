### 이번 바퀴에서 조심할 곳 넷

1. **이번 이야기도 주인공이 test.exe 가 아니다.**
   - `\RPC Control` 방은 부팅 때 **관리인 smss** 가 만든다 (run98). 그 방에 명부가 붙는 순간도 그때다.
   - 다만 이번에 본 커널 함수 (`ObInsertObjectEx`) 는 **test.exe 를 만들 때도** 지나간다 (2.12). 그래도 흐름도 그림의 노드 **안쪽** 이라 그림은 그대로다.
2. **"넘긴 명부" 와 "붙은 명부" 는 다르다 — 이게 이번 바퀴의 답이다.**
   - run98 해설 "조심할 곳" 3번에서 "다를 수 있다 `[추측]`" 이라고 남겼던 것이, 이번에 **`[정적]` 으로 "다르다"** 가 됐다. 무엇이 어떻게 다른지가 2절 전체다.
3. **바이트 표의 소유자 · 소속 칸은 가정 값이다.**
   - 소유자 `S-1-5-32-544` (16B) · 소속 `S-1-5-18` (12B) 은 "smss 가 SYSTEM 신분증이면" 이라는 `[추측]` 이다.
   - 그래서 총 길이 `0xe8` 도 **이 가정 위에서** 맞다. 길이가 다르면 오프셋 몇 개와 총 길이가 따라 움직인다 (2.10).
4. **에뮬레이터 쪽 숫자는 우리 `[관찰]` 이 아니다.**
   - "샘플 53개가 토큰 라벨을 못 받음", `namespace.cpp:21`, `handles.hpp:14` 는 원문 요청, 즉 **PE_emulator 쪽** 에서 왔다. 이 글에서도 "에뮬레이터 쪽 관찰" 로만 부른다.
   - 오프셋은 **call 자리** 다. ret 자리는 run 문서 "정적 — 호출 지점" 표에 있다.

### 한 줄로 먼저 — 무엇을 얻었나

**이번 글의 중심은 이 세 줄이다.** `[정적]`

> **관리인이 넘긴 명부는 "그대로" 붙지 않는다.** 관리사무소가 방에 붙이기 전에 새로 베껴 쓰면서 다섯 가지를 바꾼다 — ① 비어 있던 주인 · 소속을 **만든 쪽 신분증** 에서 채우고, ② 허락 쪽 0 ~ 2번 줄의 넓은 이름표를 **디렉터리 구체 권한** 으로 풀고, ③ 크기 칸 둘을 **다시 재고** (`0xb8 → 0x9c`, `0x20 → 0x1c`), ④ `Control` 에 `0x8000` · `0x800` 을 더하고 (`0x14` → **`0x8814`**), ⑤ 저장 차례를 바꾼다 (특수 쪽이 맨 앞).

> **바꾸지 않는 것도 분명하다.** 줄 개수 · 차례 · 플래그, **상속 전용 줄 넷의 마스크**, 신뢰 등급 표 한 줄 전체. 부모 방 (루트 `\`) 의 줄은 **섞이지 않는다.**

> **그래서 에뮬레이터가 돌려줄 대답이 정해졌다.** `0x17` 대답은 `0xe8` 바이트, `0x10` 대답은 `0x30` 바이트. 그리고 **신분증 (토큰) 객체 명부엔 신뢰 등급 표가 늘 붙는다** — run97 의 `[공백]` 이 닫혔다.

| 요청서 질문 | 한 줄 답 | 이 글 |
|---|---|---|
| 1 사슬 | 이름 있는 방은 한 칸 더 돈다: `ObInsertObjectEx +0x443` → `ObpCreateHandle +0x13bd` → `ObpInsertOrLocateNamedObject +0x1fe` → `ObpAssignSecurity +0xd9` → `SeAssignSecurityEx2 +0x65` → `RtlpNewSecurityObject`. 저장은 `SeDefaultObjectMethod` (EDX=3) | 2.1 ~ 2.4, 2.9 |
| 2 소유자 · 그룹 | 만든 쪽 신분증 칸 `+0x98` · `+0x90` · `+0xa8`, `DEFAULTED` 안 켬, 값은 VM | 2.5 |
| 3 DACL | 상속 전용 아닌 셋만 풀기, 상속 전용 넷 그대로, `AclSize 0x9c`, 부모 안 섞임 | **2.6** |
| 4 SACL · 라벨 | 라벨 그대로, 라벨만이면 특권 안 물음, 없을 때 규칙 표 | 2.7 |
| 5 `Control` | `0x8814` (`0x800` 이 확신 가장 낮음) | **2.8** |
| 6 토큰 | 라벨 `0x11` 이 조건 없이 붙음 | 2.11 |
| 7 바이트 | 저장 `0xe8`, `0x17` 대답 `0xe8`, `0x10` 대답 `0x30` | **2.10** |

## 1. 이번 바퀴의 질문

### 큰 그림에서 어디인가

이번 길도 test.exe 가 태어나기 **훨씬 앞**, 부팅 때다. 요청 34 의 네 조각을 시간 차례로 놓으면 이렇다.

```
(부팅)
 관리사무소 (커널) 부팅 — 루트 \ 방 · 디렉터리 형 · 신분증 형 만들기
 │
 관리인 smss
 └─ NtCreateDirectoryObject("\RPC Control", 느슨한 명부)            (run98: 무엇을 넘기나)
      └─ 관리사무소 안: 명부를 새로 베껴 써서 방에 붙임              ← 이번 (run100)
 │
 … (로그온, cmd.exe → test.exe 초기화 → main)
 │   test.exe 를 만들 때도 같은 ObInsertObjectEx 를 지나감          ← 이번 (2.12, 신분증 쪽)
 │
(rpcrt4 를 쓰는 다른 프로그램이라면 — PE_emulator 가 만난 상황)
 rpcrt4 → NtQuerySecurityObject(\RPC Control, 0x17)                 (run99: 받는 쪽)
      └─ 관리사무소: 붙은 명부를 잘라 사본으로                       (run97: 어떻게 답하나)
```

- "로그온, cmd.exe" 줄의 정확한 차례는 이번 근거에 없다. 차례를 보여 주려는 그림일 뿐이다.

### 왜 이 질문이 지금 왔나

- run97 은 "**붙어 있는** 명부를 어떻게 잘라 주나" 였다.
- run98 은 "관리인이 **넘기는** 명부" 였다.
- 그런데 둘 사이가 비어 있었다. **넘긴 명부가 그대로 붙나, 바뀌어 붙나?**
  - 그대로라면 run98 표를 그대로 run97 규칙에 넣으면 된다.
  - 바뀐다면 무엇이 어떻게 바뀌는지 알아야 에뮬레이터가 대답 바이트를 만들 수 있다.
- run98 해설 2.5 에서도 "주인 · 소속이 비었으면 누가 채우나? — 관리사무소가 신분증에서 채울 것이다 `[추측]`", "넓은 이름표를 구체 권한으로 바꿔 두나 — 모른다 → Q180d" 로 남겼다. 그 둘이 이번 질문이다.

### 무엇이 궁금했나

"관리인이 넘긴 느슨한 명부가 `\RPC Control` 방에 붙을 때, 관리사무소는 **주인 · 소속 · 허락 쪽 · 특수 쪽 · `Control`** 을 각각 어떻게 다시 쓰나? 그 결과로 `0x17` · `0x10` 질문엔 **정확히 어떤 바이트** 가 나가나? 그리고 같은 계산으로, 신분증 객체 명부엔 신뢰 등급 표가 붙나?"

### 바퀴 전에 알던 것

- `[정적]` (run98) 느슨한 명부 = 주인 · 소속 **없음**, `Control 0x14`, 허락 쪽 `AclSize 0xb8` · 7줄 (0 ~ 2번 플래그 0, 3 ~ 6번 플래그 `0x0b`), 특수 쪽 `AclSize 0x20` · 신뢰 등급 표 1줄 (`0x11` · 마스크 1 · `S-1-16-4096`). 넘기는 꼴은 **절대형** ([run98 해설 2.5](run98-rpc-dir-create-해설.md)).
  - run98 해설은 "허락 쪽은 쓰인 건 156B, 뒤 28B 는 안 씀", "특수 쪽은 쓰인 건 28B" 라고 적었다. 이번에 이 숫자가 다시 나온다 (2.6).
- `[정적]` (run97) 질문 대답 차례 = 머리 `0x14` → 주인 → 소속 → 허락 쪽 → 특수 쪽. LABEL 만 물으면 특수 쪽에서 `0x11` 줄만 고른다.
- `[정적]` (run97) 디렉터리 · 신분증 형의 보안 담당은 둘 다 `SeDefaultObjectMethod`. 신분증은 `ObInsertObjectEx +0x325 SeAssignSecurityEx2` → `+0x38c SeDefaultObjectMethod` 를 지난다.
- `[공백]` (run97) 신분증 객체 명부에 신뢰 등급 표 (`0x11`) 가 기본으로 붙나. `NtDuplicateToken` 이 붙이는 건 `0x14` (프로세스 신뢰 라벨) 였다.
- `[추측]` (run98) 관리사무소가 주인 · 소속을 채우고, 넓은 이름표를 바꾸고, 크기를 다시 잴 **수 있다** — flow.md 3장 run98 절 비유 "주인 칸은 시청이 채운다" 도 이 `[추측]` 이었다.

### 2.1 한눈에 — 넘긴 명부가 방에 붙기까지

run 문서 "호출 관계" 에서 대표만 남겼다. 숫자는 run 문서 그대로다. 모두 `[정적]`.

```
nt!NtCreateDirectoryObject +0xc → ObpCreateDirectoryObject
 ├─ +0xe0  ObCreateObjectEx → … → SeCaptureSecurityDescriptor        넘긴 명부 → 한 덩어리 사본 (0x14 → 0x8014)  ← 2.3
 └─ +0x18a ObInsertObjectEx
      │  +0x279 이름 있음 → 명부 계산 블록 (+0x28c ~ +0x3e6) 건너뜀       ← 2.3 (이름 없는 신분증은 여기로 → 2.11)
      └─ +0x443 ObpCreateHandle
           └─ +0x13bd ObpInsertOrLocateNamedObject
                │  +0x175 부모 방 (루트 \) 명부 가져오기 · 자동 상속 0       ← 2.4
                └─ +0x1fe ObpAssignSecurity
                     ├─ +0xd9  SeAssignSecurityEx2 → +0x65 RtlpNewSecurityObject
                     │     ├─ +0x1dc ~ +0x202  신분증에서 주인 · 소속          ← 2.5
                     │     ├─ +0x155e RtlpInheritAcl2 (라벨)  → 특수 쪽 0x1c   ← 2.7, 2.8
                     │     ├─ +0x1668 RtlpInheritAcl2 (허락 쪽) → +0x290 RtlpCopyAces
                     │     │     +0x14e 상속 전용 아니면 넓은 이름표 풀기 · 0x9c  ← 2.6
                     │     └─ +0x1225 조립: 머리 → 특수 → 허락 → 주인 → 소속 · 0x8814  ← 2.8, 2.10
                     └─ +0x14a SeDefaultObjectMethod (EDX=3)   보관함에 넣고 헤더에 걸기  ← 2.9
```

- **읽는 순서**: 위에서 아래로 시간 순서다. 들여쓰기 한 칸 = "그 함수 안에서 부른 것".
- 명부를 실제로 고쳐 쓰는 건 거의 다 **`RtlpNewSecurityObject` 한 함수** (8746B) 안이다. 위쪽 다섯 줄은 거기까지 **가는 길** 이다.

비유로 한 번:

1. 관리인이 창구에 "이 이름으로 방 하나, 이 명부 붙여서" 를 낸다.
2. 창구는 명부를 먼저 **한 장짜리 사본** 으로 받아 둔다.
3. 방에 **이름이 있으니** 이름 붙이는 부서로 넘긴다. 그 부서가 **윗방 (루트 `\`)** 명부도 가져온다.
4. 명부 담당이 **새 명부를 베껴 쓴다** — 신분증 보고 주인 · 소속 채우기, 넓은 이름표 풀기, 크기 다시 재기.
5. 다 쓴 명부는 **보관함** 에 넣고, 방 헤더엔 보관함 칸을 가리키는 쪽지만 붙인다.

### 2.2 한 줄씩 읽는 법

#### 줄 ①: `└─ +0x1fe ObpAssignSecurity`

- **누가**: `nt!ObpInsertOrLocateNamedObject` — 이름 있는 객체를 이름 공간에 넣거나 찾는 함수.
- **어디서**: 자기 코드 `+0x1fe` (ret `+0x203`). 그 앞에서 이름을 찾고 (`+0x117 ObpLookupObjectName`), 부모 방 명부를 가져온다 (`+0x175 ObpGetObjectSecurity`).
- **누구를**: `ObpAssignSecurity` (rva `0x87e330`) — 새 객체에 명부를 **계산해 붙이는** Ob 쪽 함수.
- **무엇을 위해**: 이름이 정해진 **바로 그 자리** 에서, 부모 방 명부 · 넘긴 명부 · 만든 쪽 신분증을 한데 모아 새 명부를 만들려고.
  - 이 함수가 `SeAssignSecurityEx2` 에 넘기는 값 (`ObpAssignSecurity` 안):
    - 만든 쪽 신분증 = `AccessState+0x20` (`+0x83`)
    - 풀이표 = 형 객체 `+0x4c` (`+0x61`)
    - "디렉터리인가" = (형 == `ObpDirectoryObjectType`) (`+0x95`)
  - 그리고 돌아온 뒤 `+0x14a` 에서 **보관함 담당** 을 부른다 (줄 ③).

#### 줄 ②: `│     +0x14e 상속 전용 아니면 넓은 이름표 풀기`

- **누가**: `nt!RtlpCopyAces` — 명부 줄 (ACE) 을 하나씩 베껴 쓰는 함수.
- **어디서**: `+0x13e` 에서 줄 하나를 **그대로 복사** 한 뒤, `+0x14e TEST byte [RBX+1],8` · `+0x152 JNZ → +0x1a8`.
- **누구를**: 부르는 함수는 없다. 방금 복사한 줄의 **플래그 칸** (`[RBX+1]`) 에 `8` (`INHERIT_ONLY`, 상속 전용) 이 있나 본다.
- **무엇을 위해**: **상속 전용 줄이면 풀기를 건너뛰고**, 아니면 그 아래 `+0x15b` ~ `+0x1a3` 에서 넓은 이름표를 풀려고 (2.6).
  - 이 한 줄이 "0 ~ 2번만 바뀌고 3 ~ 6번은 그대로" 의 **갈림길** 이다.

#### 줄 ③: `└─ +0x14a SeDefaultObjectMethod (EDX=3)`

- **누가**: `nt!ObpAssignSecurity`.
- **어디서**: `+0x14a` (ret `+0x14f`). 형 객체 `+0x98` (보안 담당) 이 정말 `SeDefaultObjectMethod` 인지 `+0x118 ~ +0x144` 에서 견주고, 아니면 `+0x1e3` 간접 호출로 간다.
- **누구를**: `SeDefaultObjectMethod` — run97 에서 만난 **기본 담당**. 이번엔 `EDX = 3` = "**새로 달기**" 갈래다.
  - run97 은 `EDX = 1` ("질문") 갈래였다. 같은 담당의 **다른 서랍** 이다. 서랍은 0 쓰기 · 1 묻기 · 2 삭제 · 3 새로 달기 (`+0x8c` · `+0x94` · `+0x1c` · `+0x9d`).
- **무엇을 위해**: 다 쓴 명부를 **보관함에 넣고** 방 헤더에 걸려고 (2.9).

### 2.3 ★ 이름 있는 방은 한 칸 더 돈다 — 요청서 가정과 다른 곳 (질문 1)

#### 요청서가 가정한 길

- 요청서는 `ObpCreateDirectoryObject` → `ObInsertObjectEx` → (`ObpAssignSecurity` →) `SeAssignSecurityEx2` 를 가정했다.
- run97 이 신분증에서 본 `ObInsertObjectEx +0x325 SeAssignSecurityEx2` 가 그 "직행" 자리처럼 보였다.

#### 실제 길 — 단계별로 `[정적]`

1. `ObInsertObjectEx` 는 먼저 **형이 명부를 꼭 요구하나** 본다 — 형 `+0x42 & 8` (SecurityRequired, `+0xde` · `+0xef`).
2. 그다음 **이름이 있나** 본다 — `+0x279 TEST R12,R12` · `+0x27c JNZ → +0x3ea`.
3. 이름이 **있으면** 명부 계산 블록 `+0x28c ~ +0x3e6` 을 **통째로 건너뛴다.** 그 블록 안에 `+0x325 SeAssignSecurityEx2` 가 있다.
4. 건너뛴 자리에서 `+0x443 ObpCreateHandle` 로 간다.
5. `ObpCreateHandle +0x13bd` → `ObpInsertOrLocateNamedObject` → `+0x1fe ObpAssignSecurity` → `+0xd9 SeAssignSecurityEx2` → `+0x65 RtlpNewSecurityObject`.

#### 그래서

- **같은 계산 함수 (`SeAssignSecurityEx2` → `RtlpNewSecurityObject`) 를 부르는 자리가 둘** 이다.
  - 이름 있는 객체 (`\RPC Control` 같은 방) → `ObpAssignSecurity +0xd9`
  - 이름 없는 객체 (신분증 등) → `ObInsertObjectEx +0x325`
- 왜 이름 있는 쪽이 따로 도나 — `[추측]` 내 짐작: 이름 있는 객체는 **부모 방이 정해져야** 부모 명부를 가져올 수 있고, 부모는 이름을 찾은 뒤에야 알 수 있기 때문으로 보인다. (근거: 실제로 이름 찾기 `+0x117` 와 부모 명부 가져오기 `+0x175` 가 `ObpAssignSecurity +0x1fe` 바로 앞에 있다 `[정적]`. 만든 사람의 뜻은 코드에 안 쓰여 있다.)
- 이 차이는 run 문서에 **정정** 이 아니다. 요청서의 가정이었고, run 문서에 적힌 적은 없다.

#### 그 앞 — 넘긴 명부를 먼저 사본으로 잡는다 `[정적]`

- `ObpCreateDirectoryObject +0xe0 ObCreateObjectEx` 안 `+0xde ObpCaptureObjectCreateInformation` → `+0x260 SeCaptureSecurityDescriptor`.
- 넘긴 명부는 **늘 한 덩어리 꼴 ([self-relative](run97-rpc-sd-query-해설.md), 2.5) 사본** 이 된다. 그래서 smss 쪽 `Control 0x14` 가 사본에선 `0x8014` 다 (`0x8000` = 한 덩어리 표시).
- 크기 칸은 4 맞춤 올림이지만, `0xb8` · `0x20` 은 이미 4 의 배수라 그대로다.
- `RtlpNewSecurityObject` 는 두 꼴을 다 읽어서, **입력 꼴은 결과에 영향이 없다** (결과서).

### 2.4 부모 방 명부는 가져오지만 섞지 않는다 — "자동 상속 0" 인 이유

#### 새 말 — 자동 상속

- **자동 상속** = 새 명부를 만들 때 **부모 방 명부의 물려주기 줄을 새로 만들어 섞을지** 정하는 스위치다 `[정적]`.
  - 켜지면: 넘긴 명부에서 `INHERITED_ACE 0x10` 가 붙은 줄은 버리고, 부모 줄을 `RtlpGenerateInheritedAce` 로 새로 만들어 섞는다 (run 문서 "DACL").
  - 꺼지면: 넘긴 명부 줄만 쓴다.
- 비유: 새 사물함 명부를 쓸 때 "**윗방 명부 아래칸 메모 (물려줄 것) 도 베껴 넣을까?**" 스위치.

#### 이번엔 꺼져 있다 — 단계별로 `[정적]`

`ObpAssignSecurity +0x6d ~ +0x74` 에서 스위치 값 = (A) `SeComputeAutoInheritByObjectTypeEx` 출력 **|** (B) 부르는 쪽 인자.

1. **(B) 부르는 쪽 인자** — `ObpInsertOrLocateNamedObject` 가 3 으로 켜는 조건은 둘 (`+0x44f`):
   - 부모 방 플래그에 `8` 이 있을 때 (`+0x14a` · `+0x150`). 이 `8` 은 `NtCreateDirectoryObjectEx` 의 `Flags & 1` 로 켜진다 (`ObpCreateDirectoryObject +0x145 OR EDX,8`).
     - 부모 = **루트 `\`**, 만든 곳 = `ObInitSystem +0x557 NtCreateDirectoryObject` (Ex 가 아닌 쪽). run 문서 결론은 "우리는 0". 실제 비트는 동적 ③ 에서 본다.
   - 전역 `ObpObjectSecurityInheritance` 가 0 이 아닐 때 (`+0x158`).
     - 파일 처음 값 0, 읽는 곳 2곳 (`+0x158` · `+0x1a6`). 값은 설정 장부 `Session Manager\Kernel` 의 `ObObjectSecurityInheritance` 로 채워진다.
     - 기본 설치엔 이 값이 없다고 보면 0 `[추측: 값은 VM]`.
   - → **(B) = 0**.
2. **(A) 형 계산** — `ObpAssignSecurity +0x4c SeComputeAutoInheritByObjectTypeEx` (call 자리는 run 문서 보탬 ①).
   - 디렉터리 형의 `SeMandatoryLabelMask` (형 `+0xd8`) 는 **0** (이유는 2.11 에서 신분증과 함께).
   - 넘긴 명부에 허락 쪽 · 특수 쪽이 **다 있어서** 자동 상속 비트도 안 켠다.
   - → **(A) = 0**.
3. → **스위치 = 0** (꺼짐).

#### 그래서

- 부모 방 (루트 `\`) 명부는 **가져오긴 한다** (`+0x175`). 그래도 허락 쪽을 만들 때 부모를 쓰는 조건 (자동 상속 · 넘긴 허락 쪽 없음 · `DACL_DEFAULTED`) 이 **하나도 안 맞아서** 부모 줄은 안 섞인다 (`RtlpInheritAcl2 +0x134 JZ → +0x48f`) `[정적]`.
- 부모 명부로 하는 일이 **하나** 있다 — 결과 바이트엔 영향 없음 `[정적]`:
  - 부모에서 물려받을 허락 쪽에 `OWNER RIGHTS` 줄이 있나 보려고 `RtlpNewSecurityObject` 를 **부모만으로 한 번 더** 돌린다 (`+0x181e` 재귀 → `+0x1846 RtlpOwnerAcesPresent`).
  - 있으면 `+0x1b22 SeAccessCheck` 로 `WRITE_DAC` 을 묻고, 못 받으면 만들기 실패. 루트 명부에 그 줄이 있나는 `[VM]`.

### 2.5 주인 · 소속은 만든 쪽 신분증에서 (질문 2)

#### 새 말 — 만든 쪽 신분증 (`SubjectContext`)

- 지금 객체를 만드는 스레드가 들고 있는 **신분증 묶음** 이다. `ObpAssignSecurity` 가 `AccessState+0x20` 으로 넘긴다 (2.2 줄 ①).
- 묶음 안에 신분증이 둘 있을 수 있다 `[정적]`:
  - **남 흉내 중일 때의 신분증** (ClientToken, `[RDI]`) — 있으면 이것.
  - **가게 자기 신분증** (PrimaryToken, `[RDI+0x10]`) — 흉내 중이 아니면 이것.
  - (`RtlpNewSecurityObject +0x1c5 MOV R8,[RDI]` · `+0x1ce JNZ` · `+0x1d4`)
  - "흉내" (impersonation) 는 다른 손님의 신분증을 잠깐 빌려 일하는 것으로 알려져 있다 `[추측]` (일반적으로 알려진 설명).
- smss 는 흉내를 안 내므로 **smss 가게 자기 신분증** 일 것이다 `[추측]`.

#### 어느 칸을 읽나 `[정적]` (`RtlpNewSecurityObject`)

| 무엇 | 신분증 칸 | 줄 |
|---|---|---|
| 주인 후보 목록 | `UserAndGroups` (`+0x98`) | `+0x1dc` |
| 그중 몇 번째 | `DefaultOwnerIndex` (`+0x90`) | `+0x1e3` |
| → 주인 SID | `UserAndGroups[DefaultOwnerIndex].Sid` (칸 16B × 번호) | `+0x202` |
| 소속 | `PrimaryGroup` (`+0xa8`) | `+0x1ea` |
| (신분증 기본 허락 쪽) | `DefaultDacl` (`+0xb8`) | `+0x1f4` |
| (신뢰 등급) | `+0xd0` 번째 칸 | `+0x21d SepLocateTokenIntegrity` |

- 이 SID 들은 `+0x2ad ExAllocatePool2(0x100, 'SeSd')` **한 덩어리** 에 복사해 둔다.

#### 고르는 법 `[정적]`

1. 넘긴 명부에 주인이 **없다** (오프셋 0).
2. `+0x459 TEST CL,0x20` — "주인은 부모에서" 옵션 (`SEF_DEFAULT_OWNER_FROM_PARENT`) 이 **꺼져 있다** (Ob 는 안 준다).
3. → **신분증의 주인 SID** 를 쓴다. 소속도 같은 식 (`+0x48f TEST CL,0x40`).
4. 못 찾으면 실패 — 주인 `0xC000007C`, 소속 `0xC000005B`.

#### 그래서

- flow.md 3장 run98 절 비유의 "주인 칸은 시청이 **세운 사람의 신분증** 을 보고 채운다" 가 **`[추측]` → `[정적]`** 이 됐다 (3절).
- **`SE_OWNER_DEFAULTED 0x1` · `SE_GROUP_DEFAULTED 0x2` 는 안 켠다** `[정적]` — `Control` 을 만드는 줄 (`+0x58e ~ +0x5ac`, `+0xfc8 ~ +0xfdf`, `+0x1102 ~ +0x1119`) 에 그 비트가 없다.
  - 비유: 신분증 보고 채워 넣지만 "**(기본값으로 채움)**" 이라는 꼬리표는 안 단다.
- **실제 SID 값은 모른다** `[VM]`. smss 가 SYSTEM 신분증이면 주인 `S-1-5-32-544` · 소속 `S-1-5-18` 일 것 `[추측: 결과서, SYSTEM 이 만든 것의 흔한 모양]` → 동적 ④.

### 2.6 ★ 허락 쪽 — 넓은 이름표를 푼다, 상속 전용 줄은 빼고 (질문 3)

#### 새 말 — generic 권한 · 풀이표 (`GenericMapping`)

- **generic 권한** = "**읽기 / 쓰기 / 실행 / 전부**" 같은 **넓은 이름표**. 객체 종류마다 다르게 풀리고, **명부가 객체에 붙을 때 그 객체용 구체 권한으로 바뀐다** `[정적]` (이번 바퀴 — 바뀌는 줄은 `RtlpCopyAces +0x146 ~ +0x1a5`).
  - 비트: `0x80000000` 읽기 · `0x40000000` 쓰기 · `0x20000000` 실행 · `0x10000000` 전부 (결과서 질문 3-가의 비트 31 · 30 · 29 · 28).
  - 느슨한 명부의 `0xE0000000` = 읽기 · 쓰기 · 실행, `0x10000000` = 전부 ([run98 해설 2.5](run98-rpc-dir-create-해설.md)).
- **풀이표** (`GenericMapping`) = 형마다 하나씩 있는 **"넓은 이름표 → 구체 권한" 표**. 칸이 넷 (읽기 · 쓰기 · 실행 · 전부) 이다.
- 비유: 명부에 "**읽기 OK**" 라고 크게만 써 두면, 방 종류 (디렉터리) 의 풀이표를 보고 "**목록 보기 · 이름 찾기**" 같은 세부 칸으로 바꿔 적는다. 사물함 종류가 다르면 같은 "읽기 OK" 도 다른 세부 칸이 된다.

#### 디렉터리 풀이표 — 숫자 넷 `[정적]`

| 칸 | 값 |
|---|---|
| 읽기 (GenericRead) | `0x20003` |
| 쓰기 (GenericWrite) | `0x2000c` |
| 실행 (GenericExecute) | `0x20003` |
| 전부 (GenericAll) | `0xf000f` |

- 어디서 왔나: `ObpDirectoryMapping` (rva `0xc7fe70`, 파일 바이트) → `ObInitSystem +0x2a0` · `+0x2df` 로 초기화 구조체 `+0xc` → 형 객체 `+0x4c` → `ObpAssignSecurity +0x61` 이 읽어 넘김.
- (참고) 신분증 풀이표 `SepTokenMapping` = `{0x2001a, 0x201e0, 0x20005, 0xf01ff}` (2.11 에서 씀).

#### 한 줄을 푸는 차례 — 단계별로 `[정적]` (`RtlpCopyAces`)

1. `+0x13e` — 줄을 **그대로** 복사한다. (복사 함수는 별칭 rva `0x6c3640`, 이름 후보 4개 — run 문서 보탬 ③.)
2. 형이 `0..0xa` · `0xd` · `0xe` 인가 (`+0x146`). 허용 줄 (형 0) 은 해당.
3. **`+0x14e` — 상속 전용 (`0x08`) 이면 4 ~ 6 을 건너뛴다** (2.2 줄 ②).
4. 마스크의 비트 31 · 30 · 29 · 28 을 하나씩 보고, 켜져 있으면 풀이표의 그 칸을 **OR** 한다 (`+0x15b` · `+0x161` · `+0x16a` · `+0x173`).
5. 넓은 이름표 4비트를 지운다 (`+0x17c AND EAX,0xfffffff`).
6. 허용 · 거부 형이면 **`& 전부 칸`** (`+0x190` 비트표 `0x673` → `+0x1a3`). 감사 · 경보 형이면 `& (전부 | 0x1000000)`.

#### 7줄에 넣어 보면 `[정적]`

| # | SID | 플래그 | 넘긴 마스크 | 상속 전용? | 붙는 마스크 |
|---|---|---|---|---|---|
| 0 | `S-1-1-0` | 0 | `0xE0000000` | 아니오 | **`0x2000f`** |
| 1 | `S-1-5-12` | 0 | `0xE0000000` | 아니오 | **`0x2000f`** |
| 2 | `S-1-5-32-544` | 0 | `0x10000000` | 아니오 | **`0xf000f`** |
| 3 | `S-1-1-0` | `0x0b` | `0xE0000000` | 예 | `0xE0000000` 그대로 |
| 4 | `S-1-5-12` | `0x0b` | `0xE0000000` | 예 | `0xE0000000` 그대로 |
| 5 | `S-1-5-32-544` | `0x0b` | `0x10000000` | 예 | `0x10000000` 그대로 |
| 6 | `S-1-3-0` | `0x0b` | `0x10000000` | 예 | `0x10000000` 그대로 |

- **0번 줄을 한 단계씩** (결과서 표의 풀이 그대로):
  - `0xE0000000` = 읽기 · 쓰기 · 실행 → `0x20003 | 0x2000c | 0x20003` = `0x2000f`
  - 넓은 이름표 비트 지움 → 그대로 `0x2000f`
  - `& 0xf000f` → **`0x2000f`**
- **2번 줄**: `0x10000000` = 전부 → `0xf000f` → `& 0xf000f` → **`0xf000f`**.
- 3 ~ 6번은 3단계에서 건너뛰어 **마스크도 플래그도 그대로** 다 (`AceFlags` 도 안 지움, `RtlpCopyAces +0x1a8 ~ +0x1b0` 의 지울 비트 = 0).

#### 상속 전용 줄은 왜 안 풀까 — `[추측]` 내 짐작

- 근거: 상속 전용 줄은 **이 방 자신에겐 안 쓰이고**, 방 안에 새로 생길 물건에 물려줄 줄이다 ([run98 해설 2.5](run98-rpc-dir-create-해설.md) "상속 전용 줄").
- 그래서: 물려받을 물건은 **디렉터리가 아닐 수도** 있다 (run98 해설의 예: `\RPC Control\epmapper` 같은 ALPC 포트). 지금 디렉터리 풀이표로 풀어 버리면 그 물건 종류엔 틀린 권한이 된다.
- 그러니 **넓은 이름표인 채로 두었다가, 물려받는 물건의 풀이표로 그때 푸는 것** 으로 보인다.
- 아직 확인 아님: "물려받을 때 푼다" 는 줄 (`RtlpGenerateInheritedAce` 쪽) 은 이번에 안 읽었다 (Q184 ⑥ 쪽 길).

#### 줄은 다 그대로 복사한다 — 순서 · 개수 `[정적]`

- 자동 상속이 꺼진 넘긴 허락 쪽은 `RtlpInheritAcl2` 모드 1 (`RtlpNewSecurityObject +0x1668`) → "전부 복사" 갈래 (`RtlpInheritAcl2 +0x208 JZ → +0x2f4` → `+0x290 RtlpCopyAces`).
- **7줄 모두, 차례 그대로** 복사한다. 상속 전용 줄도 지우지 않는다.
- 풀기는 **한 번만** 한다. `RtlpNewSecurityObject` 의 마지막 복사에도 같은 풀기 루프 (`+0x13e2 ~ +0x1480`) 가 있지만, `RtlpInheritAcl2` 가 새 목록을 만들었으면 건너뛴다 (`+0x13b3`).

#### 크기 칸을 다시 잰다 — `0xb8 → 0x9c` `[정적]`

- `RtlpInheritAcl2 +0x1b1 ADD SI,8` · `+0x1b5 ADD SI,R12W` · `+0x1bb MOV [RBX+2],SI` = `8 + 148 = 0x9c`.
  - 148 = 줄 크기 합 `20+20+24+20+20+24+20` (run 문서 · 결과서). 24 짜리 둘은 SID 가 긴 `S-1-5-32-544` 줄 (2번 · 5번).
  - 8 = 목록 머리.
- `AceCount` = 7 (복사할 때마다 하나씩, `RtlpCopyAces +0x1b4`), 리비전 = 2.
- **run98 숫자와 이어 보기**: run98 해설은 느슨한 명부 허락 쪽을 "쓰인 건 156B, 뒤 28B 는 안 씀" 이라고 적었다. `0x9c` = 156 이다. 즉 관리사무소는 **안 쓴 빈칸을 버리고 실제로 쓴 만큼만** 크기 칸에 적는다.
  - 비유: 넉넉한 종이에 써 온 명부를, 내용이 딱 맞는 종이에 옮겨 적는 것.

#### `Control` 에도 — `+0x4` `[정적]`

- 허락 쪽이 생겼으니 `Control |= 0x4` (`+0x110f`). 2.8 에서 다른 비트와 같이 본다.

### 2.7 특수 쪽 — 신뢰 등급 표는 바이트 그대로 (질문 4)

#### 넘긴 신뢰 등급 표가 붙는 길 — 단계별로 `[정적]`

1. 형의 등급 마스크가 0 일 때만 (`+0x781 JZ → +0xbd3`) 넘긴 특수 쪽에서 `0x11` 줄을 찾는다. 디렉터리는 0 → 찾는다.
2. 그 줄의 플래그가 "상속 전용뿐 (`== 8`)" 이거나 `INHERITED 0x10` 가 있으면 무시. 우리는 플래그 0 → 쓴다.
3. 다시 만들 때 검사 (`+0xdb0 ~ +0xee1`): SID 권한이 `{0,0,0,0,0,0x10}` 아님 · 플래그 `& 0xffffffe0` · 마스크 `& 0xfffffff8` (`+0xe38`) 이면 `0xC000000D`. 우리 값 (플래그 0 · 마스크 1) 은 통과.
4. `RtlpInheritAcl2` **모드 3** (`+0x155e`) 이 이 줄을 복사한다 → `RtlpCopyAces` → `RtlpCopyEffectiveAce` (형 > `0xe` 는 통째 복사 후 `AceFlags &= 0xe0`, 플래그 0 이라 변화 없음).
5. `+0xf73 RtlpCombineAcls` 가 특수 쪽 조각을 형 차례로 모은다 → **`{리비전 2, AclSize 0x1c, AceCount 1}` + 등급 표 20B**.

- 부모의 특수 쪽은 "출력에 이미 `0x11` 이 있으면 안 섞음" (`RtlpInheritAcl2 +0x5ab RtlFindAceByType`) 이라 안 섞인다.
- **run98 숫자와 이어 보기**: `0x20 → 0x1c`. run98 해설은 "쓰인 건 28B" 라고 적었다. `0x1c` = 28 이다. 허락 쪽과 같은 이야기다.

#### 새 말 — 특권

- **특권** (privilege) = 신분증에 따로 찍혀 있는 **특별 허가 도장** 으로 알려져 있다 `[추측]` (일반적으로 알려진 설명). 이번엔 둘이 나온다:
  - `SeSecurityPrivilege` — 감사 줄 (특수 쪽의 감사 기록) 을 명부에 넣을 때 필요 `[정적: 갈래]`
  - `SeRelabelPrivilege` — 내 등급보다 높은 등급 표를 붙일 때 필요 `[정적: 갈래]`

#### 등급 표만 있으면 특권을 안 묻는다 — 단계별로 `[정적]`

1. `+0x116d CMP BL,1` — 유저 쪽에서 온 부름인가. smss 는 유저 쪽 → 계속.
2. `+0x1172 CMP byte [RBP-0x7f],0` — 넘긴 특수 쪽에 **등급 표가 아닌 줄** 이 있었나 (모드 2 가 켜는 표시). 우리는 등급 표뿐 → **안 켜짐**.
3. → 특권 검사 `+0x1ec3 SePrivilegeCheck(SeSecurityPrivilege)` 로 **안 간다.**

- 만약 감사 줄이 있었고 특권이 없으면? → 특수 쪽을 **버리지 않고 실패** 한다 (`+0x1eed 0xC0000061`).
- 비유: 명부 특수 쪽에 "**신뢰 등급 표만**" 있으면 관리사무소는 특별 허가 도장을 확인하지 않는다. "**감사 기록 줄**" 이 끼어 있으면 도장을 보자고 하고, 없으면 접수를 거절한다.

#### 새 말 — 등급 이기기 (`RtlSidDominates`)

- 두 등급 SID (`S-1-16-x`) 의 **마지막 숫자를 견줘서, 신분증 쪽이 크거나 같은가** 를 보는 함수다 `[정적]` (결과서 `RtlSidDominates.c`).
- `+0xfea TEST R9B,8` (특권 검사 생략 옵션) 이 없으면 `+0x1022` 에서 부른다. 못 이기면 `+0x1c99 SePrivilegeCheck(SeRelabelPrivilege)`.
- smss 를 `S-1-16-16384` 로 가정하면 `S-1-16-4096` (낮음) 을 이긴다 → 통과 `[추측: smss 무결성 값]`.

#### 넘긴 등급 표가 **없을 때** — 규칙 표 `[정적]`

이번 방엔 해당 없지만, 에뮬레이터가 다른 객체를 만들 때 쓴다. 2.11 (신분증) 에서 바로 쓰인다.

| 조건 | 결과 |
|---|---|
| 형 `SeMandatoryLabelMask ≠ 0` | `{플래그 0, 마스크 = 형 마스크, SID = 만든 쪽 등급}`. 이때는 넘긴 명부에서 등급 표를 찾지도 않고, 있으면 그 마스크에 형 마스크를 OR (`SeComputeAutoInheritByObjectTypeEx +0x130`) |
| 형 마스크 0, 만든 쪽 등급 `< 0x2000` (Medium 미만) | `{플래그 0, 마스크 1, SID = 만든 쪽 등급}` |
| 그 밖 | 안 붙임 (부모 특수 쪽에 물려줄 등급 표가 있으면 모드 3 이 만들 수 있음) |

### 2.8 ★ `Control` — `0x14` 가 `0x8814` 가 되기까지 (질문 5)

#### 비트 하나씩 `[정적]`

| 비트 | 켜지나 (`\RPC Control`) | 왜 |
|---|---|---|
| `SE_SELF_RELATIVE 0x8000` | 켜짐 (늘) | 결과는 늘 한 덩어리 꼴 (`+0x58e` · `+0x598`) |
| `SE_DACL_PRESENT 0x4` | 켜짐 | 허락 쪽이 있음 (`+0x110f`) |
| `SE_SACL_PRESENT 0x10` | 켜짐 | 특수 쪽이 만들어짐 (`+0xfd3 ~ +0xfdc`) |
| **`SE_SACL_AUTO_INHERITED 0x800`** | **켜짐** | 아래 단계별 |
| `SE_DACL_AUTO_INHERITED 0x400` | 안 켜짐 | 허락 쪽 자동 상속 꺼짐 (2.4, `+0x10aa`) |
| `*_PROTECTED` · `*_DEFAULTED` (DACL · SACL) | 넘긴 명부에 있으면 옮김 — 우리는 없음 | `& 0x1408` (`+0x1106`) |
| `SE_OWNER_DEFAULTED` · `SE_GROUP_DEFAULTED` | 안 켜짐 | 2.5 |

- 조립: `+0x124b OR word [R14+2],R13W` · `+0x1250 MOV byte [R14],1`. 결과 = `0x8000 | 0x800 | 0x10 | 0x4` = **`0x8814`**.

#### `0x800` 은 왜 켜지나 — 단계별로 `[정적]`

이상하게 보이는 곳이다. 허락 쪽 자동 상속은 꺼져 있는데 (2.4), 특수 쪽엔 "자동 상속됨" 비트가 켜진다.

1. 등급 표 갈래를 부를 때 (`+0x155e RtlpInheritAcl2` 모드 3), 자동 상속 인자를 **상수 1** 로 넘긴다 (`+0x1559`).
   - 허락 쪽 갈래 (`+0x1668`) 는 스위치 값 `& 1` = 0 을 넘긴다 (`+0x1663`). **두 갈래가 다른 값을 넘기는 것** 이 핵심이다.
2. `RtlpInheritAcl2 +0xd3 ~ +0xe9` 가 그 인자 1 을 보고 **출력 플래그 `0x400`** 을 낸다.
3. `RtlpNewSecurityObject +0x1599` 가 그 플래그를 읽는다.
4. `+0xfc8 ~ +0xfdc` 에서 계산해 `0x810` (= `SACL_PRESENT 0x10` | `SACL_AUTO_INHERITED 0x800`) 을 `Control` 에 더한다.

- 비유: 관리사무소가 특수 쪽 (등급 표) 을 옮겨 적을 땐 **늘 "자동 상속 모드" 로 옮겨 적는 서식** 을 쓴다. 그래서 서식에 "자동 상속됨" 칸이 체크된 채 나온다. 허락 쪽은 다른 서식이라 체크가 없다.
- 왜 등급 표만 늘 그 모드인지는 코드에 안 쓰여 있다 — 모른다.

#### 확신이 가장 낮은 한 곳

- 결과서 · run 문서 모두 "**코드 줄은 분명하지만 이 바퀴에서 확신이 가장 낮은 칸**" 이라고 적었다.
- 그래서 VM 대조 **1순위** 다 (동적 ①). 실제가 `0x8014` 면 1번 (`+0x1559` 인자) 이나 3번 (`+0x1599` 읽기) 을 다시 본다.
- `0x10` 대답의 `Control 0x8810` 도 같은 비트에 기대고 있다 (2.10).

### 2.9 저장 — 보관함에 넣고 헤더엔 쪽지만 (질문 1 끝)

#### 새 말 — 명부 보관함 (SD 캐시)

- `ObsSecurityDescriptorCache` — 관리사무소가 **같은 바이트의 명부를 한 장만** 두는 보관함이다 `[정적]`.
- 비유: flow.md 의 "**시청 서고**". 방이 여러 개여도 내용이 똑같은 명부면 서고에 한 장만 두고, 방마다 "서고 ○번 칸" 쪽지를 붙인다.

#### 새로 달기 서랍 (EDX=3) 이 하는 일 — 차례대로 `[정적]` (`SeDefaultObjectMethod`)

1. **크기 재기** — `0x14` + 주인 · 소속 · 허락 쪽 · 특수 쪽 각각 4 맞춤 (`+0xaf ~ +0x161`).
2. **바이트로 해시** (`+0x172 ~ +0x18e`) → 보관함에서 같은 해시 · 같은 크기 · 같은 바이트를 찾는다 (`+0x213 ~ +0x33e`).
3. 있으면 **참조만 하나 늘린다** (`+0x340`). 없으면 `+0x277 ExAllocatePool2` (태그 `ObSc`) 로 `머리 0x20 + 명부 사본` 을 만든다 (`+0x29f` 복사).
4. `RtlpNewSecurityObject` 가 만든 임시 명부는 놓는다 (`+0x395`).
5. 객체 헤더 `[몸통-8]` 에 `항목+0x20 | 0xf` 를 쓴다 (`+0x3a3` · `+0x3a7`).

#### 그래서

- **붙은 명부 바이트 = `RtlpNewSecurityObject` 가 만든 바이트 그대로** (사본) 다. 보관함은 바이트를 바꾸지 않는다.
- run97 동적 ① 의 "헤더 명부 칸 = 몸통 `-8` 값 `& ~0xf`" 가 이 5번 줄로 **정적으로도 섰다** (run 문서).
- `\Windows` 가 처음 받는 명부도 같은 smss 명부라, **처음엔 같은 보관함 칸** 일 것이다 `[추측: 같은 입력 · 같은 만든 이면]` → 동적 ②. (뒤에 csrss 가 `\Windows` 허락 쪽을 바꾸면 달라진다 — run98.)

### 2.10 ★ 그래서 바이트는 — 저장 차례와 대답 차례가 다르다 (질문 7)

#### 저장 차례 `[정적]`

- 붙은 명부 (= 보관함 안) 의 차례는 **머리 → 특수 쪽 → 허락 쪽 → 주인 → 소속** 이다 (`RtlpNewSecurityObject +0x1225` 조립).
- run97 의 **대답 (사본) 차례는 머리 → 주인 → 소속 → 허락 쪽 → 특수 쪽** 이었다.
- 둘이 **거꾸로에 가깝다.** 그래서 같은 명부라도 "보관함 바이트" 와 "대답 바이트" 는 오프셋이 다르다.

| 머리 칸 | 붙은 명부 (저장) | `0x17` 대답 |
|---|---|---|
| `+0x2` `Control` | `0x8814` | `0x8814` |
| `+0x4` Owner | `0xcc` | `0x14` |
| `+0x8` Group | `0xcc + 주인 크기` (가정 `0xdc`) | `0x24` (가정) |
| `+0xc` Sacl | `0x14` | `0xcc` |
| `+0x10` Dacl | `0x30` | `0x30` |
| 총 길이 | `0xe8` (가정) | `0xe8` (가정) |

- 읽는 법: 저장에선 특수 쪽 (28B) 이 머리 바로 뒤 (`0x14`) 라 허락 쪽이 `0x14 + 0x1c = 0x30`. 대답에선 주인 16B · 소속 12B 가 먼저라 허락 쪽이 `0x14 + 16 + 12 = 0x30`. **우연히 허락 쪽 자리만 같다** — 앞에 오는 조각이 둘 다 28B 이기 때문이다 (가정 크기에서).
- 총 길이 셈 (run 문서, flow-writer 가 다시 셈): `0x14 + 16 + 12 + 0x9c + 0x1c = 0xe8`.

#### `0x10` (라벨만) 대답 — 통째로 `[정적]`

주인 · 소속 · 허락 쪽을 안 물으니 **`[VM]` 칸이 하나도 없다.** run 문서 그대로:

```
0000  01 00 10 88 00 00 00 00 00 00 00 00 14 00 00 00
0010  00 00 00 00 02 00 1c 00 01 00 00 00 11 00 14 00
0020  01 00 00 00 01 01 00 00 00 00 00 10 00 10 00 00
```

- `01 00` = Revision 1 · Sbz1 0
- `10 88` = `Control 0x8810` (`0x8000 | 0x810`, 허락 쪽 비트 `0x4` 는 안 물어서 안 옮김 — run97 규칙)
- `14 00 00 00` (`+0xc`) = 특수 쪽 오프셋 `0x14`, 나머지 오프셋 0
- `02 00 1c 00 01 00 00 00` = 특수 쪽 머리 (리비전 2 · `AclSize 0x1c` · `AceCount 1`)
- `11 00 14 00 01 00 00 00` = 등급 표 줄 (형 `0x11` · 플래그 0 · 크기 `0x14` · 마스크 1)
- `01 01 00 00 00 00 00 10 00 10 00 00` = SID `S-1-16-4096`
- 길이 `0x30`.

#### `0x17` 대답 — 머리만 읽어 보기

전체 16줄은 run 문서 "에뮬레이터가 돌려줄 대답 바이트". 첫 두 줄만:

```
0000  01 00 14 88 14 00 00 00 24 00 00 00 cc 00 00 00
0010  30 00 00 00 [01 02 00 00 00 00 00 05 20 00 00 00
```

- `14 88` = `Control 0x8814`. 그다음 Owner `0x14` · Group `0x24` · Sacl `0xcc` · Dacl `0x30` (위 표의 오른쪽 칸).
- `[` 부터가 주인 SID (가정 `S-1-5-32-544`). `[ ]` 칸은 **`[VM]`** — 주인 `0x14 ~ 0x23`, 소속 `0x24 ~ 0x2f`.
- **첫 부름** (봉투 NULL · 길이 0) 은 "봉투가 작아요" `0xC0000023` + 필요 길이 `0xe8` (run97 · run99 최소 조건 3).

#### 이 표는 어디서 나왔나

- 숫자는 `ms/` 에서 읽은 값 (smss `.asm` SID 줄, `ObpDirectoryMapping` 파일 바이트) + 위 규칙으로 **만든 것** 이라 `[정적]` 이다. 실제로 떠 본 바이트가 아니다.
- 그래서 주인 · 소속 칸은 `[VM]`, 그리고 `Control` 의 `0x800` 은 2.8 의 낮은 확신을 그대로 안고 있다.

### 2.11 신분증 (토큰) 객체 명부 — 신뢰 등급 표가 늘 붙는다 (질문 6)

run97 해설 2.8 에서 "`0x11` 을 기본으로 붙이나는 `[공백]`" 으로 남긴 곳이다.

#### 왜 신분증 형은 1, 디렉터리 형은 0 인가 — 단계별로 `[정적]`

형을 만들 때 넘기는 **초기화 구조체의 길이** 가 갈림길이다.

1. `ObCreateObjectTypeEx +0x45c ~ +0x464` — 구조체 길이가 **`0x80` 이상일 때만** 구조체 `+0x78` 칸을 형 `+0xd8` (`SeMandatoryLabelMask`) 로 옮긴다.
2. **신분증 형** — `SepTokenInitialization` 이 길이를 `0x80` 으로 두고 (`+0x29` · `+0x4e`), `+0x78` 칸에 1 을 쓴다 (`+0x59 MOV EBX,1` · `+0x8a`). → 형 `+0xd8` = **1**.
3. **디렉터리 형** — `ObInitSystem +0x219` 가 길이를 `0x78` 로 둔다. → 1번 조건이 안 맞아 형 `+0xd8` = **0**.

- 비유: 형 등록 서류에 "**새 물건엔 등급 표 자동 부착**" 칸이 있는데, 디렉터리는 **그 칸이 없는 옛 서식** 으로 냈고, 신분증은 **그 칸이 있는 새 서식** 에 1 을 적어 냈다.

#### 그래서 신분증 명부는 `[정적]`

- 신분증은 이름 없는 객체라 `ObInsertObjectEx` 명부 계산 블록을 탄다 (2.3): `+0x282` → `+0x2c8 SeComputeAutoInheritByObjectTypeEx` (신분증은 `0x100` = NO_WRITE_UP) → `+0x325 SeAssignSecurityEx2` → `+0x38c SeDefaultObjectMethod` (EDX=3).
- 넘긴 명부가 없을 때 (`NtDuplicateToken` 에 SD 가 없을 때 보통) `RtlpNewSecurityObject` 는 빈 명부 (`+0x621` · `+0x637`) 를 넘긴 명부로 쓴다. 결과:
  - 주인 · 소속 = 만든 쪽 신분증 (2.5)
  - 허락 쪽 = 만든 쪽 신분증의 `DefaultDacl` 사본 + **신분증 풀이표** 로 풀기 한 번 (`+0x10c6` · `+0x10d6`, `+0x13e2 ~ +0x1480` 루프). 기본 허락 쪽이 NULL 이면 허락 쪽 없음.
  - **특수 쪽 = 등급 표 `0x11` 하나** `{플래그 0, 마스크 1, SID = 만든 쪽 등급}` — 2.7 규칙 표의 첫 줄이다.
  - `Control` = 허락 쪽이 있으면 `0x8814`.
- 넘긴 명부에 등급 표가 있으면 그 마스크에 `| 1` (`SeComputeAutoInheritByObjectTypeEx +0x130`).

#### 아직 안 닫힌 절반

- 등급 표 SID = 신분증을 **만든 순간의 만든 쪽 등급** → `[VM]`.
- `NtDuplicateToken` 이 명부 없이 불렸을 때 **뒤에 더 붙이는 것** (`+0x21e SepAppendAceToTokenObjectAcl` · `+0x338 SepSetProcessTrustLabelAceForToken` → `0x14`, run97) 은 이번에 안 읽었다. 신분증 명부의 **최종 모양** 은 그 둘까지 읽어야 닫힌다 → Q184 ⑤.
- 즉 run97 의 `[공백]` 은 "**`0x11` 이 붙나?**" 에 대해서만 닫혔다 — **붙는다** `[정적]`.

### 2.12 test.exe 길에 있나 — 같은 함수는 지나간다. 그래도 그림은 그대로

- **`\RPC Control` 사슬은 test.exe 초기화 밖** 이다. 부팅 때 smss 가 부른다 (run98).
- **같은 `ObInsertObjectEx` 는 test.exe 를 만들 때도 있다** `[정적: 지도]` — `_map/NtCreateUserProcess_edges.tsv` 에 caller `PspInsertProcess +0x1de` (깊이 2) · `PspInsertThread +0x3e5` (2) · `SeSubProcessToken +0x80e` (4) 등.
  - 지도에선 `ObInsertObjectEx` 가 caller 63곳인 **공용 도구** 라 안을 안 펼쳤다. 그래서 이번 사슬은 지도에서 안 보였고, 따로 export 해야 했다 (run 문서 "도구 메모").
- **test.exe 신분증** (`SeSubProcessToken +0x80e`) 은 이름 없는 길 → 2.11 형 규칙으로 **등급 표 `0x11` (마스크 1 이상) 이 있다** `[정적: 형 규칙]`.
  - 만든 쪽 = 부모 cmd 스레드라 SID 는 cmd 의 등급일 것 `[추측]`.
  - `SeSubProcessToken` 이 넘기는 명부와, 뒤 `+0x847 SepAppendAceToTokenObjectAcl` · `+0x85b SepFinalizeTokenAcls` 가 무엇을 바꾸나는 안 봤다 `[공백]` → Q184 ② · ⑤.
- 프로세스 · 스레드 객체가 이 명부 블록을 타는지 (형 `SecurityRequired`) 는 안 봤다 `[공백]` → Q184 ⑧.
- 그래서 **그림은 안 고친다** — 새 함수들은 이미 있는 `nt!ObInsertObjectEx` 노드 (`PspInsertProcess` 의 "객체 등록") **안쪽** 이고 (대표 지점 규칙), `\RPC Control` 사슬은 지도 밖이다.

### 2.14 결과서와 다르게 적은 곳 · 보탠 것 (짧게)

run 문서 "결과서와 다르게 적은 곳 · 보탠 것". **다르게 적은 곳은 없다** (flow-writer 가 다시 본 줄 모두 일치).

- ① (보탬) `ObpAssignSecurity +0x4c SeComputeAutoInheritByObjectTypeEx` 의 **call 자리**. 결과서는 출력을 합치는 줄 (`+0x6d ~ +0x74`) 만 적었다.
- ② (보탬) `RtlpNewSecurityObject` 가 `RtlpInheritAcl2` 를 부르는 자리는 **넷** — `+0x85b` · `+0xaef` · `+0x155e` · `+0x1668`. 앞 두 자리 중 어느 것이 모드 2 (등급 표 아닌 특수 쪽) 인지는 안 가렸다. 결과 바이트엔 영향 없음 → Q184 ⑦.
- ③ (보탬) 복사 함수는 별칭 — rva `0x6c3640`, run97 ③ 과 같은 주소 (이름 후보 `RtlCopyMemory` · `RtlMoveMemory` · `memcpy` · `memmove`).
- ④ (보탬) test.exe 길 — `ObInsertObjectEx` caller 자리 셋 (2.12).
- ⑤ (보탬, `[추측]`) run99 의 rpcrt4 `RtlNewSecurityObjectEx` 6번째 인자 `1` 이 자동 상속 플래그라면 `[추측: 공개 원형]`, **커널 쪽 규칙으로는** 부모 (`\RPC Control`) 의 상속 전용 줄 넷 (`0x0b`) 이 rpcrt4 기본 명부에 섞이는 갈래다. 그런데 ntdll 의 같은 이름 함수는 **다른 바이너리** 라 이 근거로는 말할 수 없다 → Q186 ① 힌트.
- run97 문서의 두 줄 (토큰 `0x11` `[공백]` · 정적 ①) 끝에 **(해결됨 → run100, Q180d)** 가 붙었다. 원래 글은 그대로다.

### 2.15 디버거 메모 — 함정 둘

- **이름 있는 객체와 이름 없는 객체는 계산 자리가 다르다** (run 문서 "함정 후보").
  - 이름 있는 쪽 (`\RPC Control`) = `nt!ObpAssignSecurity+0xd9`
  - 이름 없는 쪽 (신분증) = `nt!ObInsertObjectEx+0x325`
  - 한 자리에만 멈춤점을 걸면 다른 쪽은 "**안 걸림**" 이지 "**안 탐**" 이 아니다. (run99 해설 2.14 의 "같은 callee 는 모든 자리에" 와 같은 이야기다.)
- **부팅 중에 멈추면 smss 시간이 바뀔 수 있다** `[추측]` — 그래서 만들 때를 잡는 동적 ⑥ 보다, 부팅 뒤 붙은 명부를 읽는 ① 이 낫다 (run98 과 같은 판단). 이번에 읽은 줄 안에 디버거 칸을 읽는 줄은 없다.

### 2.16 정리 — 비유로 한 번 더

- 관리인 (smss) 이 부팅 때 관리사무소 창구에 "`\RPC Control` 방 하나, **이 명부** 붙여서" 를 낸다. 명부는 넉넉한 종이에 쓴 **느슨한 명부** 다. 주인 · 소속 칸은 비어 있다.
- 창구는 먼저 명부를 **한 장짜리 사본** 으로 받는다.
- 방에 이름이 있으니 **이름 붙이는 부서** 가 받아서 윗방 (루트 `\`) 명부를 꺼내 온다. 하지만 "윗방 메모 베껴 넣기" 스위치는 **꺼져** 있다.
- 명부 담당이 **새 종이에 다시 쓴다**:
  - 주인 · 소속 — 관리인 **신분증** 을 보고 채운다. "기본값으로 채움" 꼬리표는 안 단다.
  - 허락 쪽 0 ~ 2번 — "읽기 · 쓰기 · 실행 OK" 같은 **넓은 이름표** 를 디렉터리 **풀이표** 로 풀어 적는다.
  - 허락 쪽 3 ~ 6번 — "**새 물건에 물려줄 메모**" 라서 원문 그대로 둔다.
  - 특수 쪽 — **신뢰 등급 표** 는 그대로. 감사 줄이 없으니 특별 허가 도장은 안 본다.
  - 크기 칸 — 넉넉한 종이 크기가 아니라 **실제로 쓴 만큼** (`0x9c` · `0x1c`).
  - 서식 위 체크칸 — "한 덩어리" · "허락 쪽 있음" · "특수 쪽 있음" · 그리고 특수 쪽 서식 탓에 "**특수 쪽 자동 상속됨**" (`0x8814`).
  - 순서 — 특수 쪽을 맨 앞에.
- 다 쓴 명부는 **시청 서고 (보관함)** 에 한 장 두고, 방에는 "서고 ○번 칸" 쪽지만 붙인다.
- 나중에 누가 "사본 주세요" 하면 (run97) 서고의 명부를 **다른 차례** (주인 → 소속 → 허락 → 특수) 로 잘라 준다. 그래서 대답은 `0xe8` 바이트, 라벨만이면 `0x30` 바이트.
- 신분증 객체는 등록 서류에 "**등급 표 자동 부착 = 1**" 이 적혀 있어서, 명부를 따로 안 줘도 등급 표가 **늘** 붙는다.

## 6. 요청 34 네 바퀴 한 번에 돌아보기

> 이 절은 flow.md 3장 "PE_emulator 요청 34 정적 답 한 장 (run97 ~ run100 잇기)" 과 네 run 문서에서 옮긴 것이다. 새 사실은 없다. 태그는 모두 그 표의 `[정적]` 이고, 값이 VM 몫인 칸은 Q181 이다.

### 6.1 처음 질문 — 무엇이 막혔었나

- PE_emulator 에서 `rpcrt4!UuidToStringA` 가 `0xe` 를 돌려주는 짧은 길이 있었다 (원문 `../PE_emulator/_workspace/05_tuning_planner/264_internals-rpc-security.md`, 에뮬레이터 쪽 관찰).

- 요청 34 는 이걸 셋으로 물었다:
  - **①** 커널은 "보안 정보 묻기" 에 어떻게 답하나 (권한 · 라벨만 · 바이트 꼴 · 크기만 · 형 함수)
  - **②** `\RPC Control` 방은 누가 어떤 명부로 만들고, 뒤에 누가 고치나
  - **③** rpcrt4 는 명부에서 무엇을 보고 언제 `0xe` 로 가나
- 대기열에선 Q180 하나로 받았다가, 차례가 오자 **네 바퀴 (Q180a ~ Q180d)** 로 나눴다. 넷째 (Q180d) 는 ① 과 ② 사이의 **빈칸** 이다.

### 6.2 네 바퀴가 닫은 것 — 시간 차례로 다시 놓으면

            │
(나중)  rpcrt4 ── "명부 사본 크기가 얼마예요?" ─────────────▶  run99 (Q180c, 요청 34 ③)

            │
        rpcrt4 ── 첫 대답이 "봉투가 작아요" 면 계속, 아니면 0xe   (run99)

  - run97 이 "**사본 규칙**" 을 줬지만, 재료 (원본 명부) 가 없었다.

### 6.3 에뮬레이터가 할 일 — 차례대로

flow.md "요청 34 정적 답 한 장" 의 다섯 줄 그대로다.

1. `\RPC Control` 객체 명부를 **run100 표** 로 채운다 (특수 쪽 칸 포함, `Control 0x8814`). 주인 · 소속은 smss 신분증 값 — 지금은 가정 `S-1-5-32-544` · `S-1-5-18`. (→ 2.10)
2. 첫 `NtQuerySecurityObject(h, 0x17, NULL, 0, &len)` → **`0xC0000023` + `len` = 필요 길이** (가정 `0xe8`). 이게 rpcrt4 `+0x164` 를 지나는 조건이다 (run99). (→ [run99 해설 2.2](run99-rpc-caller-해설.md))
3. 둘째 부름 → run100 의 `0x17` 대답 바이트 (run97 대답 차례). `0x10` 만 물으면 `0x30` 바이트. (→ 2.10)
4. 신분증 객체 명부에 등급 표 `{0x11, 0, 마스크 1, 만든 쪽 등급 SID}` 를 둔다 (run100). (→ 2.11)
5. 그다음 벽은 **신분증 질문** (run99 최소 조건 6 ~ 13) · 정책 레지스트리 — 요청 34 **밖** 이다. (→ [run99 해설 2.10 · 2.11](run99-rpc-caller-해설.md))

- 2번이 **가장 먼저 고칠 한 마디** 다 — 지금 에뮬레이터가 떨어지는 곳이 여기다 (run99).
- 1 · 3 · 4번은 2번을 고친 뒤 **둘째 부름 · 토큰 라벨 질문** 이 처음으로 나올 때 필요해진다.

### 6.4 VM 으로 남은 것 · 정적으로 남은 것

**VM 으로 남은 것 → Q181** (flow.md 그대로):

- 주인 · 소속 SID (smss 신분증)
- `Control` 의 `0x800` (확신 가장 낮음, 2.8)
- 신분증 등급 표 SID
- 루트 `\` 명부
- 레지스트리 값 — `ProtectionMode` · `ObjectDirectories` · `ObObjectSecurityInheritance`
- 진짜 대답 — status · 길이 · 바이트

**정적으로 남은 것** (flow.md 그대로, 대기열 번호는 `plan.md`):

- `0x20001` 접근 검사 (4장 run97 ② · run100 ②) → **Q184 ①**
- 신분증 명부 덧붙임 (run100 ①) → **Q184 ⑤** (· test.exe 쪽 `SeSubProcessToken` 은 Q184 ②)
- ntdll 쪽 `RtlpNewSecurityObject` (run99 ① · run100 힌트) → **Q186 ①**

- 정리하면: **"무엇을 돌려줘야 하나" 는 정적으로 다 정해졌고**, 남은 건 "**실제 값이 가정과 같은가**" (Q181) 와 "**그다음 벽**" (Q184 · Q186) 이다.
