# 판정 기준과 결과 문단 양식

## 판정 셋 중 하나

| 판정 | 고르는 때 | 다음 |
|---|---|---|
| **분석성공** | 요청서의 **성공 기준이 로그로 채워졌다**. 중간에 작은 실수가 있었어도 기준이 채워졌으면 이것. | flow-writer로 |
| **사용자실수** | 기준이 안 채워졌고, 원인이 **runbook대로 하지 않은 것**이다. 예: 명령 오타, 단계 건너뜀, 주소를 잘못 옮김, `.logopen` 빠짐, test.exe를 멈춤점 전에 실행, 로그 일부만 붙여넣음. | 같은 키워드로 재시도 |
| **예기치못한상황발생** | 기준이 안 채워졌고, runbook대로 했는데 **예상과 다르게** 됐다. 예: 멈춤점이 안 걸림, 예상 못 한 함수·순서, 크래시·멈춤, 주소가 바뀜, 심볼 짝 안 맞음, **runbook 자체가 틀림**. | 오케스트레이터가 사용자와 다음을 정함 |

- runbook이 틀렸으면 사용자 탓으로 돌리지 않는다. "runbook의 ○○ 단계가 틀렸다"고 그대로 쓴다.
- 로그로 확인할 수 없는 건 판정 근거로 쓰지 않는다. (사용자가 말로 한 설명은 "사용자 설명"이라고 밝힌다)
- 예상과 다른 결과도 **그 자체가 발견**일 수 있다. 버리지 말고 문단에 적는다.

## 결과 파일 — `ms/logs/NN_키워드_result.md`

**한 문단.** 무엇을 / 어떻게 / 결과 순서. 판정 단어는 굵게, 정확히 셋 중 하나의 글자 그대로.

```markdown
**무엇을**: <요청서 "확인할 것" 한 줄> (dast/NN, sast/NN 질문 n). **어떻게**: <기준점>에서 test.exe(EPROCESS `<값>`)를 얻은 뒤 <멈춤점과 필터>를 걸고 <찍은 것>을 기록했다 (`ms/logs/NN_키워드.txt`). **결과**: **<판정>** — <성공 기준과 대조한 결과: 무엇이 몇 번, 어떤 콜스택/값으로 찍혔나>. <못 본 것이나 남은 의문 한 문장>.
```

- `<...>` 자리는 로그에서 **실제로 본 값**으로만 채운다. 못 본 값은 "못 봄"이라고 쓴다.

## 오케스트레이터에게 돌려줄 말 (결과 파일과 별개)

```
판정: 사용자실수 | 예기치못한상황발생 | 분석성공
결과 파일: ms/logs/NN_키워드_result.md
새로 본 것: (한두 줄, 오프셋 포함)
재시도면 고칠 점: (runbook 몇 단계를 어떻게)
flow-writer가 볼 로그 위치: (줄 번호 범위나 ==== 표시)
```
