# pe-flow-cycle Skill

질문 하나를 **정적 → (필요하면) 동적 → 문서 → 커밋**으로 닫는 한 바퀴를 정한다.
이 스킬은 "언제 누구를 부르나"를 정하는 **메타 스킬**이라 오케스트레이터만 쓴다.

- 동적분석은 **정적분석으로 확인 못 한 것**만 본다. (VM 작업은 사람 시간이 들어서 비싸다)
- 에이전트끼리는 **파일로만** 주고받는다. 한 바퀴가 끊겨도 파일만 보면 이어서 할 수 있다.

## 파일 지도

| 파일 | 쓰는 쪽 | 읽는 쪽 |
|---|---|---|
| `_workspace/sast/NN_키워드.md` (정적 요청서) | orchestrator | decompiler |
| `_workspace/sast/NN_키워드_result.md` (정적 결과서) | decompiler | orchestrator, flow-writer, dast-mentor |
| `ms/decomp/<모듈>/*.c`, `ms/disassemble/<모듈>/*.asm`, `_calls.tsv` | decompiler | flow-writer, dast-mentor |
| `_workspace/dast/NN_키워드.md` (동적 요청서) | orchestrator | dast-mentor |
| `_workspace/dast/NN_키워드_runbook.md` (실행 안내) | dast-mentor | orchestrator → 사용자 |
| `ms/logs/NN_키워드.txt` (디버거 로그) | dast-mentor가 빈 파일 생성 → **사용자가 붙여넣음** | dast-mentor, flow-writer |
| `ms/logs/NN_키워드_result.md` (판정 한 문단) | dast-mentor | orchestrator, flow-writer |
| `runs/NN_sprint/runN-키워드.md` | flow-writer | 사람 |
| `runs/NN_sprint/flow.md` | flow-writer | 사람, 모든 에이전트 |
| `runs/NN_sprint/runN-키워드-해설.md` (해설서) | explainer | 사람 (근거로 쓰지 않는다) |
| git 커밋 | committer | 사용자 (push는 사용자가 직접) |
| `_workspace/plan.md` (분석 진행표) | orchestrator | orchestrator, 사용자 |

## 번호와 이름 규칙

- 번호는 손으로 세지 않고 스크립트로 얻는다:
  ```bash
  python3 .claude/skills/pe-flow-cycle/scripts/next_index.py next sast    # 다음 정적 NN
  python3 .claude/skills/pe-flow-cycle/scripts/next_index.py next dast    # 다음 동적 NN
  python3 .claude/skills/pe-flow-cycle/scripts/next_index.py next run     # 다음 runN
  python3 .claude/skills/pe-flow-cycle/scripts/next_index.py sprint       # 지금 스프린트 폴더
  python3 .claude/skills/pe-flow-cycle/scripts/next_index.py keyword <kw> # 키워드 검사
  ```
- sast 번호와 dast 번호는 **따로** 센다. `ms/logs` 번호 = dast 번호.
- 키워드 = **영어 소문자·숫자·하이픈** (예: `mapview`, `graph-build`). WinDbg 명령(`.logopen`)에 들어가므로 한글 금지.
- 같은 주제면 sast와 dast 키워드를 똑같이 쓴다 (나중에 찾기 쉬움).
- runN은 스프린트가 바뀌어도 이어진다 (예: 01_sprint가 run8에서 끝났으면 02_sprint는 run9부터).
- 지금 스프린트 = `runs/NN_sprint` 중 가장 큰 번호. 새 스프린트는 사용자가 말할 때만 만든다.

## 분석 순서 — 대기열(먼저 들어온 것 먼저)

다음 바퀴 주제는 `_workspace/plan.md` 의 **대기열**에서 고른다. 줄 서기와 같다: 먼저 선 사람이 먼저, 새로 온 사람은 맨 뒤.

### 처음 대기열 = 시간 순서

처음 만들 때 아래 순서로 항목을 넣는다 (flow.md 그림과 4장에서 뽑는다).

| 단계 | 범위 (flow.md 절) | 주로 | 끝났다고 보는 때 |
|---|---|---|---|
| 1. nt 지도 | 부모 cmd 스레드의 `NtCreateUserProcess`부터, test.exe 첫 스레드가 `ntdll!LdrInitializeThunk`에 도착할 때까지 (2.1 ~ 2.3) | 정적 (ntoskrnl) | 그림의 nt 함수마다 정적 callee 목록(depth 1)이 run 문서에 있고, 2.2·2.3이 `[공백]`이 아니다 (최소 `[정적]`) |
| 2. ntdll 지도 | `LdrInitializeThunk`부터 `test!main`까지 (2.4 ~ 2.10) | 정적 (ntdll) | 그림의 ntdll 함수마다 같은 작업. 2.5·2.6의 "올리기"와 의존 관계 그래프 만들기가 최소 `[정적]`으로 채워짐 |
| 3. 빈 곳 채우기 | 그때 남아 있는 flow.md 4장 공백 목록, 4.1 `?` 표 | 동적 | 대기열이 빌 때 |

- 단계 안에서도 시간 순서: flow.md 절 번호 순서, 같은 절이면 그림에서 왼쪽(caller)부터.
- 항목 하나 = 한 바퀴 = 함수 1 ~ 5개, depth 1. 모듈을 통째로 뽑지 않는다.

### 대기열 규칙

1. **다음 주제 = 위에서부터 첫 번째 "대기" 항목.** 순서를 건너뛰거나 바꾸지 않는다.
2. **새로 생긴 문제·할 일은 맨 아래에 붙인다.** 출처를 같이 적는다 (예: `sast/03 결과`, `ms/logs/02 판정`, `run10 아직 확인 필요`).
   - 단계 1·2 도중 나온 "동적으로 확인할 것"도 맨 아래로 간다. 동적은 대기열 차례가 왔을 때 한다.
   - 이미 대기 중인 항목과 **같은 것**이면 새로 붙이지 않고 그 항목에 출처만 더한다.
3. **끝난 항목은 지우지 않는다.** 상태를 `끝 (runN)` 으로 바꾼다. 기록이 남아야 나중에 따라갈 수 있다.
4. 항목이 한 바퀴에 너무 크면 **그 자리에서** 나눈다 (`Q5` → `Q5a`, `Q5b`). 맨 뒤로 보내지 않는다.
5. 차례가 온 동적 항목끼리 같은 기준점·멈춤점으로 볼 수 있으면 한 run에 묶어도 된다. 단, 묶을 수 있는 건 **연달아 있는 대기 항목**까지만.
6. 한 단계의 처음 항목이 다 끝나면 사용자에게 "단계 N 끝, 남은 공백 …"을 알리고 **멈춘다.** 다음 단계는 사용자가 "다음"이라고 할 때 시작한다.

### 애매하면 사용자에게 묻는다 (`AskUserQuestion`)

이럴 때는 정하지 말고 선택지를 보여준다:
- 새 문제가 **지금 항목을 막는다** (그게 풀려야 지금 바퀴를 끝낼 수 있다) → "새 항목을 지금 먼저 할까 / 지금 항목을 보류하고 둘 다 맨 뒤로 / 지금 항목을 아는 만큼만 끝낼까"
- 새 문제가 기존 항목과 **같은지 다른지** 헷갈린다
- 새 문제인지 **디버거 때문에 생긴 잡음인지** 헷갈린다
- 사용자가 대화 중에 주제를 꺼냈는데 **지금 하자는 건지, 줄에 세우자는 건지** 분명하지 않다 (분명하게 "지금"이라고 하면 바로 한다)
- 처음 대기열을 만들 때 항목 순서가 flow.md만으로 정해지지 않는다
- 항목을 끝났다고 봐도 되는지 애매하다 (끝 조건을 반만 채움)

묻는 건 한 번에 하나. 답을 받으면 진행표 "결정 기록"에 한 줄 남긴다.

### 첫 바퀴

- ntoskrnl analyze는 오래 걸리니 맨 먼저 뒤에서 걸어 둔다 (decompiler). 기다리는 동안 서버 메모리에 여유가 있으면 ntdll analyze로 스크립트를 시험해도 된다 (단계 2 준비, 대기열 순서는 그대로).

## Workflow

1. **상태 보기** (매 대화 시작, 그리고 사용자가 "어디까지 했지?" 할 때)
   - `_workspace/plan.md` 를 읽는다. 없으면 [templates.md](templates.md)의 "진행표" 양식으로 처음 대기열을 만들어 사용자에게 보여주고 확인받는다: flow.md 그림의 nt 함수 → 단계 1, ntdll 함수 → 단계 2, 4장 표 → 단계 3.
   - `next_index.py sprint`, `latest sast`, `latest dast` 를 본다.
   - 요청서는 있는데 짝 파일이 없으면 그 바퀴가 **진행 중**이다:
     - sast 요청서만 있고 `_result` 없음 → 3번부터 이어서
     - dast 요청서만 있고 `_runbook` 없음 → 5번부터
     - `ms/logs/NN_키워드.txt`가 비어 있음 → 사용자에게 로그를 붙였는지 묻는다
     - 로그는 있는데 `ms/logs/NN_키워드_result.md` 없음 → 7번부터
2. **사용자 말 나누기**
   - 이미 있는 문서(flow.md, run 문서, 결과서)로 답할 수 있는 질문 → **에이전트 부르지 않고** 직접 답한다. 근거 파일을 같이 말한다.
   - "다음 하자", "run 진행하자"처럼 주제가 없으면 → 대기열 첫 "대기" 항목을 한 줄로 알리고 3번.
   - 사용자가 새 주제를 말함 → "지금"이 분명하면 3번, 아니면 맨 아래에 붙일지 물어본다 (위 "애매하면").
   - "로그 붙였어" → 7번.
   - 실행 중 디버거·VM 질문 → 6번.
   - "커밋해줘" → 9번. "새 스프린트" → `runs/NN+1_sprint/` 폴더를 만들고 알린다 (flow.md 복사는 flow-writer가 한다).
3. **정적 요청** (기본은 정적 먼저)
   - 쓰기 전에 지도(`ms/disassemble/<모듈>/_map/`)에서 대상 함수의 깊이·caller·직접 호출을 본다. 지도가 없거나 스크립트가 바뀌었으면 decompiler 에게 `run_ghidra.sh map` 부터 하게 한다.
   - [templates.md](templates.md)의 "정적 요청서" 양식으로 `_workspace/sast/NN_키워드.md`를 쓴다. 질문은 **예/아니오나 이름으로 답할 수 있게** 좁힌다. 지도에서 본 것은 "지도에서 본 것" 절에 옮긴다.
   - `decompiler` 를 부른다. 프롬프트엔 요청서 경로만 준다 (요청서에 다 있어야 한다).
   - 결과서 `_workspace/sast/NN_키워드_result.md`를 읽고 사용자에게 짧게 알린다.
4. **동적이 필요한가** — 아래 중 하나라도 해당하면 동적이 필요하다. 필요 없으면 8번.
   - 지금 항목이 정적 항목이면: 동적 확인거리는 **대기열 맨 아래**에 붙이고 8번 (flow-writer가 4장에도 넣는다). 이게 없으면 지금 항목을 못 끝낸다면 → "애매하면"대로 사용자에게 묻는다.
   - 지금 항목이 동적 항목(차례가 와서 꺼낸 것)이면 5번.
   - 간접 호출(`indirect:`)의 실제 대상
   - 갈림길 중 **실제로 탄 쪽**, 함수가 **실제로 불리는지**
   - 실행 때만 정해지는 값 (주소, `rcx`/`rdx`/`r8`, 모듈 이름)
   - 스레드 사이의 시간 순서
   - 정적 결과서의 "동적분석으로 확인해야 할 것"
   - 판단이 애매하면 사용자에게 묻는다 (VM 작업은 사용자 시간).
5. **동적 요청 → 실행 안내 만들기**
   - "동적 요청서" 양식으로 `_workspace/dast/NN_키워드.md`. 정적 결과서의 추천 멈춤점을 옮긴다. **성공 기준**을 꼭 적는다.
   - `dast-mentor` 를 **준비 모드**로 부른다 → `_workspace/dast/NN_키워드_runbook.md` 와 빈 `ms/logs/NN_키워드.txt` 가 생긴다.
   - runbook을 읽어 사용자에게 **그대로** 보여준다 (줄이거나 명령을 바꾸지 않는다). 로그를 어디에 붙여넣는지 꼭 말한다.
6. **실행 중 질문 중계**
   - runbook "자주 하는 실수"나 `windbg-kd-runbook` 스킬로 바로 답할 수 있으면 직접 답한다.
   - 그 밖에(출력 해석, 다음 명령에 주소 채우기, 계획 바꾸기)는 같은 `dast-mentor` 에게 `SendMessage`로 질문+출력을 넘기고, 답을 그대로 전한다. `SendMessage`가 안 되면 새로 부르되 요청서·runbook 경로와 지금까지 출력을 같이 준다.
   - 급한 것(호스트가 멈춘 것 같다, 타깃이 안 풀린다)은 기다리지 말고 스킬의 "급할 때" 항목으로 바로 답한다.
7. **판정**
   - `ms/logs/NN_키워드.txt`가 비어 있지 않은지 확인 → `dast-mentor` 를 **판정 모드**로 부른다 (가능하면 `SendMessage`로 같은 에이전트).
   - `ms/logs/NN_키워드_result.md`를 읽고 판정에 따라:
     - **분석성공** → 8번
     - **사용자실수** → 실수를 고친 새 동적 요청서(다음 dast NN, 같은 키워드, "재시도: 이전 NN") → 5번. 같은 질문 재시도는 **최대 2번**, 그다음은 사용자에게 어떻게 할지 묻는다.
     - **예기치못한상황발생** → 사용자에게 알리고 같이 정한다: (a) 코드로 이유를 찾을 수 있으면 새 정적 요청, (b) 계획을 바꾼 새 동적 요청, (c) 그 자체를 발견으로 기록하고 8번.
8. **문서**
   - `flow-writer` 를 부른다. 프롬프트에 줄 것: 이번 바퀴의 sast/dast 요청서·결과서·로그 경로 전부, `next run` 번호, 스프린트 폴더, 키워드.
   - 돌아온 보고에서 `check_mermaid.sh` 통과 여부를 확인한다. 실패로 돌아오면 그 내용 그대로 한 번 더 부른다 (최대 1번 더).
   - 사용자에게: 새 run 문서 경로, flow.md에서 바뀐 절, 새로 생긴/채워진 공백.
   - 진행표를 고친다: 지금 항목 `끝 (runN)`, 결과서·판정·run 문서의 "아직 확인 필요"에서 나온 새 할 일은 **맨 아래에** 출처와 함께 추가 (같은 게 있으면 출처만 더함). 단계의 처음 항목이 다 끝났으면 사용자에게 알린다.
8-1. **해설**
   - `explainer` 를 부른다. 프롬프트에 줄 것: run 문서 경로, 이번 바퀴 요청서·결과서(·판정) 경로, run 번호·키워드, 사용자가 이전에 어려워한 부분(있으면).
   - 해설서 `runs/NN_sprint/runN-키워드-해설.md` 를 읽는다. 10번에서 사용자에게 설명할 때 이 글을 바탕으로 한다.
   - 해설서는 **근거 문서가 아니다.** 다른 에이전트에게 사실의 근거로 주지 않는다.
9. **커밋**
   - `committer` 를 부른다. 프롬프트에 이번 바퀴 요약(어떤 run, 무엇을 찾았나)을 한두 줄 준다.
   - 돌아온 커밋 해시·메시지를 사용자에게 알리고 **push는 직접 해 달라**고 말한다.
10. **멈추기** — 바퀴 하나가 끝났다.
   - 사용자에게 이번 바퀴를 쉬운 말로 설명한다: 찾은 것 → 왜 중요한가 → 아직 모르는 것. 해설서(8-1)를 바탕으로 하고, 경로를 알려 준다.
   - **다음 항목을 스스로 시작하지 않는다.** 사용자가 "다음"이라고 하면 2번으로 간다.
   - 하네스 제안·대기열 질문이 쌓였으면 설명과 같은 메시지에 섞지 말고, 사용자가 설명을 다 본 뒤 하나씩 꺼낸다.

## 규칙 바꾸기

- 바퀴의 결과는 `runs/NN_sprint/` 문서에만 쌓인다. `CLAUDE.md`와 `.claude/`(하네스)는 바퀴 결과를 적는 곳이 아니다.
- 하네스를 고치는 건 **오케스트레이터만, 사용자 검토 뒤에**:
  1. 하위 에이전트의 제안("pitfalls에 추가 제안", 결과서의 "스크립트 문제" 등)이나 내가 본 문제를 모아, 바꿀 파일·이유·바뀌는 줄을 사용자에게 보여준다. 여러 개면 목적별 **묶음**으로 나눈다.
  2. 사용자가 OK 한 묶음만 고친다.
  3. 묶음마다 `committer` 를 불러 **하네스 파일만 담은 커밋 하나**를 만든다 (`fix|feat|docs(harness)`). 분석 산출물(`runs/`, `_workspace/`, `ms/logs/`)과 같은 커밋에 넣지 않는다.
  4. 커밋 해시를 `_workspace/plan.md` 결정 기록에 남긴다.
  5. 되돌리기는 그 커밋을 `git revert` (사용자 허락 뒤). 그래서 묶음 하나 = 커밋 하나로 둔다.
- 스크립트(`scripts/`)는 그 스크립트를 쓰는 작업(예: ntoskrnl analyze)이 도는 중엔 고치지 않는다. 끝난 뒤 고치고, 작은 시험으로 확인한 뒤 커밋한다.
- 하위 에이전트는 하네스를 고치지 않는다. `.claude/settings.json` 의 권한(permissions)은 사용자가 직접 고친다.

## 팀 에러 정책

- 같은 에이전트가 같은 입력으로 **2번** 실패하면 멈추고 사용자에게 묻는다.
- decompiler가 "빌드가 다르다(PDB GUID 불일치)"를 보고하면 바퀴 전체를 멈춘다.
- committer가 MS 파일(바이너리·심볼·디컴파일 결과)을 빼고 커밋했다고 하면, 사용자 허락 없이 다시 넣으라고 하지 않는다.
- 사용자 답이 없는데 결정을 되돌릴 수 없으면(커밋 지우기 등) 하지 않는다.
