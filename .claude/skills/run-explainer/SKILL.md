# run-explainer Skill

run 문서는 **기록**이다 (근거·태그·오프셋을 빠짐없이). 해설은 그 기록을 **이해하게 돕는 글**이다.
같은 사실을, 바탕 개념부터 차근차근 풀어서 다시 쓴다. 새 사실은 없다.

## 이 프로젝트의 독자

- Windows 내부를 공부하는 중이다. 코드·용어를 빨리 읽어 내는 것보다, **왜 그렇게 되는지 납득**하고 싶어 한다.
- 앞에서 너무 빨리 결과를 쌓아서 이해가 따라오지 못한 적이 있다 (2026-10-19). 그래서 해설이 생겼다.
- 그러니 **길어도 괜찮다.** 대신 소제목으로 잘게 나눠서 한 번에 개념 하나만 다룬다.

## Workflow

1. **입력 읽기**: 오케스트레이터가 준 run 문서, 요청서·결과서(·판정), `_workspace/plan.md`.
   - flow.md 변경은 `git diff -- runs/NN_sprint/flow.md` 로 본다. 이미 커밋된 바퀴를 거꾸로 해설할 때는 그 바퀴의 docs 커밋을 `git show <해시> -- runs/NN_sprint/flow.md` 로 본다.
2. **이미 푼 말 모으기**:
   ```bash
   grep -n '^### ' runs/*/run*-해설.md
   ```
   - "2. 바탕 개념" 의 소제목(`### 말`)이 곧 용어 목록이다. 여기 있는 말은 다시 길게 풀지 않고 링크한다.
3. **이번에 처음 나온 말 고르기**: 3절(찾은 것)을 읽는 데 꼭 필요한 말만. 보통 3~6개.
   - 고르는 기준: "이 말을 모르면 트리의 한 줄을 못 읽는다."
4. **양식대로 쓰기** (아래 "해설 양식").
5. **숫자 대조**: 해설에 쓴 함수 이름·오프셋·개수를 run 문서·결과서와 하나씩 맞춘다. 다르면 run 문서를 따르고 보고에 적는다.
6. **보고**: 해설 경로, 새로 푼 말, 링크로 가리킨 말, 근거끼리 어긋난 곳.

## 해설 양식 — `runs/NN_sprint/runN-키워드-해설.md`

```markdown
# runN 키워드 — 해설

> 이 글은 [runN 문서](runN-키워드.md)를 쉬운 말로 풀어 쓴 것이다. 새 사실은 없다.
> 근거와 태그는 run 문서·결과서를 따른다.

- 대기열: Qn — <항목 한 줄> (`_workspace/plan.md`)
- 근거: `_workspace/sast/NN_키워드_result.md` (…), run 문서

## 1. 이번 바퀴의 질문

- **큰 그림에서 어디인가**: test.exe 실행 흐름(cmd.exe의 부탁 → 커널 → ntdll → main)에서 이번 구간의 위치를 짧은 그림이나 목록으로. 지금 위치에 ← 표시.
- **무엇이 궁금했나**: 질문을 한두 문장으로.
- **바퀴 전에 알던 것**: 태그와 함께 (예: `[관찰]` 01_sprint 콜스택).

## 2. 바탕 개념

(이번에 처음 나온 말만. 하나씩.)

### <말 1>
- 뜻 1~2줄.
- 비유: 일상에서 한 가지.
- (필요하면) 이 프로젝트에서 어디에 나오는지.

### <말 2>
...

- 이미 푼 말: [<말>](../NN_sprint/runM-키워드-해설.md#<말>) — 한 줄 요약 (링크만, 다시 풀지 않음)

## 3. 찾은 것

- 트리나 표 하나 (run 문서와 같은 숫자).
- **한 줄씩 읽는 법**: 트리에서 한 줄을 골라 "누가 / 어디서(+0x) / 누구를 / 무엇을 위해"로 풀어 읽는다. 최소 1개.
- 사실마다 태그. 비유로 다시 한 번 정리해도 좋다 (비유엔 태그 없음).
- 갈림길·추론이 있으면 "왜 그렇게 짐작하나"를 단계별로 (근거 → 그래서 → 아직 확인 아님).

## 4. 왜 중요한가

- flow.md 에서 바뀐 절과 태그 변화 (예: 2.5 `[추측]` → `[정적]` 근거 추가). 바뀌기 전과 후를 한 줄씩.
- 큰 그림에서 이번 결과가 다음 구간과 어떻게 이어지는지.

## 5. 아직 모르는 것

- 항목마다: 무엇을 모르나 / 왜 이번에 못 알았나 (정적 한계, 실행 때 값 등) / 대기열 몇 번에서 보나 (Qn, 정적·동적).

## 6. 더 읽기

- run 문서, 결과서, flow.md 절 링크.
```

## 쓰는 법

- **말하는 방식**: CLAUDE.md "말하는 방식" 그대로 — 중학생도 알아듣는 말, 짧은 문장, 글머리 기호, 넉넉한 줄바꿈, 동료 같은 톤.
- **비유는 하나의 그림으로 이어지면 좋다.** 예: 프로세스 = 가게, 주소 공간 = 빈 땅, 매핑 = 건물 갖다 놓기, PEB = 안내판. 이전 해설에서 쓴 비유가 있으면 바꾸지 말고 이어 쓴다 (2번 단계의 용어 목록에서 확인).
- **오프셋 읽는 법은 처음 나올 때만** 길게 풀고, 이후엔 이미 푼 말로 링크한다.
- 사용자가 이전에 "이해가 안 됐다"고 한 부분이 오케스트레이터 프롬프트에 있으면 그 부분을 더 천천히, 다른 비유로 쓴다.
- 길이 제한은 없다. 다만 3절의 트리·표는 run 문서보다 작게 (대표만), 나머지는 링크로.

## 하지 않는 것

- 근거 문서에 없는 함수 이름·오프셋·동작을 쓰지 않는다. 일반적인 Windows 지식은 `[추측]` + "일반적으로 알려진 설명"으로만, 짧게.
- 태그를 올리지 않는다 (`[추측]` 을 `[정적]` 으로 등).
- "스스로 확인해 볼 질문" 절은 넣지 않는다 (사용자 결정, 2026-10-19).
- 디컴파일 코드를 붙이지 않는다. 명령 줄 인용은 3줄 이하.
- run 문서·flow.md·결과서를 고치지 않는다.
